# 운영 이미지의 실제 모델·개정·복원 평가

2026-09-10 한국시간. 직접 작성한 가상 은하군 자료이며 실제 고객 지침이 아니다. 작성·검토·이용 계정으로 정식 API와 브라우저 폼을 사용했다. 고객 업무 담당자의 전문 검토는 미실시다.

## 원문부터 개정 게시까지

최초 원문은 정상 통신 30초 갱신, 통신 장애 중 충족 판정 금지, 마지막 수신 시각·중단 표시, 마지막 값을 최신으로 표시 금지, 재연결 후 60초 확인, 정상 장비 기록 72시간 보관 및 장애 장비 제외를 담았다. 예산과 장애 장비 보관 기간은 미기재라고 명시했다. 개정 원문은 **30초를 45초로 바꾼 한 곳만 다르다**.

최초 자동 생성은 출처 요약·통신 상태 확인·점검 기록 관리 3페이지를 한 묶음으로 만들었다. 전체 원문 5문단을 처리하고 제목 1개는 주장 없음으로 분류했으며 사실·조건 11개와 근거를 보존했다. 각 페이지의 원문과 본문을 직접 대조한 후 작성 계정이 검토 요청하고 검토 계정이 게시했다.

개정 때도 3개 주소를 유지했다. 갱신 간격이 바뀐 두 페이지는 충돌 검토, 나머지는 현재 원문 근거 재연결 대상으로 제시했다. 원래 본문과 새 근거 단락을 결합한 상태에서 검토가 필요하므로, 정식 수정 폼에서 두 본문의 30초를 45초로 바꾸고 반복 단락을 정리했다. 점검 기록 본문은 그대로 유지했다. 세 페이지의 기존 링크와 부정문을 보존한 새 묶음을 재검토·게시했다. [수정 결정과 저장 결과](revision-manual-review.json)

| 새 질문 | 실제 답변 대조 |
| --- | --- |
| 통신을 끊은 두 교차로를 갱신 기준 충족으로 기록해도 되는가 | 충족 판정 금지와 각각의 점검·기록을 구분 |
| 연결 복구 후 언제 무엇을 확인하는가 | 60초 안에 새 데이터 수신 확인 |
| 장애 장비 기록도 72시간 뒤 삭제해도 되는가 | 정상 장비 조건이며 장애 장비 적용 제외, 별도 삭제 판단 근거 없음 |
| 사업 예산은 얼마인가 | 원문에 미기재라고 안내 |
| 개정 후 정상 갱신 간격 | 45초와 통신 장애 제외 |
| 이어서, 끊긴 동안에도 충족으로 보는가 | 같은 대화에서 충족 판정 금지, 개정 원문 버전 인용 |

여섯 답변을 모두 직접 읽고 사용 인용을 대조했다. 개정 후 두 답변의 사용 인용은 모두 현재 원문 버전을 가리켰다. 최초 질문은 1.67~5.46초, 개정 질문은 2.11~2.46초였다. 성공한 최초 전체 분석은 약 16.3초, 생성 작업은 27.0초였다. 최초 생성 지시문 보완 때 완료 분석을 재사용했다. 개정의 마지막 성공 실행은 분석 약 18.4초·생성 약 32.7초였다. 코드 수정·이미지 빌드·직접 검토 대기 시간은 이 수치에서 제외했다.

## 실패를 포함한 사용량

생성 단락의 문서 이름 축약으로 2회, 개정 분석의 대상 표현 재작성으로 2회 검증에 실패했다. 실패 응답·부분 결과·호출 사용량을 보존했다. 생성 `v5`와 분석 `v3` 지시문은 원문 대상 문자열을 정확히 유지하도록 보완했으며 검증 조건은 완화하지 않았다. 실패한 같은 분석 구간으로 별도 모델 실험 1회를 수행하고 11개 주장을 대조했다.

## 품질 결과와 담당 처리

개정 원문 공개 후 기존 위키 3개는 오래된 근거로 표시됐다. 검토 계정은 본문 수정·게시 대기 사유를 남겨 보류했고, 게시 후 구조 재점검에서 3건 모두 해결됐다. AI 점검은 상위 요약과 독립 절차 사이의 중복 3건, 각 페이지에 없는 다른 절차의 설명 보완 2건을 제시했다.

다섯 후보의 구절과 연결된 페이지를 대조해 수치·조건이 일치하고 다른 절차가 관련 위키에 있음을 확인했다. 페이지마다 같은 내용을 반복할지에 관한 편집 판단은 담당자 검토 전까지 보류했다. **남은 후보 5건은 기록된 검토 대상이며 확정된 사실 오류 5건을 뜻하지 않는다.** 구조 해결과 의미 후보 보류를 포함한 `review_event`는 24개다. [finalQuality·semanticReviewNotes](revision.json)

## 백업·복원·실패 복귀

운영 이미지에서 빈 DB 마이그레이션 18개와 public 테이블 48개를 확인했다. 웹·작업자·모델 설정 및 일반 DB 역할을 검사했다. 작업자를 멈춘 일관된 상태에서 DB 전체 덤프와 원본 2개를 저장하고 모든 업무 테이블 행 수·내용 지문, 덤프 SHA-256, 원본 바이트 수·SHA-256을 대조했다.

별도 `wiki-stage16-restored` 환경에 같은 고정 이미지로 복원했다. 서비스 시작 **전** 48개 테이블의 행 내용·스키마 이력·복사된 원본 해시가 일치했다. AI 작업 6개·단계 26개·정리 실행 4개·생성 호출 27개·위키 3개/6버전·품질 실행 4개/단계 12개/후보 8개·검토 이벤트 24개가 포함된다. 분석 결과와 재사용 근거는 AI 작업·단계의 JSON에, 위키 관계는 본문·메타데이터·근거에 보관되므로 함께 검증했다. 브라우저 그래프 계산 캐시는 복원 대상이 아니며 복원된 관계에서 재계산한다.

손상된 DB 덤프·손상된 원본·원본 프로필 덮어쓰기·기존 복원 서비스 덮어쓰기를 각각 거부했다. 새 복원 환경에서는 존재하지 않는 이미지와 `--pull never`로 기동 실패를 유발하고, DB 48개 테이블이 바뀌지 않았음을 확인한 뒤 검증된 이미지로 정상 복귀했다. 동일 스키마의 이미지 기동 실패 복귀 시험이며 파괴적 스키마 변경의 역마이그레이션 시험은 아니다.

복원 후 새로 로그인해 두 원본 파일, 게시 위키 본문, 저장 답변, 읽기 역할 제한, 최신 그래프의 3개 위키·버전·원문 연결, 품질 후보 상태를 대조했다. 원문·위키·채팅·작업·품질·그래프 6화면을 1440px/390px에서 확인했고, 모두 HTTP 200·가로 넘침 0·브라우저 오류 0이었다. 로그인으로 새 세션이 생기므로 로그인 후 계정 세션 행 수를 백업 시점과 같다고 주장하지 않는다.
