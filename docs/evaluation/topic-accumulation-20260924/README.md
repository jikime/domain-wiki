# 여러 자료의 주제별 지식 축적 평가

2026-09-24. 가상 교통관제 사업의 자료 세 개를 사용했다. 실제 고객 자료나 담당자의 업무 판정은 포함하지 않는다.

## 확인하려는 흐름

| 입력 | 기존 지식에 더할 내용 | 기대 결과 |
| --- | --- | --- |
| [기본 RFP 조건](01-rfp.md) | 주 화면 30초 | 화면 갱신 조건 주제의 첫 버전 |
| [추가 설계 조건](02-design.md) | 보조 화면 90초 | 같은 주소의 두 번째 버전, 두 대상의 수치 구분 |
| [장애 예외](03-exception.md) | 통신 단절 시 자동 갱신 금지, 마지막 값을 최신 값으로 표시하지 않음 | 같은 주소의 세 번째 버전, 기존 조건과 새 예외 보존 |

문서별 요약은 각 원문을 설명하는 페이지로 남기고, 주제 위키는 세 자료의 조건을 함께 정리한다. 다른 사업의 같은 이름은 별도의 지식으로 유지한다.

## 발견한 문제와 수정

1. **기존 주제 탐색에 별칭이 빠져 있었다.** 생성 전 후보의 점수를 계산할 때 제목·본문과 함께 별칭도 비교하도록 바꿨다. 본문에 같은 단어가 없는 두 번째 자료에서도 ‘가시화응답성’이라는 별칭으로 기존 주제를 찾는 사례를 검사했다.
2. **같은 제목의 주제를 새로 만들겠다는 계획을 허용했다.** 같은 프로젝트·유형에서 제목 또는 별칭이 겹치는 신규 주제는 기존 대상을 다시 비교하도록 차단한다. 자동으로 합칠 대상을 추정하지 않는다. 원문별 요약, 다른 프로젝트, 다른 유형은 이 규칙으로 강제 병합하지 않는다.
3. **페이지의 정리 범위가 생성 후 사라졌다.** 생성 계획의 `subject`와 `scope`를 위키 메타데이터에 저장하고 다음 생성의 기존 페이지 문맥으로 전달한다. 기존 값이 있으면 새 자료 하나의 범위로 덮어쓰지 않는다. 기존 페이지에 이 값이 없더라도 읽을 수 있는 선택 항목으로 추가했다.
4. **같은 목적지의 두 링크 표기가 오류가 됐다.** 실제 모델이 기존 위키 ID와 수정 계획의 페이지 번호를 함께 반환했다. 같은 페이지를 가리킨다는 것을 서버가 확인한 경우 하나의 링크로 정규화한다. 동일 표기의 반복, 자기 참조와 알 수 없는 목적지는 계속 거부한다.

생성 규칙은 `wiki-generation-v10-topic-scope`다. 정리 범위는 편집 기준이며 사실의 근거로 사용하지 않는다. 주 화면과 보조 화면을 같은 페이지에 정리해도 두 대상의 수치·조건은 따로 유지한다.

## 실제 DB와 API 검사

`domain_wiki_test` 전용 DB에 실행마다 새 작업공간·계정을 만들었다. 원문·청크는 검사 준비 과정에서 직접 등록했다. 파일 업로드·문서 파서의 품질 검사는 이번 범위가 아니다.

그 뒤에는 실제 분석·생성 API, 작업자, 변경안, 작성자 제출·다른 검토자 승인, 이용 직원의 재조회를 사용했다. 모델은 반복 가능한 고정 응답 서버다. 이 검사는 저장·검토·권한·버전의 동작을 확인하며 실제 모델의 판단 품질을 증명하지 않는다.

| 단계 | 주제 주소 | 게시 버전 | 연결된 원문 근거 | 보존한 입력 |
| --- | --- | ---: | ---: | ---: |
| 첫 자료 | 동일 주소 | 1 | 1 | 1 |
| 두 번째 자료 | 동일 주소 | 2 | 2 | 2 |
| 세 번째 자료 | 동일 주소 | 3 | 3 | 3 |

최종 게시 결과는 **주제 페이지 1개와 원문 요약 3개**다. 두 번째·세 번째 변경안이 아직 승인되지 않았을 때 이용 직원에게 보이는 버전이 바뀌지 않는 것도 확인했다. 정리 범위는 게시·재조회 후에도 유지됐다.

세 통합 검사는 정상 누적, 중복 신규 계획의 실패와 기존 게시본 유지, 다른 프로젝트의 별도 주제 생성을 다룬다. 마지막 누적 단계에는 같은 링크의 두 표기를 넣어 실제 모델에서 발견한 오류도 재현했다. 시험 종료 후 이 실행에서 만든 계정·공간·자료는 정리한다.

결과: [계약 평가 기록](contract-results.json).

## 실제 모델의 계획 선택

연결된 Claude Code의 `sonnet` 모델로 계획 단계를 별도 실행했다. 입력 분석 주장은 사람이 구성한 가상 표본이며, 이 실행에서는 본문 생성·병합·DB 게시를 하지 않았다. API·DB 검사와 실제 모델 계획 평가를 합쳐 하나의 실제 모델 전체 실행으로 해석하면 안 된다.

- [범위를 명시하지 않은 첫 평가](real-plan-results.json): 모델은 주 화면과 보조 화면을 다른 대상으로 보고 페이지를 분리했다. 기존 본문이 주 화면만 다루고 있었으므로 타당한 해석이었다. 상위 주제 페이지를 의도한다면 그 정리 범위가 필요하다는 점을 확인했다.
- [정리 범위를 명시한 평가](real-plan-scoped-results.json): 보조 화면 조건을 같은 주제의 수정으로 선택했다. 다음 예외 조건 평가에서는 링크 검증 오류로 중단했다. 당시 스크립트가 두 번째 실패 원문을 보존하지 못해 그 제한을 기록했다.
- [예외 조건 재평가](real-plan-exception-results.json): 모델은 기존 주제 보완을 선택했고, 적용 화면과 복구 조건을 확인 질문으로 남겼다. 다만 기존 ID와 수정 계획 번호로 같은 목적지를 두 번 연결하여 서버 검증에서 실패했다. 이 응답을 보존해 링크 정규화의 회귀 사례로 사용했다.
- [최종 검증으로 저장 응답 재검사](real-plan-replay.json): 보조 화면 추가와 장애 예외 추가의 계획 2건 모두 같은 주제의 수정으로 검증을 통과했다. 새 모델 호출이 아니라 저장된 실제 응답의 재검증 결과다.

고정 응답에서 가정한 합리적인 계획을 실제 모델이 항상 선택한다고 보지 않고, 실제 응답이 보여 준 범위 해석과 링크 오류를 구분해 보완했다. 작은 표본의 결과이며 대량 자료·다양한 표현에서의 정확도나 재현율을 측정한 것은 아니다.

```bash

# 중복 주제·실제 모델 링크 응답·1단계 근거 검증 회귀
npx vitest run --config vitest.ai.config.ts src/server/ai/wiki-topic.test.ts src/server/ai/claim-grounding.test.ts

# 실제 모델 계획 평가: 기존 기록을 덮어쓰지 않도록 새 출력 경로 지정
node --conditions=react-server --import tsx scripts/evaluate-topic-plans.ts 새-출력-경로.json
```

관련 단위 검사 41개와 API 통합 검사 3개를 통과했다. 타입 검사와 변경 파일의 코드 형식 검사도 수행했다. 전체 통합시험, UI 브라우저 평가, 고객 자료 평가와 운영 배포는 이번 범위에 포함하지 않았다.

## 남은 한계

제목·별칭 중복 검사는 표현이 완전히 다른 동일 개념을 모두 찾지 못한다. 동의어·의미 검색과 많은 자료에서의 후보 누락 평가는 남아 있다. 페이지의 정리 범위를 모델이 정확히 정했는지도 검토 대상이며, 범위를 넓게 적었다고 원문의 적용 범위가 넓어지는 것은 아니다.

다음 단계는 여러 프로젝트의 경험을 원래 근거와 적용 조건을 보존하면서 회사 공통 지식으로 검토·승격하는 흐름이다.
