# AI 도메인 위키 구축 및 운영 역량 강화 교육 제안서

**개인의 경험을 조직의 지식으로, 교육 결과물을 실제 업무 서비스로**

| 구분 | 제안 내용 |
|---|---|
| 제안 대상 | 엠큐닉 UX·기획·AX 관련 직원 및 도메인 실무 담당자 |
| 제안 및 강의 | 김동학 · Anthony Kim |
| 교육 형태 | 실제 업무 자료를 활용한 프로젝트형 교육 및 구현 코칭 |
| 교육 기간 | 10주, 주 1회 3시간, 총 30시간의 기본 편성안 |
| 참여 규모 | 5명 내외, 권장 4~6명 |
| 구축 방향 | 도메인 위키 중심의 지식 서비스 구축 → 제한된 사내 시험 운영 → 동일 코드와 데이터 기반의 확장 |
| 문서 상태 | 고객 검토용 제안 초안 v1.0 |
| 작성일 | 2026년 9월 7일 |

> **제안의 핵심**  
> 직원이 회사의 문서와 실무 경험을 근거 기반 도메인 지식으로 구조화하고, 이를 탐색·질의·요구사항 검토에 활용하는 서비스를 직접 구축합니다. 교육 종료 후에도 회사가 같은 코드와 지식 자산을 유지하면서 신규 자료를 등록하고, 결과를 검증·수정하며, 다른 프로젝트와 도메인으로 확장할 수 있는 내부 역량을 확보하는 것이 목표입니다.

본 문서는 사전 협의에서 확인된 업무 요구와 교육 방향을 바탕으로 작성한 제안안입니다. 실제 구현 및 교육 가능성은 강사의 사전 레퍼런스 개발과 실습 재현을 통해 검증하며, 세부 범위·일정·비용·운영 조건은 착수 전에 협의하여 확정합니다.

## 1. 제안 배경 및 고객 요구 이해

귀사는 ITS·교통관제 등 익숙한 분야뿐 아니라 새로운 사업 분야에서도 요구사항 분석, 서비스 기획, 화면설계와 관련 업무를 수행하고 있습니다. 사전 협의에서 확인된 핵심 과제는 문서의 부족보다 **지식이 사람과 프로젝트에 분산되어 있고, 이를 다음 업무에서 다시 활용하기 어렵다는 점**입니다.

경험자는 알고 있는 규정, 발주처 특성, 운영 절차와 수정 이유를 새로운 담당자는 다시 조사해야 합니다. RFP에 명시되지 않은 내용을 뒤늦게 확인하거나, 기존 자료의 최신성과 적용 범위를 판단하기 어려워 검토와 재작업이 반복되는 상황도 논의되었습니다.

| 확인된 업무 과제 | 교육과 서비스가 해결할 방향 |
|---|---|
| 담당자별 도메인 이해도에 편차가 있음 | 핵심 용어·업무 절차·공식 자료·사례를 연결한 공통 지식 기반 마련 |
| 과거 프로젝트 경험이 개인에게 남아 있음 | 추가 요구사항, 수정 이유, 실패 사례를 짧은 지식 기록으로 축적 |
| 자료가 여러 문서와 업무 시스템에 흩어져 있음 | 승인된 자료부터 공통 분류체계로 등록하고 원문과 연결 |
| RFP에 당연한 전제나 세부 운영 조건이 빠져 있음 | 관련 지식과 과거 사례를 찾아 추가 확인 질문을 만들도록 지원 |
| AI 답변과 출처를 다시 확인해야 함 | 주장·원문·적용 범위를 함께 보여주고 근거 부족을 명시 |
| 지식 정리가 본업에 밀려 지속되기 어려움 | AI가 정리 초안을 만들고 직원이 검토하는 운영 순환 정착 |
| 대규모 투자 전에 효과를 확인해야 함 | 한 개 도메인에서 실제 효용과 운영 부담을 측정한 뒤 확대 판단 |

따라서 본 제안은 **도메인 지식의 축적과 재사용을 중심에 두고, 챗봇은 접근 수단으로, RFP 검토는 업무 활용을 검증하는 대표 과제로 배치**합니다.

## 2. 교육 목표와 고객이 확보할 핵심 성과

### 2.1 교육 목표

본 과정의 목표는 AI 도구를 사용하는 방법을 소개하거나, 일회성 시연용 챗봇을 만드는 데 있지 않습니다. 직원이 직접 회사의 지식 구조와 활용 서비스를 만들고, 교육 이후에도 수정·운영·확장할 수 있는 상태에 도달하는 것을 목표로 합니다.

### 2.2 고객이 확보할 다섯 가지 성과

| 핵심 성과 | 교육 종료 시 확보할 내용 | 회사에 남는 가치 |
|---|---|---|
| 재사용 가능한 도메인 지식 | 개념·절차·근거·발주처 특성·프로젝트 경험이 연결된 위키 | 특정 담당자에게 집중된 경험의 조직 자산화 |
| 근거를 확인할 수 있는 서비스 | 위키 탐색, 원문 검색, 출처 기반 질의응답 | 신규 업무 이해와 실무 판단을 돕는 공통 작업 기반 |
| 직원의 직접 구축·개선 역량 | 새 문서 등록, 검색 오류 진단, 생성 규칙 수정, 재검증 | 외부 의존도를 낮추고 내부에서 서비스를 발전시킬 능력 |
| 지속적인 지식 운영 방식 | 자료 등록, 전문가 검토, 게시, 개정, 오류 수정 절차 | 프로젝트를 수행할수록 지식이 누적되는 업무 체계 |
| 운영 전환 및 투자 판단 근거 | 회사 관리 저장소, 평가 결과, 운영 문서, 후속 개발 목록 | 교육 결과를 유지하면서 사내 서비스로 발전시킬 출발점 |

### 2.3 직원이 교육 후 수행할 수 있어야 하는 일

직원은 새로운 문서를 등록하고 분류한 뒤, 문서가 제대로 읽혔는지 확인할 수 있어야 합니다. 원하는 자료가 검색되지 않으면 분류·문서 분할·검색 조건 중 어디를 점검해야 하는지 설명하고, AI 코딩 도구와 검증 절차를 이용해 수정할 수 있어야 합니다.

또한 새로운 프로젝트 경험을 위키에 추가하고, 잘못되거나 오래된 내용을 근거와 함께 수정하며, 다른 도메인에 적용할 때 바꿔야 할 분류체계·지식 양식·평가 질문을 정의할 수 있어야 합니다. 모든 직원에게 동일한 개발 깊이를 요구하기보다, 공통 흐름은 함께 이해하고 구현·검토·운영은 역할에 따라 분담합니다.

## 3. 구축할 서비스의 모습

### 3.1 서비스 정의

**AI 도메인 위키**는 회사가 가진 문서와 실무 경험을 정리하고, 직원이 업무에 필요한 지식을 탐색하거나 질문하며, 그 근거와 적용 범위를 확인할 수 있는 웹 기반 지식 서비스입니다.

질문하는 화면만 제공하지 않습니다. 도메인을 처음 접하는 직원도 무엇을 알아야 하는지 발견할 수 있도록, 도메인 개요에서 용어·업무 절차·규정·대표 사례로 이어지는 탐색 구조를 함께 구성합니다.

### 3.2 핵심 기능

| 기능 | 직원이 수행하는 작업 | 구현 범위 |
|---|---|---|
| 문서 등록과 원본 관리 | 승인된 자료를 등록하고 도메인·프로젝트·발주처·버전을 지정 | 원본 보관, 처리 상태 확인, 오류 확인과 재처리 |
| 경험 지식 기록 | 추가 요구사항, 수정 이유, 실무 관행을 짧게 기록 | 적용 범위와 근거를 연결한 지식 카드 작성 |
| 도메인 위키 | 핵심 개념, 절차, 공식 자료와 프로젝트 사례 탐색 | AI 초안 생성, 관련 페이지 연결, 직원 검토와 게시 |
| 근거 기반 검색·챗봇 | 전문용어 또는 자연어로 질문하고 원문 확인 | 검색 결과와 답변의 출처 표시, 근거 부족·충돌 안내 |
| RFP 검토 지원 | 대표 요구사항의 관련 지식과 과거 사례 비교 | 누락 가능 항목과 발주처 확인 질문의 검토 초안 생성 |
| 평가와 운영 확인 | 부정확한 결과를 신고하고 원인을 확인 | 기본 피드백, 처리 이력, 평가 결과, 운영 절차 |

### 3.3 세 가지 대표 활용 시나리오

**새로운 담당자의 업무 이해**  
직원이 처음 맡은 교통관제 업무의 개요와 핵심 용어를 위키에서 확인합니다. 관련 운영 절차와 과거 사례를 따라가며 질문하고, 필요한 원문 자료를 직접 열어 확인합니다.

**기존 프로젝트 경험의 재사용**  
이전 프로젝트에서 추가된 기능과 수정 이유를 지식 카드로 남깁니다. 다음 담당자는 이를 찾아 해당 발주처의 특성인지, 여러 프로젝트에 적용할 수 있는 내용인지 판단하고 확인 질문을 준비합니다.

**RFP의 초기 검토**  
대표 RFP의 일부 요구사항을 등록하고, 관련 규정·위키·과거 프로젝트 사례를 찾아 비교합니다. 서비스가 제시한 누락 가능성과 질문을 실무자가 검토해 발주처 협의에 활용합니다. AI의 제안을 확정 요구사항이나 법적 판단으로 자동 처리하지 않습니다.

### 3.4 지식이 쌓이는 전체 흐름

```text
승인된 문서와 실무 경험 등록
→ 내용·구조·출처 정리
→ 필요한 원문 검색
→ AI의 위키 초안 작성
→ 담당 직원의 검토·게시
→ 탐색·질의·RFP 검토에 활용
→ 오류와 새로운 경험 반영
→ 다음 프로젝트에서 재사용
```

**AI가 만든 내용과 회사가 검토한 지식은 구분하며, 위키와 답변에서 원본 근거로 돌아갈 수 있는 연결을 유지합니다.**

## 4. 교육 범위와 구현 원칙

### 4.1 30시간의 우선순위

| 구분 | 내용 |
|---|---|
| 반드시 확보할 핵심 | 한 개 도메인의 문서·경험 지식 등록, 위키 탐색·검토, 원문 검색, 근거 기반 답변, 직원의 수정·재검증 |
| 업무 적용 검증 | 대표 RFP 1건 또는 핵심 요구사항 묶음을 대상으로 관련 근거와 확인 질문 생성 |
| 운영 전환 기반 | 회사 관리 저장소, 권한, 원본·버전 관리, 비동기 처리와 재처리, 기본 기록, 배포·복구 안내 |
| 이후 확대할 기능 | 전체 RFP 일괄 분석, 다중 도메인, 전사 권한 연동, 업무 시스템 자동 동기화, 복잡한 관계 분석 |

일정 조정이 필요할 때에는 도메인 지식의 품질, 원문 연결, 권한, 검토 절차를 유지합니다. 먼저 자동 분석의 범위와 부가 화면을 줄여 핵심 학습과 서비스의 안전한 기반을 확보합니다.

### 4.2 초기 자료 범위안

첫 도메인은 내부 경험자와 검증 자료를 확보할 수 있는 ITS·교통관제·VMS 중 한 분야로 선정합니다. 초기 자료는 **전체 20~50건을 목표로 선정하되, 첫 구현은 대표 자료 5~10건으로 시작**합니다. 문서 수보다 올바르게 읽히고 검증 가능한지가 중요합니다.

평가 질문은 30~50개를 준비하고, RFP는 대표 1건을 업무 적용 검증에 사용합니다. 위 수량은 선정 기준을 제시한 범위안이며, 사전 문서 점검 결과에 따라 확정합니다.

문서 처리는 텍스트 기반 PDF를 우선 검증합니다. PPTX·DOCX, 스캔본, 복잡한 표와 화면설계서는 대표 샘플의 처리 품질을 확인한 뒤 포함 범위를 결정합니다. 모든 형식의 완전 자동 처리를 교육 성과로 약속하지 않습니다.

### 4.3 간결한 기술 구성

| 영역 | 제안 구성 | 교육에서 다룰 핵심 |
|---|---|---|
| 웹 서비스 | Next.js·TypeScript 및 공통 UI | 업무 화면과 서버 기능의 연결 |
| 계정·원본·업무 데이터 | Supabase Auth·Storage·PostgreSQL | 사용자 권한, 문서·지식·이력 관리 |
| 문서 처리 | Python·Docling | 문서 내용·구조·원문 위치의 확인 |
| 검색 | PostgreSQL 기반 키워드 검색과 pgvector | 정확한 용어와 의미를 함께 고려하는 검색 |
| AI 호출 | 회사가 승인한 공급사의 공식 SDK | 모델 호출, 결과 검증, 사용량 기록 |
| 위키·경험 지식 | 회사에 맞춘 페이지 양식과 관계 데이터 | 지식 생성·검토·게시·개정 |
| 긴 작업 처리 | 데이터베이스 기반 작업 관리와 별도 처리 프로그램 | 처리 상태, 실패 원인, 재처리 |
| 기본 품질·운영 | 자동 검사, 평가 자료, 변경 기록, 실행 안내 | 재현 가능한 개발과 운영 전환 |

본 표는 제안 아키텍처입니다. 공급사와 모델, 문서 처리 설정, 배포 방식은 사전 검증 및 회사 보안 정책을 반영해 확정합니다. 생성 기능과 문서의 의미 검색용 변환 기능을 같은 공급사에서 제공받을 수 있는지도 함께 확인합니다.

LiteLLM·any-llm, Neo4j, GraphRAG, LangGraph 등은 초기 필수 구성에 넣지 않습니다. 다만 모델 호출·검색·문서 처리와 업무 흐름을 분리해, 실제 필요가 확인되면 해당 부분을 수정·확장할 수 있도록 설계합니다.

## 5. 교육 추진 방식

### 5.1 강사의 사전 개발과 검증

강사는 교육 전에 동일한 아키텍처의 레퍼런스 구현체를 직접 개발합니다. 먼저 합성 또는 공개 사용이 가능한 자료로 전체 흐름을 확인하고, 이후 회사가 승인한 대표 자료로 업무 적합성을 검증합니다.

| 검증 영역 | 확인할 내용 |
|---|---|
| 기술 가능성 | 문서 등록부터 검색·근거 답변·위키·대표 RFP 검토까지 실제로 연결되는지 |
| 업무 적합성 | 회사가 어려워하는 질문에 도움이 되는지, 적용 범위와 불확실성을 표시하는지 |
| 교육 가능성 | 직원용 시작 프로젝트와 단계별 프롬프트로 핵심 기능을 재현할 수 있는지 |
| 운영 전환 가능성 | 권한, 실패 재처리, 원본 보존, 배포와 복구 절차가 준비되는지 |

사전 검증은 수행 계획이며, 현재 문서만으로 구현 성공이나 품질이 확인되었다고 간주하지 않습니다. 검증 결과를 바탕으로 교육 시작 전 필수 실습 범위와 제공 코드를 확정합니다.

### 5.2 회사가 계속 사용할 시작 프로젝트 제공

시작 프로젝트(Starter Repository)는 교육 후 폐기하는 예제가 아니라 회사가 계속 발전시킬 코드 저장소의 출발점입니다. 강사는 보안과 운영에 필요한 기본 구조를 제공하고, 직원은 회사에 맞는 핵심 지식 기능을 구현합니다.

| 강사가 준비하는 기반 | 직원이 직접 설계·구현·검증하는 내용 |
|---|---|
| 프로젝트 구조, 기본 화면, 환경 설정 | 실제 업무 흐름과 화면의 세부 요구 |
| 로그인·권한·데이터베이스 변경 관리 골격 | 문서 분류, 발주처·프로젝트·적용 시점 정보 |
| 문서 처리·작업 관리·재처리 골격 | 문서 유형별 분할 규칙과 결과 검토 |
| 모델 호출과 테스트의 기본 구조 | 검색 조건, 답변 규칙, 출처 검증 |
| 위키와 분석 결과의 기본 양식 | 위키 유형, 경험 기록, 검토·게시 규칙 |
| 배포·운영 안내와 단계별 복구 지점 | 회사 환경 설정, 평가 자료, 운영 문서 보완 |

### 5.3 AI 코딩 도구를 활용한 직접 구현

각 단계는 **요구 정의 → 개발 프롬프트 작성·실행 → 생성 코드와 결과 확인 → 테스트 → 수정 → 변경 기록** 순서로 진행합니다. 프롬프트를 입력하는 행위 자체가 아니라, 직원이 기대 결과와 검증 기준을 설명하고 잘못된 결과를 고칠 수 있는지를 확인합니다.

핵심 구현은 수업 내 실습으로 편성합니다. 자료 선정·사용 승인·계정 준비는 사전 준비사항이며, 추가 실습은 선택 과제로 운영합니다. 핵심 기능의 완성을 사실상 수업 외 개발에 의존하도록 구성하지 않습니다.

## 8. 주차별 상세 교육 내용

### 1주차. 업무 문제와 서비스 목표 정의

**학습 목표**  
직원이 현재 업무에서 반복되는 조사와 재작업의 원인을 정리하고, 도메인 위키로 해결할 첫 번째 문제를 결정합니다.

**직원에게 전달하는 내용**  
일반 지식과 회사의 실무 경험을 구분하고, 파일 보관·지식 정리·검색·챗봇의 역할 차이를 설명합니다. RFP에 드러나지 않는 전제, 신규 담당자의 지식 격차, 선임자에게 반복되는 질문을 서비스 요구로 바꾸는 방법을 다룹니다. 한 개 도메인에 집중하고, 구현할 기능보다 확인할 업무 효과를 먼저 정하는 방법을 배웁니다.

**직원 직접 실습**  
현재 업무 흐름에서 지식을 찾거나 확인하는 지점을 표시합니다. 대표 사용자와 업무 시나리오를 정의하고 실제 질문을 작성합니다. 우선 적용할 도메인, 대표 문서, RFP 검토 범위와 이번 과정에서 제외할 기능을 결정합니다.

**산출물과 완료 확인**  
업무 문제 정의서, 서비스 목표, 범위표, 대표 질문 목록을 작성합니다. 직원이 “누가, 어떤 업무에서, 무엇을 더 쉽게 하게 되는가”를 설명할 수 있는지 확인합니다.

### 2주차. 도메인 지식 구조와 운영 규칙 설계

**학습 목표**  
문서와 경험을 같은 기준으로 정리하고, 사실·관행·추론을 구분하며, 다른 직원이 재사용할 수 있는 지식 구조를 설계합니다.

**직원에게 전달하는 내용**  
도메인·발주처·프로젝트·문서 유형·버전·적용 시점·보안등급을 메타데이터로 관리하는 이유를 설명합니다. 법적 기준, 공식 지침, 내부 검증 지식, 프로젝트 관행, AI 추론을 구분합니다. 위키의 페이지 유형과 연결 관계, 실무 경험을 짧게 기록하는 양식, 검토·게시·개정 책임을 다룹니다. 정답과 근거를 미리 정한 평가 질문의 작성법도 익힙니다.

**직원 직접 실습**  
대표 자료를 분류하고 개념·절차·규정·사례의 위키 양식을 만듭니다. 추가 요구사항이나 수정 이유를 경험 지식 카드로 작성합니다. 답이 있는 질문과 답이 없는 질문을 구분하고, 기대 근거와 적용 범위를 기록합니다.

**산출물과 완료 확인**  
문서 분류표, 위키 양식, 경험 기록 양식, 검토 규칙, 평가 질문 초안을 작성합니다. 다른 직원이 동일 자료를 같은 기준으로 분류할 수 있는지 확인합니다.

### 3주차. AI 코딩과 서비스 기반 이해

**학습 목표**  
직원이 회사 저장소에서 시작 프로젝트를 실행하고, AI 코딩 도구가 만든 결과를 검증하며 기능을 개발하는 방법을 익힙니다.

**직원에게 전달하는 내용**  
화면, 서버 처리, 데이터베이스, 문서 처리 프로그램, AI 호출의 역할을 설명합니다. 개발 프롬프트에 목적·입출력·수정 범위·검증 기준을 명시하는 방법을 배우고, 코드 변경 전후 테스트와 기록의 중요성을 다룹니다. 환경변수와 API 키 보호, 모델 호출을 한곳에 모으는 구조, 구조화된 응답의 의미를 설명합니다.

**직원 직접 실습**  
시작 프로젝트를 실행하고 회사 개발 계정에 연결합니다. 간단한 입력 화면에서 서버를 거쳐 AI를 호출하고 결과를 확인합니다. 작은 기능을 프롬프트로 수정한 뒤 테스트하고, 변경 사항과 남은 문제를 저장소에 기록합니다.

**산출물과 완료 확인**  
실행 가능한 회사 저장소, 환경 설정 예시, 첫 AI 호출과 기본 테스트를 남깁니다. 직원이 브라우저에 비밀키를 넣지 않는 이유와 각 처리 단계의 역할을 설명할 수 있는지 확인합니다.

### 4주차. 문서·경험 지식 등록과 권한 관리

**학습 목표**  
승인된 자료를 안전하게 등록하고, 원본·버전·처리 상태와 접근 범위를 관리하는 기능을 구현합니다.

**직원에게 전달하는 내용**  
원본과 AI가 만든 파생 정보를 분리하는 이유를 설명합니다. 같은 문서의 새 버전과 중복 업로드를 구분하고, 사용자·프로젝트 권한이 검색 결과에도 적용되어야 함을 다룹니다. 긴 문서 작업을 웹 화면에서 기다리게 하지 않고 별도 작업으로 접수하는 방식과 실패 상태·재처리의 의미를 배웁니다.

**직원 직접 실습**  
문서 등록·목록·상세 화면을 연결하고 분류 정보를 수정합니다. 경험 지식 카드도 같은 도메인과 프로젝트에 연결해 등록합니다. 파일 중복, 권한이 다른 계정의 접근, 처리 실패 표시를 시험합니다.

**산출물과 완료 확인**  
문서·경험 등록 화면, 원본 관리, 버전 정보, 작업 상태 화면을 완성합니다. 권한 밖 자료가 보이지 않고, 실패 원인과 재처리 경로를 확인할 수 있는지 점검합니다.

### 5주차. 문서 해석과 검색 단위 구성

**학습 목표**  
직원이 문서 처리 결과를 검토하고, 도메인별로 의미가 유지되는 검색 단위를 만들 수 있도록 합니다.

**직원에게 전달하는 내용**  
단순 텍스트 추출과 제목·본문·표·읽기 순서 분석의 차이를 설명합니다. 문서 분할은 글자 수만 맞추는 작업이 아니라 한 조각만 읽어도 의미를 이해할 수 있게 만드는 작업임을 다룹니다. 보고서의 절, 법령의 조항, 화면설계서의 화면 ID 등 문서 유형별 기준을 비교합니다. PDF 페이지, 슬라이드 번호, 문서 제목·절 등 실제 형식에 맞는 원문 위치를 보존하는 방법을 익힙니다.

**직원 직접 실습**  
대표 문서를 처리하고 누락·표 붕괴·잘못된 읽기 순서를 점검합니다. 분할 규칙을 바꾸어 결과를 비교하고, 각 조각에서 원문으로 돌아갈 수 있는지 확인합니다. 동일 자료를 다시 처리했을 때 중복이 생기지 않는지 시험합니다.

**산출물과 완료 확인**  
문서 유형별 처리·분할 규칙, 원문 위치가 연결된 검색 단위, 실패 사례 기록을 만듭니다. 지원하지 못하는 형식은 잘못된 결과를 정상 처리로 표시하지 않고 제한 사항으로 남깁니다.

### 6주차. 도메인 검색과 품질 진단

**학습 목표**  
정확한 전문용어와 자연어 질문을 함께 다루는 검색을 구현하고, 원하는 근거를 찾지 못하는 원인을 분석합니다.

**직원에게 전달하는 내용**  
의미 검색에 사용하는 숫자 표현인 임베딩의 역할을 설명합니다. 키워드 검색과 의미 검색의 장단점을 비교하고, 도메인·발주처·프로젝트·적용 시점 필터를 함께 사용하는 방법을 다룹니다. 한글 표현과 약어, 동의어를 점검하고, 검색 순위와 실제 관련성을 평가하는 방법을 익힙니다.

**직원 직접 실습**  
같은 의미의 전문용어 질문과 자연어 질문을 실행해 결과를 비교합니다. 두 검색의 결과를 결합하고 프로젝트 필터를 적용합니다. 평가 질문을 실행해 기대 근거가 상위 결과에 있는지 확인하고, 실패한 질문의 원인을 문서 분할·분류·검색 조건으로 나누어 수정합니다.

**산출물과 완료 확인**  
통합 검색 기능, 결과 진단 화면, 검색 평가표와 개선 기록을 만듭니다. 직원이 “답변 모델을 바꾸기 전에 무엇을 확인해야 하는가”를 설명할 수 있는지 확인합니다.

### 7주차. 근거 기반 챗봇과 원문 검증

**학습 목표**  
직원이 검색된 자료에 근거해 답하고, 답변과 원문이 맞는지 직접 확인할 수 있는 챗봇을 구현합니다.

**직원에게 전달하는 내용**  
질문 해석, 관련 자료 선택, 답변 생성, 출처 확인의 전체 흐름을 설명합니다. AI가 문서명과 주소를 임의로 만들지 않도록 실제 검색된 근거 식별자만 사용하게 하는 방식을 다룹니다. 출처의 존재와 주장·근거 일치 여부는 별도로 확인해야 함을 강조합니다. 근거 부족, 자료 충돌, 적용 범위 불명확을 숨기지 않는 응답 규칙을 익힙니다.

**직원 직접 실습**  
답변 화면에 출처 카드와 원문 확인 기능을 붙입니다. 답할 수 있는 질문과 자료에 없는 질문을 비교합니다. 존재하지 않는 출처, 적용 시점이 다른 문서, 문서 안에 포함된 지시문을 이용한 오작동 시도를 점검하고 수정합니다.

**산출물과 완료 확인**  
근거 기반 챗봇, 출처 검사, 원문 확인, 피드백 기능을 완성합니다. 핵심 주장과 실제 근거를 직원이 대조하고, 불확실한 내용을 확정적으로 답하지 않는지 확인합니다.

### 8주차. LLM Wiki 생성·검토와 지식 순환

**학습 목표**  
원문과 경험 기록을 사람이 읽기 쉬운 위키로 정리하고, 지식을 검토·게시·개정하는 운영 흐름을 구현합니다.

**직원에게 전달하는 내용**  
LLM Wiki를 “AI가 초안을 정리하고 직원이 검토하는 지식 축적 방식”으로 설명합니다. 개념·절차·기관·규정·사례별 양식, 기존 페이지 검색과 갱신, 중복과 충돌 처리, 원문 근거 연결을 다룹니다. 위키의 관련 페이지를 연결하는 관계 정보를 설계하고, 초안과 게시본을 구분합니다. 경험 기록을 다음 프로젝트에서 다시 찾을 수 있게 만드는 방법도 익힙니다.

**직원 직접 실습**  
문서와 경험 지식 카드로 위키 초안을 생성합니다. 기존 페이지와 비교해 수정·병합 후보를 검토하고, 근거와 적용 범위를 확인한 뒤 게시합니다. 다른 직원이 새 위키를 탐색하고 질문하여 이해할 수 있는지 상호 검토합니다.

**산출물과 완료 확인**  
위키 탐색 화면, 초안·검토·게시 흐름, 버전과 관련 페이지, 경험 반영 사례를 만듭니다. AI 생성 직후 자동 게시되지 않고, 지식을 등록하지 않은 직원도 원문과 맥락을 이해할 수 있는지 확인합니다.

### 9주차. RFP 초기 검토에 업무 적용

**학습 목표**  
축적한 도메인 지식이 실제 요구사항 검토에 도움이 되는지 대표 과제로 확인합니다.

**직원에게 전달하는 내용**  
RFP 원문에서 요구사항과 조건을 구분하고 기능·데이터·운영·보안·UI 등으로 분류하는 방법을 설명합니다. 관련 위키와 원문, 과거 프로젝트 사례를 찾아 비교하되 과거 사례를 모든 사업의 의무로 일반화하지 않는 원칙을 다룹니다. 누락 확정이 아닌 누락 가능성, 불명확성, 충돌로 결과를 구분하고 실무자가 검토할 질문을 작성합니다.

**직원 직접 실습**  
대표 RFP의 합의된 요구사항 묶음을 분석합니다. 관련 근거를 연결하고, 추가로 확인할 항목과 발주처 질문을 생성합니다. 도메인 담당자가 유용한 제안과 부정확한 제안을 구분하고 수정 이유를 남깁니다.

**산출물과 완료 확인**  
원문에 연결된 요구사항, 근거 비교표, 확인 질문, 직원 검토 결과를 작성합니다. 자동 보고서의 분량보다 실제로 도움이 된 근거와 질문이 있는지 평가합니다. 대규모 RFP 자동 분석은 후속 개발 범위로 분리할 수 있습니다.

### 10주차. 독립 운영 검증과 사내 서비스 전환

**학습 목표**  
직원이 강사의 직접 구현 없이 신규 자료를 반영하고 결과를 개선할 수 있는지 확인하며, 사내 시험 운영의 조건을 결정합니다.

**직원에게 전달하는 내용**  
기능 실행 여부와 지식·답변의 품질을 구분하는 평가법을 정리합니다. 검색·답변·출처·권한·재처리 결과를 종합하고, API 사용료뿐 아니라 지식 검토와 유지관리 시간까지 운영 부담으로 확인합니다. 기본 배포·백업·복구 절차, 운영 역할, 후속 기능의 우선순위 결정 방법을 설명합니다.

**직원 직접 실습**  
사전 시연에 사용하지 않은 문서 또는 질문을 대상으로 등록·검색·위키 반영·오류 수정·재검증을 수행합니다. 누적 평가 결과와 운영 문서를 확인하고 최종 시연을 진행합니다. 시험 운영 가능, 제한 조건부 가능, 보완 후 재검증 중 하나로 판정합니다.

**산출물과 완료 확인**  
최종 서비스 후보, 직원 독립 수행 기록, 평가 보고서, 운영 안내, 시험 운영 범위와 후속 개발 목록을 제출합니다. 중대한 권한·외부 전송·근거·복구 문제가 남으면 실제 사용자 공개를 보류합니다.

## 10. 성과 평가와 성공 기준

### 10.1 교육 종료 시 평가

교육 종료 평가는 화면의 완성도나 AI 답변의 길이가 아니라 **지식의 재사용, 결과 검증, 직원의 독립 개선, 운영 전환 준비**를 기준으로 수행합니다.

| 평가 영역 | 확인 방법 | 제출할 증거 |
|---|---|---|
| 지식 재사용 | 등록자가 아닌 직원이 위키와 원문을 이용해 대표 업무를 설명 | 상호 검토 기록과 적용 사례 |
| 검색 품질 | 기대 근거가 검색 상위 결과에 포함되는지 평가 | 질문별 검색 결과와 실패 원인 |
| 근거 적합성 | 출처가 존재하는지와 실제 주장을 뒷받침하는지를 각각 확인 | 주장·원문 대조 평가 |
| 불확실성 처리 | 답이 없는 질문과 충돌 자료에 대한 응답 확인 | 답변 보류·충돌 안내 결과 |
| 직원 독립 수행 | 처음 보는 문서나 질문을 등록·수정·재검증 | 수행 기록과 변경 내역 |
| 지식 운영 | 경험 기록이 초안·검토·게시를 거쳐 재사용되는지 확인 | 게시 이력과 검토 책임 |
| 안전한 운영 전환 | 권한, 외부 전송, 재처리, 원본·데이터 복구 경로 점검 | 점검표와 제한 사항 |

검색과 답변 품질의 정량 목표는 대표 문서의 사전 측정 결과를 기준으로 고객과 합의합니다. 수치 목표를 확정하기 전부터 **권한 밖 자료 노출이나 승인되지 않은 외부 전송을 허용하는 방식으로 성능을 높이지 않는다**는 원칙을 적용합니다.

### 10.2 사내 시험 운영 이후 측정할 효과

| 기대 효과 | 실제 업무에서 비교할 지표 |
|---|---|
| 자료 조사 부담 감소 | 같은 유형의 업무에서 지식과 근거를 찾는 데 걸리는 시간 |
| 신규 담당자의 이해 개선 | 대표 업무 이해에 필요한 선임자의 지원과 반복 질문 |
| 검토 품질 향상 | 직원이 유용하다고 인정한 추가 확인 항목과 질문 |
| 지식 누락으로 인한 재작업 감소 | 수정 발생 원인과 사전에 확인할 수 있었던 사항 |
| 지속 운영 가능성 | 문서 등록·위키 검토·오류 수정 시간과 API·운영 비용 |
| 조직 내 활용 확대 | 반복 사용자, 재사용된 위키와 프로젝트 적용 사례 |

업무 시간이나 재작업 감소율은 교육 전에 보장하지 않습니다. 기존 업무의 기준값을 확보하고 실제 프로젝트에서 사용한 결과를 비교해 개선 효과를 판단합니다.

### 10.3 사내 공개 판정

| 판정 | 의미 | 후속 조치 |
|---|---|---|
| 시험 운영 가능 | 합의한 제한 범위에서 품질·권한·운영 준비가 확인됨 | 승인된 직원과 문서를 대상으로 사용 시작 |
| 제한 조건부 가능 | 특정 형식·기능·사용 범위를 제한하면 운영 가능 | 제한 사항을 공개하고 보완 일정 수립 |
| 보완 후 재검증 | 중대한 보안·근거·복구 문제 또는 담당 체계 미비 | 공개를 보류하고 문제 해결 후 재평가 |

**교육 이수와 운영 승인은 구분합니다.** 운영 공개는 고객의 보안·운영 책임자가 검토하며, 교육 종료만으로 전사 운영 수준이 확보되었다고 판단하지 않습니다.

## 12. 지식·보안·운영 관리 원칙

### 12.1 원본과 지식의 신뢰성

원본 자료와 AI 요약은 구분하고, 위키·답변·RFP 검토 결과에서 사용한 문서 버전과 실제 원문 위치를 확인할 수 있게 합니다. PDF 페이지가 없는 형식에는 절·슬라이드 등 확인 가능한 위치를 사용하며, 존재하지 않는 페이지를 생성하지 않습니다.

법령·지침·과거 관행·AI 추론은 구분하여 표시합니다. 원문이 있다는 이유만으로 현재 사업의 의무라고 판단하지 않으며, 적용 시점과 범위를 검토합니다. 법적 기준의 최종 해석과 업무 적용 판단은 회사의 담당자가 수행합니다.

### 12.2 외부 AI 전송과 접근 권한

공개 자료 또는 회사가 사용을 승인한 내부 자료로 시작합니다. 문서 원문뿐 아니라 검색된 일부 내용, 임베딩 요청, 개발 도구 입력, 오류 로그에도 민감정보가 포함될 수 있으므로 전송 허용 범위를 먼저 정합니다.

등록 자료와 파생 위키에도 원본의 접근 범위를 반영하고, 권한이 낮은 직원이 위키나 답변을 통해 제한 문서 내용을 우회 조회하지 않도록 검증합니다. 기밀·개인정보가 포함된 자료는 제거·익명화하거나 회사가 승인한 별도 환경에서 다룹니다.

### 12.3 변경·삭제·복구

문서와 위키의 변경 이력을 남기고, 원본 변경·삭제 시 연결된 검색 데이터와 위키의 재검토 여부를 확인합니다. 긴 작업은 상태를 기록하며 실패 원인을 확인하고 재처리할 수 있도록 합니다.

데이터베이스와 원본 파일을 각각 복구 대상으로 포함합니다. 사전 검증과 운영 전환 준비 과정에서 합의된 범위의 복구 절차를 점검하고, 교육 종료 시 담당 직원에게 실행 안내와 제한 사항을 인계합니다.

## 14. 제공 범위와 비용 협의

### 14.1 본 제안의 기본 제공 범위

총 30시간의 교육·구현 코칭, 합의된 범위의 강사 사전 검증, 시작 프로젝트와 단계별 개발 프롬프트, 평가 기준과 결과 리뷰, 운영 전환 안내를 기본 제안 범위로 합니다. 사전 검증과 교육 자산 준비의 세부 분량 및 비용 반영 방식은 견적·계약에서 확정합니다.

본 과정은 직원이 직접 구축하도록 역량을 이전하는 교육입니다. 강사가 고객의 모든 요구 기능을 대신 구현하는 구축 용역이나, 교육 이후의 상시 장애 대응·유지보수 계약을 자동으로 포함하지 않습니다.

### 14.2 비용 항목

| 비용 구분 | 협의할 내용 |
|---|---|
| 교육 및 코칭 | 총 30시간, 회차 구성, 진행 장소·방식, 리뷰 범위 |
| 사전 검증·교육 자산 준비 | 대표 자료 처리, 레퍼런스 검증, 시작 프로젝트·프롬프트 준비 범위 |
| AI 사용 | 개발용 코딩 도구와 서비스 API 사용 계정, 사용 상한과 집계 방식 |
| 데이터·배포 환경 | 데이터베이스, 원본 저장, 실행 환경, 백업과 기타 운영 비용 |

구체적인 금액은 본 초안에 포함하지 않습니다. 사용 모델·자료량·배포 환경과 제공 범위를 합의한 뒤 견적을 확정합니다. 기존 PC와 회사 계정을 우선 검토하며, 고가 장비의 선구매를 전제로 하지 않습니다.

### 14.3 착수 전 확정할 사항

첫 도메인과 대표 시나리오, 참여 직원 및 역할, 실제 일정과 총시간, 사전 자료·계정 승인, 교육비와 실사용 비용의 구분, 작성물의 이용·관리 범위, 교육 이후 운영 책임과 추가 지원 조건을 확인합니다.

## 15. 제안의 기대 가치

본 과정의 최종 성과는 위키 화면이나 챗봇 하나가 아닙니다. 회사의 문서와 경험을 다른 직원이 재사용할 수 있는 지식으로 전환하고, 그 지식의 근거와 적용 범위를 확인하면서 실제 업무에 활용하는 방법을 확보하는 것입니다.

강사는 전체 흐름의 기술·업무·교육 가능성을 사전에 검증하고, 직원은 검증된 기반 위에서 회사가 계속 사용할 서비스를 직접 구현합니다. 교육 이후에는 새로운 문서와 경험을 추가하고, 잘못된 결과를 개선하며, 실제 활용 기록을 바탕으로 다음 투자를 판단합니다.

> **도메인 지식이 사람에게만 남지 않고 회사에 축적되며, 교육에서 만든 서비스가 일회성 결과물로 끝나지 않고 직원의 손으로 계속 발전하도록 하겠습니다.**
