# 프롬프트를 직접 쓰고 실행해 보기

프롬프트는 **AI에게 무엇을 해 달라고 요청하는 글**입니다. 어려운 명령어나 특별한 문체를 배울 필요는 없습니다. 동료에게 일을 부탁하듯 현재 상황, 원하는 결과, 지켜야 할 조건을 적습니다. 이 교재에서는 ‘요청문’과 같은 뜻으로 사용합니다.

각 단계의 기존 실습 중 한 번은 **내가 작성 → AI에 전송 → 실제 결과 확인 → 한 조건을 보완해 다시 전송 → 두 결과 기록**을 수행합니다. 완성 예시를 읽는 데서 끝내지 않고, 예시의 한 부분이라도 자신의 상황에 맞게 작성합니다. 문장이 길거나 첫 답이 만족스럽다는 이유만으로 좋은 요청이라고 판단하지 않습니다.

창 선택부터 헷갈리면 [입력 위치 안내](start-here.md#어디에-입력하나요)를 먼저 봅니다. 아래 요청문은 한국어로 읽고 바꾸어 쓰는 예시입니다. 프로그램 실행 명령을 넣는 일반 터미널과 AI 대화창을 구분합니다.

## 1. 어디에 입력하나요

| 하려는 일 | 입력할 곳 | 확인할 결과 |
| --- | --- | --- |
| 코드·구조 설명, 화면 변경, 오류 수정 요청 | 실습 프로젝트에서 실행한 Claude Code의 대화 입력창 | 실제 파일에 근거한 설명, 변경 계획·결과 |
| 등록한 업무 자료에 관한 질문 | domain-wiki 브라우저의 채팅 입력창 | 선택한 프로젝트의 근거와 답변 |
| 위키 작성 기준 변경 후 초안 비교 | 개발용 AI에서 기준 문장 작성 → 교육생이 관리 화면의 목적·위키 구조에 반영 → 기존 AI 초안 생성 기능 실행 | 적용한 기준, 원문과 초안의 차이 |

터미널에서 `claude`를 실행하면 AI 대화를 시작합니다. 아래 예시의 한국어 문장은 **Claude Code 대화창**에 입력하며, 일반 Git Bash·Terminal 명령줄에 붙여 넣지 않습니다. ‘위키 채팅용’으로 표시한 예시는 브라우저의 채팅창에 입력합니다. 서비스 AI도 CLI를 사용하지만 두 입력창의 역할은 다릅니다.

개발용 AI는 프로젝트의 코드 파일을 읽을 수 있습니다. 위키 채팅은 선택 범위에서 검색되는 공개 자료를 사용합니다. 파일 이름이나 ‘첨부한 자료’라는 말만 적었다고 AI에게 자료가 전달되는 것은 아닙니다. 실제 프로젝트 위치, 자료 등록·공개 상태와 선택 범위를 확인합니다.

## 2. 처음에는 세 줄로 시작하기

1단계에서는 아래에서 **대괄호 한 곳을 자신이 궁금한 대상으로 바꿉니다.** 나머지 문장은 그대로 사용해도 됩니다. 대괄호와 선택지는 지우고 전송합니다.

```text
이 domain-wiki에서 [웹 서버 / 작업자 / DB 중 하나]가 무엇을 하는지 초보자에게 설명해 주세요.
AGENTS.md, package.json, docs/design/hince/DESIGN.md를 읽고 실제 프로젝트를 기준으로 설명해 주세요.
파일 수정·서버 실행은 하지 말고, 환경 파일·계정 파일의 비밀 값은 읽거나 출력하지 마세요.
```

예를 들어 `작업자`를 골랐다면 결과에 ‘문서 처리’, ‘웹 서버와 별도로 실행’ 같은 역할이 설명되는지 확인합니다. 이 설명은 기대 기준이며 실제 AI 응답을 미리 작성한 것은 아닙니다.

첫 답을 읽고 **이해하기 어려운 표현 한 개** 또는 **추가로 확인하고 싶은 점 한 개**를 고릅니다. 다음처럼 자신의 후속 요청을 작성하고 다시 실행합니다.

```text
방금 설명한 작업자가 언제 필요한지 아직 잘 모르겠습니다.
문서 한 건을 등록했을 때 웹 서버와 작업자가 하는 일을 각각 한 줄로 비교해 주세요.
'구성 요소 / 하는 일' 두 열의 표로 쓰고, 실제 확인한 파일 위치를 덧붙여 주세요.
파일 수정이나 실행은 하지 말고 설명만 해 주세요.
```

두 번째 결과에서 역할을 구분할 수 있는지 확인하고, 두 요청과 실제 결과의 차이를 [T3 기록표](templates.md#t3-ai-개발-요청)에 남깁니다. 첫 답이 이미 이해하기 쉬웠다면 없는 오류를 만들지 말고 예시·비교·확인 질문을 추가합니다.

## 3. 업무 요청에 필요한 다섯 가지

간단한 질문에 매번 다섯 항목을 모두 쓸 필요는 없습니다. 작업이 복잡하거나 AI가 의도를 놓쳤을 때 빠진 내용을 찾아 보완하는 기준으로 사용합니다.

| 확인할 것 | 스스로 묻는 질문 | 동의어 개선 요청의 예 |
| --- | --- | --- |
| 목표 | 무엇을 하려는가? | 동의어가 각각 저장되게 개선 |
| 상황·자료 | 어떤 화면·입력·자료를 봐야 하는가? | 관리 화면에서 `VMS; 전광표지， VMS`를 저장한 결과 |
| 원하는 결과 | 무엇이 나오면 되는가? | `VMS`, `전광표지` 두 항목으로 저장·재조회 |
| 지킬 조건 | 무엇을 유지하거나 추측하지 말아야 하는가? | 길이·개수 제한, 권한, 입력 순서·대소문자 유지 |
| 확인 방법 | 내가 무엇으로 완료를 판단할 것인가? | 같은 입력 저장·다시 열기, 기존 거부 입력 확인 |

‘최고의 전문가처럼’, ‘완벽하게’라고 쓰기보다는 어떤 값을 입력하고 어떤 결과를 기대하는지 적으면 요청이 분명해집니다. 파일 이름이나 기술 용어를 모르면 ‘실제 코드에서 위치를 찾아 설명해 주세요’라고 적습니다.

아래는 **작성 틀**입니다. 2단계부터 이번 과제에 맞게 필요한 줄을 채웁니다.

```text
하고 싶은 일: [이번에 해결할 한 가지]
현재 상황과 볼 자료: [화면·입력·실제 결과 또는 원문 위치]
원하는 결과: [기대 동작 또는 답변의 형태]
지킬 조건: [기존 동작·범위·근거·변경하지 않을 것]
확인할 방법: [내가 실행할 입력과 기대 결과]

먼저 현재 상태를 확인하고 필요한 작업과 확인 방법을 설명해 주세요.
확인하지 못한 내용은 미확인으로 표시해 주세요.
```

코드 변경 과제에서는 계획을 읽은 뒤 구현을 요청합니다. 설명·조사만 필요한 단계에는 ‘지금은 파일을 수정하지 마세요’를 덧붙입니다. 업무 사실을 묻는 경우에는 근거 자료와 범위를 적고, 자료에 없는 내용은 모른다고 답하도록 요청합니다.

## 4. 막연한 요청을 구체적으로 바꾸기

### 개발용 AI · 2단계 도움말 개선

`화면을 편하게 만들어 주세요.`만으로는 어떤 화면에서 무엇을 바꿀지 알기 어렵습니다. 현재 실습의 화면·문구·유지 조건을 넣어 봅니다.

```text
실무 기록의 '작성 당시 메모' 도움말에
'프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요.'를 추가하고 싶습니다.
메모가 없어도 작성할 수 있고 AI 정리가 원문을 바꾸지 않는다는 기존 안내는 유지해 주세요.
입력 항목·저장·권한·화면 스타일은 유지해 주세요.
먼저 변경 계획을 설명해 주세요. 완료 후에는 제가 화면을 다시 열어 안내 문구와 메모 입력을 확인하겠습니다.
```

이 예시는 자신의 초안과 비교할 참고입니다. 먼저 직접 써 본 뒤, 빠진 목표·조건 한 가지를 골라 고칩니다. 구현 후 문구가 보이지 않는다면 ‘안 됩니다’ 대신 실제 접속 화면, 기대 문구, 보인 결과를 전달합니다.

### 위키 채팅용 · 업무 근거 확인

등록·공개된 [프로젝트 A 사업 개요](samples/01-project-a.md)를 사용할 때의 예입니다. 브라우저에서 프로젝트 A를 선택하고 입력합니다.

```text
프로젝트 A의 공개 사업 자료를 근거로 도로전광표지 설치 수량과 현장 장비 교체의 포함 여부를 알려 주세요.
'항목 / 확인된 내용 / 근거' 세 열의 표로 작성해 주세요.
자료에 없는 내용은 추측하지 말고, 제가 확인할 수 있도록 실제 근거를 연결해 주세요.
```

답변을 원문의 ‘24대’, ‘현장 장비 교체 제외’와 대조합니다. 프로젝트 B를 선택했거나 자료가 아직 비공개라면 프롬프트를 길게 고쳐도 같은 근거를 사용할 수 없습니다. 1단계에서는 필수 업무 질문을 먼저 수행하고 이 확장 예시는 참고용으로 사용합니다.

## 5. 한 번 실행한 뒤 어떻게 고치나요

1. **전송 전:** 이번 요청의 목표 한 가지와 완료 기준을 적습니다. 안내한 위치에서 AI가 실제 자료를 확인할 수 있는지 봅니다.
2. **실행:** 초안 요청을 전송하고 응답·처리 완료를 기다립니다. 요청을 적은 것과 실행한 것을 구분합니다.
3. **확인:** 설명은 실제 파일·원문, 코드 변경은 실제 화면과 저장 결과로 확인합니다. 기대 결과와 다른 부분을 한 가지 고릅니다.
4. **수정 후 재실행:** 확인한 차이를 넣어 후속 요청을 작성하고 전송합니다. 기존에 맞았던 조건은 유지합니다.
5. **비교 기록:** 처음과 수정 후의 요청·결과, 바꾼 조건, 좋아진 점 또는 남은 문제를 T3·T5에 남깁니다.

후속 요청도 직접 작성합니다. 아래 틀에서 이번에 확인한 사실만 채웁니다.

```text
방금 결과에서 [실제 확인한 부분]은 기대와 같습니다.
다만 [실제 결과]가 나왔고, 필요한 결과는 [기대 결과]입니다.
[추가할 자료·조건 또는 확인할 위치]를 반영해 다시 진행해 주세요.
이미 맞았던 [유지할 조건]은 유지하고, 수정한 점과 확인 결과를 알려 주세요.
```

코드를 고쳐 달라고 다시 요청할 때는 현재 결과가 기대와 어떻게 다른지 함께 적습니다. 그래야 AI가 같은 수정만 반복하지 않습니다. 오류가 없으면 정상 결과를 기록하고 다른 입력의 확인을 요청합니다. 두 번의 결과만으로 프롬프트의 일반적인 성능이 좋아졌다고 판단하지 않습니다.

## 6. 단계별 연습

아래 연습은 **기존 실습에 포함**합니다. 수업 전 필수 과제를 추가하지 않으며, 각 단계의 코드 구현과 저장, 근거 확인 활동으로 이어 갑니다.

| 단계 | 직접 작성하고 실행할 것 | 결과 확인과 후속 요청 |
| --- | --- | --- |
| 1 | 세 줄 틀에서 궁금한 구성 요소 선택 | 첫 설명을 읽고 예시·비교를 추가해 재실행 |
| 2 | 화면·원하는 문구·유지 조건 | 계획을 보고 빠진 조건을 보완한 뒤 구현·화면 확인 |
| 3 | 원문·적용 범위·사실과 미확인 조건 | 제안의 누락을 보완하고 기준 반영·위키 초안 확인 |
| 4 | 기준 평가를 마친 뒤 작성 규칙의 수정 요청 | 같은 v1로 미게시 초안 비교, 원래 설정 복원 |
| 5 | 본인이 확인한 입력·기대 저장 결과·기존 제한 | 계획의 범위를 보완한 뒤 구현·같은 입력 재확인 |
| 6 | 재현 순서·실제 결과·기대 결과·확인한 검사 | 원인과 가설을 구분하게 보완하고 수정 결과 확인 |
| 7 | 팀 과제의 초안을 예시를 가리고 작성 | 팀원이 빠진 조건을 찾아 보완, 각자 후속 요청 전송 |

4단계의 **기준 평가 질문 12개는 고쳐 쓰지 않습니다.** 프롬프트·작성 규칙 수정 연습은 기준 평가가 끝난 뒤의 실습 B에서 수행하고, 기준 점수와 섞어 기록하지 않습니다.

AI 응답이 지연되면 작성·전송·응답 확인 중 실제로 마친 곳까지 기록합니다. 로그인 만료·자료 미공개·작업자 중지처럼 실행 환경 문제라면 오류 안내로 해결하며, 더 좋은 문장을 쓰면 해결되는 문제로 취급하지 않습니다. 강사의 예시 응답을 읽은 것은 본인이 실행한 결과와 구분합니다.

## 7. 완료 확인

팀 활동에서는 함께 쓴 첫 요청의 본인 작성 부분과 본인이 전송한 후속 요청을 남깁니다.

각 단계의 대표 활동 한 번에서 다음 네 가지를 남깁니다. 긴 보고서 대신 실제 요청문과 결과 일부, 차이에 대한 한두 문장이면 됩니다.

- 내가 채우거나 새로 작성해 전송한 첫 요청
- 실제 응답과 원문·화면에서 확인한 내용
- 그 결과를 보고 작성·전송한 후속 요청
- 재실행 결과와 남은 문제 또는 추가로 확인한 조건

평가에서는 문장 길이·전문 용어·특정 틀 암기를 보지 않습니다. **원하는 일을 전달하고, 결과를 확인해 필요한 조건을 보완했는지**를 봅니다. 기록은 [T3](templates.md#t3-ai-개발-요청), 실제 변경 전후 확인은 [T5](templates.md#t5-변경-전후-비교)를 사용합니다.
