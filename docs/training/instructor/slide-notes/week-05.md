# 5회차 강사용 설명 메모 — 채팅과 지식 그래프로 근거 확인하기

교육생 공개 화면·워크북·다운로드에 포함하지 않습니다. 공통 원고와 생성기에서 함께 갱신합니다. 파일 반영 상태이며 사용자 확인과 교육생 실습 리허설 완료를 뜻하지 않습니다.

## 오늘의 연결

4회차에서 게시한 검수 업무 절차·범위 위키와 공개 원문 v2를 이어 사용합니다. 같은 위키 코드를 연 Claude Code와 실제 앱을 나란히 엽니다.

| 구간 | 장 | 할 일 | 설명·작업 순서 |
| --- | --- | --- | --- |
| 1교시 | 4–16장 | 질문 저장과 범위 재사용 | 현재 화면 → 계획 → 확인 후 실행 → 직접 작업 |
| 2교시 | 17–29장 | 답변 근거와 개인 확인 기록 | 현재 화면 → 계획 → 확인 후 실행 → 직접 작업 |
| 3교시 | 30–41장 | 관련 위키 비교와 탐색 복귀 | 현재 화면 → 계획 → 확인 후 실행 → 직접 작업 |
| 4교시 | 42–54장 | 대표 구현과 첫 통합 | 현재 화면 → 계획 → 확인 후 실행 → 직접 작업 |

마지막 55장은 직접 확인한 결과를 정리합니다. 개발과 통합 활동을 구분한다. 공통 단계를 모두 진행하고 실제 동작·저장·권한을 확인한다. 설명이나 AI 대기로 실습 시간을 채우지 않는다.

## 운영과 코칭

도입 5분, 교시별 50분, 휴식 세 번 각 10분, 마무리 5분으로 240분을 계획합니다. 각 교시의 직접 개발·사용 약 40분을 확보하려는 운영 기준이며 실측값은 아닙니다. 고정 시간을 교육생 화면에 표시하지 않습니다.

계획의 기술 용어를 읽는 대신 ‘원하는 동작인가 / 무엇을 누구의 기록으로 남길까 / 누가 볼 수 있을까 / 어떻게 확인할까’를 묻습니다. 코드 조사·구현·기술 검사는 AI가 맡고 교육생에게 코드 독해를 완료 조건으로 요구하지 않습니다.

네 교시의 공통 단계를 모두 수행합니다. 추가 도전은 공통 과제를 마친 뒤 진행하며 다음 회차의 시작 조건에는 포함하지 않습니다. 막히면 다음 기능에 필요한 최소 동작부터 함께 완성하되 미완료 항목을 완료로 표시하지 않습니다. 오류나 AI 대기 시간이 있어야 성립하는 실습으로 운영하지 않습니다.

각자 위키를 개발하고 배정된 역할별 계정으로 본인이 확인합니다. 동료의 사용을 실습 완료 조건으로 삼지 않습니다. 자료 공개·위키 게시의 별도 검토 담당과 제품의 권한 규칙은 유지합니다. 공용 환경 반영과 실제 운영 인수는 담당의 준비·확인 상태를 따로 기록합니다.

DB 구조 변경 파일, 실제 개발용 DB 적용, 화면의 저장·조회는 각각 확인합니다. 새로고침만으로 DB 저장을 증명하지 않습니다. 같은 서버 주소에 다른 브라우저로 로그인해 확인하고, 다른 사람의 개인 기록이 보이지 않는지도 확인합니다. 서로 다른 개인 서버의 DB는 자동으로 합쳐지지 않습니다.

## 이번 회차의 분량 운영과 리허설

## 4시간 운영과 실제 분량

도입·마무리 10분, 네 교시 각 50분, 휴식 세 번 각 10분으로 240분 운영안이다. 학생 화면에는 고정 분 단위를 넣지 않는다. 교시별 약 40분은 요구 판단·개발·확인·보완에 사용한다. 첫 요청만 실행하고 교시를 끝내지 않으며 네 공통 단계를 모두 수행한다.

1교시는 사용자별 질문·범위 DB, 불러오기와 입력 보존, 수정·복제·삭제, 목록 필터다. 2교시는 답변 ID와 인용 관계, 개인 기록과 공유 의견의 분리, 역할·상태별 확인이다. 3교시는 게시 위키 비교·실제 근거·탐색 복귀·개인 목록 보관이다. 4교시는 실제 서로 다른 변경의 비교·충돌 해결·DB 적용·업무 확인이다. 요청문 복사나 AI 대기 시간으로 분량을 채우지 않는다.

실제 교육생 개발 시간을 아직 측정하지 않았다. 4시간은 운영 설계이며 브라우저 확인이나 장수로 증명한 실습 시간이 아니다. 공통 기능을 마친 교육생은 같은 기능의 확장 과제를 진행한다. 어려운 부분은 다음 교시에 필요한 연결부터 코칭하고 미완료를 기록한다.

## 강사가 수업 전에 준비할 것

- 모든 교육생의 공개 원문 v2와 두 게시 위키, 역할별 계정, 앱 모델 연결을 확인한다. 3회차의 개인 초안·대기 기록을 임의 공개하지 않는다.
- 통합 기준표의 실제 저장소 주소, 대표 브랜치·커밋, 질문 고정하기 추가 변경 커밋, 별도 작업 사본 경로, 통합 개발 DB 식별 정보를 제공한다. 대표 구현에는 질문·답변 확인·위키 비교가 포함돼 있어야 한다.
- 추가 변경은 채택할 교육생 구현 또는 사전 준비한 공통 변경을 사용한다. 질문 고정·해제·상단 정렬과 DB 변경이 포함돼야 하며 대표 구현과의 차이 및 충돌을 미리 확인한다. 이 교재 작성 과정에서 해당 대표 저장소·추가 커밋을 생성한 것은 아니다.
- 통합 개발 DB에는 대표 구현과 호환되는 구조·가상 공개 자료·계정, 검수 조건 v2와 보완한 두 게시 위키가 준비돼 있어야 한다. 개인 운영 DB를 대신 연결하지 않는다. 설치·DB 준비에 수업 시간을 쓰지 않는다.
- origin은 교육생 fork, upstream은 강사 기준 저장소다. fetch와 병합을 구분하고 개인 작업은 별도 브랜치에 보관한다. 패키지 변경·DB 적용 이력을 함께 확인한다. 이미 적용한 DB 변경 파일을 덮어쓰지 않는다.
- 모두 같은 추가 변경을 자신의 통합 사본에서 직접 확인한다. 강사가 최종 기준 커밋·DB 변경 목록을 확정해 제공하며, 학생이 실제로 가져와 적용한 결과를 확인한다. 원격 게시나 운영 배포는 교육생 프롬프트에 섞지 않는다.

## 화면 확인의 범위

현재 앱에서 작성 계정으로 A 범위를 골라 실제 질문을 보냈고 답변·참고 자료·위키와 원문 인용을 확인했다. 현재 DB는 초기 v1 샘플이므로 60초·90일 답변이었다. 수업의 출발 상태는 4회차 결과인 v2이며 캡처와 구분한다. 지식 그래프의 필터·위키 목록·문서 미리보기·원문 근거를 실제로 확인했다. 신규 질문 모음·개인 확인 기록·비교 기능과 통합 실습은 아직 구현·실행하지 않았다.


## 전체 과정 연결 확인

[통합·회차 전환 준비표](../integration-readiness.md)의 실제 코드·주소·DB·자료 상태를 수업 전에 채운다. 문서가 있다는 이유로 준비 완료로 표시하지 않는다. 5회차 첫 통합과 6회차 버전별 보고서 재료, 7회차 동일 DB의 기록 보존을 확인한다. 실측 결과가 없는 교시는 수업 시간 적합성을 미검증으로 남긴다.


## 장별 설명

### 1장 · 채팅과 지식 그래프로 근거 확인하기

- **꼭 전할 말:** 앞에서 게시한 위키에 질문하고 근거를 읽습니다. 자주 묻는 질문과 확인한 내용을 다시 찾기 쉽게 만들고, 관련 위키를 함께 비교합니다.
- **시작할 말:** “앞에서 게시한 위키에 질문하고 근거를 읽습니다. 자주 묻는 질문과 확인한 내용을 다시 찾기 쉽게 만들고, 관련 위키를 함께 비교합니다.”
- **설명 순서:** 현재 화면 → 만들 결과 → 확인 기준
- **사례 하나:** 지금도 범위를 골라 질문하고 답변의 근거를 열 수 있습니다. 반복 질문과 확인 기록을 다시 사용하는 기능을 더합니다.
- **마무리할 말:** “다음은 ‘질문에서 확인 기록으로, 비교에서 통합으로’입니다.”
- **전환 기준:** 앞에서 만든 기능과 같은 사례를 이어 사용하고, 지금 확인할 결과를 분명히 한다.

### 2장 · 질문에서 확인 기록으로, 비교에서 통합으로

- **꼭 전할 말:** 같은 자료와 위키를 이어 사용합니다. 각 교시의 결과가 다음 작업의 시작점이 됩니다.
- **시작할 말:** “같은 자료와 위키를 이어 사용합니다. 각 교시의 결과가 다음 작업의 시작점이 됩니다.”
- **설명 순서:** 현재 화면 → 만들 결과 → 확인 기준
- **사례 하나:** 저장한 질문 → 실제 답변 → 개인 확인 기록 → 두 위키 비교 → 코드·DB 통합
- **마무리할 말:** “다음은 ‘게시한 위키와 채팅 범위를 먼저 확인합니다’입니다.”
- **전환 기준:** 앞에서 만든 기능과 같은 사례를 이어 사용하고, 지금 확인할 결과를 분명히 한다.

### 3장 · 게시한 위키와 채팅 범위를 먼저 확인합니다

- **꼭 전할 말:** 자료실의 원문 v2와 두 게시 위키가 출발점입니다. 준비가 안 된 상태를 질문 오류로 판단하지 않습니다.
- **시작할 말:** “자료실의 원문 v2와 두 게시 위키가 출발점입니다. 준비가 안 된 상태를 질문 오류로 판단하지 않습니다.”
- **설명 순서:** 현재 화면 → 만들 결과 → 확인 기준
- **사례 하나:** writer로 진행하고 reviewer·reader로 확인합니다. 첫 통합용 코드·전용 DB·공개 원문 v2·두 게시 위키는 강사가 준비합니다.
- **마무리할 말:** “다음은 ‘자주 묻는 질문을 범위와 함께 저장합니다’입니다.”
- **전환 기준:** 앞에서 만든 기능과 같은 사례를 이어 사용하고, 지금 확인할 결과를 분명히 한다.

### 4장 · 자주 묻는 질문을 범위와 함께 저장합니다

- **꼭 전할 말:** 질문 문장만 남기면 프로젝트를 잘못 고를 수 있습니다. 질문과 적용 범위를 같이 다시 사용하게 만듭니다.
- **시작할 말:** “질문 문장만 남기면 프로젝트를 잘못 고를 수 있습니다. 질문과 적용 범위를 같이 다시 사용하게 만듭니다.”
- **설명 순서:** 저장과 불러오기 → 질문 관리 → 다시 찾기
- **사례 하나:** 최근 대화는 이미 나눈 질문과 답변입니다. 내 질문 모음은 새 대화에서 다시 사용할 문장과 범위입니다.
- **마무리할 말:** “다음은 ‘저장할 질문 세 개를 미리 살펴봅니다’입니다.”
- **전환 기준:** 앞에서 만든 기능과 같은 사례를 이어 사용하고, 지금 확인할 결과를 분명히 한다.
- **저장·권한 코칭:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.

### 5장 · 저장할 질문 세 개를 미리 살펴봅니다

- **꼭 전할 말:** 아래 문장은 앱에 넣을 업무 질문입니다. 먼저 저장 기능을 만들고 각 항목을 입력합니다.
- **시작할 말:** “아래 문장은 앱에 넣을 업무 질문입니다. 먼저 저장 기능을 만들고 각 항목을 입력합니다.”
- **설명 순서:** A 검수 기준 → A 자동 복구 확인 → B 검수 기준
- **사례 하나:** 이름은 목록에서 알아볼 짧은 제목입니다. 질문 내용은 AI에게 보낼 문장입니다. B 질문은 A 질문을 복제한 뒤 문장과 프로젝트를 함께 바꿉니다.
- **마무리할 말:** “다음은 ‘숫자보다 먼저 질문 범위를 봅니다’입니다.”
- **전환 기준:** A 질문 두 개와 B 질문 한 개를 구분해 저장합니다.
- **저장·권한 코칭:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.

### 6장 · 숫자보다 먼저 질문 범위를 봅니다

- **꼭 전할 말:** 같은 문장이라도 어떤 자료를 찾는지가 다르면 답변도 달라집니다.
- **시작할 말:** “같은 문장이라도 어떤 자료를 찾는지가 다르면 답변도 달라집니다.”
- **설명 순서:** 프로젝트 A → 프로젝트 B → 문서에 없는 내용
- **사례 하나:** 현재 교재 캡처는 개정 전 샘플의 실제 화면입니다. 실습은 앞서 공개한 v2로 진행합니다. 새 대화에서 현재 자료를 확인하고 과거 답변을 고쳐 쓰지 않습니다.
- **마무리할 말:** “다음은 ‘내 질문 저장과 목록 만들기 · 계획하기’입니다.”
- **전환 기준:** 확인할 값과 확인할 수 없는 내용을 구분합니다.
- **저장·권한 코칭:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.
