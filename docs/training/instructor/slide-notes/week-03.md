# 3회차 강사용 설명 메모 — 회사 경험을 기록하고 다시 찾는 위키 만들기

교육생 공개 화면·워크북·다운로드에 포함하지 않습니다. 공통 원고와 생성기에서 함께 갱신합니다. 파일 반영 상태이며 사용자 확인과 교육생 실습 리허설 완료를 뜻하지 않습니다.

## 오늘의 연결

2회차의 내 위키·즐겨찾기와 같은 코드를 연 Claude Code를 준비합니다. 공개 샘플 원문·경험 기록과 관리자·작성 계정을 확인하고, 현재 작성 화면과 AI의 설명을 비교합니다.

| 구간 | 장 | 할 일 | 설명·작업 순서 |
| --- | --- | --- | --- |
| 1교시 | 4–18장 | 작성 화면과 업무 유형별 안내 만들기 | 작성 화면을 모달로 분리하기 → 본 과제 계획·실행 → 기본 개발 → 내 업무 적용 |
| 2교시 | 19–32장 | 여러 초안을 저장하고 이어 쓰기 | 현재 화면 → 계획 → 실행 → 기본 개발 → 내 업무 적용 |

마지막 61장은 직접 확인한 결과를 정리합니다. 교시마다 계획을 읽고 교육생이 결정한 뒤 구현합니다. 작은 기능의 계획 설명만으로 한 교시를 채우지 않습니다.

## 운영과 코칭

도입 5분, 교시별 50분, 휴식 세 번 각 10분, 마무리 5분으로 240분을 계획합니다. 각 교시의 직접 개발·사용 약 40분을 확보하려는 운영 기준이며 실측값은 아닙니다. 고정 시간을 교육생 화면에 표시하지 않습니다.

계획의 기술 용어를 읽는 대신 ‘원하는 동작인가 / 무엇을 누구의 기록으로 남길까 / 누가 볼 수 있을까 / 어떻게 확인할까’를 묻습니다. 코드 조사·구현·기술 검사는 AI가 맡고 교육생에게 코드 독해를 완료 조건으로 요구하지 않습니다.

1교시 업무 적용은 모두 인수인계 유형 등록 → 기록 저장 확인 → 숨기기·다시 사용 순서로 진행합니다. 2교시도 모두 저장 → 목록·수정 → 삭제·취소 → 복사 → 프로젝트별 보기 순서로 진행합니다. 3교시도 모두 근거와 나란히 보기 → 제출 전 확인 목록을 이어 만듭니다. 4교시도 모두 미완료 보기 → 프로젝트별 내 할 일 개수를 이어 만듭니다. 기능을 교육생별로 나눠 맡기지 않습니다. 강사는 첫 단계의 동작을 함께 확인한 뒤 다음 구현 요청을 안내합니다. 먼저 마친 교육생은 같은 확인 기준으로 다른 입력을 시험하고, 막힌 교육생은 강사의 코칭으로 공통 기능을 이어 완성합니다. 막히면 다음 기능에 필요한 최소 동작부터 함께 완성하되 미완료 항목을 완료로 표시하지 않습니다. 오류나 AI 대기 시간이 있어야 성립하는 실습으로 운영하지 않습니다.

각자 위키를 개발하고 배정된 역할별 계정으로 본인이 확인합니다. 동료의 사용을 실습 완료 조건으로 삼지 않습니다. 자료 공개·위키 게시의 별도 검토 담당과 제품의 권한 규칙은 유지합니다. 공용 환경 반영과 실제 운영 인수는 담당의 준비·확인 상태를 따로 기록합니다.

DB 구조 변경 파일, 실제 개발용 DB 적용, 화면의 저장·조회는 각각 확인합니다. 새로고침만으로 DB 저장을 증명하지 않습니다. 같은 서버 주소에 다른 브라우저로 로그인해 확인하고, 다른 사람의 개인 기록이 보이지 않는지도 확인합니다. 서로 다른 개인 서버의 DB는 자동으로 합쳐지지 않습니다.

## 회차 전체의 계정별 확인

관리자와 일반 사용자의 확인을 교육생 본인이 나눠 수행합니다. 같은 서버 주소를 사용하고 계정을 전환하거나 별도 브라우저·프로필을 사용합니다.

### 1교시 · 유형과 작성 안내

- 관리자: 관리 → 도메인 → 업무 유형별 안내에서 수정·저장·인수인계 등록·숨기기·다시 사용을 확인한다.
- 일반 사용자: 작성 창에서 저장한 안내와 사용 가능한 유형을 확인하고 기록을 저장한다. 관리자 설정은 바꿀 수 없어야 한다.

### 2교시 · 개인 초안

- 일반 사용자: 저장·목록·수정·삭제·복사·프로젝트별 보기를 확인한다.
- 관리자: 자신의 초안만 보이며 일반 사용자의 초안에 접근하지 못한다. 직접 요청 차단은 AI 서버 검사로 확인한다.

### 3교시 · 근거와 검토 요청

- 일반 사용자: 공개 자료에서 별도 연습 초안을 만들고 C1 원본·C3를 근거와 함께 검토 요청한다. C2·C4·C1 복사본·연습 글은 초안으로 남긴다.
- 관리자: 현재 코드에서는 검토 권한도 포함하므로 일반 사용자가 제출한 C1·C3 결과 기록을 읽을 수 있다. 타인의 개인 초안·개인 제출 완료 목록은 열 수 없게 한다.
- 공개 승인·반려는 이번 실습에서 실행하지 않는다. 관리자를 포함해 본인이 등록한 기록의 승인은 금지된다. 화면에서 직접 확인한 결과와 AI 권한 검사 결과를 구분한다.

### 4교시 · 검색과 개인 할 일

- 일반 사용자: C1·C3를 검색하고 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개의 할 일을 저장·수정·완료·미완료로 되돌리기 한다. 미완료 목록과 프로젝트별 숫자를 확인한다.
- 관리자: 제출된 C1은 읽을 수 있지만 작성자의 개인 할 일은 보이지 않아야 한다. 관리자 확인용을 자신의 계정으로 등록해 사용자 목록·집계에 섞이지 않는지 확인한다.
- 관리자 연습 항목을 삭제하고 사용자 세 가지 일을 모두 미완료로 둔다. 직접 요청 차단은 AI 검사 결과로 구분하며 공개 승인·반려는 하지 않는다.

## 이번 회차의 분량 운영과 리허설

2회차에서 시간이 많이 남았다는 사용자 피드백을 반영했다. 정확한 실습 소요 시간과 완료 범위는 아직 수집하지 못했으므로 4시간 충분성을 실측 완료로 표시하지 않는다.

운영 목표는 도입·정리 10분 + 네 교시 각 50분 + 휴식 세 번 각 10분이다. 교시별 설명 5분, 공통 개발 18분, 업무 적용 17분, 직접 확인 5분, 정리·코칭 5분을 출발점으로 삼는다. 개발·적용·직접 확인 합계 40분은 배분안이며 대기나 오류가 필요한 조건이 아니다. 화면에는 이 숫자를 표시하지 않는다.

첫 실행 요청만 수행한 것을 교시 완료로 판단하지 않는다. 후속 기능 두 개와 업무 적용까지 기본이며, 빠른 교육생은 확장 과제 두 개 중 하나를 고른다. 적용 요구는 이름 변경이 아니라 저장·조회·선택·변경 중 실제 동작을 바꿔야 한다. 기본이 막히면 강사가 최소 동작부터 코칭하고 미완료를 기록한다.

준비된 입력 사례 네 개는 개발할 기능의 비교 재료다. 기록을 여러 건 손으로 쓰거나 샘플 설치 오류를 해결하는 시간을 개발 분량으로 계산하지 않는다. 2교시 기능을 만든 뒤 개발용 사례 준비 요청을 사용해 반복 입력을 줄일 수 있다. 기존 원문과 공개 샘플은 다시 등록하지 않는다.

공통과 업무 적용을 빠르게 마치면 추가 도전으로 이어가고, 그 결과도 빨리 완성된다면 업무 적용의 요구 수준을 조정한다. 슬라이드·요청 수가 늘었다는 이유만으로 시간 검증을 통과 처리하지 않는다.

1교시는 모달 계획·실행을 먼저 한다. 새 과제를 추가해도 교시 수는 네 개로 유지한다. 닫기·복원 확인 후 유형 안내로 연결하고, 이미 동작하는 폼·AI 정리·근거 선택을 다시 구현하지 않는다. 강사는 진행 속도를 보고 추가 도전의 범위를 조절한다.

9–12장은 기존 워크북의 두 후속 요청을 계획·실행으로 나눠 보여 주는 장이다. 새 기능 분량을 더한 것으로 계산하지 않는다. 13장에서 별도 유형 확인용 기록 한 건을 직접 저장하고 검토 대기로 둔다. C1–C4의 초안·제출 배치는 그대로 유지한다.

2교시는 19–32장이다. 22–25장에 목록·수정과 삭제의 계획·실행을, 28–31장에 복사와 프로젝트별 보기의 계획·실행을 보여 준다. 기존 워크북에 있던 요청을 슬라이드에서도 볼 수 있도록 나눈 것이며 장수 증가를 실습 소요 시간으로 계산하지 않는다. 32장에서 일반 사용자·관리자 확인 후 작성 계정으로 돌아와 33장의 근거 연결로 이어간다.

3교시는 33–46장으로 구성한다. 내 초안의 C1·C3를 먼저 열어 2교시와 이어지는 목표를 설명한다. 자료에서 시작하는 기능은 별도 연습 초안으로 확인한 뒤 C1으로 돌아온다. C1 원본에서 근거·미리 보기·검토 요청을, 아직 작성 중인 C3로 모든 실무 기록에 적용할 나란히 보기·확인 목록을 개발한다. C3에는 프로젝트 B의 승인된 조건·적용 범위 두 본문 문단을 연결해 전환도 확인한다. 46장에서 C3 제출·C4 빈칸 안내와 관리자·일반 사용자 확인을 마친다. 결과는 내 초안의 제출 완료 영역에서 다시 연다. 관리자는 현행 코드상 검토 권한을 포함하되 자기 기록 승인은 금지된다. 공개 승인 없이 검토 대기로 마친다. 요청을 나눈 장수 증가를 개발 시간 측정으로 보지 않는다.

4교시는 47–60장이다. 48–53장에 기록 검색·개인 할 일·즐겨찾기 연결의 계획과 실행을 각각 둔다. 54장에서 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개의 할 일을 확인하고, 55–59장에서 미완료 보기와 프로젝트별 개수를 모두 개발한다. 60장에서 관리자와 일반 사용자의 개인 목록·집계를 비교한다. 새 기능이나 사례를 계속 늘리지 않고 같은 세 가지 일의 상태를 바꿔 확인한다. C1·C3는 검토 대기, C2·C4는 초안으로 유지한다. 61장에서 전체 결과를 정리한다. 요청을 슬라이드로 분리한 장수는 실제 개발 시간 측정값이 아니다.

14~18장은 유형 등록의 계획·실행·기록 저장 확인과 숨기기의 계획·실행이다. 기존 한 장에 모였던 절차와 입력 예시를 나눠 보여 주며 새 실습 기능을 추가한 것은 아니다. 삭제 연습용 초안은 삭제 실습에서 한 번만 지우고 다음 확인 장에서는 없어진 결과를 확인한다. 할 일 제목은 개인 할 일 구현에서 한 번 고친 뒤 후속 확인 장에서 유지 여부를 본다.

## 장별 설명

### 1장 · 회사 경험을 기록하고 다시 찾는 위키 만들기

- **꼭 전할 말:** 실무 기록 작성 창을 모달로 분리하고 업무 유형별 안내를 더합니다. 여러 초안을 DB에 보관하고 원문 근거를 붙여 검토를 요청한 뒤, 기록과 개인 확인할 일을 관리하는 기능을 이어 개발합니다.
- **시작할 말:** “먼저 현재 화면을 보겠습니다. 실무 기록에 상황과 판단, 결과를 쓰고 실무 기록 저장을 누르면 검토 대기로 등록됩니다. 지금도 기록을 남길 수 있습니다.”
- **설명 순서:** 현재 메뉴·작성·저장 → 내 업무에서 생길 불편 → 업무 유형·개인 초안·할 일 추가 → 네 교시와 연결 메뉴
- **사례 하나:** 검수 기록에 무엇을 써야 할지 막힌다면 업무 유형을 고를 때 작성 안내와 예시가 나오게 만듭니다. 예를 들어 검수에는 “무엇을 어떤 기준으로 확인했나요?”, 장애 대응에는 “어떤 문제가 발생했고 무엇부터 확인했나요?”를 보여 줍니다. 기존 네 입력칸은 유지합니다. 여러 기록을 쓰다 중단할 때는 개인 초안을, 후속 업무를 따로 챙길 때는 내 확인할 일을 추가합니다. 모두 현재 없는 개발 과제이며 같은 탭의 임시 복원과 개인 DB 초안은 다릅니다.
- **마무리할 말:** “실무 기록을 중심으로 네 교시를 이어갑니다. 관리에서 유형 안내를 설정하고, 자료실의 원문과 2회차 즐겨찾기도 연결합니다. 먼저 각 기능이 어떤 불편을 줄이는지 확인하고, 다음 장에서 개발 순서를 보겠습니다.”
- **전환 기준:** 현재도 작성·저장이 가능하고 오른쪽은 새 기능임을 구분한다. 개인 초안은 이어 쓰기용이며 완성한 글의 필수 제출 단계가 아니다. 실무 기록 중심으로 다른 메뉴를 연결하는 범위를 이해하면 다음 장으로 넘어간다.

### 2장 · 만든 기능을 다음 교시에서 이어 씁니다

- **꼭 전할 말:** 각 교시의 결과를 다음 교시에서 이어 쓰며 계획 확인과 직접 개발을 반복한다.
- **시작할 말:** “앞 장에서는 무엇을 왜 만들지 봤습니다. 이번에는 어느 화면에서 시작하고, 앞 교시의 결과에 무엇을 더할지 보겠습니다.”
- **설명 순서:** 각 행을 시작 화면 → 개발할 동작 → 완성 결과 → 이어서 할 일 순서로 읽고, 다음 행으로 내려간다.
- **사례 하나:** 1교시에 실무 기록의 작성 폼을 별도 창으로 옮기고, 관리 화면에서 설정한 검수·장애 대응 안내를 보여 줍니다. 2교시는 그 창에 여러 개인 초안의 저장·목록·수정·삭제를 붙입니다. 3교시는 자료실의 원문에서 작성을 시작하는 경로와 초안의 근거·미리 보기·검토 요청을 연결합니다. 4교시는 제출한 기록에서 남은 일을 관리하고, 기존 공개 기록을 2회차 즐겨찾기에서 다시 엽니다. 새 검토 대기 기록이 공개됐다고 가정하지 않습니다.
- **마무리할 말:** “매 교시 공통 기능을 직접 확인하고, 내 업무에 맞는 기능 한 가지까지 이어 만듭니다. 다음 장에서는 현재 작성 화면을 열고 AI의 코드 설명과 비교하겠습니다.”
- **전환 기준:** 앞에서 만든 기능에 무엇을 더할지 설명할 수 있으면 현재 화면 확인으로 넘어간다. 입력 사례는 업무 유형별 안내를 계획하는 7장에서 소개한다.

### 3장 · 현재 화면을 확인하고 실습을 준비합니다

- **꼭 전할 말:** 2회차의 내 위키·즐겨찾기와 같은 코드를 연 Claude Code를 준비합니다. 공개 샘플 원문·경험 기록과 관리자·작성 계정을 확인하고, 현재 작성 화면과 AI의 설명을 비교합니다.
- **시작할 말:** “지금까지 개발한 위키에서 실무 기록 메뉴를 열고 작성 버튼을 눌러 보세요. AI에도 이 메뉴의 작성·저장 흐름을 확인하라고 요청하겠습니다.”
- **설명 순서:** 실무 기록 메뉴·작성 버튼 확인 → 해당 기능의 코드 조사 → 화면과 설명 비교 → 다른 점·미확인 사항 확인
- **사례 하나:** 관리자(admin@wiki.local)는 유형·안내 설정과 제출된 기록 확인, 일반 사용자(writer@wiki.local)는 작성·초안·개인 할 일을 확인한다. 관리자는 검토 권한도 포함하지만 본인 등록 기록은 승인할 수 없다. 이번에는 승인하지 않으며 강사가 배정한 계정으로 바꿔도 된다.
- **마무리할 말:** “현재 화면과 AI 설명이 맞는지 확인했으면, 다음 장에서 처음 바꿀 동작을 정하겠습니다.”
- **전환 기준:** 교육생은 화면을 확인하고 AI는 코드를 조사한다. 저장 이후 동작은 코드 조사 결과로 구분한다. 화면과 설명이 다르거나 확인하지 못한 부분은 강사와 확인한 뒤 개선 범위를 정한다. 이 장에서는 입력 사례를 읽거나 계획·구현을 요청하지 않는다.

### 4장 · 작성할 때만 입력창을 열도록 바꿉니다

- **꼭 전할 말:** 목록을 볼 때는 기록에 집중하고, 새 글을 쓸 때만 별도 창을 열도록 바꿔 봅니다.
- **시작할 말:** “현재는 목록과 작성 폼이 한 페이지에 있습니다. 목록을 보고 싶을 때 긴 폼과 구분되도록, 작성할 때만 여는 창으로 바꿔 보겠습니다.”
- **설명 순서:** 현재 목록·작성 폼 → 나누려는 이유 → 버튼으로 열기 → 닫을 때 글 보호 → 기존 입력·저장 유지
- **사례 하나:** 제목과 상황을 쓰다 목록을 보고 싶다면 내용을 남기고 닫습니다. 같은 탭에서 다시 작성 버튼을 누르면 쓰던 글이 보여야 합니다.
- **마무리할 말:** “어디서 열고, 어떻게 닫고, 무엇을 유지할지 정했으니 이제 이 조건으로 계획을 받겠습니다.”
- **전환 기준:** 교육생이 작성 창을 나누려는 이유와 열기·닫기·입력 보존의 기대 동작을 말할 수 있으면 5장으로 간다. 업무 유형은 7장부터, 개인 DB 초안은 2교시이며 이번 계획에 섞지 않는다.
- **저장·권한 코칭:** 업무 유형과 입력칸별 작성 안내·예시는 해당 도메인에 연결해 DB에 저장합니다. 같은 도메인의 작성자가 함께 사용합니다. 8장에서 검수·장애 대응의 기본 안내를 저장하고 작성 창에서 불러오게 만듭니다. 9·10장에서는 관리 → 도메인 → 해당 도메인 수정에 안내 편집 영역을 만듭니다. 각 실무 기록에는 선택한 업무 유형과 당시 유형 이름을 따로 연결해 저장합니다. 유형이 없던 기록은 일반 기록으로 읽으며 본문과 공개 상태는 유지합니다.

### 5장 · 정한 동작대로 작성 창 분리를 계획합니다

- **꼭 전할 말:** AI의 계획을 읽고 동작·저장·권한·확인 방법을 교육생이 판단한다. 이 단계에서는 구현하지 않는다.
- **시작할 말:** “앞 장에서 정한 동작을 계획으로 받겠습니다. AI가 제시한 방법이 원하는 사용 방식과 맞는지 먼저 보세요.”
- **설명 순서:** 계획 요청 → 열기·닫기·입력 복원 대조 → 저장 성공·실패 확인 → 다른 점 수정 → 실행 여부 결정
- **사례 하나:** 같은 탭에서 다시 열었는데 제목만 남고 선택한 근거가 사라지는 계획이라면, 실행 전에 근거도 복원하도록 고쳐 달라고 합니다.
- **마무리할 말:** “원하는 동작과 계획이 맞으면 다음 장의 실행 요청을 보내세요. 맞지 않으면 이 단계에서 계획을 고칩니다.”
- **전환 기준:** 코드를 읽게 하지 않고 원하는 동작을 판단하게 한다. 화면 크기를 줄였을 때 입력칸과 저장 버튼이 보이는지, Tab 키로 입력칸을 옮길 수 있는지 뜻을 풀어 설명한다. 작성 창의 배치·조작만 바꾸고 기존 동작은 유지한다. 계획 확인 전에는 실행 요청을 보내지 않는다.
- **저장·권한 코칭:** 현재 작성 폼과 같은 탭의 임시 복원을 재사용하므로 이 변경에 새 DB 테이블은 필요하지 않습니다. “내용을 남기고 닫기”는 같은 탭에서 이어 쓰는 기능입니다. 탭을 닫거나 다른 브라우저로 이동한 뒤에도 남기는 저장 기능과 구분합니다.

### 6장 · 버튼으로 열리는 작성 창을 만듭니다

- **꼭 전할 말:** 확인한 계획에서 이번 단계만 구현한다. 계획에 없던 저장·권한 변경은 다시 확인한다.
- **시작할 말:** “확인한 계획으로 작성 창을 만들겠습니다. AI가 끝냈다고 하면 내 화면에서 열기와 닫기, 입력 복원을 확인하세요.”
- **설명 순서:** 확인한 계획 실행 → 모달 열기·입력 → 닫기 선택 → 다시 열어 복원 확인 → 창을 좁혀 스크롤·Tab 키 이동 확인
- **사례 하나:** 제목에 창 확인용, 상황에 한 줄을 적고 내용을 남기고 닫기를 누릅니다. 같은 탭에서 작성 버튼을 다시 눌러 두 입력값과 고른 근거가 남는지 봅니다. 확인용 글은 기록으로 등록하지 않습니다.
- **마무리할 말:** “열기와 입력 복원이 확인됐으면, 다음 장에서 같은 창에 업무 유형별 안내를 더하는 계획을 세우겠습니다.”
- **전환 기준:** 목록 아래 중복 폼이 없고 닫기·복원이 동작하면 7장으로 간다. 저장 실패·성공 처리는 AI 검사 결과를 먼저 받고, 유형 저장을 만든 뒤 13장에서 확인용 기록을 직접 등록한다.
- **저장·권한 코칭:** 현재 작성 폼과 같은 탭의 임시 복원을 재사용하므로 이 변경에 새 DB 테이블은 필요하지 않습니다. “내용을 남기고 닫기”는 같은 탭에서 이어 쓰는 기능입니다. 탭을 닫거나 다른 브라우저로 이동한 뒤에도 남기는 저장 기능과 구분합니다.

### 7장 · 입력칸별 작성 안내를 어떻게 보여 줄까요?

- **꼭 전할 말:** AI의 계획을 읽고 동작·저장·권한·확인 방법을 교육생이 판단한다. 이 단계에서는 구현하지 않는다.
- **시작할 말:** “작성 창이 열리고 쓰던 글이 남는지 확인했으니, 이제 업무에 맞는 작성 안내를 더하겠습니다. 아래 기록 개발 실습 사례 링크부터 열어 주세요.”
- **설명 순서:** 사례 링크 열기 → 유형별 작성 안내 표와 검수·장애 대응 예제 읽기 → 입력칸 옆 작성 안내 선택 → 계획 받기·판단
- **사례 하나:** 작성 안내는 무엇을 적으면 되는지 알려주는 문구입니다. 검수의 상황 칸에는 “무엇을 어느 기준으로 확인하려는가?”를 보여 줍니다. 실제 본문은 작성자가 직접 씁니다. 지금은 유형 선택·안내 표시, 관리자 편집, 기록 유형 저장의 세 단계를 계획하며 다음 장에서는 첫 단계만 구현합니다.
- **마무리할 말:** “작성 안내가 업무에 맞는지, 누가 안내를 고칠지, 이미 쓴 글은 어떻게 남길지 계획에서 확인하세요. 맞으면 다음 장에서 유형 선택부터 만들겠습니다.”
- **전환 기준:** 작성 안내 표와 C1·C2를 참고하고 DB 준비 요청은 아직 실행하지 않는다. 작성 안내·관리자 편집·기록 유형 저장을 차례로 만들며, 새 유형 추가·숨기기는 14~18장에서 다룬다.
- **저장·권한 코칭:** 업무 유형과 입력칸별 작성 안내·예시는 해당 도메인에 연결해 DB에 저장합니다. 같은 도메인의 작성자가 함께 사용합니다. 8장에서 검수·장애 대응의 기본 안내를 저장하고 작성 창에서 불러오게 만듭니다. 9·10장에서는 관리 → 도메인 → 해당 도메인 수정에 안내 편집 영역을 만듭니다. 각 실무 기록에는 선택한 업무 유형과 당시 유형 이름을 따로 연결해 저장합니다. 유형이 없던 기록은 일반 기록으로 읽으며 본문과 공개 상태는 유지합니다.

### 8장 · 업무 유형을 고르면 작성 안내가 달라집니다

- **꼭 전할 말:** 확인한 계획에서 이번 단계만 구현한다. 계획에 없던 저장·권한 변경은 다시 확인한다.
- **시작할 말:** “가상 교통관제 자료에 검수·장애 대응의 기본 안내를 연결해 저장하고, 작성 창에서 불러오게 하겠습니다. 관리자가 직접 고칠 화면은 그다음에 만듭니다.”
- **설명 순서:** 확인한 계획 실행 → 도메인·업무 유형에 안내 저장 → 작성 창에서 불러오기 → 안내 변화·입력 유지 확인
- **사례 하나:** 검수를 고르면 상황 옆에 “무엇을 어느 기준으로 확인하려는가?”가 보입니다. “검수 조건을 읽었다.”를 적고 장애 대응으로 바꾸면 “어떤 화면에서 어떤 증상이 보였는가?”로 안내가 달라져야 합니다. 적은 문장은 그대로 남습니다.
- **마무리할 말:** “유형에 따라 안내가 바뀌는 것을 확인했으니, 이제 관리자가 그 안내를 고칠 수 있게 만들어 봅시다.”
