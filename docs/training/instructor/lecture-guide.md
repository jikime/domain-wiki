# 회사 위키 개발 코칭 · 강사용

교육생은 각자의 위키를 개발하고 직접 사용해 판단합니다. 강사는 계획의 범위·저장·권한·완료 기준을 함께 살펴보고 막힌 부분을 코칭합니다. 이후 대표 구현과 추가 기능을 골라 회사 위키로 통합합니다. 이 문서는 공개 워크북·다운로드에 포함하지 않습니다.

[강의 기본 구성 원칙](../../lectures/TEACHING-STRUCTURE.md)을 따릅니다. 장별 노트는 슬라이드·워크북과 같은 원고에서 생성되며, 아래 링크에서 확인합니다.

[회차 전환·통합 준비표](integration-readiness.md)에 기준 코드·전용 DB·자료 상태·실행 주소를 실제 값으로 채웁니다. 특히 5회차의 질문 고정하기는 강사가 제공할 통합 연습 변경이고, 7회차의 최종 반영은 해당 교육생이 사용하던 DB의 기록을 유지해야 합니다. 교재 파일 완성과 수업 환경 준비 완료는 별도입니다.

4~7회차는 [전체 재구성안](../../lectures/COURSE-04-07-PLAN.md)의 16개 교시를 기준으로 진행합니다. 4~7회차는 슬라이드·워크북·강사 노트와 입력 사례까지 새 구성으로 반영했습니다. 아래 표는 현재 생성된 파일 목록입니다.

## 수업의 진행

개발 교시는 현재 화면 → 계획 요청 → 교육생의 확인·수정 → 실행 요청 → 직접 작업으로 진행합니다. 계획을 읽는 단계에서 코드를 수정하게 하지 않습니다. 확인한 범위를 실행한 뒤 다음 기능도 같은 순서로 이어갑니다. 조회·자료 등록·운영 기록은 해당 활동의 안내를 따릅니다.

계획에서 교육생에게 물을 것은 네 가지입니다. 원하는 동작인지, 무엇이 누구의 기록으로 남는지, 누가 보고 바꿀 수 있는지, 어떤 조작으로 완성을 확인할지입니다. 기술 용어와 코드 설명은 판단에 필요한 만큼만 짚습니다. 같은 작은 변경의 계획·수정·확인만으로 네 교시를 채우지 않습니다.

## 시간과 난이도

7회 × 4시간의 운영안입니다. 도입 5분 + 교시 네 번 각 50분 + 휴식 세 번 각 10분 + 마무리 5분으로 240분을 계획합니다. 각 교시에서 직접 개발·사용 약 40분을 확보하려는 기준이며 실측값은 아닙니다. 교육생 화면과 워크북에는 고정 분량을 표시하지 않습니다.

4~7회차의 공통 단계는 모두 함께 진행합니다. 공통 과제를 마친 교육생만 추가 도전으로 넓히며, 이를 다음 회차의 필수 조건으로 사용하지 않습니다. 막히면 다음 기능에 필요한 최소 연결부터 함께 완성하되 미완료를 완료로 표시하지 않습니다. AI 대기·오류·반복 입력으로 시간을 채우지 않고 실제 소요 시간을 기록해 조절합니다.

2회차는 DB 저장까지 기본에 포함합니다. 일괄 읽음 변경과 홈 고정은 선택 과제입니다. 회사 자료 준비·실행 환경·계정 문제를 반복 실습 분량으로 세지 않습니다.

## 회차별 코칭 초점

- **1회차:** 위키 채팅과 개발용 AI를 구분합니다. 별도 공개·게시 검토를 유지하고, 첫 작은 변경부터 계획을 확인합니다. 계정 준비 뒤 `db:seed-training`과 `db:check-training`으로 A/B 샘플·원본·게시 위키를 준비하고 실제 화면에서 확인합니다.
- **2회차:** 같은 위키 서버의 DB에 개인 기록을 저장합니다. 구조 변경 파일·개발 DB 적용·실제 저장과 조회를 구분합니다. 폴더 삭제·즐겨찾기 해제·원문 삭제와 내 메모·원문 제목을 구분합니다. 다른 브라우저의 같은 계정과 다른 계정을 본인이 확인합니다.
- **3회차:** 실무 기록 메뉴의 목적과 위치를 확인하고 작성 모달부터 만든다. 이어서 유형별 작성 안내·여러 개인 DB 초안·근거와 검토 요청·개인 확인할 일의 네 묶음이다. 공통 기능 뒤에 교시별 업무 적용 기능까지 기본으로 수행한다. 2회차에서 시간이 많이 남은 피드백을 반영했지만 소요 시간은 아직 미측정이다. 사례 C1–C4는 개발 후 사용할 입력 재료이며 기존 DB 백업이 아니다. 3교시는 내 초안의 C1·C3에서 시작해 실무 기록 개발을 이어간다. 자료실의 새 버튼은 별도 연습 글로 확인한 뒤 C1으로 돌아온다. C1으로 제출 흐름을 완성하고, 아직 작성 중인 C3로 비교·확인 기능을 보강한다. 새 기능은 모든 기록에 공통으로 적용한다. 초안·검토 대기·공개·개인 할 일 완료를 구분하고, 같은 초안의 중복 제출과 다른 사람의 개인 정보 접근을 검사한다. 강사 노트의 분량 운영·리허설 표를 사용한다.
- **4회차 운영:** 자료별 검색에서 찾은 원문으로 업무 절차 위키를 작성하고 수정 의견·재요청·게시를 연결합니다. 검수 조건 v2는 기존 자료의 새 버전으로 다루고 관련 위키를 보완합니다. 개인 실무 경험과 게시할 업무 절차를 구분하며, 앞 회차의 초안·검토 대기 기록은 그대로 둡니다.
- **5회차 운영:** 채팅의 질문 모음·답변 확인 기록과 그래프의 문서 비교를 개발합니다. 기존 근거 패널·위키 초안 저장·문서 미리보기를 재사용합니다. 후반에는 대표 구현과 채택할 추가 변경을 정해 첫 통합을 진행하고 모두 같은 기준을 직접 확인합니다. 모두 같은 질문 고정하기 변경을 합칩니다. 대표·추가·최종 기준 커밋과 별도 통합 개발 DB를 사전에 준비하고, 수업에서 코드와 DB 적용을 함께 확인합니다. 개인 데이터 이관은 별도 계획입니다.
- **6회차 운영:** 공통 업무 도구는 RFP 분석 보고서입니다. 항목 확인과 질문 답변을 개발하되 보고서 승인과 상태를 섞지 않습니다. 관리자는 회사 용어·운영 안내를 편집하고 사용자는 그 결과를 확인합니다. 후속 요청은 별도 원문으로 준비하고 여섯 항목의 초안에서 시작합니다. 새 버전의 확인 상태를 초기화하고 이전 회신은 참고로 연결합니다. 검토함의 담당·오류 처리와 RFP 상세 검토를 구분합니다. 두 변경 묶음을 통합본에 합치고 역할별로 점검합니다.
- **7회차 운영:** 새 업무를 수행하고 저장 실패·재접속·수정 충돌을 보완한 뒤 운영을 인계합니다. 공통 대상은 후속 요청 즐겨찾기의 내 메모입니다. 오프라인 복귀·같은 계정의 두 탭 충돌·계정 전환을 확인합니다. 별도 운영 연습 v1을 미리 공개하고 수업에서 v2로 갱신합니다. 실패 사례는 개발 환경에서 준비하며 공용 DB 중단·초기화로 실습하지 않습니다. 운영 인수자가 없으면 본인 확인과 실제 인수 확인을 구분합니다. 담당이 확인한 백업·복원 기록을 인계하며 교육생이 공용 DB를 복원하지 않습니다.

동료의 사용은 실습 완료 조건이 아닙니다. 배정된 역할별 계정으로 본인이 확인합니다. 자료 공개·위키 게시의 별도 검토 담당과 권한 규칙은 계속 유지합니다. 실제 직원 시범 사용은 준비된 경우 별도 근거로 남깁니다.

## 반영과 검증 상태

원고의 파일 반영, 사용자의 내용 확인, 실제 개발 리허설, 회사 도입 완료를 구분합니다. 기능 구현·DB 변경을 교육자료 작성 작업에서 실행하지 않습니다. 공용 환경 미준비는 담당·다음 행동이 있는 도입 과제로 남기고 로컬 성공을 도입 완료로 표시하지 않습니다.

`lecture-plan.json`은 이전 구성의 보관본입니다. 현재 수업은 `docs/lectures/course.json`과 위 장별 노트를 기준으로 진행합니다.
