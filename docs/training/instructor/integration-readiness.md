# 4~7회차 전환·통합 준비표 · 강사용

이 표는 준비 여부를 확인하는 양식입니다. 현재 저장소에 교육생이 개발할 기능이나 각 회차의 완성 DB가 모두 들어 있다는 뜻은 아닙니다. 강사가 실제 값을 채우고 확인한 뒤 사용합니다. 강사용 운영 자료이므로 공개 워크북에 넣지 않습니다.

## 준비 기준

- 교육생은 각자 코드와 DB를 사용합니다. 공통 `writer`·`reviewer` 계정 이름이 같아도 교육생끼리 한 DB를 동시에 수정하지 않습니다.
- 개인 개발본과 통합 코드 사본을 구분합니다. 수업마다 어느 사본·주소·DB를 쓰는지 먼저 표시하고, 원래 개인 작업은 보존합니다.
- 강사의 기준 커밋과 교육생의 실제 통합 커밋을 각각 남깁니다. 병합·선별 적용 방식에 따라 번호는 달라질 수 있습니다. 채택한 코드 내용·DB 변경·동작을 대조하며 번호를 맞추려고 강제로 초기화하지 않습니다.
- 기본 샘플 설치 파일은 초기 v1 상태입니다. v2·보완한 위키·교육 중 만든 기능·개인 기록을 모두 복원하는 백업으로 사용하지 않습니다.
- DB 변경 파일만 적용해도 기존 자료의 식별자·소유자·버전 관계가 유효한지 확인합니다. 서로 다른 구현의 테이블을 합치려면 기존 데이터의 변환 계획까지 정합니다.

## 회차 전환에서 실제로 열어 볼 것

| 시점 | 코드에 필요한 기능 | DB·앱에서 확인할 상태 |
| --- | --- | --- |
| 4회차 시작 | 2회차 개인 검색·즐겨찾기, 3회차 실무 기록 | 초기 검수 조건 v1·60초·90일, 기존 범위 위키, writer 소유·reviewer 검토 가능 |
| 5회차 시작 | 4회차 검색·작성·위치별 의견·개정 확인 | 공개 검수 조건 v2·30초·90일, 보완·게시한 업무 절차와 범위 위키. 다른 영향은 별도로 남김 |
| 5회차 첫 통합 직전 | 2~4회차 누적 기능과 질문 모음·답변 확인·위키 비교가 있는 대표 구현 | 학생별 통합 DB의 v2·두 게시 위키·역할 계정·모델 연결. 질문·대화·개인 메모는 이 환경에서 만든 확인용 결과를 사용 |
| 6회차 시작 | 첫 통합의 질문 고정하기까지 반영한 기준 | 공개 후속 요청, writer 소유의 여섯 항목·두 질문을 가진 시작 초안. 가상 회신·새 내부 상태는 아직 넣지 않음 |
| 6회차 추가 통합 직전 | RFP 변경과 관리 변경을 순서대로 반영할 기준 | 이전 회신·보류/재개 이력과 현재 질문을 가진 연습 보고서, 회사 용어·안내. 구조 적용 전에는 원문·기존 초안까지, 신규 구조 적용 후에는 후속 사례 입력까지 준비 |
| 7회차 시작 | 6회차 통합 기능 전체 | RFP 이전 회신·현재 R5/R6 질문, 용어·메뉴 안내, 별도 운영 연습 원문 v1 공개. v2는 아직 등록하지 않음 |
| 7회차 최종 반영 | 채택한 메모 안정화 변경 | 이번 실습 DB의 준비 기록·할 일·최종 메모·공개 운영 연습 v2·문의 안내를 유지. 빈 DB로 바꾸지 않음 |

자료가 빠졌다면 소유자가 분명한 교육용 사례만 해당 앱에서 준비합니다. 기존 자료를 중복 등록하거나 개인 DB 전체를 섞지 않습니다. 상태가 앞서 진행된 환경은 되돌리려고 삭제하지 말고 강사가 별도의 시작 환경을 준비합니다. 이 표 자체는 DB 생성·복원 명령이 아닙니다.

## 첫 통합의 추가 변경은 어디에서 오는가

5회차의 **질문 고정하기**는 교육생의 앞 실습에 포함되지 않은 통합 연습용 변경입니다. 강사가 대표 구현에 맞춰 고정·해제·상단 정렬과 DB 변경을 준비하고 실제로 시험해 제공합니다. 개인별 질문 모음 구현이 다른 상태에서 임의의 고정 기능 커밋을 합치게 하지 않습니다.

대표 구현은 그날 교육생의 결과에서 채택하거나 미리 검증한 기준 구현을 사용합니다. 당일 채택할 때도 통합 시작 전에는 필요한 기능과 자료를 실제로 열어 확인합니다. 구현이 준비되지 않았다면 통합 수업 준비는 미완료이며, 커밋 번호를 임의로 채우거나 새 기능 작성 시간을 통합 시간으로 바꿔 계산하지 않습니다.

6회차도 같은 방식으로 RFP·관리 변경을 준비합니다. 7회차에는 그 기준에 맞는 메모 안정화 변경을 제공합니다. 기준 자료는 학생이 `upstream`에서 읽을 수 있어야 하며 실제 fetch로 접근을 확인합니다. 학생의 `origin`은 본인 fork로 유지합니다.

## 교육생에게 전달할 실제 값

| 항목 | 실제 값·확인 결과 |
| --- | --- |
| 교재 기준·전달 위치 | [교재 커밋 / 슬라이드 주소 또는 파일 / 확인자] |
| upstream·origin | [기준 저장소 / 학생 fork / 접근 확인] |
| 시작 기준 | [브랜치 / 커밋 / 포함 기능] |
| 추가 변경 | [변경별 커밋 또는 범위 / 선행 변경 / DB 적용 순서] |
| 최종 비교 기준 | [기준 커밋 / 확인할 동작 / 확정자] |
| 개인·통합 사본 | [각 경로 / 브랜치 / 실제 커밋] |
| 실행 주소·포트 | [개인 / 통합 / 필요한 인증 주소 설정] |
| 전용 DB | [비밀값 없는 식별 정보 / 현재 구조 / 적용할 변경] |
| 웹·추출 작업자·AI | [해당 사본·DB 연결 / 실행 상태 / 실제 연결 확인 결과] |
| 교육 자료·계정 | [위 표의 자료 주소·버전·소유자 / 역할별 계정] |
| 미준비 | [빠진 항목 / 담당 / 준비 방법 / 확인 결과] |

환경 파일·비밀번호·API 키·개인 업로드는 기준표나 Git에 넣지 않습니다. 다른 포트의 앱을 동시에 띄울 경우 로그인 후 돌아오는 주소와 추출 작업자의 DB 연결도 확인합니다. 수업 중 환경 설치 대기를 실습 분량으로 세지 않습니다.

## 기존 기능이 유지되는지 볼 지점

- 자료실 검색 → 원문 → 같은 검색 조건과 펼친 자료로 복귀
- 실무 기록의 근거 → 원문 → 같은 기록·작성 상태로 복귀
- 그래프 비교 → 원문 → 같은 비교 대상·필터로 복귀
- RFP 항목 → 원문 → 같은 보고서 버전·항목·검색으로 복귀
- 동의어 표시를 추가한 뒤에도 자료별 묶음·즐겨찾기·저장 검색 조건 유지
- 도메인 용어·메뉴 안내 저장 뒤에도 실무 기록의 유형·작성 안내와 홈 입문 안내 유지
- 계정을 바꾼 뒤에도 작성자의 개인 질문·메모·할 일이 다른 계정에 노출되지 않음

모든 경로가 같은 원문 화면을 사용할 수 있습니다. 마지막으로 만든 복귀 버튼 하나가 이전 복귀 기능을 대체하지 않는지 각각 시작 메뉴에서 확인합니다.

## 시간과 회사 도입은 별도로 확인

4시간은 운영 설계이며 실측 완료가 아닙니다. 특히 4회차의 버전별 검토, 5·6회차 통합, 7회차 운영 점검은 준비 상태에 따라 편차가 큽니다. 6회차의 여섯 항목 초안은 사전에 준비해 입력 반복 대신 분석·개발·판단에 시간을 씁니다.

| 대표 실습 | 계획 판단 | 개발·보완 | 직접 확인 | AI 대기·코칭 | 실제 합계·조정 |
| --- | --- | --- | --- | --- | --- |
| 4회차 위치별 의견·반려·새 버전 게시 | 미측정 | 미측정 | 미측정 | 미측정 | 미검증 |
| 5회차 질문·비교와 첫 통합 | 미측정 | 미측정 | 미측정 | 미측정 | 미검증 |
| 6회차 항목·회신과 추가 통합 | 미측정 | 미측정 | 미측정 | 미측정 | 미검증 |
| 7회차 업무 연결·안정화·운영 인계 | 미측정 | 미측정 | 미측정 | 미측정 | 미검증 |

모든 공통 단계는 함께 수행합니다. 이미 공통 과제인 질문 목록 검색·비교 목록 저장 등을 빠른 교육생만 하는 선택 과제로 바꾸지 않습니다. 추가 도전은 다음 회차의 필수 조건으로 쓰지 않습니다.

회사 공용 환경·실제 인수 담당·보관 및 복구 확인 기록은 7회차 전에 준비 상태를 확인합니다. 없으면 해당 범위를 미완료로 남기고 담당·다음 행동·완료 기준을 정합니다. 교육용 통합 성공을 실제 회사 운영 인수로 기록하지 않습니다.
