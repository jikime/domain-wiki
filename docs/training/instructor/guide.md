# 강사용 지도서와 실습 해설

이 문서는 [7주 상세 교육안](../README.md)의 강사용 자료입니다. 시간표와 교육생 조작 절차는 각 주차 교재를 사용하고, 여기서는 설명의 중심, 예상 답, 오류 대응, 진행 조정을 확인합니다. 실제 수업 전에는 환경과 자료 상태를 확인합니다.

## 1. 공통 진행 원칙

설명은 ‘어떤 문제인가 → 화면에서 무엇을 보나 → 어떤 개념과 연결되나 → 어떻게 확인하나’ 순서로 진행합니다. 기술 이름을 한꺼번에 소개하지 않습니다. 교육생이 용어를 몰라도 먼저 입력과 실제 결과를 설명하게 합니다.

강사가 시연할 때는 마우스 조작만 보여 주지 말고 판단을 말로 설명합니다. 예를 들어 ‘처리가 끝났지만 아직 공개 전이므로 검색 코드를 먼저 바꾸지 않겠습니다’라고 이유를 짚습니다. 교육생에게 같은 판단을 다른 사례로 해 보게 합니다.

힌트는 세 단계로 제공합니다. 첫째, 확인할 질문을 던집니다. 둘째, 화면·파일 위치를 알려 줍니다. 셋째, 해결 예를 보여 준 뒤 다른 입력으로 직접 해 보게 합니다. 강사가 직접 수정한 경우 도움 수준을 남깁니다.

각 회차 마지막 40분은 검증과 기록을 위한 시간입니다. 구현이 늦어져도 이 시간을 전부 개발로 바꾸지 않습니다. 늦어진 팀은 선택 과제를 줄이고 최소 기능의 결과를 확인합니다.

9월 13일 모델 연결 개정은 기존 시간 안에서 설명·진단·기록에 반영합니다. 현재는 환경 변수로 API·Claude Code CLI·Codex CLI를 선택하고 관리자 화면에서 조회·연결 확인을 합니다. 연결 등록·선택·저장 화면과 재시작 없는 적용은 후속 설계안입니다. 이 차이를 먼저 설명하고 수업에서 존재하지 않는 조작을 지시하지 않습니다. 전체 PDF는 9월 11일 작성본이므로 최신 수업 준비에는 Markdown을 사용합니다.

## 2. 1주차 지도

교재: [1주차](../weeks/01-experience.md). 시연 자료는 03 검수 조건 v1, 직접 등록 자료는 01 사업 개요입니다.

### 설명할 내용

‘자료를 저장하는 일, 읽어 내는 일, 동료에게 공개하는 일은 서로 다른 단계입니다. 지금 보이는 상태가 어느 단계인지 확인하면 어디에서 막혔는지 찾을 수 있습니다.’라고 시작합니다. AI 답변을 보여 줄 때는 출처를 먼저 열고 수치와 적용 범위를 대조합니다.

기존 AI 시도가 잘 안 된 이유를 프롬프트 문제로 단정하지 않습니다. 요구가 너무 컸는지, 실행 환경이 준비되지 않았는지, 코드가 바뀌었지만 확인이 없었는지 교육생의 실제 경험에서 나눕니다.

### 기대 답과 질문

| 질문 | 기대하는 설명 |
| --- | --- |
| 처리 완료인데 왜 이용자에게 안 보이나요? | 공개 검토 대기일 수 있으며 범위·권한도 확인 |
| A 사업에 장비 교체가 포함되나요? | 01 원문에서 제외했다고 확인 |
| 갱신 60초는 장애 복구 시간인가요? | 03 원문에서 화면 갱신이며 복구 시간은 미정 |
| 인용이 있으면 모두 맞나요? | 인용 문단의 실제 의미·조건을 읽어야 함 |

위키 참고 구성은 ‘포함: 상태 화면·이력·검토 기록 / 제외: 장비 교체·제어 자동 전송 / 미정: 종료일’입니다. 원문 문단을 실제 선택해야 하며 교재의 자료 번호를 근거 ID로 입력하지 않습니다.

### 막힐 때와 종료 확인

검토 권한·작성자가 같아 승인에 막히면 별도 검토 계정을 사용합니다. 모델 실패 시 수동으로 원문 답안을 만들고 모델 미확인을 기록합니다. 모든 교육생에게 자료 상태 하나와 답이 없는 질문 하나를 설명하게 합니다.

## 3. 2주차 지도

교재: [2주차](../weeks/02-architecture.md). 코드 흐름의 시작은 `record-editor.tsx`, 핵심 서버 함수는 `saveRecord`, 검증은 `recordInput`입니다.

### 시연할 연결

입력값을 보여 주고 같은 이름이 `JSON.stringify`에 있는지 찾습니다. API 라우트가 실제 저장을 모두 수행하는 것이 아니라 서비스로 전달한다는 점을 짚습니다. 서비스는 작성 권한과 근거를 확인한 뒤 실무 기록을 Markdown 원문으로 만들어 기존 자료 등록 흐름을 재사용합니다.

전체 DB 구조를 설명하기보다 ‘기록이 어디에 어떻게 남는가’, ‘왜 입력 검증이 필요한가’에 집중합니다. `use client`가 있는 파일과 서버 서비스의 역할을 구분하되 컴포넌트 렌더링 이론 전체를 다루지는 않습니다.

14:20–15:00의 구조 설명 중 8분은 `streamModel`의 API·CLI 분기를 보여 줍니다. ‘브라우저→위키 서버 API’와 ‘위키 서버→외부 모델 API 또는 CLI’를 따로 그립니다. 모델에 CLI를 사용해도 위키 서버의 권한·근거 검사는 거친다는 점을 짚습니다. 회사 공용 환경의 연결 설정은 시연 중 변경하지 않습니다.

| 확인 질문 | 기대하는 설명 |
| --- | --- |
| CLI를 쓰면 브라우저가 서버를 거치지 않나요? | 기존 위키 서버 API를 거치고 서버에서 CLI 프로세스를 실행 |
| CLI는 항상 구독 안에서 무료인가요? | 인증·과금 방식과 이용 한도에 따라 다르며 CLI 이름만으로 판단 불가 |
| 지금 관리 화면에서 연결을 바꾸고 저장할 수 있나요? | 현재는 조회·응답 점검, 선택은 환경 변수로 하고 웹 서버·작업자 재시작 필요 |
| 채팅을 CLI로 바꾸면 임베딩과 웹 검색도 CLI인가요? | 임베딩과 Tavily 등 검색은 별도 API 연결 유지 |

개인 구독을 공용 서버에 연결해 비용을 없앨 수 있다고 안내하지 않습니다. [공식 조건을 포함한 프로젝트 안내](../project-guide.md#8-모델-연결의-현재-기능과-설정-화면-권장안)를 읽고 회사 공용 API를 기본으로 준비합니다. CLI 실제 실습은 이용 조건·설치·인증을 확인한 환경에서만 선택합니다.

### 도움말 참고 답안

원래 뜻: ‘메모가 없어도 아래 항목을 직접 작성할 수 있습니다. AI 정리는 메모를 바꾸지 않습니다.’

변경 예: ‘프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요. 메모가 없어도 아래 항목을 직접 작성할 수 있습니다. AI 정리는 메모를 바꾸지 않습니다.’

기존 `FieldDescription` 안의 텍스트만 바꾸면 됩니다. 입력 필드·상태·API·DB 변경은 필요하지 않습니다. 자동 테스트를 새로 쓰게 하기보다 diff와 실제 화면을 확인하게 합니다.

### 자주 생기는 오해

- 파일을 저장한 사본과 접속한 서버가 다르면 화면에 반영되지 않습니다.
- 새 파일의 내용은 기본 diff에 나타나지 않을 수 있어 Git 상태도 봐야 합니다.
- 커밋은 파일 이력이며 사용자의 DB 자료를 저장하는 기능이 아닙니다.

완료 확인은 ‘수정한 문장’, ‘화면 파일’, ‘서버 검증 파일’, ‘확인한 입력’ 네 가지로 합니다. 3주차로 넘길 때 불필요한 코드 수정은 정리하고 기준을 기록합니다.

## 4. 3주차 지도

교재: [3주차](../weeks/03-domain.md). [설정 예시](../samples/domain-settings.md)를 사용합니다.

### 설명과 관찰

관리 화면의 실무 기록 기본 양식은 안내문입니다. 교육생이 ‘검수자’ 한 줄을 추가하고 입력 필드가 안 생겼다고 하면, 설정 문서와 DB·폼 구조가 다르다는 점을 실제 코드로 확인합니다. 새로운 필드 개발로 확대하지 않고 기존 항목 안에서 검수자를 기록할 작성 기준을 정합니다.

용어는 `도로전광표지 | 설명 | VMS, 전광표지`를 사용합니다. 동의어가 검색에 적용되는 경로는 관리 폼 → 도메인 저장 → `workspaceSearchGroups` → `searchGroups`입니다. 의미 검색만으로 이미 결과가 나오는 경우에는 검색 개선을 억지로 주장하지 말고 저장 배열과 검색어 확장 동작을 구분하게 합니다.

### 실무 경험 해설

06 메모에서 확인한 사실은 표본 3대, 잘못된 날짜 조건, 날짜 변경 후 표시, 코드·자료 복구를 하지 않았다는 점입니다. ‘DB가 손상됐다’, ‘모든 장비 정상’, ‘항상 날짜 문제’는 메모에서 확인하지 않았습니다. AI가 이를 덧붙이면 제안에서 제거하고 이유를 설명하게 합니다.

검수 위키에는 A·v1·화면 60초·이력 90일·표본 3대와 미정인 장애 복구 시간을 구분합니다. 이 위키가 6주차 개정 영향의 대상이 되므로 실제 v1 문단과 게시 상태를 확인합니다.

### 시간 조정

자료 공개와 용어 설정에 시간이 걸리면 위키 구조를 새로 설계하는 선택 과제를 줄입니다. 준비된 구조를 사용해 근거 연결과 검토를 완료합니다. A·B 자료와 현재 v1 상태를 다음 회차 시작 조건으로 남깁니다.

### 평가 운영

팀별로 질문을 나누되 모든 질문의 결과가 남도록 담당을 배정합니다. 모델 호출을 동시에 몰아서 보내지 않습니다. 근거가 검색되지 않으면 생성 점수와 별도로 원인을 기록합니다. 실제 결과가 모두 좋으면 없는 실패를 만들지 않고 공통 입력 계약의 문제를 사용합니다.

T5에서 연결 방식·용도별 모델·임베딩 설정을 확인합니다. API와 CLI는 같은 모델 이름이어도 입력 구조가 다르므로 평가 중 바꾸지 않습니다. 연결 실패는 답변의 사실 오류와 분리하고, 5주차 코드 비교에도 같은 연결 조건을 유지합니다.

공통 코드 과제의 변경 전 입력은 `VMS; 전광표지， VMS`입니다. 현재 코드에서는 쉼표만 분리하므로 다른 구분자가 남을 수 있습니다. 저장 화면에 다시 표시된 값을 보게 합니다. 일반 검색이 우연히 성공해도 입력 분리가 올바르다는 증거는 아닙니다.

### 확정할 과제

공통 개발은 5주차의 동의어 입력 개선, 팀 응용은 기존 실무 기록 안내 또는 위키 구조 개선 한 개입니다. 더 큰 요구는 T8에 보관합니다. 과제마다 정상 입력, 실패 입력, 변경 파일 후보, 완료 기준을 정합니다.

## 6. 5주차 지도와 코드 답안

교재: [5주차](../weeks/05-development.md). 참고 구현은 [term-aliases.ts.txt](reference/term-aliases.ts.txt)입니다. 이 파일은 교육용 참고 답안이며 제품 코드에 적용된 상태가 아닙니다.

### 참고 구현의 설명

함수는 허용 구분자로 문자열을 나누고, 각 항목의 앞뒤 공백을 없앤 뒤 빈 값을 제거합니다. Set으로 완전히 같은 중복을 정리하고 배열로 반환합니다. 순서와 대소문자, 내부 공백은 유지합니다.

중복 제거가 ‘같은 뜻’을 판단하는 것은 아닙니다. `VMS`와 `vms`는 입력 계약상 서로 다른 문자열로 유지합니다. 검색 단계의 정규화와 입력 단계의 보존 규칙을 섞지 않습니다.

### 폼 연결 참고

`src/components/settings-form.tsx`에 다음 import를 추가합니다.

```typescript
import { splitAliases } from "@/lib/term-aliases";
```

기존 `aliases.split(",").map(...).filter(...)` 부분은 다음처럼 바꿉니다. 용어·설명은 기존 처리를 유지합니다.

```typescript
return {
  term: term.trim(),
  definition: definition.trim(),
  aliases: splitAliases(aliases),
};
```

관리 페이지 도움말 예: ‘한 줄에 용어, 설명, 동의어를 세로 구분선으로 나누어 입력하세요. 동의어는 쉼표·전각 쉼표·세미콜론으로 구분합니다. 동의어는 생략할 수 있으며 검색할 때 같은 뜻으로 사용합니다. 최대 100개 용어를 저장합니다.’

### 검증과 판정

[입력 검사기](../exercises/check-aliases.mjs)는 지정한 함수 파일을 검사합니다. 교육생 코드와 강사 참고 코드를 혼동하지 않도록 실행 명령의 마지막 인수를 확인합니다.

```bash
node docs/training/exercises/check-aliases.mjs docs/training/instructor/reference/term-aliases.ts.txt
```

위 명령은 **강사 참고 답안만** 검사합니다. 실제 교육생은 `src/lib/term-aliases.ts`를 대상으로 실행해야 합니다. 검사기는 빈 값·구분자·중복·순서·내부 공백·대소문자와 기존 제한을 위해 남겨야 할 값을 확인합니다. 서버 저장·권한·검색·화면은 별도 시나리오로 확인합니다.

완료 판단: 함수 검사 성공 + 폼 연결 + 저장 후 재조회 + 기존 쉼표 입력 + 잘못된 입력의 서버 거부 + 검토한 diff입니다. 함수만 복사했거나 도움말만 바꾼 경우에는 완료로 표시하지 않습니다.

### 늦어진 팀

함수의 일부를 제공하고 폼 연결과 정상·실패 입력 확인을 직접 하게 합니다. 받은 도움을 기록한 뒤 다른 구분자 조합으로 다시 설명하게 합니다. 전체 검색 로직 재설계로 과제를 확대하지 않습니다.

## 7. 6주차 지도

교재: [6주차](../weeks/06-debugging.md). 개정본은 [검수 조건 v2](materials/acceptance-v2.md)입니다.

### 진단 해설

미공개 자료 실습의 원인은 공개 검토 대기입니다. 이 경우 일반 이용자 검색에서 안 보이는 것은 의도된 상태입니다. 교육생이 ‘인덱스를 다시 만든다’고 하면 그 전에 공개 상태를 확인했는지 질문합니다.

잘못된 동의어 길이·개수 입력이 거부되는 것은 회귀가 아니라 유지해야 할 검증입니다. 프런트엔드에서 임의로 자르거나 서버 제한을 삭제하지 않고 입력을 수정해야 합니다.

### 개정 해설

1. v1의 값은 60초, v2는 30초입니다.
2. 두 버전 모두 이력 90일·표본 3대입니다.
3. v2 등록 전후가 아니라 **공개 승인 전후**를 나누어 봅니다.
4. 위키 본문 숫자와 실제 근거 문단을 함께 갱신해야 합니다.
5. 과거 답변의 근거 상태도 영향을 받을 수 있지만 모든 화면의 정확한 안내 문구를 정답으로 고정하지 않습니다. 현재 유효한 원문·근거를 확인하는 행동을 봅니다.

실습 후 v1·v2가 다른 독립 자료로 동시에 공개되어 있다면 등록 방식을 바로잡아야 합니다. 기존 원문의 ‘새 원본 버전 등록’을 사용했는지 확인합니다.

### 선택 시연

작업자는 개인 환경의 해당 프로세스만 조작합니다. Tavily는 [설정 예](../troubleshooting.md)로 키·제공자·작업공간·프로세스 적용을 설명합니다. 실제 키·회사 자료를 노출하거나 전송하는 시연은 하지 않습니다.

API·CLI 연결 진단을 선택하면 다른 선택 사례를 줄여 시간표를 유지합니다. ‘실행 파일 없음→설치 경로’, ‘인증 확인 필요→서버 운영 계정’, ‘한도 초과→제공자 한도’, ‘시간 초과→대기와 실행 시간’으로 가설을 연결하게 합니다. 실제 장애를 일부러 만들거나 공용 로그인을 바꾸지 않고 준비한 오류 문구로 설명할 수 있습니다. CLI 실패 뒤 API가 호출되지 않는 것은 현재 의도한 동작임을 확인합니다. 실제 호출 없이 진단한 경우에는 연결 성공으로 기록하지 않습니다.

## 8. 7주차 지도와 업무 답안

교재: [7주차](../weeks/07-application.md). 신규 자료는 [요청 문서](materials/new-rfp.md), 상세 해설은 [RFP 참고 답안](materials/rfp-answer.md)입니다.

### 설명의 중심

기존 A의 30초와 신규 R1의 45초는 문서 기준이 다릅니다. 숫자만 비교하면 기존 값이 더 작지만, 실제 후속 환경과 측정 조건의 충족까지 확인한 것은 아닙니다. 기존 보관 90일과 신규 180일은 차이가 있어 추가 검토가 필요합니다.

R4는 제외가 명시되어 있습니다. R5는 자료 연계를 요구하지만 대상·항목·주기·책임이 정해지지 않았고, R6도 허용 중단 시간과 확인 방법이 미정입니다. 교육생이 이를 임의로 채우는지 봅니다.

### 팀 보고서와 개인 확인

팀 보고서는 명시 요구 2개, 기준 또는 사례 1개, 추론 또는 불명확 1개 이상을 앱에 작성하고 전체 6개 요구의 검토 상태를 표에 남깁니다. 모든 항목의 앱 게시를 시간 안에 강제하지 않습니다. 핵심은 근거·해석·질문·미완료 구분입니다.

개인 10분은 수행 요약 2분, 근거·파일 확인 3분, 다른 입력이나 질문 3분, 인계 설명 2분으로 운영합니다. ‘AI가 해 줬다’에서 끝나면 변경 이유와 확인 결과를 다시 설명하게 합니다.

### 종료 점검

다른 팀이 인계 문서에서 접속 방법, 코드 기준, 대표 질문, 원본·DB 담당을 찾게 합니다. 찾지 못한 내용은 마지막 시간에 보완합니다. 다음 과제 3개는 구체적인 사용자 문제와 완료 기준으로 작성하고 추가 지원을 약속하는 문장으로 만들지 않습니다.

AI 연결의 인계에는 선택 방식·모델·사용 조건 확인 결과·한도·관리 담당과 재시작 절차를 포함합니다. 인증·과금 정보를 확인하지 못했다면 미확인으로 남깁니다. 연결 선택 화면을 후속 과제로 기록한 팀은 현재 조회 기능과 필요한 저장·권한·적용 기능을 구분해 설명하게 합니다. API 키·로그인 토큰을 인계 문서에 넣지 않습니다.
