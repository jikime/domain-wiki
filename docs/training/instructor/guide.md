# 강사용 지도서와 실습 해설

이 문서는 [7주 상세 교육안](../README.md)의 강사용 자료입니다. 시간표와 교육생 조작 절차는 각 주차 교재를 사용하고, 여기서는 설명의 중심, 예상 답, 오류 대응, 진행 조정을 확인합니다. 실제 수업 전에는 환경과 자료 상태를 확인합니다.

## 1. 공통 진행 원칙

설명은 ‘업무 문제 → 이 프로젝트에서 기술이 맡은 역할 → AI에게 요청할 조건 → 결과 확인’ 순서로 진행합니다. **기술은 목적·용도만 설명하고, 코드 조사·구현·기술 검사는 AI가 수행합니다.** 문법 연습·함수/Zod/API/DB/테스트 코드 직접 작성·코드 줄별 해설을 교육생에게 요구하지 않습니다. 이 지도서의 코드·명령은 강사·AI의 준비와 검사용 참고이며 따라 치기나 시험 범위가 아닙니다.

강사가 시연할 때는 마우스 조작만 보여 주지 말고 판단을 말로 설명합니다. 예를 들어 ‘처리가 끝났지만 아직 공개 전이므로 검색 코드를 먼저 바꾸지 않겠습니다’라고 이유를 짚습니다. 교육생에게 같은 판단을 다른 사례로 해 보게 합니다.

힌트는 세 단계로 제공합니다. 첫째, 확인할 질문을 던집니다. 둘째, 화면·파일 위치를 알려 줍니다. 셋째, 해결 예를 보여 준 뒤 다른 입력으로 직접 해 보게 합니다. 강사가 핵심 요청·판단·확인을 대신한 경우 도움 수준을 남깁니다. AI가 코드를 작성하는 것은 기본 수행 방식으로 별도 도움이나 감점으로 취급하지 않습니다.

1–6주차의 마지막 40분은 검증과 기록, 다음 과제 확인에 사용합니다. 7주차에는 시간표의 검증 30분과 인계 60분을 확보합니다. 구현이 늦어져도 확인 시간을 전부 개발로 바꾸지 않고 선택 과제를 줄여 최소 기능의 결과를 확인합니다.

9월 13일 모델 연결 개정은 기존 시간 안에서 설명·진단·기록에 반영합니다. 기본은 Claude Code CLI·sonnet이며, 환경 변수로 API·Claude Code CLI·Codex CLI를 선택하고 관리자 화면에서 조회·연결 확인을 합니다. 연결 등록·선택·저장 화면과 재시작 없는 적용은 후속 설계안입니다. 이 차이를 먼저 설명하고 수업에서 존재하지 않는 조작을 지시하지 않습니다. 전체 PDF는 9월 11일 작성본이므로 최신 수업 준비에는 Markdown을 사용합니다.

### 초보자에게 안내하는 방법

실습 시작 때 [입력 위치 안내](../start-here.md#어디에-입력하나요)를 함께 보고 ‘지금은 어느 창에 입력하는지’를 짚습니다. 각 실습의 ‘정상 결과 예시’를 시연한 뒤 교육생이 자기 화면과 비교하게 합니다. AI 응답의 문구를 그대로 맞추기보다 업무 사실과 실제 동작을 확인합니다.

‘오늘 필요한 말’만 먼저 풀어 설명하고 기술 표·코드 링크는 질문이 있을 때 참고합니다. 막힌 교육생에게는 [도움 요청 틀](../start-here.md#결과가-다르면-이렇게-도움을-요청하세요)로 증상을 보여 달라고 안내합니다. 다음 수업을 시작할 때 [다시 사용하는 방법](../daily-use.md)을 사용합니다. 이 안내는 기존 시연·실습 안에 포함하며 별도 과제나 시간을 추가하지 않습니다.

### 실습 환경 준비

[실제 사용 따라 하기](../wiki-chat-guide.md)는 1주차 선택 활동과 3주차 기존 위키 실습의 조작 안내로 사용합니다. ‘초안 저장’과 ‘게시’를 구분하고, 게시 후 ‘이 위키에 질문하기’로 연결되는 장면을 보여 주세요. 답변의 인용이 위키인지 원문인지 함께 확인하며, 답변이 나왔다는 이유만으로 위키를 인용했다고 설명하지 않습니다. 답변의 위키 초안 저장은 선택 활동으로 두고, 4주차 기준 평가 중에는 이 안내를 따라 새 위키를 게시하거나 질문 범위를 바꾸지 않습니다.

강사는 [00. 기본 개발 환경 준비](../environment-setup.md)와 [소스 다운로드·실행 안내](../getting-started.md)에 따라 시연·대체 환경을 사전에 준비합니다. **교육생은 기본 도구 설치부터 개인 위키 실행까지 1주차 수업 안에서 진행합니다.** 사전에 요청할 것은 PC·계정·설치 권한·네트워크 확인입니다. Windows는 Git for Windows·Git Bash를 설치하고 VS Code의 기본 터미널로 선택합니다. Node.js는 Windows 설치 파일로, Claude Code는 Git Bash의 WinGet 명령으로 설치합니다. Ubuntu는 설치하지 않으며 WSL2는 Docker Desktop용으로 준비합니다.

Claude Code는 개인 개발용 인증·실제 응답을 확인하고 위키의 서비스 AI 설정과 구분합니다. 디자인 하네스는 교재에 고정한 버전의 에이전트 5개·스킬 6개를 프로젝트에 설치하고, CLAUDE.md에서 저장소의 AGENTS.md·hince 문서를 참조하는지 확인합니다. 1주차에는 설치와 기존 디자인 기준 설명을 확인하며 실제 UI 변경은 2주차 이후로 연결합니다.

1주차는 기본 도구 설치 100분과 내 PC 위키 실행 50분을 배정합니다. 설치·인증·실제 실행 결과를 [T0 환경 기록표](../templates.md#t0-내-pc-업무환경-기록표)에 기록하고, 장비 제약으로 원격 환경을 사용하면 로컬 설치 완료와 구분합니다. 설치를 미리 끝내지 않았다는 이유로 개인 실습을 생략하지 않습니다.

저장소에는 강사용 해설과 참고 답안도 포함됩니다. 주차별로 읽을 범위를 안내하고, 독립 평가에서 사전 열람을 배제해야 한다면 저장소에 없는 새 입력·질문을 수업 때 제공합니다.

### 프롬프트 작성·실행 지도

[프롬프트 실습 안내](../prompt-practice.md)를 함께 사용합니다. 완성 요청문을 먼저 받아쓰게 하지 말고, 1주차는 세 줄 틀의 대상을 고르게 합니다. 2주차부터는 초안 작성 뒤 예시와 비교하고, 7주차는 예시를 가린 채 팀 초안을 씁니다.

대표 실습에서 ‘작성 → 전송 → 응답·결과 확인 → 후속 요청 전송 → 비교 기록’을 한 번씩 확인합니다. 1주차 약 8분, 2·3·5·6·7주차 약 10분을 기존 요청 활동 안에서 사용합니다. 4주차는 기존 위키 비교 20분에 포함합니다. 시간표를 늘리거나 설치·코드 구현·마지막 확인 시간을 별도 과제로 대체하지 않습니다.

| 교육생이 막힌 지점 | 강사가 줄 힌트 | 교육생이 직접 할 일 |
| --- | --- | --- |
| 무엇을 써야 할지 모름 | ‘어느 화면에서 무엇이 달라지면 좋을까요?’ | 목표와 기대 결과 한 문장 작성 |
| 자료를 전달하지 않음 | ‘AI가 그 자료를 어디에서 볼 수 있나요?’ | 파일·자료 범위·현재 위치 확인 |
| 결과가 마음에 안 듦 | ‘기대한 것과 실제 결과 중 한 가지 차이는 무엇인가요?’ | 차이를 넣어 후속 요청 전송 |
| 첫 결과가 이미 맞음 | ‘다른 입력이나 더 필요한 설명은 무엇인가요?’ | 확인 입력·예시를 추가해 재실행 |
| 로그인·연결 오류 | 환경 준비·문제 해결 안내로 확인 | 작성·전송·응답 여부를 구분해 기록 |

강사는 답을 통째로 대신 작성하기 전에 위 질문을 사용합니다. T3에 본인이 쓴 문장과 실제 응답을 남기게 하고, 문장 길이·전문 용어보다 목표·조건·결과 확인을 봅니다. 팀에서는 첫 요청의 본인 작성 부분과 개인 후속 요청을 확인합니다. 한 사본의 코드 변경은 순서를 정해 실행합니다.

4주차 평가 질문 12개는 그대로 사용하고, 작성 규칙 수정 연습은 기준 평가 후의 별도 비교로 기록합니다. 응답을 기다릴 수 없어 준비된 예시를 사용하는 경우에는 교육생의 실제 실행 성공으로 기록하지 않습니다.

## 2. 1주차 지도

교재: [1주차](../weeks/01-experience.md). 핵심 결과는 내 PC의 개발 도구·위키 업무환경, T0 기록표와 T1 업무 문제 카드, T3의 첫 프롬프트·후속 요청 기록입니다. 시연 자료는 03 검수 조건 v1, 교육생이 등록할 자료는 01 사업 개요입니다.

휴게는 15:00–15:10과 16:00–16:10입니다. 설치된 도구는 정상 확인 후 다음 단계로 진행하고, 미설치 도구는 수업에서 함께 설치합니다. 다운로드가 진행되는 동안 해당 도구의 역할을 설명하되, 휴게를 필수 조작 시간으로 사용하지 않습니다.

Windows 실습은 Git Bash와 Windows의 프로젝트 폴더로 통일합니다. Claude Code는 Git Bash에서 WinGet으로 설치한 뒤 같은 터미널에서 실행하고, 하네스도 같은 프로젝트에 복사합니다. PowerShell은 Docker용 WSL2 설치·업데이트가 필요한 단계에서만 사용합니다. Git Bash 설치·확인은 첫 50분, WSL2 준비·재부팅은 Docker 설치 시간에 포함합니다.

초기 DB 설정은 개발 작업공간·개발 예시 프로젝트를 만듭니다. 이것이 교재의 교육용 도메인·프로젝트 A/B까지 준비했다는 뜻은 아닙니다. 강사·AI는 개인 사본의 관리 화면에서 공통 교육용 도메인·프로젝트를 준비하고, 실제 작업공간 이름과 계정 역할을 T0에 남기도록 안내합니다. 설치 명령을 반복해 기존 데이터를 초기화하지 않습니다.

### 설명할 내용

설치 중에는 각 도구의 목적과 어디서 실행되는지 설명합니다. 업무 흐름 시연에서는 ‘자료를 저장하는 일, 읽어 내는 일, 동료에게 공개하는 일은 서로 다른 단계입니다’라고 짚습니다. AI 답변의 출처를 열고 실제 수치·범위를 대조합니다. 설치와 실행을 설명만 듣고 넘긴 상태를 개인 실습 완료로 처리하지 않습니다.

기존 AI 시도가 잘 안 된 이유를 프롬프트 문제로 단정하지 않습니다. 요구가 너무 컸는지, 실행 환경이 준비되지 않았는지, 코드가 바뀌었지만 확인이 없었는지 교육생의 실제 경험에서 나눕니다.

### 기대 답과 질문

| 질문 | 기대하는 설명 |
| --- | --- |
| 내 PC에서 다시 사용하려면 무엇을 확인하나요? | 같은 프로젝트·DB·웹 서버·작업자·접속 주소, T0에 기록한 순서 |
| Claude Code가 응답하면 위키 AI도 준비됐나요? | 개발 인증과 서비스 AI 연결을 각각 확인해야 함 |
| 처리 완료인데 왜 이용자에게 안 보이나요? | 공개 검토 대기일 수 있으며 범위·권한도 확인 |

| 갱신 60초는 장애 복구 시간인가요? | 03 원문에서 화면 갱신이며 복구 시간은 미정 |
| 인용이 있으면 모두 맞나요? | 인용 문단의 실제 의미·조건을 읽어야 함 |

위키는 근거가 연결된 게시본을 시연합니다. 개인 초안 작성은 환경 준비를 마친 교육생의 선택 활동이며, 참고 구성은 ‘포함: 상태 화면·이력·검토 기록 / 제외: 장비 교체·제어 자동 전송 / 미정: 종료일’입니다. 교재의 자료 번호를 근거 ID로 입력하지 않습니다.

### 막힐 때와 종료 확인

설치가 지연되면 선택 위키 작성과 추가 질문 비교를 먼저 생략합니다. 마지막 40분도 실제 실행·확인과 T0 기록에 사용합니다. 장비 제약이 있으면 원격 환경에서 업무 흐름을 이어가되 내 PC의 미완료 단계·지원 담당·다음 확인 방법을 별도로 남깁니다. 확인하지 않은 설치·AI 응답은 완료로 표시하지 않습니다.

자료 등록·공개 뒤 답이 있는 질문 한 개와 없는 질문 한 개를 확인합니다. 검토 권한·작성자가 같아 승인에 막히면 별도 검토 계정을 사용합니다. 모든 교육생은 자기 환경 위치와 다시 사용할 순서, 원문·위키·답변의 차이와 근거 하나를 설명합니다. 명령을 암기해 직접 입력하는 능력은 평가하지 않습니다.

## 3. 2주차 지도

교재: [2주차](../weeks/02-architecture.md). [공통 안내](../project-guide.md)의 기술 표·업무 지도·구조 그림을 사용합니다. 교육생은 기술의 역할을 이해하고 AI의 변경 범위를 판단합니다.

### 설명과 활동 배치

14:20–15:00의 40분은 기술 목적 12분, 실행·데이터 흐름 20분, 서비스 모델 연결 8분으로 나눕니다. Next.js·React는 화면·연결, Zod는 입력 조건, PostgreSQL·Drizzle은 저장, 큐·작업자는 오래 걸리는 처리에 사용한다고 설명합니다. 문법 예제를 만들지 않습니다.

실행·데이터 흐름 20분 중 약 4분은 [실행 명령과 세 가지 구성](../project-guide.md#실행-명령과-세-가지-구성)을 설명합니다. `dev`는 화면과 API 백엔드를 함께 담당하고, `worker`는 작업 큐의 문서·AI 작업을 처리하며, DB가 별도로 필요합니다. 두 명령을 프런트엔드·백엔드로 일대일 대응시키지 않습니다. pgvector·pg-boss는 DB 안의 기능, OpenAI는 현재 설정의 외부 API, MinerU는 선택적 추출 연결로 구분합니다. 기존 임베딩 설명 3분과 함께 배치하고 나머지 13분에 요청·데이터 흐름을 연결합니다.

실행·데이터 흐름 20분 중 약 3분은 [OpenAI 임베딩과 pgvector](../project-guide.md#현재-임베딩-모델과-pgvector)에 사용합니다. 현재 준비 환경의 `text-embedding-3-small`은 벡터를 만들고, pgvector는 DB에서 저장·비교하며, 작업자·서버가 모델 API와 DB를 연결한다고 설명합니다. 원문·위키와 질문에 같은 임베딩 모델을 사용한다는 점을 짚습니다. 모델 이름을 외우거나 API·SQL 코드를 작성하게 하지 않습니다.

이어지는 60분에는 교육생이 개발용 AI에게 실무 기록의 저장 흐름을 묻고 T2를 작성합니다. 파일·함수 위치는 AI가 찾아 안내하고, 교육생은 화면·검증·보관·처리·검토라는 역할로 설명하면 됩니다. 실무 기록은 작성 권한·근거를 확인한 뒤 Markdown 원문으로 만들어 기존 자료 등록을 재사용합니다. 강사 확인 위치는 `record-editor.tsx`, `saveRecord`, `recordInput`입니다.

다음 60분에는 교육생이 도움말 변경을 요청하고 AI가 구현합니다. 교육생은 계획의 범위를 판단한 뒤 화면에서 문구·입력 동작을 확인합니다. 직접 코드 입력·Git 명령 수행·변경 줄 해설은 요구하지 않습니다.

| 확인 질문 | 기대하는 설명 |
| --- | --- |
| 입력 조건을 바꾸려면 무엇을 알려 주나요? | 필수값·길이 등 업무 조건을 AI에 전달, 구현은 AI가 현재 검증 방식을 사용 |
| 서버는 왜 입력과 권한을 확인하나요? | 저장 가능한 정보와 역할을 확인하기 위해 |
| 저장 API는 dev와 worker 중 어디에 있나요? | dev로 실행한 Next.js 웹 서버, worker는 백그라운드 처리 |
| pgvector와 작업 큐 서버도 따로 실행하나요? | pgvector와 pg-boss는 같은 PostgreSQL을 사용, DB는 웹·작업자와 별도로 준비 |
| 문서가 대기하는데 화면은 열리나요? | 웹 서버와 문서 작업자의 역할·실행이 다름 |

| 지금 관리 화면에서 모델 연결을 선택·저장하나요? | 현재는 조회·응답 점검, 선택은 환경 변수·재시작으로 적용 |

인증·과금·연결 조건의 운영 준비는 [프로젝트 안내](../project-guide.md#8-모델-연결의-현재-기능과-설정-화면-권장안)를 따릅니다. 연결 방식을 기술별 구현 실습으로 확대하지 않습니다.

### 도움말 참고 답안과 확인

변경 예: ‘프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요. 메모가 없어도 아래 항목을 직접 작성할 수 있습니다. AI 정리는 메모를 바꾸지 않습니다.’

AI가 기존 `FieldDescription` 안의 텍스트만 수정하면 됩니다. 강사는 입력 필드·상태·API·DB가 불필요하게 바뀌지 않았는지 확인합니다. 교육생은 안내의 뜻·입력 동작·실행 사본을 확인하고 T3·T5에 요청과 결과를 남깁니다. 단순 문구 변경에 자동 테스트 작성 과제를 붙이지 않습니다.

완료 판단은 기술 이름 암기가 아니라 ‘왜 바꿨는가, AI 계획이 맞았는가, 실제로 무엇을 확인했는가’로 합니다. AI가 알려 준 변경 위치는 인계 자료에 남깁니다.

## 6. 5주차 지도와 코드 답안

교재: [5주차](../weeks/05-development.md). 참고 구현은 [term-aliases.ts.txt](reference/term-aliases.ts.txt)입니다. 이 파일은 강사·AI가 확인할 참고 답안이며 제품 코드에 적용된 상태가 아닙니다. 교육생은 요구·AI 요청·계획 판단·화면 확인을 수행합니다. 아래 문법·구현 설명을 교육생의 직접 코딩 실습으로 사용하지 않습니다.

### 참고 구현의 설명

함수는 허용 구분자로 문자열을 나누고, 각 항목의 앞뒤 공백을 없앤 뒤 빈 값을 제거합니다. Set으로 완전히 같은 중복을 정리하고 배열로 반환합니다. 순서와 대소문자, 내부 공백은 유지합니다.

중복 제거가 ‘같은 뜻’을 판단하는 것은 아닙니다. `VMS`와 `vms`는 입력 계약상 서로 다른 문자열로 유지합니다. 검색 단계의 정규화와 입력 단계의 보존 규칙을 섞지 않습니다.

### 폼 연결 참고

`src/components/settings-form.tsx`에 다음 import를 추가합니다.

```typescript
import { splitAliases } from "@/lib/term-aliases";
```

기존 `aliases.split(",").map(...).filter(...)` 부분은 다음처럼 바꿉니다. 용어·설명은 기존 처리를 유지합니다.

```typescript
return {
  term: term.trim(),
  definition: definition.trim(),
  aliases: splitAliases(aliases),
};
```

관리 페이지 도움말 예: ‘한 줄에 용어, 설명, 동의어를 세로 구분선으로 나누어 입력하세요. 동의어는 쉼표·전각 쉼표·세미콜론으로 구분합니다. 동의어는 생략할 수 있으며 검색할 때 같은 뜻으로 사용합니다. 최대 100개 용어를 저장합니다.’

### 검증과 판정

[입력 검사기](../exercises/check-aliases.mjs)는 지정한 함수 파일을 검사합니다. AI가 실제 실습 사본에 구현한 코드와 강사 참고 코드를 혼동하지 않도록 실행 대상을 확인합니다.

```bash
node docs/training/exercises/check-aliases.mjs docs/training/instructor/reference/term-aliases.ts.txt
```

위 명령은 **강사 참고 답안만** 검사합니다. 실습 사본에서는 AI가 `src/lib/term-aliases.ts`를 대상으로 실행해야 합니다. 교육생에게 명령 실행을 요구하지 않습니다. 검사기는 빈 값·구분자·중복·순서·내부 공백·대소문자와 기존 제한을 위해 남겨야 할 값을 확인합니다. 서버 저장·권한·검색·화면은 별도 시나리오로 확인합니다.

실습 사본의 기술 검사는 AI가 다음 범위로 실행하고 실패·미실행 항목을 보고합니다.

```bash
node docs/training/exercises/check-aliases.mjs src/lib/term-aliases.ts
git diff --check
npx biome check src/lib/term-aliases.ts src/components/settings-form.tsx "src/app/w/[workspaceId]/admin/page.tsx"
npm run typecheck
```

새 함수가 실제 폼에 연결되었는지와 관리 페이지 안내도 AI가 확인합니다. 전체 통합시험·반복 빌드는 기본 절차로 추가하지 않습니다.

완료 판단: 교육생의 요구·AI 요청 + AI의 입력 검사·변경 보고 + 교육생의 저장 후 재조회·기존 쉼표 입력·잘못된 입력 거부 확인입니다. 함수만 복사했거나 도움말만 바꾼 경우에는 완료로 표시하지 않습니다.

### 늦어진 팀

강사는 AI에 전달할 조건이나 정상 사본을 제공할 수 있습니다. 이후 교육생이 다른 입력으로 AI에 확인·보완 요청을 하고 실제 화면을 재확인하게 합니다. AI가 구현을 맡는 것을 강사 도움으로 기록하지 않습니다. 전체 검색 로직 재설계로 과제를 확대하지 않습니다.

## 7. 6주차 지도

교재: [6주차](../weeks/06-debugging.md). 5주차의 정상 함수·폼 연결과 검수 조건 v1을 준비하고, 개정 실습에는 [검수 조건 v2](materials/acceptance-v2.md)를 사용합니다.

### 코드 오류 사본 준비

1. 교육생의 5주차 정상 파일과 설정을 보관합니다. `src/lib/term-aliases.ts`는 검사 14개를 통과하고, 폼에서 혼합 구분자를 두 항목으로 저장하는 상태여야 합니다. 미완료 교육생에게는 정상 사본을 제공하고 지원 여부를 기록합니다.
2. 개인 실습 사본의 `src/components/settings-form.tsx`에서 **동의어 처리 부분만** 아래의 이전 방식으로 바꿉니다. 사용하지 않게 된 `splitAliases` import는 제거하되 함수 파일은 유지합니다.
3. 함수 검사 14개는 계속 통과하지만 `VMS; 전광표지， VMS`가 화면에서는 한 항목으로 저장되는지 확인합니다. 실제 수업에서 사용 중인 공용 서버나 제품 원본에 오류를 적용하지 않습니다.

```typescript
return {
  term: term.trim(),
  definition: definition.trim(),
  aliases: aliases
    .split(",")
    .map((item) => item.trim())
    .filter(Boolean),
};
```

위 코드는 **5주차 완료본에 준비할 교육용 오류**입니다. 현재 배포 소스의 기본 분리 방식과 같지만, 수업에서는 정상 함수가 별도로 존재하는데 폼이 이를 사용하지 않는 상황을 다룹니다. 오류를 포함한 전체 프로젝트나 별도 실행 체크포인트가 이미 제공된 것으로 안내하지 않습니다.

### 지도와 판정

교육생에게는 ‘어떤 입력인가? → AI의 검사 보고와 실제 결과가 어떻게 다른가? → AI에 어떤 조사를 요청할까?’ 순서로 묻습니다. AI·강사는 검사 대상과 실제 폼 호출이 같은지 확인합니다. 정답은 정상 함수의 import와 `splitAliases(aliases)` 호출을 복원하는 것입니다. 5주차와 다른 새 알고리즘을 만들거나 서버 검증을 삭제할 필요가 없습니다.

15:10–16:10의 60분은 교육생의 재현 10분, AI의 조사·계획과 교육생 판단 15분, AI 수정·검사 20분, 교육생의 화면 재확인 15분으로 진행합니다. 교육생은 AI에 전달한 정보·판단과 저장 후 재조회 결과를 남기며 코드 연결 수정은 AI가 수행합니다. 한 글자·11개 동의어 입력의 서버 거부도 유지되어야 합니다.

미공개 자료 진단은 14:20–15:00 구조 설명 중 약 10분에 시연합니다. 같은 검색어가 공개 전에는 보이지 않고 검토 후에는 보이는 상태를 비교해, 모든 증상이 코드 오류는 아니라는 점을 설명합니다. 실제 코드 수정 과제를 이 시연으로 대체하지 않습니다.

### 개정 해설과 다음 주 연결

v1의 화면 갱신은 60초, v2는 30초이며 이력 90일·표본 3대는 유지됩니다. 공개 승인 전후를 나누고, 위키 본문과 실제 근거 문단을 함께 갱신합니다. 이 결과는 코드 변경 효과와 다른 T5 기록으로 남깁니다. v1·v2를 별도 독립 자료로 동시에 공개한 경우에는 기존 원문의 새 버전으로 등록했는지 확인합니다.

종료 전에는 정상 코드와 설정을 확인하고, 약 10분 동안 [7주차 팀 과제](../weeks/07-application.md#4-팀-코드-개선-과제)를 고릅니다. 교육생은 업무 문제·입력·완료 기준을 정하고 AI가 대상 위치를 설명하게 합니다. 구현은 7주차에 AI가 수행합니다.

작업자·Tavily·API/CLI 선택 진단은 여유가 있을 때 하나만 진행합니다. 준비한 오류 문구로 진단할 수 있으며, 실제 공용 프로세스나 인증 설정을 바꾸지 않습니다. 코드 과제를 미완료한 팀은 선택 진단보다 수정·재검증을 먼저 합니다.

## 8. 7주차 지도와 업무 답안

교재: [7주차](../weeks/07-application.md). 팀당 작은 코드 개선 하나를 AI에게 구현 요청해 완성합니다. 교육생에게 코드 작성이나 줄별 검토를 요구하지 않습니다. 신규 자료는 [요청 문서](materials/new-rfp.md), 업무 해설은 [RFP 참고 답안](materials/rfp-answer.md)입니다. 새 RFP는 수업 시작에 각 실습 환경에서 사용할 수 있도록 처리·공개 상태를 준비합니다.

### 과제와 시간 운영

첫 20분에 새 문서와 구현 범위를 확인하고, AI 구현 요청·보완 55분과 교육생 결과 확인 30분을 확보합니다. RFP 작성은 30분에 명시 요구 1개·불명확 항목 1개로 줄입니다. 마지막 워크숍 30분에는 개인별로 다른 입력을 확인하고 결과를 정리합니다. 6시간 운영과 휴게 30분은 유지합니다.

기본 과제 A는 RFP의 확인 질문 누락 개수, B는 실무 메모 입력 길이 표시입니다. 둘 다 현재 소스의 상태와 기존 폼으로 구현할 수 있습니다. 새 DB·API·외부 모델 연결은 요구하지 않습니다. 단순 고정 문구 수정이나 설정값 변경은 이번 팀 기능의 완료로 보지 않습니다.

### A · RFP 개수 계산 참고 · 강사·AI용

`src/components/rfp-editor.tsx`의 `rows`에서 계산합니다. 저장할 때 질문을 trim하고 빈 값을 거르는 기존 처리와 기준을 맞춥니다.

```typescript
const missingQuestionCount = rows.filter(
  (row) =>
    (row.kind === "inference" || row.kind === "unclear") &&
    !row.questions.some((question) => question.trim().length > 0),
).length;
```

계산한 값을 기존 보고서 항목 영역에 표시합니다. 별도 상태로 개수를 저장하지 않으면 `rows`가 바뀔 때 같은 렌더링에서 다시 계산할 수 있습니다. 질문 없는 명시 요구는 0개, 공백 질문만 있는 불명확 항목은 1개로 셉니다. 두 미작성 항목 중 하나를 채우면 2→1, 유형 변경·추가·삭제도 현재 목록에 맞게 반영되어야 합니다.

저장 검증은 유지합니다. 개수 0은 인용·권한·제목 등 모든 저장 조건을 충족했다는 뜻이 아닙니다. 질문 없는 불명확 항목이 거부되는 것과 올바른 원문·질문을 갖춘 보고서가 저장되는 것을 각각 확인합니다.

### B · 메모 길이 계산 참고 · 강사·AI용

`src/components/record-editor.tsx`의 현재 `rawNote.length`를 기존 메모 안내에 표시합니다. 별도 입력 상태나 저장 필드를 추가할 필요가 없습니다. 빈 값은 0, ‘현장 점검’은 공백을 포함해 5입니다. 입력·삭제·다시 열기에 따라 바뀌는지 확인합니다.

기존 12,000 입력 제한, `rawNote` 저장, AI 정리와 다른 필드의 동작을 유지합니다. 새 안내를 입력창과 연결할 때도 기존 Field·Textarea 구성을 따릅니다. 값이 바뀌지 않는 고정 숫자나 도움말 문구만 추가한 경우에는 미완료입니다.

### AI가 수행할 기술 검사

AI가 선택한 컴포넌트에 형식 검사, 관련 타입 검사와 변경 내역 확인을 수행하고 결과를 보고합니다. A는 `src/components/rfp-editor.tsx`, B는 `src/components/record-editor.tsx`가 기준입니다. `git diff --check`, 해당 파일의 `npx biome check`, `npm run typecheck`를 사용하고, 교육생은 명령을 입력하는 대신 실제 입력·삭제·저장·다시 열기로 결과를 확인합니다.

### RFP 업무 해설

기존 A v2의 30초와 신규 R1의 45초는 적용 문서가 다릅니다. 기존 조건이 후속 환경의 충족을 증명하지 않으며, 보관 기간도 기존 90일과 신규 180일을 구분합니다. R4는 제외 범위, R5·R6은 대상·책임·전환 조건 등을 확인할 항목입니다.

필수 보고서는 R1 등의 명시 요구 한 항목과 R5 등의 불명확 한 항목으로 구성합니다. 해당 RFP의 실제 원문 문단·구절을 연결하고 확인 질문을 남깁니다. R1–R6 전체의 검토 여부는 짧게 기록합니다. 참고 답안의 나머지 항목은 추가 실습용이며 전부 작성하도록 요구하지 않습니다.

### 개인 확인과 인계

AI의 요청·변경 요약·검사 보고와 교육생의 변경 전후 화면·정상·경계 입력·기존 동작 확인이 있어야 합니다. 코드 개선을 RFP 작성이나 설정 변경으로 대신하지 않습니다. 늦어진 팀에는 범위를 표시 기능 하나로 좁혀 주고, 도움을 받은 뒤 다른 입력으로 직접 검증하게 합니다. 끝내 동작을 확인하지 못했다면 미완료로 남깁니다.

개인 10분은 업무 문제 2분, AI 요청·판단 3분, 다른 입력 확인 3분, 인계 설명 2분입니다. 모든 교육생이 요구·요청·계획 판단·보완 중 하나와 개별 화면 확인에 참여하고 T5에 남기게 합니다. AI 구현을 감점하지 않으며 코드 문법 설명은 요구하지 않습니다.

다른 팀이 인계 카드에서 새 기능의 코드·실행 방법·확인 입력을 찾고 재현합니다. AI 연결·모델·사용 조건·한도·관리 담당과 재시작 절차도 남기되 키·로그인 토큰은 기록하지 않습니다. 운영 배포나 모델 설정 선택 화면 같은 큰 기능은 후속 과제로 구분합니다.
