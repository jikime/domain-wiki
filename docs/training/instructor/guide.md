# 예제 확인과 코칭 참고 · 강사용

수업 운영은 [공동 개발 코칭표](lecture-guide.md)를 따릅니다. 이전의 기능별 설명 순서를 추가 수업으로 진행하지 않습니다. 교육생은 프레젠테이션의 작업 화면과 같은 제목의 워크북을 사용합니다.

## 예제에서 확인할 사실

프로젝트 A 사업 개요는 도로전광표지 24대입니다. 검수 v1의 화면 갱신은 60초, 보관은 90일이며 협의 메모의 180일은 확정 기준과 구분합니다. 개정 v2는 갱신 30초·보관 90일입니다. 실제 판단은 원문을 열어 확인하게 합니다.

신규 RFP의 확정 요구와 기존 A/B의 사례를 섞지 않습니다. [신규 요청 문서](materials/new-rfp.md)와 비공개 [참고 답안](materials/rfp-answer.md)을 사용합니다. 자료가 없는 답은 추측하지 않고 확인할 질문으로 남깁니다.

## 개발 예제 코칭

[기능 개발 예제](../development-recipes.md)는 선택지입니다. 현재 구현을 조사한 뒤 회사 요구와 연결합니다. 문구·링크에서 기존 입력칸의 회사 예시·선택 기능 완성으로 이어 가고, 기존 기능이면 실제 부족한 동작을 개선합니다.

- 작성 예시: 네 입력칸 옆의 읽기 안내부터 만듭니다. 예시를 입력값으로 저장하지 않고 기존 글·초안·AI 정리·저장·검토를 보존합니다.
- 검색 안내: 문서 수와 문단·위키 검색 결과 수를 구분합니다. 캡처의 55개를 고정 정답이나 오류로 보지 않습니다.
- 범위 유지: 자료실에서 실무 기록으로 이동하는 경로를 재현하고 직접 접속·잘못된 값·권한도 확인합니다.
- RFP 누락 표시: 먼저 짧은 두 항목을 직접 입력해 기존 흐름을 익힙니다. 추론·불명확과 나머지 유형을 구분하고 공백·유형 변경·추가·삭제를 확인합니다. 기존 저장 검증은 유지합니다.
- 동의어: 실제 구현 파일과 폼 연결을 확인합니다. 참고 답안만 검사한 결과를 완료로 삼지 않습니다.
- 메모 길이: 기존 제한과 같은 기준으로 계산하고 저장·다시 열기도 확인합니다.

코드 문법을 암기시키지 않습니다. 교육생이 원하는 동작을 설명하고 AI 계획을 판단하며 직접 다른 입력으로 확인하도록 돕습니다.
