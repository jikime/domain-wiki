# RFP·회사 설정 실습 사례

후속 요청을 분석한 보고서에서 항목 확인·질문 답변을 관리하고, 같은 도메인의 용어·이용 안내를 개발할 때 쓰는 사례입니다. 이 문서는 입력 안내이며 자료실에 업로드하지 않습니다. 개발 요청은 [업무 결과물과 회사 설정 관리하기](../weeks/06-debugging.md)에 있습니다.

## 원문과 시작 보고서 준비

강사는 수업 전에 공개 후속 요청과 아래 여섯 항목의 시작 초안을 writer 소유로 준비합니다. 교육생은 기존 초안을 열어 원문과 대조하고 누락만 보완합니다. 아래 등록·작성 순서는 자료가 없는 환경의 준비 절차이며 같은 자료·초안을 반복 생성하지 않습니다. 시작 초안에는 이번에 개발할 항목 확인 상태·가상 회신을 미리 넣지 않습니다.

1. [후속 단계 요청 문서](../instructor/materials/new-rfp.md)를 내려받습니다. 작성 계정으로 자료실에 **새 사업 자료**로 등록하고, 도메인 `가상 교통관제 자료`와 `프로젝트 A · 가람시`를 선택합니다. 추출 후 별도 검토 계정으로 **검토함 → 자료 공개 요청**에서 확인합니다. 이미 같은 자료가 공개됐다면 다시 등록하지 않습니다.
2. 작성 계정으로 **업무 도구 → RFP 분석 보고서 → 새 분석 작성**을 열고 공개된 후속 요청 문서를 고릅니다. RFP는 제안 요청 문서라는 뜻입니다.
3. **직접 작성·수정**에서 제목을 `[가상 실습] 프로젝트 A 후속 요청 분석`으로 정합니다. **분석 항목 추가**로 아래 여섯 항목을 만듭니다.
4. 각 항목의 **근거 문단 선택**에서 R1–R6에 해당하는 실제 원문을 찾고 **이 문단 인용**을 누릅니다. 인용은 그대로 두고 내 해석은 **의미·적용 범위**에 적습니다.
5. **검토 전 초안 저장**을 누릅니다. 저장한 보고서의 제목·초안 상태·버전·여섯 항목·질문 두 개를 확인한 뒤 개발을 시작합니다.

| 항목 제목 | 구분 | 의미·적용 범위 | 확인 질문 |
| --- | --- | --- | --- |
| R1 · 화면 갱신 | RFP 명시 요구 | 후속 단계 표시 갱신은 45초 이내다. | 비움 |
| R2 · 이력 보관 | RFP 명시 요구 | 후속 단계 이력은 180일간 보관한다. | 비움 |
| R3 · 검토 기록 | RFP 명시 요구 | 확인 항목·시각·기대 결과·실제 결과·확인자를 기록한다. | 비움 |
| R4 · 제외 업무 | RFP 명시 요구 | 현장 장비 교체·제어 명령 자동 전송은 제외한다. | 비움 |
| R5 · 외부 기관 연계 | 불명확한 범위 | 연계는 필요하지만 대상·자료·주기·책임은 미정이다. | 대상 기관·자료 항목·연계 주기·책임 주체는 무엇인가? |
| R6 · 운영 전환 | 불명확한 범위 | 운영에 지장이 없어야 하지만 허용 중단 시간·확인 방법은 미정이다. | 허용 중단 시간과 전환 확인 방법은 무엇인가? |

기존 운영의 **30초·90일**과 후속 요청의 **45초·180일**은 다른 적용 범위입니다. 후속 요청을 기존 검수 조건 v2에 덮어쓰지 않습니다. R1–R6는 문서에서 찾을 표기이며 DB 식별자가 아닙니다. 실제 자료·버전·문단과 연결하세요.

앱의 **AI 분석 초안 만들기**는 기존 기능입니다. 사용했다면 같은 여섯 항목으로 원문과 대조해 고칩니다. 공통 실습은 직접 작성으로도 진행할 수 있습니다.

## 항목 확인과 새 버전

항목 확인은 **원문과 분석의 뜻을 대조했다**는 기록입니다. 요청 기능을 구현하거나 실제 장비 검수를 마쳤다는 뜻이 아닙니다.

1. 항목 상태 기능을 만든 뒤 R1은 `확인 완료`, R2는 `확인 중`, 나머지는 `미확인`으로 둡니다. 이때 전체 여섯 항목 중 미확인은 네 개입니다.
2. 미확인과 `연계` 검색으로 R5를 찾습니다. 원문을 읽고 돌아오면 보고서 버전·항목·필터·검색이 유지돼야 합니다. R5는 미정 조건을 메모하고 확인 중으로 바꿉니다.
3. 기존 **새 버전으로 수정**에서 R2 의미에 `기존 운영의 90일과 구분한다.`를 더하고 저장합니다. 새 버전은 모든 항목을 미확인으로 시작하고 이전 버전의 상태·메모는 남겨야 합니다.
4. 새 버전의 R1–R4를 다시 읽고 확인합니다. R5·R6는 미정 사항을 남겨 다음 질문 관리에서 이어갑니다.

항목을 추가하거나 순서를 바꿔도 이전 기록이 다른 항목에 붙으면 안 됩니다. 제목과 표시 순서가 아닌 항목 식별자로 연결하도록 계획을 확인하세요.

## R5 회신과 R6 보류

다음 회신은 기능 확인용 가상 입력입니다. 실제 발주처의 답변이나 확정 요구로 사용하지 않습니다.

| 입력칸 | R5에 넣을 값 |
| --- | --- |
| 답변 내용 | [가상 회신] 교육용 교통정보센터의 상태 요약을 10분마다 받는 방안을 검토해 주세요. 책임 주체와 세부 항목은 추가 협의가 필요합니다. |
| 받은 경로 | 수업용 회신 카드 |
| 답변자·문서명 | 가상 업무 담당 / R5 회신 예시 |
| 상태 | 답변 기록 |
| 남은 확인 | 책임 주체와 세부 자료 항목 |

R5 원문 문단을 참고 자료로 연결해 보세요. 이 원문은 **원래 요청의 근거**이며 새 회신 내용의 근거는 아닙니다. 연결 해제는 참조만 빼고 원문을 삭제하지 않아야 합니다. 해제 동작을 확인한 뒤 다시 연결해 둡니다.

R6는 `보류`로 두고 다음 내용을 적습니다.

- 보류 사유: 운영 담당과 허용 중단 시간·전환 시험 방법을 아직 정하지 못했다.
- 다음 확인: 교육용 운영 담당에게 중단 허용 범위와 전환 확인 절차를 확인한다.

이후 R6를 다시 열어 `확인 대기`로 바꿉니다. 이전 이유와 다음 행동은 남아 있어야 합니다. 실제 담당자에게 메시지를 보내는 실습은 아닙니다.

## 회신을 참고한 보고서 보완

R5의 **의미·적용 범위**에 아래 내용을 덧붙입니다. 원문 구절은 바꾸지 않습니다.

> [가상 회신 참고] 교육용 교통정보센터의 상태 요약을 10분마다 받는 방안이 제안됐다. 책임 주체와 세부 자료 항목은 아직 협의가 필요하다. 이는 원문의 확정 요구가 아니다.

확인 질문은 `책임 주체와 세부 자료 항목은 무엇인가?`로 좁힙니다. 새 버전을 저장한 뒤 이전 회신을 참고로 연결합니다. 질문이 달라졌으므로 같은 질문이라고 자동 처리하지 않고 연결 대상을 직접 확인하세요. 새 질문은 `확인 대기`, 새 항목은 `미확인`에서 다시 판단합니다.

종합 확인에서는 이전 버전의 R5 회신과 R6 보류·재개 이력을 읽고, 새 버전의 질문과 상태를 확인합니다. 같은 회신을 새로 입력하거나 확인용 버전을 한 번 더 만들지 않습니다.

질문의 답변 기록·항목 확인·보고서 게시 승인은 별개입니다. 회신을 저장하거나 질문을 모두 처리해도 보고서를 자동 승인하지 않습니다.

## 회사 용어와 검색 확인

관리자로 **관리 → 도메인 → 가상 교통관제 자료 수정**을 엽니다. 현재 핵심 용어는 이미 도메인 DB에 저장되고 동의어 검색에 사용됩니다. 새 실습에서는 이를 행별로 편집하고 적용된 검색어를 보여 줍니다.

| 입력칸 | 값 |
| --- | --- |
| 용어 | 상태 변경 이력 |
| 설명 | 장비 상태가 바뀐 내용을 시간 순서로 남긴 자료 |
| 기존 동의어 | 상태 로그 |
| 추가할 동의어 | 변경로그 |

기존 행을 수정하며 같은 용어를 중복 등록하지 않습니다. 취소 후 원래 값을 확인하고, 다시 추가해 저장합니다. 작성 계정으로 자료실에서 같은 도메인·프로젝트 A와 `변경로그`를 검색하세요. 서버가 실제 적용한 단어와 원문 결과를 확인합니다. 추가한 동의어만 제거한 상태도 비교한 뒤 다시 저장해 남깁니다. 결과 개수는 고정하지 않습니다.

취소하면 수정 전 저장값으로 돌아가고, 저장에 실패하면 작성 중 입력을 남깁니다. 검색에 동의어 안내를 붙여도 기존 자료별 묶음·문단 펼침·즐겨찾기·저장 조건·검색 복귀는 유지합니다. RFP 원문 복귀를 개발할 때도 자료실·실무 기록·그래프의 기존 복귀 기능을 함께 확인합니다.

## 메뉴별 이용 안내

**관리 → 가상 교통관제 자료 수정 → 메뉴별 이용 안내**는 이번에 만들 편집 영역입니다. 기존 홈의 **입문 순서·추천 읽기 편집**과 구분합니다.

| 대상 메뉴 | 제목 | 안내 본문 |
| --- | --- | --- |
| RFP 분석 보고서 | 후속 요청을 읽는 순서 | 후속 요청의 45초·180일과 기존 운영의 30초·90일을 구분하세요. 미정인 범위는 확인 질문으로 남기고, 회신은 출처와 함께 기록하세요. |
| 자료실 | 자료를 찾을 때 확인할 것 | 도메인과 프로젝트를 먼저 고르세요. 검색에 적용된 동의어를 확인하고 원문 제목·버전·문장을 함께 읽으세요. |

문의 담당은 `교육용 업무 담당`, 표시 여부는 `표시함`으로 저장합니다. 문의 담당은 읽는 안내 문구이며 자동 메시지 발송 기능은 만들지 않습니다.

자료실은 선택한 도메인, RFP 작성·상세는 분석 원문의 도메인에 해당하는 안내를 엽니다. 관리자만 편집하고 사용자는 읽습니다. 숨김·다시 표시·안내 미등록·도메인 미선택 상태도 확인하세요. 일반 열람자는 게시한 보고서만 볼 수 있으므로 초안을 억지로 공개하지 않습니다.

## 추가 통합과 역할별 확인

강사에게 기준 저장소·이전 통합 커밋·RFP 변경 커밋·관리 변경 커밋·최종 기준 커밋, 별도 작업 사본과 준비된 통합 개발 DB를 받습니다. 그 DB에도 공개 원문·역할 계정·소유자가 분명한 연습 보고서가 있어야 합니다. 코드를 합친다고 개인 개발 DB의 자료가 함께 옮겨지지는 않습니다.

각자의 통합 사본·실행 주소·전용 DB를 확인합니다. 기준과 내 실제 커밋 번호를 구분해 적고 코드 내용·DB 적용을 대조합니다. 신규 구조 적용 뒤에는 그 DB에 이전 회신·보류/재개 이력과 현재 질문을 가진 교육용 보고서, 용어·안내를 준비해야 합니다. 원래 개인 자료를 자동으로 복사하거나 초기화하지 않습니다. 종합 확인에서는 앞 단계에서 요청·게시한 결과를 다시 열고 대기 중인 요청만 처리합니다.

내 작업을 별도 브랜치에 보관한 뒤 **RFP 변경 → 관리 변경** 순서로 코드와 DB 구조를 반영합니다. 기존 자료와 적용 이력을 지우지 않습니다. 통합본에서는 다음을 직접 확인합니다.

| 계정 | 직접 할 일 |
| --- | --- |
| 작성자 | 내 보고서의 상태·회신·새 버전·원문 복귀 확인, 근거와 미정 내용을 읽고 검토 요청 |
| 검토자 | 검토함 → 담당·오류 처리의 RFP 대기 건 또는 업무 도구 → RFP 목록에서 보고서 열기, 검토·버전에서 수정 요청 또는 검토 완료·게시 판단 |
| 관리자 | 도메인 용어·이용 안내 저장, 다른 설정과 개인 데이터가 보존되는지 확인 |
| 열람자 | 게시본·원문·이용 안내 읽기, 초안과 새 내부 상태·답변 메모의 접근 제한 확인 |

새 내부 회신 기록과 본문에 직접 반영한 회신 요약은 다릅니다. 분석 본문과 질문 목록은 게시하면 열람자에게 보일 수 있으므로 게시 전에 포함할 내용을 검토합니다. 질문이 남은 분석을 게시하더라도 그 요구가 확정되거나 구현됐다는 뜻은 아닙니다.

기존 질문 모음·개인 답변 메모·위키 비교도 함께 확인합니다. 통합 커밋·DB 변경·보고서 버전·통과·실패·미확인과 남은 담당을 남기세요. 공용 반영·백업·복구는 확인한 준비 상태만 적고 운영 DB 초기화나 배포를 자동 실행하지 않습니다.
