# 운영 인수인계 실습 사례

[강의 화면](/lectures/week-07.html)과 [실습 순서](../weeks/07-application.md)에서 같은 업무와 문장을 사용합니다. 아래 예시는 교육용이며 실제 회사의 업무 완료나 운영 인수를 뜻하지 않습니다.

## 시작할 상태

6회차의 통합본과 개발 DB, 가상 교통관제 자료·프로젝트 A를 사용합니다. 작성 writer@wiki.local, 검토 reviewer@wiki.local, 관리 admin@wiki.local, 열람 reader@wiki.local을 같은 서버에서 구분합니다. 비밀번호는 배정받은 값을 사용하세요.

여기서 같은 서버는 **각 교육생에게 지정한 서버·전용 DB**입니다. 교육생 모두가 한 DB의 같은 계정으로 작업한다는 뜻은 아닙니다. 최종 코드 반영 때도 이번에 만든 기록·메모·자료 갱신 결과가 있는 DB를 이어 씁니다.

다음이 준비돼 있어야 합니다.

- 공개 검수 조건 v2, 그 근거로 보완한 두 게시 위키, 공개된 후속 단계 요청 문서
- 이전 가상 회신과 현재 질문이 연결된 RFP 보고서
- 앞에서 개발한 즐겨찾기·내 메모·실무 기록·개인 할 일·질문 모음·답변 확인·위키 비교·도메인 이용 안내
- 강사가 지정한 통합 커밋·사본·개발 DB·역할 계정·확인용 자료
- 별도 자료로 등록·공개한 [운영 연습 원문 v1](handover-source-v1.md). [v2](handover-source-v2.md)는 운영 실습에서 같은 자료에 새 버전으로 등록합니다.

초기 샘플에는 앞 회차 개발 기능과 개정 결과가 모두 들어 있지 않습니다. 빈 목록을 채우려고 개인 DB를 초기화하거나 샘플 백업으로 덮어쓰지 않습니다.

## 업무 상황 카드

**맡은 업무:** 프로젝트 A 후속 단계의 운영 인수인계를 준비합니다. 운영 담당에게 현재 기준과 후속 요청, 아직 정하지 않은 조건을 설명할 수 있어야 합니다.

먼저 사용할 메뉴와 이유를 정합니다. 남길 결과는 근거와 판단이 있는 실무 기록 하나, 미완료 할 일 두 개, 후속 요청 원문의 즐겨찾기 메모입니다.

| 확인 대상 | 구분할 내용 |
| --- | --- |
| 검수 조건 v2 | 기존 운영의 화면 표시 갱신 30초 이내·상태 변경 이력 90일 보관 |
| 후속 요청 R1·R2 | 후속 단계의 표시 갱신 45초 이내·이력 180일 보관. 기존 운영의 개정본이 아님 |
| RFP의 R5 | 이전 가상 회신의 대상·주기는 제안. 책임 주체·세부 자료 항목은 미정 |
| RFP의 R6 | 허용 중단 시간·전환 확인 방법은 미정. 이전 보류·재개 이력과 현재 질문을 구분 |

자료실에서 실제 원문·버전을 읽고, 지식 그래프의 비교 목록에서 업무 절차 위키와 범위·검수 기준 위키의 근거를 확인합니다. 채팅의 공개 원문·게시 위키 검색과 RFP의 내부 회신은 별개입니다. 내부 회신은 보고서에서 직접 읽습니다.

## 실무 기록과 내 할 일

실무 기록 → 작성에서 가상 도메인·프로젝트 A와 앞에서 만든 인수인계 유형을 고릅니다.

| 입력칸 | 예시 |
| --- | --- |
| 제목 | [가상 실습] 프로젝트 A 후속 단계 인수인계 준비 |
| 상황 | 기존 운영과 후속 요청이 함께 있어 적용 범위를 나눠 확인했다. |
| 판단과 이유 | 기존 30초·90일과 후속 45초·180일을 구분했다. R5 회신은 제안이며 책임·세부 항목, R6 전환 조건은 아직 미정이다. |
| 결과 | 기준과 근거를 비교한 준비 기록을 남겼다. |
| 추가 확인할 내용 | 연계 책임·자료 항목과 허용 중단·전환 확인 방법을 정해야 한다. |

검수 조건 v2의 갱신·보관 문단과 후속 요청 R1·R2 문단을 실제 근거 선택으로 연결합니다. 가상 회신을 원문 구절로 넣지 않습니다. 기존 저장 흐름으로 등록한 뒤 같은 기록을 다시 엽니다. 별도 공개 검토를 생략하지 않습니다.

내 확인할 일 두 개를 이 기록에 연결하고 둘 다 미완료로 둡니다.

1. 연계 책임 주체·세부 자료 항목 확인
2. 허용 중단 시간·전환 확인 방법 확인

RFP 질문 상태와 개인 할 일이 자동으로 동기화되는 것은 아닙니다. 각각의 위치에서 확인합니다.

## 즐겨찾기 메모와 저장 확인

후속 요청 원문을 기존 즐겨찾기에 담고 다음 메모를 저장합니다. 같은 원문을 중복 등록하지 않습니다.

> 후속 요청 45초·180일. 연계 책임과 전환 조건은 확인 필요.

### 저장 실패와 온라인 복귀

1. 자신의 실습 브라우저에서 메모 편집 화면에 ‘세부 자료 항목도 확인 필요.’를 더합니다.
2. 개발자 도구 → Network(네트워크)에서 Offline(오프라인)을 선택합니다. 서버·DB를 종료하는 것이 아닙니다.
3. 저장을 눌러 입력이 남고 미저장 또는 확인 필요 상태가 안내되는지 봅니다. 여기서 새로고침하지 않습니다.
4. Network를 원래 온라인 설정으로 돌립니다. 서버에 저장된 값을 다시 확인하고 필요한 내용만 저장합니다.
5. 응답만 끊기고 서버에는 저장된 상황은 AI의 반복 검사에서 따로 확인합니다. 오프라인 저장 실패와 같은 결과라고 단정하지 않습니다.

### 두 탭의 수정 충돌

앞 단계에서 저장한 메모를 같은 계정의 두 탭에 먼저 엽니다. 프로젝트 A·B가 아니라 같은 메모를 연 탭1·탭2입니다.

| 순서 | 할 일 | 기대 결과 |
| --- | --- | --- |
| 탭1 | 지금 저장된 메모 뒤에 ‘연계 책임 주체를 확인할 것.’을 더해 저장 | 새 버전으로 저장 |
| 탭2 | 새로고침하지 않은 옛 화면에서 ‘전환 확인 방법을 정할 것.’을 더해 저장 | 최신 내용을 덮지 않고 충돌 안내 |
| 비교 | 최신 저장문과 내 작성문을 함께 읽기 | 두 내용이 남아 있음 |
| 결정 | 최신 메모와 추가 문장 두 개를 모두 포함해 저장 | 최신 버전을 기준으로 갱신 |
| 재조회 | 두 탭·홈·목록에서 같은 메모 다시 열기 | 같은 최종 문장, 즐겨찾기 수는 증가하지 않음 |

AI는 DB의 버전 비교와 갱신이 한 번에 처리되는지 검사합니다. 교육생은 실제 충돌 안내와 최종 저장문을 확인합니다. 종합 확인에서 같은 문장을 반복해 덧붙이지 않습니다.

### 계정과 재접속

같은 서버에 같은 계정으로 별도 브라우저에서 로그인해 DB에 저장된 값을 읽습니다. 다른 계정으로 바꾸면 이전 사용자의 메모·임시 입력이 남아 있지 않아야 합니다. 주소를 바꿔 다른 사람의 메모를 조회하거나 저장하는 요청도 서버에서 막아야 합니다. 테스트에는 지정한 교육용 계정·자료만 사용합니다.

## 운영 연습 자료 갱신

[운영 연습 v1](handover-source-v1.md)은 가상 도메인·프로젝트 A의 별도 사업 자료로 미리 등록·공개합니다. 기존 검수 조건이나 후속 요청 파일을 대체하지 않습니다.

1. writer로 ‘[가상 실습] 운영 안내 변경 연습’ 상세를 엽니다.
2. **새 원본 버전 등록**에서 [v2 파일](handover-source-v2.md)을 올립니다. v2는 문의에 자료 제목·버전·증상·기대·실제 결과를 적도록 바뀝니다.
3. 추출한 원문과 공개 검토 대기 상태를 확인합니다. **승인하기 전에** reader로 바꾸어 자료실에서 같은 자료를 찾아 공개 v1을 읽습니다. writer의 미공개 v2 주소를 복사해 열지 않습니다.
4. reviewer로 검토함 → 공개·게시 검토에서 해당 요청을 열고 v2의 변경 내용을 대조해 공개 여부를 판단합니다.
5. reader로 자료실에서 같은 자료를 다시 찾아 공개 v2를 읽습니다. 특정 버전에 고정된 이전 주소를 새로고침하는 것과 구분합니다. 일반 열람자에게 작성·승인 버튼이 없어야 합니다.

자료 등록·추출과 공개 승인은 다른 단계입니다. 이미 등록한 v2를 다시 올리지 않습니다. 자동 자료 정리로 위키 변경안이 생겼다면 별도 변경안으로 구분하고 임의로 게시하지 않습니다.

## 운영 상황 카드

| 상황 | 직접 확인할 위치 | 다음 행동 |
| --- | --- | --- |
| 자료 처리 실패 | 관리 → 작업·사용량·보존 관리 → 문서 처리 상태, 해당 원문의 오류 | 원인 해결 뒤 작성자·검토자가 실패·취소 상태의 처리 재시도 사용. 결과를 다시 확인 |
| AI 연결 오류 | 관리 → 모델 연결, 운영 화면의 최근 모델 오류 | 실제 연결·인증·한도와 메시지 확인. 필요할 때 지정 담당이 연결 점검. 설정 입력과 연결 성공을 구분 |
| 추출 완료·검토 대기 | 검토함 → 공개·게시 검토 또는 담당·오류 처리 | 요청·담당을 확인하고 원문 내용 검토. 추출 완료만으로 공개하지 않음 |
| 현재 오류 없음 | 같은 운영 화면 | 없음으로 기록. 실행하지 않은 재시도를 성공으로 적지 않음 |

최근 30일 모델 사용량과 임베딩 사용량은 따로 봅니다. 토큰·단가 미확인 상태를 0원이라고 적지 않습니다. ‘대화·생성 작업 보존 일수’는 사업의 90일·180일 보관 요구와 다른 설정이며, 저장해도 자동 삭제되지 않습니다.

DB·업로드 원본·코드·필요 설정의 보관 위치와 담당, 기존 별도 환경 복구 확인 기록을 확인합니다. `training-snapshot.json`은 교육 시작 자료이며 개인 메모·대화·계정의 전체 백업이 아닙니다. 이 실습에서 운영 DB 복원·Docker 조작·삭제는 실행하지 않습니다.

관리의 기존 메뉴별 이용 안내에서 자료실 안내에 다음 문장을 덧붙이고 실제 배정된 문의 담당을 적습니다.

> 문의에는 자료 제목·버전·증상·기대·실제 결과를 남기세요.

writer·reader로 안내를 다시 읽습니다. 실제 담당이 없으면 교육용 업무 담당과 실제 담당 미정을 구분해 적습니다.

## 최종 반영과 인계

강사가 지정한 이전 통합 기준·채택한 안정화 변경·최종 기준 커밋, 통합 사본·개발 DB를 먼저 맞춥니다. 개인 변경을 보존한 뒤 채택한 코드·DB 변경을 순서대로 반영합니다. 개인 DB의 메모가 코드 병합으로 옮겨지지는 않습니다.

최종 코드 사본은 이번 업무에서 사용한 **내 전용 통합 DB**를 이어 사용합니다. 준비 기록·개인 할 일·최종 메모·연습 원문 v2·문의 안내를 남긴 채 필요한 구조 변경만 적용합니다. 다른 DB가 꼭 필요하면 옮길 교육 자료·소유자·버전과 검증 순서를 먼저 정하고, 빈 DB에서 기존 결과가 보일 것으로 가정하지 않습니다. 기준 커밋과 내 실제 커밋 번호는 각각 기록합니다.

같은 서버에서 작성·검토·관리·열람 계정으로 처음 업무를 다시 확인합니다. 원문·게시 위키·채팅 근거·RFP 질문·준비 기록·개인 할 일·메모·안내를 이어 엽니다. 좁은 화면의 저장 버튼·결과 안내도 확인합니다.

같은 환경에서 이미 받은 채팅 답변은 다시 열어 근거를 확인합니다. 해당 환경의 답변이 없을 때만 질문을 보내고 확인하지 못한 결과를 완료로 적지 않습니다.

| 구분 | 완료 근거 |
| --- | --- |
| 개인 실행 | 개인 개발 환경·버전에서 직접 수행한 결과 |
| 통합 확인 | 지정 통합본의 최종 커밋·DB 적용·자료·역할별 업무 확인 |
| 공용 반영 | 실제 회사 주소의 반영 버전과 역할별 접속·업무 확인 |
| 운영 인수 | 실제 담당이 갱신·오류 확인·보관·문의 절차와 위치를 받아 확인 |

공용 환경이나 인수 담당이 없으면 해당 항목은 미완료입니다. 교육용 계정을 바꿔 본 결과를 실제 운영 인수로 적지 않습니다.

인계 문서에는 주소·최종 커밋·DB 적용·자료 버전·담당·확인 결과·보관 위치·미확인을 남깁니다. 비밀번호·API 키 값은 적지 않습니다. R5·R6의 업무 미정, 기능 보완, 공용 도입 준비마다 **문제 / 담당 또는 담당을 정할 사람 / 다음 행동 / 완료 기준**을 적습니다.
