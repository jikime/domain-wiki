# 질문·답변 확인·위키 비교 실습 사례

채팅과 지식 그래프를 개발한 뒤 사용할 입력 사례입니다. 이 문서를 자료실에 업로드하지 않습니다. 계획·실행 요청과 전체 개발 순서는 [채팅과 지식 그래프로 근거 확인하기](../weeks/05-development.md)에 있습니다.

## 시작할 상태

앞 실습에서 공개한 **프로젝트 A 검수 조건 v2**와 보완·게시한 두 위키를 사용합니다.

- `[가상 실습] 프로젝트 A 검수 업무 절차`
- `프로젝트 A의 범위와 검수 기준`

두 위키의 현재 게시 본문과 근거에서 갱신 **30초 이내**, 이력 보관 **90일**을 확인하세요. 아직 v1이나 60초가 남았다면 앞 실습의 개정·게시부터 마칩니다. 60초가 보이는 강의 캡처는 초기 샘플 화면이며 이번 실습의 완료 기준이 아닙니다. 개인 초안이나 검토 대기 중인 실무 기록을 공개할 필요는 없습니다.

작성 계정으로 실습하고, 검토함은 별도 검토 계정으로 확인합니다. 다른 계정에서 개인 기록이 보이는지는 같은 위키 서버의 열람 계정으로 확인하세요. 비밀번호는 배정받은 값을 사용합니다.

## 내 질문 모음에 저장할 세 질문

상단 **채팅**에서 도메인 `가상 교통관제 자료`를 선택한 뒤 프로젝트를 고릅니다. 공통 사례는 기본 탐색, 원문만 사용 끔, 웹 검색 끔으로 맞춥니다. 특정 자료나 위키만 골라 둔 상태라면 그 한정도 해제합니다. 저장 기능 자체는 이런 한정 조건도 빠짐없이 보관하도록 개발합니다.

| 이름 | 프로젝트 | 질문 전체 |
| --- | --- | --- |
| A 검수 기준 | 프로젝트 A · 가람시 | 프로젝트 A의 현재 상태 화면 갱신 주기와 이력 보관 기간은? 원문 근거와 적용 범위를 함께 알려줘. |
| A 자동 복구 확인 | 프로젝트 A · 가람시 | 프로젝트 A의 장애 자동 복구 시간은 얼마야? 문서에 없으면 없다고 말하고 확인할 항목을 알려줘. |
| B 검수 기준 | 프로젝트 B · 누리시 | 프로젝트 B의 상태 조회 주기와 이력 보관 기간은? 프로젝트 A와 구분해서 알려줘. |

1. 세 질문을 이름·질문 문장·선택한 범위와 함께 저장합니다. 저장하거나 목록을 누르는 것만으로 질문을 전송하면 안 됩니다.
2. `A 검수 기준`을 불러옵니다. 질문과 A 범위를 확인한 뒤 새 대화에 적용합니다. 입력 중이던 문장이 있다면 바꿀지 묻고, 취소하면 그 문장을 남겨야 합니다.
3. A 질문을 복제해 이름·질문 문장·프로젝트를 B 검수 기준으로 바꿉니다. 삭제는 별도 ‘삭제 연습’ 복제본으로 확인하고 공통 세 질문은 유지합니다. 이미 삭제한 항목을 종합 확인에서 다시 만들지 않습니다.
4. 이름·문장으로 검색하고 프로젝트로 거릅니다. 검색 결과가 없으면 전체 목록으로 돌아갈 방법이 있어야 합니다.
5. `A 검수 기준`을 새 대화에 적용하고 직접 전송합니다. 완료된 답변은 다음 실습에서 다시 사용합니다.

같은 서버에 다른 브라우저로 같은 계정으로 로그인해 질문 목록을 확인합니다. 다른 계정에서는 내 질문이 보이지 않아야 합니다.

## 답변과 원문을 비교하고 내 확인 기록 남기기

답변의 **참고 자료**를 눌러 **답변의 원문 근거**를 엽니다. 문서 제목만 읽지 말고 인용한 문장, 프로젝트, 원문 버전을 함께 확인합니다.

| 답변 | 직접 확인할 내용 | 개인 상태·메모 예시 |
| --- | --- | --- |
| A 검수 기준 | 현재 공개 검수 조건의 30초·90일. 갱신 주기는 장애 자동 복구 시간이 아님 | 원문과 일치하면 `확인함`. “표시 갱신은 30초 이내, 이력 보관은 90일. 자동 복구 기준과 구분했다.” |
| A 자동 복구 확인 | 제공 자료에 자동 복구 시간이 명시되어 있지 않음 | `추가 확인`. “자동 복구 기준의 별도 문서가 있는지 담당자에게 확인할 필요가 있다.” |
| B 검수 기준 | 프로젝트 B의 갱신 120초 이내·보관 30일. A의 조건과 다름 | 해당 B 원문을 확인한 뒤 상태를 정함 |

AI가 위 수치대로 답했더라도 인용 근거가 다른 프로젝트나 과거 버전이면 확인 완료로 표시하지 않습니다. 답변이 나오지 않았다면 실제 답변 확인은 미완료로 남깁니다.

1. 첫 답변에 내 메모를 저장하고 실제로 확인한 근거를 연결합니다. 갱신·보관이 한 문단이거나 게시 위키 하나로 인용될 수 있으므로 두 개로 맞추지 않습니다. 해당 답변의 실제 인용에서 고르고, `E1` 같은 화면 번호만 저장하지 않고 답변·위키·원문 버전·문단과 연결하는지 확인하세요. 아직 없는 별도 확인 목록은 다음 단계에서 만듭니다.
2. `A 자동 복구 확인`도 전송한 뒤 `추가 확인`으로 남깁니다. 내 목록에서 상태로 거르고, 원래 답변과 근거로 돌아갑니다.
3. 메모를 수정·취소하고 다른 브라우저에서 다시 확인합니다. 이 기록은 내 판단을 남기는 기능이며 회사의 게시 승인이 아닙니다.
4. 별도 확인을 요청하려면 기존 **답변에 의견 남기기**를 사용합니다. 개발한 연결 기능으로 메모를 옮길지 고른 뒤, 보낼 글을 `자동 복구 기준의 별도 문서가 있는지 확인해 주세요.`로 확인하고 직접 전송합니다.
5. 검토 계정으로 **검토함**에서 앞 단계에 보낸 의견 한 건을 확인한 뒤 작성 계정으로 돌아옵니다. 종합 확인에서 같은 의견을 다시 보내지 않습니다. 아직 취소만 했다면 한 번 전송합니다. 개인 메모 저장만으로 검토함에 전송되면 안 됩니다.

기존 **위키 초안으로 저장**은 완료된 답변과 근거로 별도 위키 초안을 만드는 기능입니다. 개인 메모·확인 상태를 함께 공개하지 않습니다. 초안 저장과 위키 게시도 다른 단계입니다.

## 두 위키를 비교하고 원문을 읽은 뒤 돌아오기

상단 **지식 그래프 → 필터**에서 `가상 교통관제 자료`, `프로젝트 A · 가람시 + 공통`을 고릅니다. **필터 닫고 보기 → 위키 목록**에서 두 게시 위키를 찾습니다. 기존 화면에는 문서 미리보기가 있고, 비교 목록과 나란히 보기는 이번에 만들 기능입니다.

1. `프로젝트 A 검수 업무 절차`와 `프로젝트 A의 범위와 검수 기준`을 비교 목록에 담습니다. 같은 위키를 다시 담아도 중복되지 않고, 세 번째 위키는 먼저 하나를 빼도록 안내해야 합니다.
2. 제목·프로젝트·현재 게시 버전·본문·근거를 나란히 읽습니다. 업무 절차는 확인할 순서, 범위 위키는 적용 대상과 해석을 설명하는지 살펴보세요.
3. 갱신 주기의 근거를 눌러 실제 원문 문단을 읽습니다. 돌아오면 같은 필터·선택 위치·두 비교 대상이 남아 있어야 합니다.
4. 다시 접속해서 같은 계정의 비교 목록을 확인합니다. 목록에는 위키 식별 정보·순서·마지막으로 본 버전을 보관하고 본문은 현재 게시본을 불러옵니다. 게시 버전이 달라지면 안내해야 합니다. 읽을 권한이 없어진 문서는 이전 본문을 보여 주면 안 됩니다.
5. 열람 계정에서도 읽을 수 있는 게시 위키를 직접 골라 비교합니다. 작성 계정의 개인 비교 목록은 보이지 않아야 합니다.

그래프에서 원문으로 들어온 경우에만 그래프로 돌아갑니다. 자료실 검색·실무 기록에서 원문을 열었을 때의 기존 복귀 기능도 유지되는지 각각 확인하세요.

비교 목록에 담는다고 그래프 관계선이 새로 생기는 것은 아닙니다. 실제 본문 링크와 원문 근거, 계산된 관련성은 구분해서 설명합니다.

## 개인 개발본을 남기고 통합본 확인하기

강사가 제공한 다음 값을 사용합니다. 값이 준비되지 않았다면 임의의 주소·커밋·DB로 대신하지 않습니다.

| 받을 값 | 쓰는 곳 |
| --- | --- |
| 강사 기준 저장소 주소 | `upstream` 연결 확인. `origin`은 내 fork |
| 대표 브랜치와 기준 커밋 | 질문 모음·답변 확인·위키 비교가 포함된 시작 버전 |
| 질문 고정하기 추가 변경 커밋 | 모두 함께 합칠 고정·해제·상단 정렬과 DB 변경 |
| 최종 비교 기준 | 강사가 확인한 최종 코드·DB 변경 목록. 내 실제 통합 커밋과 구분해 기록 |
| 별도 작업 사본 경로 | 내 개발본을 보존하면서 통합 작업할 위치 |
| 실행 주소·포트·전용 개발 DB | 내 통합 사본의 실행 위치와 DB. 비밀번호를 작업 기록에 쓰지 않음 |
| 통합용 자료·계정 | 공개 원문 v2·두 게시 위키·역할 계정과 모델 연결. 개인 DB의 자료가 자동 이동하지 않음 |

대표 구현에는 2~4회차 누적 기능과 이번 질문 모음·답변 확인·위키 비교가 포함돼 있어야 합니다. **질문 고정하기는 강사가 사전에 시험해 제공하는 통합 연습 변경**이며 앞에서 빠뜨린 개발 과제가 아닙니다. 교육생마다 전용 DB를 사용하고, 같은 계정 이름으로 한 DB를 공동 수정하지 않습니다.

1. 개발용 AI가 내 변경 파일·브랜치·DB 변경·원격 연결을 조사하고 계획을 제시하게 합니다. 보관할 파일을 확인한 뒤 개인 작업을 별도 브랜치의 커밋으로 남깁니다. 환경 파일과 개인 자료는 포함하지 않습니다.
2. 기준 저장소의 변경을 받아 별도 작업 사본과 브랜치에서 대표 구현을 엽니다. `fetch`는 변경을 받아 확인하는 단계이고, 병합은 내 작업에 반영하는 단계입니다.
3. 같은 **질문 고정하기** 변경을 합칩니다. 충돌이 있다면 두 구현의 의도를 확인한 뒤 해결하고, 필요한 DB 변경을 지정한 통합 개발 DB에 적용합니다. 기존 DB 변경 이력을 지우지 않습니다.
4. 강사가 제공한 최종 기준의 코드 내용과 DB 변경 목록을 대조합니다. 병합 방식에 따라 내 실제 커밋 번호는 다를 수 있으므로 두 번호를 각각 적고 강제로 초기화하지 않습니다. 질문 고정·해제, 답변·근거·개인 확인 기록, 두 위키 비교·복귀를 확인합니다. 같은 통합 환경에서 이미 만든 질문·답변은 다시 사용하고 없을 때만 준비합니다.
5. 기준 커밋·적용한 DB 변경·직접 확인한 결과·남은 문제를 적습니다. 개인 개발 DB의 메모나 대화는 코드를 합친다고 자동으로 통합되지 않습니다.

통합 개발본 확인과 회사 운영 배포는 별도입니다. 이 단계에서는 운영 DB 초기화나 원격 강제 반영을 하지 않습니다.
