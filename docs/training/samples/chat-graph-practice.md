# 질문·답변 확인·위키 비교 실습 사례

채팅과 지식 그래프를 개발한 뒤 사용할 입력 사례입니다. 이 문서를 자료실에 업로드하지 않습니다. 계획·실행 요청과 전체 개발 순서는 [채팅과 지식 그래프로 근거 확인하기](../weeks/05-development.md)에 있습니다.

## 시작할 상태

채팅에는 프로젝트 A·B의 현재 공개 자료를 사용합니다. 위키 비교 실습에서는 아래 두 게시 위키를 예로 듭니다.

- `[가상 실습] 프로젝트 A 검수 업무 절차`
- `프로젝트 A의 범위와 검수 기준`

실습 계정으로 공개 자료와 게시 위키가 열리는지 확인하세요. 필요한 자료가 없으면 강사와 함께 준비합니다. 특정 버전 번호나 수치를 맞추려고 원문을 수정하지 않습니다. 답변의 갱신 주기·보관 기간은 실제로 연 원문과 대조합니다. 개인 초안이나 검토 대기 중인 실무 기록을 임의로 공개하지 않습니다.

기본 실습은 `writer` 계정으로 진행합니다. 검토함은 `reviewer`, 개인 기록 분리는 `reader`로 확인한 뒤 `writer`로 돌아옵니다. 모두 같은 교육생의 앱·작업공간을 사용하며 비밀번호는 배정받은 값을 씁니다.

## 내 질문 모음에 저장할 세 질문

상단 **채팅**에서 도메인 `가상 교통관제 자료`를 선택한 뒤 프로젝트를 고릅니다. 공통 사례는 기본 탐색, 원문만 사용 끔, 웹 검색 끔으로 맞춥니다. 특정 자료나 위키만 골라 둔 상태라면 그 한정도 해제합니다. 저장 기능 자체는 이런 한정 조건도 빠짐없이 보관하도록 개발합니다.

| 이름 | 프로젝트 | 질문 전체 |
| --- | --- | --- |
| A 검수 기준 | 프로젝트 A · 가람시 | 프로젝트 A의 현재 상태 화면 갱신 주기와 이력 보관 기간은? 원문 근거와 적용 범위를 함께 알려줘. |
| A 자동 복구 확인 | 프로젝트 A · 가람시 | 프로젝트 A의 장애 자동 복구 시간은 얼마야? 문서에 없으면 없다고 말하고 확인할 항목을 알려줘. |
| B 검수 기준 | 프로젝트 B · 누리시 | 프로젝트 B의 상태 조회 주기와 이력 보관 기간은? 프로젝트 A와 구분해서 알려줘. |

개발 요청은 저장·불러오기 등의 기능을 만드는 요청입니다. 위 질문을 자동으로 등록하는 요청은 아닙니다. 기능이 완성되면 교육생이 다음 순서로 앱에서 직접 입력합니다.

1. **7장 · A 질문 두 개 저장:** 앱 채팅에서 프로젝트 A를 고릅니다. 표의 첫 질문 문장을 입력하고 이름을 `A 검수 기준`으로 저장합니다. 이어서 두 번째 질문 문장을 입력해 `A 자동 복구 확인`으로 저장합니다. 새로고침해 두 이름·문장·프로젝트가 남는지 확인하며 아직 질문 보내기는 누르지 않습니다.
2. **8장 · 저장한 A 질문 불러오기:** 새 대화의 프로젝트를 B로 바꾼 뒤 내 질문 모음의 `A 검수 기준`을 고릅니다. B용 저장 질문을 찾는 것이 아닙니다. 적용하면 문장과 프로젝트가 A로 바뀌어야 합니다. 프로젝트 B와 입력 문장 `작성 중인 질문`을 둔 상태에서 불러오기를 취소하면 문장과 프로젝트 B가 모두 남아야 합니다.
3. **9장 · B 질문 복제·수정·삭제:** `A 검수 기준`을 복제합니다. 이름은 `B 검수 기준`, 질문 문장은 표의 B 질문, 프로젝트는 `프로젝트 B · 누리시`로 바꿔 저장합니다. B 질문을 한 번 더 복제해 `삭제 연습`으로 저장합니다. 이 복제본의 이름을 `삭제 확인용`으로 수정·저장하고, 다시 다른 이름을 입력하다 취소하면 `삭제 확인용`이 남아야 합니다. 이 연습 복제본만 삭제하고 공통 세 질문은 남깁니다.
4. **10장 · 검색과 필터 확인:** 프로젝트 A와 `검수`를 함께 적용하면 이번 사례에서는 `A 검수 기준`이 나오고 나머지 두 질문은 제외돼야 합니다. 다른 기존 질문도 조건에 맞으면 나올 수 있습니다. 없는 검색어로 결과 0개를 확인한 뒤 조건을 지우면 이번 세 질문과 기존 질문이 다시 보여야 합니다. 전체 개수를 3개로 맞추려고 기존 질문을 지우지 않습니다.
5. **11장 · 첫 답변 받기:** `writer`의 내 질문 모음에서 공통 세 질문을 찾습니다. 빠진 항목만 7·9장의 입력 순서로 준비합니다. `reader`로 바꿔 작성자의 개인 항목이 보이지 않는지 확인한 뒤 `writer`로 돌아옵니다. `A 검수 기준`을 새 대화에 적용하고 직접 전송합니다. 완료된 답변은 다음 실습에서 다시 사용합니다.

`A 검수 기준`은 **내 질문 모음에 붙인 이름**입니다. 최근 대화·내 확인 목록에서는 실제로 보낸 `프로젝트 A의 현재 상태 화면 갱신 주기와 이력 보관 기간은?`으로 시작하는 질문을 찾습니다. 저장한 이름이 대화 제목이나 답변 목록에 그대로 표시된다고 가정하지 않습니다.

## 답변과 원문을 비교하고 내 확인 기록 남기기

답변의 **참고 자료**를 눌러 **답변의 원문 근거**를 엽니다. 문서 제목만 읽지 말고 인용한 문장, 프로젝트, 원문 버전을 함께 확인합니다. **14·15장은 기록할 내용을 살펴보는 예시입니다.** 메모 저장은 16장, 근거 연결은 17장, 확인 목록은 18장, 의견 작성 연결은 19장에서 개발한 뒤 사용합니다.

| 답변 | 직접 확인할 내용 | 개인 상태·메모 예시 |
| --- | --- | --- |
| A 검수 기준 | 답변의 갱신 주기·보관 기간이 프로젝트 A 원문과 일치하는지 확인 | 직접 대조한 뒤 `확인함`. 메모에는 읽은 원문의 조건과 확인한 내용을 적음 |
| A 자동 복구 확인 | 원문에 자동 복구 시간이 있는지 확인. 표시 갱신 주기와 구분 | 기준을 찾지 못했다면 `추가 확인`. “자동 복구 기준의 별도 문서가 있는지 담당자에게 확인할 필요가 있다.” |

숫자가 맞아 보여도 인용 근거가 다른 프로젝트나 현재 적용할 수 없는 버전이면 확인 완료로 표시하지 않습니다. 답변이 나오지 않았다면 실제 답변 확인은 미완료로 남깁니다.

1. 갱신 주기·보관 기간 질문의 실제 답변에 메모·상태를 저장합니다. 확인이 끝났다면 `확인함`, 더 알아볼 내용이 있다면 `추가 확인`으로 남깁니다. 수정·저장·취소·새로고침을 확인합니다. 17장 기능을 만든 뒤 이 답변에서 읽은 실제 인용 근거를 연결합니다. 근거 개수를 억지로 맞추지 않으며 `E1` 같은 화면 번호만 저장하지 않고 답변·위키·원문 버전·문단과 연결하는지 확인합니다. 별도 확인 목록은 아직 없으므로 최근 대화에서 같은 답변을 다시 엽니다.
2. 확인 목록을 만든 뒤 `A 자동 복구 확인`을 새 대화에 불러와 한 번 전송합니다. 완료 답변이 미확인 목록에 보이는지 먼저 확인한 뒤 원문을 읽고 상태·메모를 저장합니다. 기준을 찾을 수 없다면 `추가 확인`, 근거로 확인했다면 `확인함`으로 둡니다. 프로젝트 A·저장한 상태·메모에 쓴 단어로 필터를 적용해 **실제 자동 복구 질문 문장**을 찾습니다. 조건을 지우면 첫 검수 기준 질문도 다시 보여야 합니다. 인용이 없으면 근거를 억지로 연결하지 않습니다.
3. 같은 대화의 현재 프로젝트를 B로 바꾸되 질문을 전송하지 않습니다. A에서 받은 답변은 확인 목록의 A 필터에 남아야 합니다. 목록은 대화의 현재 설정이 아니라 **각 답변을 만들 당시의 범위**로 분류합니다. 확인 후 대화 범위를 A로 돌립니다.
4. 메모와 상태는 각 답변에 대한 개인 판단입니다. 회사의 게시 승인이나 위키 게시 상태로 취급하지 않습니다.
5. **19장**에서 자동 복구 답변의 메모로 개발한 연결 기능을 확인합니다. 기존 **답변에 의견 남기기**를 열어 질문·실제 답변 요약·확인 요청을 적습니다. 검토자는 개인 대화 전체를 자동으로 볼 수 없습니다. 기준을 찾지 못했다면 별도 기준 문서가 있는지, 기준을 찾았다면 그 적용 범위가 맞는지 확인을 요청할 수 있습니다. 예시와 답변이 다르면 실제 내용에 맞춰 씁니다.
6. **답변 평가**도 직접 고릅니다. 기준이 없다고 올바르게 답했다면 `도움이 되었어요`, 값을 지어내거나 근거를 잘못 적용했다면 `내용이나 근거 수정이 필요해요`를 선택합니다. 개발한 취소 버튼으로 미전송을 확인한 뒤 다시 열어 한 번 보냅니다. `의견이 접수되었습니다 · 수정하기`로 내용을 보완해 같은 의견이 갱신되는지도 확인합니다.
7. **20장**에서 프로젝트 A를 고르고 상태·메모 검색을 지워 두 답변의 질문 문장으로 확인 기록을 찾습니다. `reviewer`의 **검토함**에서는 앞서 보낸 최종 의견을 확인합니다. 개인 대화를 열지 않아도 요청 내용을 이해할 수 있어야 하며 개인 메모 전체가 공유되면 안 됩니다. 끝나면 `writer`로 돌아옵니다.

여기서는 별도 위키 초안을 만들거나 게시하지 않습니다. 다음 실습은 미리 준비한 게시 위키 두 개를 사용합니다.

## 두 위키를 비교하고 원문을 읽은 뒤 돌아오기

상단 **지식 그래프 → 필터**에서 `가상 교통관제 자료`, `프로젝트 A · 가람시 + 공통`을 고릅니다. **필터 닫고 보기 → 위키 목록**에서 두 게시 위키를 찾습니다. 기존 화면에는 문서 미리보기가 있고, 비교 목록과 나란히 보기는 이번에 만들 기능입니다.

1. **23장**에서 두 게시 위키를 하나씩 열어 확인합니다. **24장** 기능을 만든 뒤 `프로젝트 A 검수 업무 절차`와 `프로젝트 A의 범위와 검수 기준`을 비교 목록에 담습니다. 중복·빼기·비우기를 확인한 뒤 같은 두 위키를 다시 담습니다. 세 번째 게시 위키가 있다면 최대 두 개 제한도 확인하고, 없으면 그 검사는 미확인으로 남깁니다.
2. **25장** 기능을 만든 뒤 제목·프로젝트·현재 게시 버전·본문·근거를 나란히 읽습니다. **24~26장의 목록은 아직 계정별 DB 저장 전**입니다. 개발 중 화면이 새로 열려 목록이 비면 같은 두 위키를 다시 담습니다. 다른 초안이 이미 있을 때만 게시본과 구분하는 검사를 추가합니다.
3. **26장** 기능을 만든 뒤 현재 필터·검색어·중심 위키·읽던 쪽을 적고 원문 문단을 엽니다. 돌아오면 같은 두 위키와 탐색 조건이 남아 있어야 합니다. 자료실에서 연 원문도 자료실로 돌아가는지 확인합니다. 근거가 연결된 실무 기록이 없으면 해당 경로 검사는 미확인으로 두고, 마지막에는 그래프의 두 위키로 돌아옵니다.
4. **27장**에서는 담기·빼기·비우기와 DB 저장을 연결합니다. `writer`로 두 위키를 직접 담아 저장 성공을 확인한 뒤 새로고침합니다. 같은 서버·작업공간에 다른 브라우저로 같은 계정으로 로그인해 두 위키가 남는지 확인합니다. 본문은 현재 게시본을 불러오고 게시본 변경·접근 제한을 안내해야 합니다.
5. `reader`로 바꿔 개인 목록이 분리되는지 확인합니다. 읽을 수 있는 위키 하나로 자신의 목록을 구성해 새로고침한 뒤 `writer`로 돌아오면 원래 두 위키가 남아야 합니다. **28장**은 이 결과를 재사용합니다. 두 문서의 차이와 남은 질문은 내 메모장에 적으며 앱의 비교 메모 기능을 새로 만들지는 않습니다.

그래프에서 원문으로 들어온 경우에만 그래프로 돌아갑니다. 자료실 검색·실무 기록에서 원문을 열었을 때의 기존 복귀 기능도 유지되는지 각각 확인하세요.

비교 목록에 담는다고 그래프 관계선이 새로 생기는 것은 아닙니다. 실제 본문 링크와 원문 근거, 계산된 관련성은 구분해서 설명합니다.

## 개인 개발본을 남기고 통합본 확인하기

강사가 제공한 다음 값을 사용합니다. 값이 준비되지 않았다면 임의의 주소·커밋·DB로 대신하지 않습니다.

| 받을 값 | 쓰는 곳 |
| --- | --- |
| 강사 기준 저장소 주소 | `upstream` 연결 확인. `origin`은 내 fork |
| 대표 브랜치와 기준 커밋 | 질문 모음·답변 확인·위키 비교가 포함된 시작 버전 |
| 질문 고정하기 추가 변경 커밋 | 모두 함께 합칠 고정·해제·상단 정렬과 DB 변경 |
| 최종 비교 기준 | 강사가 확인한 최종 코드·DB 변경 목록. 내 실제 통합 커밋과 구분해 기록 |
| 별도 작업 사본 경로 | 내 개발본을 보존하면서 통합 작업할 위치 |
| 실행 주소·포트·전용 개발 DB | 내 통합 사본의 실행 위치와 DB. 비밀번호를 작업 기록에 쓰지 않음 |
| 통합용 자료·계정 | 채팅에 사용할 공개 원문·비교할 두 게시 위키·역할 계정과 모델 연결. 개인 DB의 자료가 자동 이동하지 않음 |

대표 구현에는 2~4회차 누적 기능과 이번 질문 모음·답변 확인·위키 비교가 포함돼 있어야 합니다. **질문 고정하기는 강사가 사전에 시험해 제공하는 통합 연습 변경**이며 앞에서 빠뜨린 개발 과제가 아닙니다. 교육생마다 전용 DB를 사용하고, 같은 계정 이름으로 한 DB를 공동 수정하지 않습니다.

1. 개발용 AI가 내 변경 파일·브랜치·DB 변경·원격 연결을 조사하고 계획을 제시하게 합니다. 보관할 파일을 확인한 뒤 개인 작업을 별도 브랜치의 커밋으로 남깁니다. 환경 파일과 개인 자료는 포함하지 않습니다.
2. 기준 저장소의 변경을 받아 별도 작업 사본과 브랜치에서 대표 구현을 엽니다. `fetch`는 변경을 받아 확인하는 단계이고, 병합은 내 작업에 반영하는 단계입니다.
3. **34장**에서 별도 통합 앱의 작성 계정으로 `A 검수 기준`·`B 검수 기준`을 직접 저장합니다. `A 검수 기준`을 전송해 실제 답변을 받고 읽은 근거와 메모·상태를 저장합니다. 실제 답변 요약과 적용 범위 확인 요청을 의견으로 한 번 보내고, 그래프에 두 위키를 담습니다. 질문 순서·대화 주소·메모 내용·비교 위키 제목을 내 메모장에 적어 둡니다. 같은 통합 DB에 이미 있으면 사용합니다. 이후 추가 변경 전후에 **같은 기록이 남는지** 대조하며 개인 개발본의 기록은 저절로 옮겨지지 않습니다.
4. Claude Code에서도 별도 통합 사본 폴더를 엽니다. 새 대화에 폴더·브랜치·시작 커밋·추가 커밋·최종 기준·실행 주소·DB 식별 정보를 전달합니다. **35장 이후 요청은 이 대화**에서 진행합니다. 질문 고정 변경을 합치기 전에 이 환경이 맞는지 확인하고, 충돌 해결과 DB 변경 적용도 지정된 통합 개발 DB에서만 진행합니다.
5. 강사가 제공한 최종 기준의 코드 내용과 DB 변경 목록을 대조합니다. 병합 방식에 따라 내 실제 커밋 번호는 다를 수 있으므로 두 번호를 각각 적고 강제로 초기화하지 않습니다. 아래쪽에 있던 질문을 고정해 위로 올라오는지, 새로고침 뒤에도 유지되는지, 해제하면 원래 정렬로 돌아오는지 봅니다. 추가 변경 전에 남긴 A 답변·근거·메모·두 비교 대상도 다시 엽니다. 질문을 다시 보내거나 새 기록을 만들어 기존 기록의 보존 확인을 대신하지 않습니다. 필요한 기록을 추가 변경 후에 만들었다면 보존 검사는 미확인으로 남깁니다.
6. **36장**에서 앞 장의 작성 계정 확인 결과를 사용하고, 검토 계정으로 변경 전에 보낸 최종 의견을 확인합니다. 열람 계정은 공개 자료와 게시 위키를 읽고 자신의 비교 목록에 위키 하나를 담아 봅니다. 다시 작성 계정으로 돌아옵니다. 직접 누른 계정·메뉴·결과를 Claude Code에 알려 `docs/practice/week-05-integration.md`에 저장하게 합니다. 코드가 같다는 이유만으로 실제 동작을 통과 처리하지 않습니다.
7. **37~39장**에서는 이 결과 파일을 읽습니다. 실제 환경·커밋·DB 적용·직접 확인·실패·미확인·다음 조치가 적혀 있는지 확인하고, 다음 회차도 같은 통합 폴더·앱·파일에서 이어갑니다.

통합 개발본 확인과 회사 운영 배포는 별도입니다. 이 단계에서는 운영 DB 초기화나 원격 강제 반영을 하지 않습니다.
