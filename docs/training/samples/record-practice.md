# 기록 개발 실습 사례

3회차에서 개발할 **유형별 안내·개인 초안·근거 연결·내 확인할 일**을 비교하는 입력 예제입니다. [3회차 워크북](../weeks/03-domain.md)과 함께 사용합니다.

기존 공개 원문은 [샘플 넣기](../sample-data.md)로 준비합니다. 이 페이지의 C1–C4는 아직 DB에 저장된 초안이 아닙니다. [사례 JSON](record-practice.json)은 입력 재료이며 기존 `db:seed-training`에 넣는 백업 파일이 아닙니다.

## 지금 읽을 부분과 나중에 쓸 부분

| 실습 단계 | 이 문서에서 사용할 부분 | 할 일 |
| --- | --- | --- |
| 7장 · 유형별 안내 계획 | 아래 작성 안내 표와 C1·C2 | 검수와 장애 대응에 어떤 작성 안내를 보여 줄지 정하기 |
| 21~26장 · 내 초안 저장·목록·수정·삭제 | C1·C2의 입력값 | 만든 화면에서 두 글을 따로 저장하고 수정하기 |
| 27~31장 · 초안 복사와 프로젝트별 보기 | C3·C4와 필요시 DB 준비 요청 | 프로젝트 B의 글 두 개를 더 저장하고 복사 → 프로젝트별 보기 순서로 모두 개발하기 |
| 35장 · 자료에서 시작 | 원문 연결 확인용 | 별도 연습 초안을 만들고 C1 원본·복사본은 유지하기 |
| 36~40장 · 근거·미리 보기·검토 요청 | C1 원본과 프로젝트 A의 두 문단 | 제출 완료 → 결과 보기로 검토 대기 기록 열기 |
| 41~46장 · 나란히 보기·확인 목록 | C3·C4 | 두 기능 모두 개발하고 C3 제출·C4 빈칸·계정별 접근 확인 |
| 47~60장 · 기록과 할 일 관리 | C1·C3의 결과 기록 | 세 가지 개인 할 일로 미완료 보기·프로젝트별 개수·계정별 분리 확인하기 |

7장에서 문서를 참조하는 목적은 **작성 안내를 설계하는 것**입니다. 아래 DB 준비 요청은 내 초안 저장·목록을 만든 뒤 사용합니다. 작성 안내와 예시를 읽는 것만으로 앱에 기록이 생기지는 않습니다.

## 업무 유형별 입력칸 작성 안내

현재 입력칸은 **상황 / 판단과 이유 / 결과 / 추가 확인할 내용**입니다. 앞의 세 칸은 기록 등록 시 필수이고, 추가 확인할 내용은 선택입니다. 이름과 필수 조건은 그대로 두고 아래 작성 안내와 예시를 각 칸 옆에 보여 줍니다. 내용을 자동으로 채우지는 않습니다.

검수·장애 대응을 고르는 **업무 유형은 이번에 새로 만들 항목**입니다. **작성 안내는 각 입력칸에 무엇을 적을지 알려주는 문구**입니다. 같은 도메인의 작성자가 함께 사용하며, 관리자가 수정·저장할 화면도 개발합니다.

8장에서는 유형 선택과 안내 표시·DB 설정 저장을 만듭니다. 9·10장에서는 관리 → 도메인의 수정 폼에 **업무 유형별 안내** 편집 영역을 추가합니다. 관리자가 안내를 저장하면 작성 창에서 불러옵니다. 14~18장에서는 모두 같은 관리 영역에 인수인계 유형 등록을 만든 뒤 숨기기·다시 사용을 이어 개발합니다.

| 입력칸 | 검수 | 장애 대응 |
| --- | --- | --- |
| 상황 | 무엇을 어느 기준으로 확인하려는가? | 어떤 화면에서 어떤 증상이 보였는가? |
| 판단과 이유 | 어떤 문서·수치·조건과 비교했는가? | 무엇을 먼저 확인했고 왜 그 순서였는가? |
| 결과 | 확인한 사실과 아직 시험하지 않은 것을 구분했는가? | 확인 뒤 달라진 점과 실제로 하지 않은 조치는 무엇인가? |
| 추가 확인할 내용 | 확인하지 못한 대상·범위·일정은 무엇인가? | 다시 같은 문제가 생기면 확인할 조건은 무엇인가? |

유형별 예시 문장은 아래 C1과 C2에서 골라 씁니다. 안내 편집 실습은 검수·장애 대응으로 진행합니다. 14~18장에서는 모두 인수인계를 등록해 기록을 저장하고, 그 유형을 숨겼다가 다시 사용하게 만듭니다. 마칠 때 인수인계·검수·장애 대응을 모두 선택할 수 있게 둡니다.

## 네 가지 입력 사례

모두 가상 교육 사례입니다. 문서를 읽어 확인한 사실과 가정한 업무 상황을 구분합니다. 실제 회사에서 점검이나 담당자 확인을 마친 기록으로 사용하지 않습니다.

### C1 · 검수 범위 확인

- **제목:** [가상 실습 C1] 프로젝트 A 검수 범위 확인
- **범위·유형:** 가상 교통관제 자료 / 프로젝트 A · 가람시 / 검수
- **상황:** 검수 준비를 위해 프로젝트 A 검수 조건과 사업 개요를 읽었다.
- **판단과 이유:** 사업 전체 대상과 검수 표본이 같은 범위인지 확인하려고 두 문서를 비교했다.
- **결과:** 사업 개요의 도로전광표지는 24대, 검수 조건의 교육용 표본은 3대다. 실제 장비 시험은 하지 않았다.
- **추가 확인할 내용:** 표본 장비 번호와 검수 일정 담당을 확인해야 한다. 두 원문만으로는 확인하지 못했다.
- **붙일 근거:** [사업 개요](01-project-a.md)의 ‘도로전광표지 24대’ 문단, [검수 조건](03-acceptance-v1.md)의 ‘교육용 표본 장비 3대’ 문단.
- **내 확인할 일 예:** ‘표본 장비 번호 확인’, ‘검수 일정 담당 확인’. 기록을 제출한 뒤 내가 선택해 별도로 등록합니다.

### C2 · 조회 조건 확인

- **제목:** [가상 실습 C2] 프로젝트 A 조회 조건 확인
- **범위·유형:** 가상 교통관제 자료 / 프로젝트 A · 가람시 / 장애 대응
- **상황:** 이력 목록이 비어 보인다는 가상 문의를 받고 확인 순서를 준비했다.
- **판단과 이유:** 기존 날짜 필터 경험 기록을 참고해 날짜·프로젝트·권한부터 확인하기로 했다.
- **결과:** 아직 문의 화면을 확인하지 않았다. 날짜 필터가 이번 문의의 원인이라고 결론 내리지 않았다.
- **추가 확인할 내용:** 문의한 화면의 조회 기간과 선택 프로젝트를 확인한다.
- **근거 사용:** 처음에는 근거 없는 초안으로 둡니다. [기존 경험 입력 메모](06-experience.md)는 참고 자료이며 새로 업로드하지 않습니다. 나중에 근거로 붙일 때는 앱의 공개된 기록에서 실제 문단을 선택합니다.
- **용도:** C1을 수정해도 이 글은 바뀌지 않는지 확인합니다.

### C3 · 사업별 조건 구분

- **제목:** [가상 실습 C3] 프로젝트 B 사업별 조건 구분
- **범위·유형:** 가상 교통관제 자료 / 프로젝트 B · 누리시 / 검수
- **상황:** 프로젝트 B의 상태 조회 조건을 검수 준비에 사용하려고 읽었다.
- **판단과 이유:** 같은 도메인의 프로젝트 A 조건과 섞지 않도록 프로젝트 이름과 문서를 함께 확인했다.
- **결과:** 프로젝트 B 문서의 도로전광표지는 12대, 갱신 주기는 120초 이내, 이력 보관은 30일이다. 실제 성능 시험은 하지 않았다.
- **추가 확인할 내용:** 실제 검수에서 사용할 장비와 확인 순서를 담당자와 정해야 한다.
- **붙일 근거:** [프로젝트 B 조건](05-project-b.md)의 승인된 조건·적용 범위 본문 두 문단. 나란히 보기에서 수치와 적용 프로젝트를 번갈아 비교합니다. 제목만 있는 문단이나 프로젝트 A 전용 문단을 고르지 않습니다.
- **용도:** 프로젝트별 초안 분류, 다른 범위의 근거 차단, 다른 프로젝트의 확인할 일에 사용합니다.

### C4 · 조회 문의 확인 대기

- **제목:** [가상 실습 C4] 프로젝트 B 조회 문의 확인 대기
- **범위·유형:** 가상 교통관제 자료 / 프로젝트 B · 누리시 / 장애 대응
- **상황:** 프로젝트 B의 조회 문의에 대응하기 위해 확인할 사항을 정리 중이다.
- **판단과 이유:** 비워 둡니다.
- **결과:** 비워 둡니다.
- **추가 확인할 내용:** 문의 화면과 조회 조건을 아직 받지 못했다.
- **근거:** 선택하지 않습니다.
- **용도:** 본문이 덜 써져도 초안은 저장되는지 확인합니다. 검토 요청 때는 기존 필수값 안내가 나와야 합니다. 빈칸을 채우지 않은 채 제출을 성공 처리하지 않습니다.

## 여러 사례를 개발용 DB에 준비하기

2교시의 **내 초안 저장·목록**을 만든 뒤 사용합니다. 처음 두 사례는 화면에서 저장해 기능을 확인하세요. 반복 입력은 아래 요청으로 줄일 수 있습니다. 이미 저장한 글은 그대로 두고 아직 없는 사례만 추가합니다.

**먼저 계획 요청 — 같은 프로젝트의 Claude Code**

```text
docs/training/samples/record-practice.json의 C1–C4를 지금 만든 내 초안에 준비하려고 해. JSON은 입력 예제이며 DB 백업이 아니야. 내가 사용할 개발용 작업공간·도메인·프로젝트와 작성 계정을 확인해. 비밀번호는 출력하지 마.

현재 초안 저장 기능을 이용해 사례별 ID와 내 계정을 연결하고 이미 준비한 사례는 건너뛰는 방법을 계획해. 실제 DB 구조에 맞춰 필요한 값을 매핑해. 근거 후보는 아직 선택된 근거가 아니며 없는 문단 ID를 만들지 마. 기존 자료와 수정한 초안은 유지하고 검토 요청·공개 승인은 실행하지 마.

코드와 DB는 아직 바꾸지 마. 내가 대상과 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**대상과 계정을 확인한 뒤 실행**

```text
확인한 개발용 환경과 내 작성 계정에만 사례 초안을 준비해. 현재 초안 저장 기능을 사용하고 각 사례의 입력값·유형·프로젝트를 매핑해. C4의 빈칸은 그대로 둬. 문단은 임의로 연결하지 말고 내가 화면에서 선택하게 해.

사례 ID와 내 계정으로 중복을 구분하고 이미 있는 사례는 덮어쓰지 마. 다시 실행해도 중복이 생기지 않게 해. 기존 자료나 다른 사람의 초안을 삭제하지 마. 추가·건너뜀·실패를 나눠 알려 줘. 검토 요청과 공개 승인은 실행하지 마.
```

현재 계정이나 대상 프로젝트가 불분명하면 먼저 확인합니다. 사례 준비가 어려우면 네 입력 예제를 화면에서 직접 저장해도 됩니다. 준비 기능 자체는 수업의 기본 개발 과제가 아닙니다.

## 만든 기능을 비교하는 순서

| 먼저 준비할 상태 | 직접 해 볼 일 | 기대 결과 |
| --- | --- | --- |
| C1·C2 두 초안 | C1만 수정하고 C2 열기 | C2는 그대로 |
| C1–C4 네 초안 | 프로젝트 A·프로젝트 B로 나누어 보기 | 이 네 사례만 비교하면 프로젝트 A 2건·프로젝트 B 2건. 다른 초안이 있으면 합산해 확인 |
| C4의 본문 빈칸 | 초안 저장 후 검토 요청 시도 | 초안 저장 가능, 제출은 기존 필수값 안내 |
| C1과 C3의 서로 다른 범위 | 근거 문단 선택 | 프로젝트 A 전용 근거가 프로젝트 B 기록에 섞이지 않음 |
| 원문에서 시작한 ‘원문 연결 확인용’ 초안 | 새 초안 저장 뒤 C1·C2 확인 | 연습 초안이 따로 저장되고 기존 두 초안 유지. 이후 C1으로 돌아가기 |
| 근거를 붙이고 네 입력값을 채운 C1 원본 | 검토 요청 후 제출 완료 → 결과 보기 다시 열기 | 한 기록과 같은 결과 링크, 검토 대기 유지. 서버 재요청은 AI 검사로 확인 |
| 나란히 보기·확인 목록과 아직 초안인 C3·C4 | C3 비교·확인·수정·재확인·제출, C4에서 필수값 안내 | C3는 검토 대기, 확인 목록을 체크해도 C4는 미완성 초안 유지 |
| C1에 프로젝트 A 두 개, C3에 프로젝트 B 한 개의 개인 할 일 | 프로젝트 A의 할 일 하나 완료 → 미완료로 되돌리기 | 프로젝트 A 개수 2·2·0 → 2·1·1 → 2·2·0, 프로젝트 B는 1·1·0 유지 |
| 기존 공개 경험 기록 | 즐겨찾기 폴더에 넣기 | 기존 2회차 폴더·개인 메모·읽음 유지 |

실습 중 복사·삭제·제출을 했다면 초안 수가 달라집니다. ‘항상 네 건’으로 맞추지 말고 내가 수행한 변경과 비교하세요. 3교시가 끝나면 C1·C3는 검토 대기 기록, C2·C4는 초안으로 남습니다. ‘원문 연결 확인용’은 새 진입 기능을 시험한 별도 초안입니다.

4교시는 제출한 C1에 **표본 장비 번호 확인**, **검수 일정 담당 확인** 두 일을, C3에 **검수 장비·순서 확인** 한 일을 등록합니다. 첫 제목을 **표본 장비 번호 3개 확인**으로 수정한 뒤 같은 세 가지 일을 계속 사용합니다. 모두 미완료 보기 → 프로젝트별 개수를 개발하며 숫자는 전체·미완료·완료 순서입니다. 프로젝트 A·프로젝트 B의 실제 다른 할 일이 있다면 합산해 확인합니다. 마지막에는 관리자 확인용 항목을 관리자 계정으로 등록해 사용자 목록·집계에 섞이지 않는지 확인하고 삭제합니다. 사용자 세 가지 일은 모두 미완료로 남깁니다. 완료 표시는 가상 기능 검사입니다. 실제 담당자에게 연락하거나 회사 업무의 확인이 끝났다고 보고하지 않습니다.

3교시는 2교시에서 저장한 C1·C3를 열어 시작합니다. 같은 일반 사용자 계정으로 C1 원본의 제출 흐름을 먼저 완성하고, 아직 작성 중인 C3로 비교·확인 기능을 보강합니다. 새 기능은 모든 실무 기록에 공통으로 적용합니다. C4에서 근거 없음 안내를 확인한 뒤에는 C3로 돌아옵니다. 관리자 확인 전에 C1·C3 결과 주소를 복사해 둡니다. C1 복사본과 원문 연결 확인용은 제출하지 않습니다. 내 초안의 제출 완료 영역에서 C1·C3의 결과 보기를 열 수 있어야 합니다. 관리자 계정은 제출된 결과 기록을 읽을 수 있지만 타인의 개인 초안 목록·본문을 열 수 없게 개발합니다. 현재 관리자는 검토 권한도 포함하며 본인 등록 버전의 승인은 금지됩니다. 이번 실습에서는 승인·반려를 실행하지 않습니다.
