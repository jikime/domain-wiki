# 실제 사용에 맞게 안정화하기

통합한 위키의 실패 안내·자료 개정·저장 동기화·운영 안내를 실제 사용 조건에 맞게 보완합니다.

[강의 화면](/lectures/week-06.html) · [회사 개발 노트](../company-project.md)

**시작할 상태:** 통합본과 확인 기록을 엽니다. 공용 환경이 준비되지 않았으면 같은 통합 개발 환경에서 확인하고 공용 적용과 구분합니다.

**남길 결과:** 입력을 보존하는 실패·재시도 안내 / 기존 근거를 보존하는 개정본 확인 연결 / 다시 접속·다른 탭의 저장 확인과 운영 안내

개발 실습은 **계획 요청 → 내가 확인·수정 → 실행 요청 → 직접 확인** 순서입니다. 계획과 실행을 한꺼번에 보내지 않습니다. 이미 합의한 범위는 이어 개발하고, 새 기능이나 저장·권한 변경은 계획부터 확인합니다. 자료 등록·위키 채팅·운영 기록은 안내에 표시된 곳에서 수행합니다.

## 1. 실패해도 작업을 이어 갈 수 있게 만들기

[함께 볼 강의 화면](/lectures/week-06.html#slide-04)

1. 실제 오류 또는 안내가 부족한 상황을 고르고 원인·수정 계획을 확인하세요.
2. 안내·입력 보존·재시도를 구현하고 실패 조건과 정상 조건을 나눠 확인하세요.
3. 중복 클릭·취소·다시 시도를 확인하고 바꾼 버전과 결과를 남기세요.

**내가 정할 것:** 저장 실패 안내를 본 뒤 입력을 유지하고 다시 시도

**저장 기준:** 수정에 DB 변경이 필요하면 별도 이유·적용 계획부터 확인합니다. 초기화로 문제를 숨기지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
[화면]에서 [순서]로 하면 [기대 결과] 대신 [실제 결과]가 나와. 원인을 조사하고 최소 수정 계획을 알려 줘. 발견한 오류가 없으면 저장 실패·결과 없음·권한 없음의 현재 안내를 조사해 부족한 부분을 계획해. 실제 DB를 끄거나 기존 데이터를 지우며 시험하지 마.

코드와 DB는 아직 바꾸지 마. 내가 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**계획을 읽고 내가 확인할 것**

- **어떻게 재현하나요?** 같은 계정·입력·순서 사용
- **실패하면 무엇이 남나요?** 작성한 입력과 다시 시도 방법
- **무엇은 유지하나요?** 기존 데이터·권한·정상 저장

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 원인과 수정 계획대로 [문제]를 고쳐. 실패를 성공으로 표시하지 말고 입력을 남겨 줘. 다시 시도 중 중복 저장을 막고 성공 후 실제 저장한 값을 보여 줘. 오류가 없던 정상 입력도 검사해. 실패 응답은 통제된 검사로 확인하고 공용 서비스나 DB를 중단하지 마.
```

**확인:** 실패 이유와 다음 행동을 화면에서 알 수 있습니다. 실패 후에도 입력이 남고 성공 때만 완료로 표시합니다. 정상 동작과 기존 기록을 유지합니다.

**기본을 마쳤다면 — 선택 과제**

- **내 업무로 확장하기:** 다른 프로젝트·입력으로 사용하고 필요한 개선 하나의 계획을 세워 이어 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

## 2. 자료 개정 사실을 확인하고 근거 유지하기

[함께 볼 강의 화면](/lectures/week-06.html#slide-08)

1. 검수 조건 v2를 기존 자료의 새 버전으로 등록하고 배정된 별도 검토 담당의 공개를 받으세요.
2. 새 버전 안내 계획을 확인해 구현하고 이전 버전 링크·메모가 남는지 확인하세요.
3. 관련 위키를 갱신해 별도 게시 검토를 받고 같은 질문의 기준·근거를 확인하세요.

**내가 정할 것:** 검수 조건 v1의 60초와 v2의 30초 비교

**저장 기준:** 기존 자료·버전 DB를 활용합니다. 읽음 표시를 새 버전까지 자동으로 이어 붙이지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
즐겨찾기한 자료에 새 공개 버전이 생기면 알고 싶어. 현재 버전 정보와 권한을 조사하고 목록에 ‘새 공개 버전 있음’ 안내와 새 버전 열기를 더할 계획을 세워. 기존 즐겨찾기 링크·메모·읽음과 게시 위키 근거는 자동으로 바꾸지 않을 거야.

코드와 DB는 아직 바꾸지 마. 내가 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**계획을 읽고 내가 확인할 것**

- **어떤 버전인가요?** 열람 가능한 새 공개 버전만
- **무엇을 보존하나요?** 저장했던 버전·문단·메모·읽음
- **무엇을 다시 확인하나요?** 갱신 주기와 위키·답변의 근거

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 새 공개 버전 안내와 별도 링크를 연결해. 기존 버전 제목 링크와 메모·읽음을 바꾸지 마. 비공개 개정본은 노출하지 말고 현재 권한을 서버에서 확인해. 최신 버전은 기존 자료 DB에서 조회하고 필요한 변경만 개발용 DB에 적용해. 이전·새 버전 열기와 비공개 상태를 검사해.
```

**확인:** 열람 가능한 새 공개 버전을 구분해 엽니다. 기존 즐겨찾기와 위키 근거를 자동으로 덮어쓰지 않습니다. 60초→30초 변경과 보관 90일 유지를 근거로 확인합니다.

**기본을 마쳤다면 — 선택 과제**

- **내 업무로 확장하기:** 다른 프로젝트·입력으로 사용하고 필요한 개선 하나의 계획을 세워 이어 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

## 3. 다른 탭과 재접속에서도 저장 내용 맞추기

[함께 볼 강의 화면](/lectures/week-06.html#slide-12)

1. 두 탭의 변경 순서와 기대 결과를 정하고 현재 조회 방식을 확인하세요.
2. 다시 조회·저장 상태·개수 갱신에서 부족한 연결을 구현하세요.
3. 동시 수정이 덮이는지 확인하고 필요하면 충돌 안내의 계획을 세워 보완하세요.

**내가 정할 것:** 한 탭에서 읽음으로 바꾼 뒤 다른 탭의 홈 개수 확인

**저장 기준:** 서버 DB를 기준으로 조회합니다. 캐시·조회 갱신과 DB 구조 변경을 구분합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
같은 계정으로 두 탭에서 폴더·메모·읽음을 사용하려고 해. 한쪽에서 바꾼 뒤 다른 쪽으로 돌아올 때 DB 값을 언제 다시 읽는지 조사해. 오래된 화면 숫자와 저장 실패를 보완할 계획을 세워. 실시간 동기화부터 새로 만들지는 마.

코드와 DB는 아직 바꾸지 마. 내가 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**계획을 읽고 내가 확인할 것**

- **언제 다시 읽나요?** 목록 이동·재접속·필요한 새로고침
- **무엇이 맞아야 하나요?** DB 값·목록·홈 개수
- **충돌은 어떻게 보나요?** 두 탭의 다른 수정이 덮이는지

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 목록 이동·재접속에서 현재 서버 값을 다시 조회해. 읽음·자료 이동 후 목록과 홈 개수를 갱신하고 저장 실패 시 성공 표시를 남기지 마. 다른 계정·도메인으로 바꾸면 이전 개인 기록을 보여 주지 마. 두 탭과 다른 브라우저에서 검사해.
```

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 선택 과제는 기본 기능 뒤에 진행합니다.

### 선택 과제 · 같은 메모의 수정 충돌 안내하기

**먼저 계획 요청**

```text
두 탭에서 같은 메모를 수정할 때 나중 저장이 앞선 변경을 덮는지 확인했어. 필요하면 기존 수정 시각·버전으로 충돌을 알리고 입력을 남기는 방법을 계획해. 테이블 항목 추가가 필요한지도 이유와 적용 순서를 알려 줘.

코드와 DB는 아직 바꾸지 마. 내가 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**내가 확인할 것**

- 다른 탭에서 바뀐 글을 조용히 덮어쓰지 않나요?
- 충돌 때 내 입력을 보존하고 최신 내용을 확인할 수 있나요?

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 이번 기능을 구현해.

확인한 충돌 처리 계획을 구현해. 필요한 DB 변경을 개발용 DB에 적용하고 서버에서 수정 기준을 비교해. 충돌 시 입력을 남기고 최신 글을 확인하도록 안내해. 정상 저장과 두 탭의 충돌을 검사해.
```

**확인:** 이동·재접속 후 DB의 현재 값을 봅니다. 목록·홈 개수와 저장 성공·실패 표시가 일치합니다. 다른 계정으로 바꾸면 이전 개인 내용이 남지 않습니다.

**기본을 마쳤다면 — 선택 과제**

- **내 업무로 확장하기:** 다른 프로젝트·입력으로 사용하고 필요한 개선 하나의 계획을 세워 이어 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

## 4. 운영 안내를 실제 화면에 연결하기

[함께 볼 강의 화면](/lectures/week-06.html#slide-16)

1. 안내가 필요한 상태와 실제 문의 담당·위치를 정하고 계획을 확인하세요.
2. 현재 상태에서 안내와 허용된 다음 화면을 연결하세요.
3. 배정된 역할별 계정으로 직접 따라가 보고 운영 메모와 화면을 맞추세요.

**내가 정할 것:** 공개 대기 안내에서 배정된 검토 담당과 확인 위치 찾기

**저장 기준:** 실제 회사 담당과 위치를 먼저 정합니다. 설정 저장이 필요한 경우에만 기존 DB를 확장합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
직원이 자료 공개 대기나 AI 응답 실패를 만났을 때 어디로 가야 할지 알게 하고 싶어. 기존 상태·검토함·운영 안내를 조사해서 회사 담당과 다음 행동을 연결하는 계획을 세워. 관리자용 오류 상세나 비밀번호는 일반 화면에 보여 주지 마.

코드와 DB는 아직 바꾸지 마. 내가 계획을 확인하고 실행을 요청할 때까지 기다려.
```

**계획을 읽고 내가 확인할 것**

- **무슨 상황인가요?** 공개 대기·처리 실패·AI 미연결
- **어디로 안내하나요?** 역할에 맞는 화면과 실제 담당
- **무엇을 숨기나요?** 비밀번호·키·관리자 오류 상세

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 [상태] 안내에 해야 할 일과 문의 위치를 연결해. 기존 권한과 상태 판단은 유지하고 일반 이용자에게 관리자용 상세 오류를 보여 주지 마. 회사 안내를 저장해야 하면 기존 설정을 활용하고 필요한 DB 변경만 개발용 DB에 적용해. 역할별 링크와 실제 상태를 검사해.
```

**확인:** 상태별 다음 행동과 실제 문의 위치를 알 수 있습니다. 역할에 맞는 화면만 열리고 기존 검토 규칙을 지킵니다. 운영 메모와 실제 화면이 일치합니다.
