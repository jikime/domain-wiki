## 1. 이번 시간의 목표와 준비

증상을 재현하고 원인 가설을 확인한 뒤 수정과 재검증을 기록합니다. 코드 오류와 자료·공개 상태 문제를 구분합니다. 준비물은 5주차 변경 상태, 오류 기록 T6, [문제 해결 안내](../troubleshooting.md), 강사가 배포할 검수 조건 v2입니다.

공통 필수 실습은 **미공개 자료 진단**과 **원문 개정 영향 확인**입니다. 작업자 중단·Tavily 연결·API/CLI 연결 진단은 강사 시연 또는 빠른 팀의 선택 실습입니다. 선택 사례는 하나만 골라 기존 시간 안에서 다룹니다. 실제 공용 환경의 설정이나 다른 사람의 프로세스를 멈추지 않습니다.

## 3. 핵심 설명

**증상과 원인.** ‘검색 결과가 없다’는 관찰입니다. ‘DB가 깨졌다’는 가설입니다. 가설을 사실처럼 쓰지 않고 공개 상태·범위·원문·로그를 순서대로 확인합니다.

**로그와 상태 코드.** 화면 오류, 브라우저 요청 결과, 서버 로그, 작업자 로그는 서로 다른 위치의 증거입니다. 401은 로그인, 403은 권한, 409는 상태 충돌, 429는 요청 한도, 5xx는 서버·외부 서비스 문제의 단서입니다. 번호만으로 원인을 확정하지 않고 실제 메시지와 발생 경로를 봅니다.

**작업 큐와 비동기.** 업로드를 받는 요청과 파일을 읽는 작업은 시간과 프로세스가 나뉩니다. 화면 접속이 된다는 사실만으로 추출·색인·AI 작업이 정상이라고 판단하지 않습니다.

**모델 연결 오류.** API의 주소·키 문제, CLI 실행 파일·운영 계정 로그인 문제, 제공사의 이용 한도, 대기·실행 시간 초과를 구분합니다. CLI 동시 실행 수는 웹 서버와 작업자 각각의 프로세스에 적용되고 대기 시간도 제한에 포함됩니다. CLI 실패 시 API를 자동 호출하지 않으므로 오류가 났다는 이유로 다른 계정이나 연결로 임의 전환하지 않습니다.

**개정과 영향.** 새 원본을 올리는 것과 공개 승인은 다릅니다. 새 버전이 공개되면 구버전 근거에 의존하던 위키·답변의 유효성에 영향이 생길 수 있습니다. 코드 커밋을 되돌린다고 공개 자료 버전까지 되돌아가지는 않습니다.

**회귀 확인.** 같은 코드에서 자료를 바꾸어 확인하는 개정 시험과, 같은 자료에서 코드를 바꾸어 확인하는 개발 시험을 나누어 기록합니다.

## 4. 실습 A · 미공개 자료와 입력 오류 진단

1. 작성 계정으로 아래 내용의 새 MD 파일을 만듭니다. 제목 끝에 교육생 이름을 붙여 기존 자료와 구분합니다.

```markdown
# [가상 교육 자료] 진단용 기록
진단 식별어는 교육실습푸른별이다.
이 문서는 공개 상태를 비교하기 위한 예제이며 실제 업무 기준이 아니다.
```

2. 프로젝트 A에 참고 자료로 등록하고 처리 완료까지 기다리되 **아직 공개 승인하지 않습니다**.
3. 작성 계정의 관리 가능한 상세 화면과 일반 이용 계정의 검색을 비교합니다. 같은 ‘교육실습푸른별’ 입력으로 상태를 기록합니다.
4. 가설을 ‘자료 없음’, ‘미공개’, ‘범위 불일치’로 적고 각 가설의 증거를 확인합니다.
5. 다른 검토자가 원문을 확인하고 공개합니다. 같은 이용 계정·범위·검색어로 다시 확인합니다.
6. 진단 기록에 ‘코드를 수정하지 않고 공개 상태를 바로잡음’이라고 적습니다. 권한 검사를 삭제해 검색되게 만드는 것은 해결로 인정하지 않습니다.
7. 5주차 동의어 함수에 정상 입력과 경계 입력을 다시 실행합니다. 화면에서 한 글자 동의어가 거부되는지 확인하고 올바른 값으로 되돌립니다.
8. 새 기능이 기존 검증을 우회하지 않는다는 결과를 남깁니다.

예상 결과: 미공개 상태와 공개 후 상태의 차이를 재현하고, 입력 처리 성공과 서버 검증 거부가 함께 올바른 동작일 수 있음을 설명합니다.

## 5. 실습 B · 검수 조건 v2와 위키 영향

1. 현재 검수 조건 v1과 Q03 답변, 그 근거를 참조하는 ‘프로젝트 A 검수 조건’ 위키를 기록합니다.
2. 해당 원문 상세의 **새 원본 버전 등록**에서 강사가 제공한 v2를 등록합니다. 새 제목의 독립 자료로 올려 v1과 v2가 동시에 기준이 되게 하지 않습니다.
3. 처리 완료 후 원문을 비교합니다. 화면 갱신은 60초에서 30초로 바뀌고 이력 90일·표본 3대는 유지됩니다.
4. 공개 전에는 현재 승인본이 무엇인지 확인합니다. 다른 검토자가 v2를 승인합니다.
5. **개정·철회 영향 확인**에서 구버전 근거를 사용한 위키 등을 살펴봅니다. 일반 조회에서 숨겨지거나 새 근거 확인이 필요한 상태를 기록합니다.
6. 작성·검토 가능한 화면에서 위키의 새 버전을 작성하고 v2의 실제 문단을 연결합니다. 본문 숫자만 바꾸고 근거는 v1으로 남기지 않습니다.
7. 다른 검토자가 새 위키를 게시한 뒤 Q03·Q04·Q05·Q09를 확인합니다. Q03은 30초, 이력 90일·표본 3대·장애 복구 미정은 유지되어야 합니다.
8. T5에 ‘코드 동일, 자료 버전 변경’임을 표시합니다. 이 결과를 동의어 기능의 정확도 개선으로 계산하지 않습니다.

시간이 부족하면 새 원문 공개와 영향 확인까지 완료하고, 강사가 준비한 새 근거 연결 예로 나머지를 함께 확인합니다. 직접 수행한 범위와 시연으로 확인한 범위를 나누어 기록합니다.

## 6. 선택 진단

**작업자:** 개인 교육용 환경에서 실행 중인 작업이 없을 때 자신의 작업자만 종료하고 새 진단 자료를 등록합니다. 대기 상태를 본 뒤 작업자를 다시 실행합니다. 공유 환경에서는 실제 중단 대신 강사가 준비한 상태 설명을 사용합니다.

**Tavily:** 키 입력만으로 연결이 완성되지 않는 사례를 다룹니다. 제공자 목록, API 키 참조, 작업공간 ID, 환경 형식, 웹 서버·작업자의 설정 반영 순서를 확인합니다. 실제 키를 화면 공유하거나 출력하지 않습니다. 외부 검색을 사용하지 않는 교육생은 [문제 해결 안내](../troubleshooting.md)의 예제 설정을 읽고 확인 순서를 설명합니다.

**API·CLI:** 이용 조건을 확인한 개인 교육 환경에서만 실제 연결을 점검합니다. 그 외에는 강사가 제공하는 ‘실행 파일 없음’, ‘인증 확인 필요’, ‘한도 초과’ 오류 문구로 T6을 작성합니다. [연결 진단 순서](../troubleshooting.md#7-진단-예-e--apicli-모델-연결-실패)에 따라 현재 연결·모델, 서버 계정, 설치 경로, 시간·동시 실행 한도를 확인합니다. 연결 확인에 사용량이 발생하므로 같은 실패를 반복 호출하지 않습니다. 실패 분류와 다음 조치를 설명하면 선택 실습 결과로 인정하며, 실행하지 않은 연결을 성공으로 기록하지 않습니다.
