# 업무 결과물과 회사 설정 관리하기

요청 문서의 항목과 남은 질문을 관리하고, 회사 용어와 이용 안내를 직접 고칠 기능을 만듭니다. 확인한 변경은 앞서 만든 통합본에 이어 반영합니다.

[강의 화면](/lectures/week-06.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 5회차 통합 기준에서 개인 작업을 이어갑니다. 후속 단계 요청 문서를 별도 공개 자료로 준비하고, 작성·검토·관리·열람 계정을 구분합니다.

**남길 결과:** 버전별로 남는 RFP 항목 확인 / 질문별 답변·출처·보류와 재확인 / 도메인 용어 편집·검색 안내·메뉴별 도움말 / 추가 통합본과 역할별 확인·운영 준비 목록

개발·통합의 공통 단계를 **계획 요청 → 내가 확인·수정 → 실행 요청 → 직접 확인** 순서로 진행합니다. 요청 상자 하나는 한 번에 입력하고 계획과 실행은 따로 보냅니다. 코드와 DB 통합·결과 정리 활동을 모두 새 기능 개발로 세지는 않습니다.

## 먼저 준비할 것

- 5회차의 통합 기준에서 개인 작업을 이어갑니다. 작성 writer@wiki.local, 검토 reviewer@wiki.local, 관리 admin@wiki.local, 열람 reader@wiki.local을 같은 서버에서 사용합니다. 비밀번호는 배정받은 값을 사용합니다.
- 후속 요청 문서 new-rfp.md를 **별도 사업 자료**로 등록하고 추출·공개 검토를 마칩니다. 기존 검수 조건 v2의 새 버전으로 올리지 않습니다. 이미 준비한 파일을 중복 등록하지 않습니다.
- 기존 운영은 30초·90일, 후속 요청은 45초·180일입니다. 후속 요청은 현재 운영 기준을 대체하지 않습니다.
- [RFP·회사 설정 실습 사례](../samples/rfp-practice.md)의 여섯 분석 항목·회신·안내 문장을 사용합니다. 같은 입력은 슬라이드에도 있습니다.
- 추가 통합에는 강사가 제공한 이전·최종 기준 커밋, RFP·관리 변경 커밋, 별도 사본·개발 DB와 같은 사례의 자료·보고서가 필요합니다. 개인 개발 DB의 자료는 코드 병합으로 옮겨지지 않습니다.

## 시작 보고서 준비

수업 전에 아래 여섯 항목을 넣어 writer 소유로 저장한 시작 초안을 준비합니다. 이미 있으면 RFP 목록에서 열어 대조하고 누락만 보완합니다. 없을 때만 업무 도구 → RFP 분석 보고서 → 새 분석 작성에서 공개된 후속 단계 요청 문서를 선택합니다. ‘직접 작성·수정’에서 제목을 **[가상 실습] 프로젝트 A 후속 요청 분석**으로 적고 분석 항목 추가로 아래 여섯 개를 만듭니다. 항목마다 근거 문단 선택에서 해당 R 문단을 찾아 **이 문단 인용**을 누릅니다. ‘원문 구절’은 실제 원문 그대로 두고 해석은 ‘의미·적용 범위’에 적습니다.

**검토 전 초안 저장** 후 여섯 항목과 두 질문이 있는 상세 화면에서 개발을 시작합니다. 앱의 AI 분석 초안 만들기를 사용했다면 같은 여섯 항목으로 원문과 대조해 수정합니다. 이 회차의 공통 실습은 앱 AI 실행 성공에 의존하지 않습니다.

현재 캡처는 초기 검수 조건을 골라 기존 작성 양식을 확인한 화면입니다. 후속 요청과 새 상태·답변 기능이 구현된 결과로 소개하지 않습니다.

## 통합 환경에서 이어가기

강사가 제공한 코드 사본·실행 주소·전용 개발 DB를 확인합니다. 교육생마다 DB를 분리하고 그 안에서 작성·검토·관리·열람 역할을 바꿉니다. 공통 계정 이름이 같다고 한 DB를 함께 수정하지 않습니다. 기준 커밋과 내 실제 통합 커밋은 각각 기록하며, 코드 내용·DB 적용·자료 상태를 함께 대조합니다.

추가 통합용 DB는 이전 회신·보류 이력과 현재 질문이 연결된 연습 보고서, 용어·안내를 준비해야 합니다. 코드를 합친 뒤 개인 DB의 기록이 나타날 것으로 가정하지 않습니다. 빠진 교육용 입력은 강사가 정한 사례로 채우고 같은 보고서·회신을 중복 만들지 않습니다.

## 준비: RFP와 관리의 기존 기능 확인

대상 메뉴를 조사한 뒤 실제 화면과 맞춰 봅니다.

```text
지금 개발한 위키의 업무 도구 → RFP 분석 보고서와 관리 → 도메인 수정을 개선할 거야. RFP의 원문 선택·항목·근거·확인 질문·초안 저장·새 버전 수정·검토 경로와 핵심 용어 저장·동의어 검색을 확인해. 이미 있는 기능과 이번에 더할 상태·답변 기록·메뉴별 안내를 구분하고 내가 눌러 볼 순서를 알려 줘. 현재 없는 버튼이나 보고서를 가정하지 마. 코드와 DB는 아직 바꾸지 마.
```

**직접 확인:** 작성·검토·관리·열람 계정의 화면과 RFP 원문 준비 여부를 확인합니다.

## 1. RFP 항목 확인과 버전별 재확인

[함께 볼 강의 화면](/lectures/week-06.html#slide-04)

**앞에서 이어받을 것:** 후속 요청 공개 원문과 여섯 항목의 저장된 분석 초안

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 아래 전체 업무를 이어 해 보고 막힌 동작을 보완합니다.

**내가 정할 것:** 앞에서 만든 기능을 같은 보고서와 계정으로 이어 확인합니다.

**저장 기준:** 항목 상태는 보고서·버전·항목·처리자에 연결합니다. 새 버전은 미확인으로 시작합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
업무 도구의 RFP 분석 보고서 상세에 항목별 확인 상태와 메모를 더할 거야. 미확인·확인 중·확인 완료를 구분해. 보고서·버전·항목·처리자·시각에 연결해 DB에 저장할 계획을 세워. 기존 항목은 제목이나 배열 순서 대신 안정적인 식별자로 연결하고 작성·저장·수정 경로도 함께 확인해. 작성자와 현재 보고서 검토 권한자만 변경하고 일반 열람자에게 내부 메모를 보이지 않게 해. 항목 확인은 보고서 게시 승인이 아니야. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **확인의 뜻** 원문과 항목의 해석을 대조함
- **저장 관계** 보고서 버전·항목·처리자
- **역할** 작성자·검토 권한자만 변경

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
RFP 보고서 상세에 확인한 항목 상태·메모·처리자·시각을 만들어. 보고서 버전과 항목을 구분해 DB 저장하고 필요한 구조 변경 파일을 개발 DB에 적용해. 기존 항목에는 식별자를 안전하게 연결해. 저장·수정·취소와 실패 시 입력 보존을 연결하고 다른 보고서나 다른 항목의 상태가 섞이지 않게 해. 확인 완료로 바꿔도 기존 보고서의 초안·검토·게시 상태는 바꾸지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 후속 요청 보고서의 R1을 원문과 대조한 뒤 확인 완료, R2는 확인 중으로 저장합니다. 새로고침 후 두 상태와 메모가 따로 남는지 보세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · 상태 필터와 남은 개수 연결하기

**먼저 계획 요청**

```text
RFP 보고서 상세에서 항목의 확인 상태로 목록을 거르고 제목·의미로 검색할 거야. 상태 기록이 없는 기존 항목은 미확인으로 포함해. 현재 선택한 보고서 버전 안에서만 전체·미확인·확인 중·완료 개수를 계산하고 두 조건을 함께 적용하는 계획을 세워. 새 버전의 상태를 과거 버전에 섞지 마. 결과 없음과 항목 없음의 안내도 구분해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 범위: 지금 열어 둔 보고서 버전
- 미확인: 확인 기록이 없는 항목 포함
- 연결: 필터·목록·개수 함께 갱신

**계획을 확인한 뒤 실행**

```text
RFP 상세에 확인한 상태 필터·항목 검색·개수를 만들어. 목록과 개수는 같은 보고서 버전·권한을 따르고 상태를 바꾸면 바로 갱신해. 상태 기록이 없는 항목은 미확인으로 포함해. 검색 결과가 없으면 조건 지우기로 전체를 보게 하고 항목을 숨기려고 원래 보고서 내용을 삭제하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

### 다음 기능 · 근거를 읽고 같은 항목으로 돌아오기

## 2. 질문 답변과 후속 판단 관리

[함께 볼 강의 화면](/lectures/week-06.html#slide-19)

**앞에서 이어받을 것:** 새 보고서 버전의 R5·R6 질문

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 아래 전체 업무를 이어 해 보고 막힌 동작을 보완합니다.

**내가 정할 것:** 앞에서 만든 기능을 같은 보고서와 계정으로 이어 확인합니다.

**저장 기준:** 답변·출처·상태는 해당 보고서 버전의 질문에 저장합니다. 새 버전에는 이전 답변을 참고로 연결합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
RFP 보고서 상세의 기존 확인할 질문에 답변 기록을 붙일 거야. 질문마다 안정적인 식별자를 두고 보고서·버전·항목·질문과 연결해 확인 대기·답변 기록·보류 상태를 DB에 저장할 계획을 세워. 답변 내용·받은 경로·답변자 또는 문서명·기록자를 남겨. 현재 보고서 작성자와 검토 권한자만 변경해. 개인 채팅 메모나 보고서 승인 상태와는 분리해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **저장 대상** 이 보고서 버전의 이 질문
- **답변 출처** 받은 경로·답변자 또는 문서
- **주의** 답변 기록은 요구 확정이 아님

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text

```

**만든 뒤 직접 확인**

1. R5의 연계 범위 질문에 제공된 가상 회신을 기록합니다. R6의 전환 질문은 보류로 두고 사유와 다음 확인 내용을 남기세요.

**이어서 개발하기**

## 3. 회사 용어와 메뉴별 이용 안내

[함께 볼 강의 화면](/lectures/week-06.html#slide-32)

**앞에서 이어받을 것:** 같은 도메인의 기존 핵심 용어와 실제 검색 화면

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 아래 전체 업무를 이어 해 보고 막힌 동작을 보완합니다.

**내가 정할 것:** 앞에서 만든 기능을 같은 보고서와 계정으로 이어 확인합니다.

**저장 기준:** 용어는 기존 도메인 DB를 재사용합니다. 새 안내는 도메인·메뉴별로 저장하고 관리자만 수정합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
관리의 도메인 수정에 있는 핵심 용어를 행별 편집 화면으로 바꿀 거야. 용어·설명·동의어를 나눠 입력하고 추가·수정·삭제·저장·취소와 저장 전 미리 보기를 계획해. 기존 도메인의 terms 구조와 검색 처리를 재사용해. 빈 용어·중복·최대 개수와 동의어 구분을 확인하고 다른 도메인 설정·실무 기록 안내는 보존해. 관리 권한은 서버에서도 확인해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **관리 위치** 관리 → 가상 교통관제 자료 수정
- **기존 저장** 도메인 핵심 용어 재사용
- **바꿀 입력** 용어·설명·동의어 별도 칸

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
관리의 도메인 수정에 확인한 용어 행 편집을 만들어. 기존 값을 불러와 용어·설명·동의어를 따로 고치고 저장 전 결과를 보여 줘. 동의어의 쉼표·줄바꿈을 정리하고 중복·빈 값을 안내해. 기존 도메인 DB 저장 구조를 재사용하고 필요할 때만 변경 파일을 적용해. 취소하면 마지막 저장값으로 돌아가고, 저장 실패에는 수정 중 입력을 남겨. 다른 설정과 기존 동의어를 지우지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 관리자로 ‘상태 변경 이력’의 기존 동의어 ‘상태 로그’를 남기고 ‘변경로그’를 추가합니다. 취소 후 원래 값, 다시 저장 후 두 동의어를 확인하세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · 검색에 적용된 동의어 보여 주기

### 다음 기능 · 메뉴별 안내와 문의 담당 편집하기

```

**내가 확인할 것**

- 자료실: 현재 선택한 도메인

```

1. 작성자와 열람자로 안내를 엽니다. 관리자가 표시하지 않음으로 저장하면 사라지는지 확인하고 다시 켭니다. RFP 미게시 초안은 열람자에게 안내를 보여 주려고 공개하지 않습니다.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

**확인:** 보고서 업무와 회사 설정을 함께 통합할 준비가 됐습니다.

## 4. 추가 통합과 역할별 업무 확인

[함께 볼 강의 화면](/lectures/week-06.html#slide-45)

**앞에서 이어받을 것:** 앞 통합 기준과 강사가 준비한 RFP·관리 변경, 별도 통합 사본·개발 DB

1. 통합 준비·코드와 DB 반영·역할별 확인·결과 정리를 같은 순서로 수행합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 아래 전체 업무를 이어 해 보고 막힌 동작을 보완합니다.

**내가 정할 것:** 앞에서 만든 기능을 같은 보고서와 계정으로 이어 확인합니다.

**저장 기준:** 코드와 DB 변경을 함께 반영하고 개인 데이터는 병합하지 않습니다. 실제 확인 결과와 운영 준비를 따로 남깁니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
RFP 항목 확인·질문 답변과 도메인 용어·메뉴별 안내 변경을 통합할 거야. 내 작업과 DB 변경을 조사하고 강사가 준 이전 통합 기준 커밋, RFP 변경 커밋, 관리 변경 커밋, 별도 통합 사본·개발 DB를 대조해. origin은 내 fork, upstream은 기준 저장소인지 확인해. 미커밋 작업 보관과 두 변경의 적용 순서부터 계획하고 준비되지 않은 값은 알려 줘. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **출발 기준** 5회차에서 확인한 통합 커밋
- **추가 묶음** RFP 변경 → 관리 변경
- **보존** 개인 개발본·DB 적용 이력

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 이번 코드·DB 변경 파일만 개인 작업 브랜치에 보관하고 커밋 번호를 남겨. 환경 파일·개인 자료는 포함하지 마. upstream의 기준과 추가 변경 이력을 fetch해 비교하고 별도 통합 브랜치를 준비해. 기존 개인 개발본을 초기화하지 마. 대상 사본·DB와 적용 순서를 기록하되 비밀번호는 출력하지 마. 아직 두 변경은 병합하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 강사가 준 기준 커밋과 두 추가 변경, 작업 사본·DB를 확인합니다. 내 작업 커밋을 남기고 기존 개인 위키가 그대로 열리는지 보세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · RFP와 관리 변경을 차례로 합치기

**먼저 계획 요청**

```text
별도 통합 사본에 RFP 변경을 먼저, 관리 변경을 다음으로 합칠 거야. 보고서 항목·질문 식별자와 기존 데이터, 도메인 terms·메뉴 안내 저장이 서로 충돌하는지 계획해. 이미 적용한 DB 변경 파일을 덮지 말고 필요한 보완 파일과 적용 순서를 설명해. 개인·운영 DB는 대상이 아니며 준비된 통합 개발 DB만 사용해. 데이터 초기화로 충돌을 해결하지 마. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 코드: 대표 구현의 차이·충돌 확인
- DB: 기존 자료와 변경 이력 보존
- 순서: RFP 반영 후 관리 변경

**계획을 확인한 뒤 실행**

```text
확인한 RFP 변경과 관리 변경만 별도 통합 사본에 차례로 반영해. 중복 구현은 동작과 저장 구조를 비교해 해결하고 한쪽 파일로 통째로 덮지 마. 지정한 통합 개발 DB에 필요한 변경을 순서대로 적용하고 기존 데이터·적용 이력을 보존해. 필요한 패키지·코드 커밋·DB 적용 결과를 각각 확인하고 운영 배포나 원격 강제 반영은 하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 통합본에서 항목 상태 저장과 질문 답변, 관리 용어·안내가 모두 열리는지 확인합니다. 기존 질문 모음·위키 비교 화면도 다시 열어 보세요.

### 다음 기능 · 역할별로 업무를 확인하고 연결 문제 고치기

**먼저 계획 요청**

```text
통합본의 RFP 확인·질문 답변·관리 설정과 기존 검색·채팅·위키 비교를 역할별로 확인할 거야. 작성자는 내 보고서 보완, 검토자는 별도 보고서 검토, 관리자는 용어·안내 편집, 열람자는 게시본과 안내 조회를 검사할 계획을 세워. 강사의 최종 기준 커밋·DB 목록과 차이도 확인해. 신규 내부 메모가 게시본에 노출되는지와 다른 계정의 개인 기록 접근을 함께 검사해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 관리자: 용어·안내 수정
- 작성·검토: 보완 후 별도 검토 판단
- 열람자: 게시본·안내만 확인

**계획을 확인한 뒤 실행**

```text
확인한 최종 기준과 통합 사본의 차이를 맞추고 자동 검사를 실행해. 실패한 연결은 재현 원인과 보완안을 먼저 보여 주고 확인한 수정만 적용해. 역할별 계정·메뉴·누를 버튼·예상 결과를 알려 줘. 내가 실제로 확인한 결과를 받은 뒤 통과·실패·미확인을 구분해 기록해. 검사를 통과했다고 검토 요청·승인이나 운영 배포를 대신 실행하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 작성자로 보완한 보고서의 검토를 요청하고 reviewer로 원문·남은 질문을 읽은 뒤 게시 여부를 판단합니다. 게시했다면 reader로 본문·안내를 확인하고 내부 답변 메모는 보이지 않는지 보세요.

### 다음 기능 · 운영 준비와 남은 확인 목록 정리하기

**먼저 계획 요청**

```text
통합본의 RFP 보고서와 회사 설정을 다음 운영 확인으로 넘길 거야. 확인한 코드 커밋·DB 적용·보고서 버전·남은 질문과 공용 반영 대상·담당·환경 설정·백업 및 복구 준비 상태를 기록할 계획을 세워. 실제 확인한 사실과 아직 준비할 일을 구분하고 인증정보·개인 대화는 기록하지 마. 운영 배포나 DB 복원은 이 요청에 넣지 마. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 완성한 것: 코드·DB·역할별 확인 결과
- 남은 질문: 담당·다음 행동·필요 자료
- 운영 준비: 실제 확인·미준비를 구분

**계획을 확인한 뒤 실행**

```text
확인한 통합 결과와 운영 준비 목록을 개발 노트에 남겨. 질문별 담당·다음 행동·확인할 자료를 적고 R5의 책임 주체와 R6의 전환 조건은 미해결이면 그대로 남겨. 공용 주소·배포 담당·설정 위치·백업과 복구 확인은 확인된 정보만 기록해. 미완료는 담당·다음 조치와 함께 남기고 개인 실행을 회사 도입 완료로 표시하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. R5 책임 주체와 R6 허용 중단 시간의 남은 일을 적습니다. 다음에는 이 보고서와 통합본으로 후속 단계 운영 인수인계 업무를 수행합니다.

### 업무 순서대로 확인

앞에서 만든 기능을 같은 보고서와 계정으로 이어 확인합니다.

1. 통합본의 이전 버전에서 R5 회신·R6 보류 후 재개 이력을 읽고, 새 버전에서 미정 질문·항목·원문 복귀를 확인합니다. DB 변경 적용도 확인합니다.
2. 관리자로 앞서 저장한 용어·안내를 다시 읽습니다. 누락된 설정만 채우고 작성자로 검색·안내·질문 모음·위키 비교를 확인합니다.
3. 앞 단계에서 요청·게시한 보고서의 결과를 다시 엽니다. 대기 중인 요청만 reviewer가 처리하고 reader로 게시본·안내와 내부 기록 접근 제한을 확인합니다.

검토에서 문제가 발견되면 수정 요청 후 새 버전을 보완·재요청합니다. 실제 확인 전에는 완료로 적지 않습니다.

**확인:** 추가 통합본과 다음 업무에 사용할 보고서를 남겼습니다.

**기본을 마쳤다면 — 선택 과제**

- **기존 자료 검사:** 변경 전 보고서·도메인 설정에도 새 기능이 정상 적용되는지 확인합니다.
- **반복 확인 자동화:** 보고서 버전·역할·안내 조회를 반복 검사할 절차를 만듭니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

공통 네 기능을 모두 확인한 뒤에만 추가 도전을 진행합니다.
