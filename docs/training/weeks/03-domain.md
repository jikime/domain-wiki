1주차 공개 자료와 검수 조건 v1을 유지합니다. 이번 주에는 스타터킷에 이미 있는 저장·검증을 활용합니다. 교육생은 업무 조건과 설정을 정하고 AI에게 적용 방법을 설명받습니다. 새 저장 항목이 꼭 필요한 요구는 AI가 영향과 범위를 설명하도록 T3에 기록하며, DB·Zod 구현 실습으로 확대하지 않습니다.

## 3. 핵심 설명

기술 설명은 5–10분 안에서 역할만 확인합니다. 화면·API는 필요한 정보를 전달하고 Zod는 입력 조건을 검사하며 PostgreSQL·Drizzle은 저장과 조회에 사용됩니다. 이 도구의 문법이나 구현 방법은 AI가 담당합니다.

**분류와 접근 권한.** 같은 도메인 안에 프로젝트 A와 B를 둡니다. 프로젝트 검색은 해당 사업과 공통 자료를 골라 보는 기능입니다. 프로젝트를 나눴다는 이유만으로 다른 사용자가 해당 프로젝트를 전혀 볼 수 없는 것은 아닙니다.

**용어 설명과 동의어.** 핵심 용어에는 표준 용어·설명·동의어가 있습니다. 설명에 ‘VMS’를 적는 것만으로 같은 뜻의 검색어로 등록되는 것은 아닙니다. 현재 검색은 명시적으로 등록한 동의어를 확장합니다.

**지식 양식과 DB 스키마.** 위키 구조는 작성·생성 시 참고하는 문서 구성입니다. 실무 기록 기본 양식은 기존 입력 항목을 어떻게 채울지 안내합니다. 이를 바꾼다고 DB 필드가 자동으로 늘거나 이미 게시한 위키가 모두 새 형태로 바뀌지는 않습니다.

**작성자 진술.** 경험은 특정 상황에서 관찰한 내용입니다. ‘날짜 필터를 바꾸자 보였다’는 사례를 ‘빈 결과는 언제나 날짜 문제’라는 규정으로 바꾸면 안 됩니다.

**문서 추출·문단·버전.** 파일에서 읽은 텍스트가 근거 문단으로 나뉘고 버전별로 보관됩니다. 표의 열·수치·부정 표현이 제대로 추출됐는지 원문과 비교합니다. 불변 원문은 예전 입력을 보존하기 위한 구조입니다.

## 4. 실습 A · 용어와 자료 범위 구성

> **입력할 곳:** 브라우저의 관리 화면에서 용어를 저장하고, 검색·채팅에서 프로젝트를 선택합니다.
>
> **정상 결과 예시:** 도로전광표지의 동의어가 `VMS`, `전광표지` 두 항목으로 유지됩니다. 검수 조건 v1은 A의 화면 갱신 60초와 B의 120초를 구분합니다.

1. 관리 화면의 교육용 도메인을 열고 목적·현재 용어를 T5에 보관합니다. 업무에 필요한 용어·설명·동의어와 입력 조건을 먼저 적고 AI에게 기존 기능으로 적용할 방법을 요청합니다.
2. AI가 제안한 설명을 [설정 예시](../samples/domain-settings.md)의 사실·용어와 비교하고 목적과 세 줄 용어를 입력합니다. 각 줄은 `용어 | 설명 | 동의어, 약어` 형식으로 작성합니다.
3. 저장하고 다시 열어 도로전광표지의 동의어가 VMS·전광표지로 나뉘어 유지되는지 확인합니다.
4. 01 문서에서 ‘VMS’ 문자열이 아니라 ‘도로전광표지’가 쓰였음을 확인한 뒤 두 검색어로 같은 자료를 찾습니다. 의미 검색이 이미 비슷한 자료를 찾을 수 있으므로 동의어 저장 확인과 검색 결과를 별도로 기록합니다.
5. 04 협의 메모는 프로젝트 A의 ‘참고 자료’, 05 문서는 프로젝트 B의 ‘사업 자료’로 등록합니다. 다른 검토자가 공개합니다.
6. 프로젝트 A에서 갱신 주기를 질문한 결과와 B에서 질문한 결과를 비교합니다. A의 기준은 60초, B는 120초입니다.
7. 공통 지침을 A 범위에서 찾고, 도메인 공통 자료가 함께 조회됨을 확인합니다.

기대 결과: 설정 입력과 저장 결과가 일치하고, A와 B의 자료를 구분합니다. 용어 설정만 바꾸어 해결된 부분과 검색 모델의 영향을 구분해 기록합니다.

## 5. 실습 B · 경험 기록과 위키 작성 기준

> **입력할 곳:** 개발용 AI에서 작성 기준을 제안받고, 브라우저의 관리·실무 기록·위키 화면에 반영합니다.
>
> **정상 결과 예시:** 검수 조건 v1에서 화면 갱신 60초와 장애 복구 시간 미정을 구분합니다. AI가 제안한 기준은 실제로 저장하고 초안에서 확인합니다.

화면 조작이 낯설면 [실제 사용 따라 하기](../wiki-chat-guide.md)의 근거 선택·검토·게시·채팅 단계를 옆에 열어 둡니다. 이번 실습에서는 아래의 ‘검수 조건’ 위키와 원문을 그대로 사용하며, 안내용 사업 범위 위키를 별도로 만들 필요는 없습니다. 답변의 위키 초안 저장은 선택적으로 확인합니다.

6번 활동의 약 10분은 [프롬프트 작성·실행](../prompt-practice.md)에 사용합니다. 개발용 AI에 전달할 자료·구분할 항목·추측하지 않을 조건을 먼저 적고 전송합니다. 제안에서 누락되거나 모호한 조건을 찾아 후속 요청을 실행한 뒤 관리 화면에 반영합니다.

```text
docs/training/samples/03-acceptance-v1.md를 읽고 프로젝트 A 검수 조건 위키의 작성 기준을 제안해 주세요.
적용 범위·확인된 조건·예외·추가 질문을 나누고 원문에 없는 기준은 만들지 마세요.
60초가 무엇의 기준인지, 미정인 조건이 무엇인지 구분할 수 있어야 합니다.
지금은 파일·설정을 바꾸지 말고 관리 화면에 반영할 기준 문장만 제안해 주세요.
```

위 문장은 초안을 작성한 뒤 비교할 참고입니다. 예를 들어 제안에서 ‘갱신’과 ‘복구’가 모호하면 그 차이를 구분하도록 후속 요청을 직접 씁니다. T3에 두 요청과 결과를 남기며, AI가 설정을 바꿨다고 가정하지 않고 교육생이 실제 저장·초안을 확인합니다.

1. 교육용 도메인의 ‘실무 기록 기본 양식’에 준비된 안내를 입력하고 저장합니다. 실무 기록 화면에 안내가 나타나는지 확인합니다.
2. ‘작성 당시 메모’에 06 예제의 메모를 넣습니다. 상황·판단과 이유·결과·추가 확인할 내용을 직접 작성하거나 AI 제안을 받아 비교합니다.
3. AI가 ‘자료가 삭제됐다’, ‘모든 장비가 정상이다’처럼 없는 내용을 보태면 반영하지 않습니다. 메모 원문과 제안이 별도임을 확인합니다.
4. 연결 가능한 공개 원문이 있으면 실제 문단을 선택합니다. 경험 자체를 공식 지침으로 바꾸지 않고 작성자 진술로 저장합니다.
5. 다른 검토자가 상황과 일반화 여부를 확인해 공개하거나 수정 요청합니다.
6. AI에게 적용 범위·확인된 조건·예외·추가 질문을 구분하는 작성 기준을 요청하고 기존 예시와 비교합니다. 관리 화면의 목적 문서·위키 구조에 반영한 뒤 ‘프로젝트 A 검수 조건’ 위키의 AI 초안을 요청합니다. 서비스 AI가 불가능해 수동 예시를 사용하면 실제 생성은 미확인으로 남깁니다.
7. 공개된 검수 조건 v1의 ‘60초’, ‘90일’, ‘표본 3대’ 문단을 연결합니다. 적용 범위·확인된 내용·예외·추가 질문을 검토합니다.
8. 다른 검토자가 게시합니다. 이후 원문 개정 영향을 살펴볼 수 있도록 위키 주소와 근거 자료 버전을 기록합니다.

## 6. 기술 이슈와 해석 오류

| 상황 | 확인할 사실 | 해결 방향 |
| --- | --- | --- |
| 용어 저장이 실패함 | 설명 필수, 동의어당 2–80자·최대 10개, 용어 최대 100개 | 서버 검증을 유지하고 입력 수정 |
| 설명을 바꿨는데 검색이 같음 | 설명과 동의어의 역할 차이 | 별도의 동의어 목록 확인 |
| 양식을 바꿨는데 입력 필드가 안 늘어남 | 양식은 작성 안내 | 기존 필드 작성 기준을 개선 |
| 목적을 바꿨는데 기존 AI 작업 결과가 이전 기준임 | 작업 시작 당시 기준 | 필요한 작업을 새 기준으로 다시 시작 |
| 경험이 규정처럼 게시됨 | 작성자 진술과 기준의 차이 | 적용 조건을 적고 동료 검토 |

## 7. 완료 기준

업무 입력 조건·AI 제안에 대한 판단을 포함한 도메인 설정 기록 1개, 공개 실무 기록 1개, 근거가 연결된 검수 위키 1개를 남깁니다. AI 요청과 실제 저장·재조회 결과를 구분합니다. 처리·공개·게시 상태와 작성·검토 역할을 함께 기록합니다. ‘설정만으로 해결한 것은 무엇인가요?’, ‘새 DB 필드가 필요한 변경과 무엇이 다른가요?’에 답합니다.

빠르게 마친 교육생은 자기 업무의 용어 2개와 실무 기록 안내를 제안합니다. 실제 회사 자료의 사실·공개 범위는 담당자 확인 뒤 적용합니다. 다음 주에는 같은 상태에서 평가 질문 12개를 실행합니다.
