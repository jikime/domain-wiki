# 회사 경험을 기록하고 다시 찾는 위키 만들기

실무 기록 작성 창을 모달로 분리하고 업무 유형별 안내를 더합니다. 여러 초안을 DB에 보관하고 원문 근거를 붙여 검토를 요청한 뒤, 기록과 개인 확인할 일을 관리하는 기능을 이어 개발합니다.

[강의 화면](/lectures/week-03.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 2회차의 내 위키·즐겨찾기와 같은 코드를 연 Claude Code를 준비합니다. 공개 샘플 원문·경험 기록과 관리자·작성 계정을 확인하고, 현재 작성 화면과 AI의 설명을 비교합니다.

**남길 결과:** 필요할 때 여는 작성 창과 업무 유형별 안내·관리 / 여러 개인 초안의 DB 저장·이어 쓰기 / 근거·미리 보기·나란히 비교·확인 목록·검토 요청 연결 / 기록 검색·개인 할 일·미완료 보기·프로젝트별 개수

**계획 요청 → 내가 확인·수정 → 실행 요청 → 공통 기능 완성 → 내 업무에 적용** 순서입니다. 1교시는 작성 창을 모달로 분리하는 작업부터 진행합니다. 이후 각 교시의 첫 요청 뒤에 후속 두 기능을 이어 만들고, 업무 적용까지 수행합니다. 1교시의 유형 등록·숨기기·다시 사용, 2교시의 초안 복사·프로젝트별 보기, 3교시의 나란히 보기·확인 목록, 4교시의 미완료 보기·프로젝트별 개수는 모두 같은 순서로 만듭니다. 요청 상자 하나는 한 번에 입력하되 계획과 실행은 따로 보냅니다.

## 실무 기록은 어떤 메뉴인가요?

**실무 기록은 일을 하면서 겪은 상황, 판단한 이유, 결과를 남기는 곳입니다.** 예를 들어 “프로젝트 A의 날짜 필터를 점검하면서 무엇을 확인했고 어떤 문제가 남았는지”를 기록합니다. 개인의 경험이므로 회사의 공식 규정과 구분합니다.

| 메뉴 | 무엇을 남기나요? | 예시 |
| --- | --- | --- |
| 자료실 | 업무에 참고할 원본 자료 | 사업 개요, 검수 조건 문서 |
| 실무 기록 | 실제 업무 경험과 판단 | 날짜 필터를 점검한 과정과 결과 |
| 위키 | 자료를 근거로 정리한 업무 설명 | 상태 화면을 검수하는 절차 |

### 어디에서 시작하나요?

1. 앱 상단의 **실무 기록**을 누릅니다. 작은 화면에서는 **전체 메뉴 열기 → 실무 기록**으로 들어갑니다.
2. **팀의 경험**에서 기존 기록의 제목을 눌러 읽습니다.
3. **+ 실무 기록 작성**을 누릅니다. 현재 스타터킷에서는 목록 아래 **새 실무 기록**으로 이동합니다. 작성 버튼은 작성 권한이 있는 계정에 보입니다.
4. 제목·도메인·프로젝트를 정하고 **상황 / 판단과 이유 / 결과 / 추가 확인할 내용**을 씁니다. AI 정리는 선택 사항이며 직접 입력해도 됩니다.

이번 실습의 첫 개선은 목록 아래의 입력칸을 **모달**로 옮기는 일입니다. 모달은 버튼을 눌렀을 때 현재 화면 위에 열리는 별도 창입니다. 그 창에 업무별 안내, 초안 저장, 근거 연결을 차례로 더합니다.

### 현재 기능을 보고, 필요한 개선을 정합니다

**현재도 본문을 작성하고 ‘실무 기록 저장’을 누르면 기록 등록이 끝납니다.** 검토 대기로 등록되며 공개는 이후 검토를 거칩니다. 같은 탭의 임시 복원은 작성 중인 내용을 보호하는 기존 기능입니다.

첫 장 오른쪽은 **앞으로 개발할 기능**입니다. 현재 입력폼을 설명하는 목록이 아닙니다. 내 업무에서도 다음 불편이 생기는지 먼저 생각해 보세요.

| 불편한 상황 | 새로 만들 기능 | 사용 예 |
| --- | --- | --- |
| 업무마다 무엇을 써야 할지 막힌다 | 업무 유형 선택과 작성 안내 | 검수에는 확인 기준, 장애 대응에는 증상과 대응 순서를 안내 |
| 여러 기록을 쓰다 중단한다 | 여러 개인 초안의 DB 저장 | 프로젝트 A 기록을 보관하고 프로젝트 B를 작성한 뒤 프로젝트 A를 다시 열기 |
| 본문에 남긴 후속 업무를 놓친다 | 내 확인할 일 | ‘표본 장비 번호 확인’을 직접 등록하고 완료 표시 |

업무 유형은 기존 **상황 / 판단과 이유 / 결과 / 추가 확인할 내용** 옆에 보여 줄 작성 안내·예시를 바꿉니다. 본문을 자동으로 채우지는 않습니다. 개인 초안은 미완성 글을 나중에 이어 쓰기 위한 기능입니다. **완성한 글은 초안 저장을 거치지 않고 바로 등록할 수 있게 유지합니다.**

### 실무 기록 메뉴에서만 개발하나요?

중심은 **회사 경험을 작성하고, 근거를 붙여 등록하고, 다시 찾아 활용하는 기능**입니다. 아래 화면을 연결해서 개발합니다.

| 화면 | 이번에 개발·연결할 것 |
| --- | --- |
| 실무 기록 | 작성 모달, 유형별 안내, 개인 초안, 검색과 후속 할 일 |
| 관리 → 도메인 | 업무 유형과 작성 안내 설정 |
| 자료실 → 공개 원문 | 원문에서 기록 작성 시작, 근거 문단 연결 |
| 2회차 즐겨찾기 | 공개된 경험 기록을 보관하고 다시 열기 |

첫 장 아래 네 칸은 **교시별 개발 순서**입니다. 작성 화면 개선 → 미완성 글 보관 → 근거·검토 요청 → 기록·남은 일 관리를 이어 만듭니다. 3교시도 같은 실무 기록 개발을 이어갑니다. 2교시의 C1·C3 초안을 열어 본문과 근거를 완성하고 검토 요청까지 연결합니다. 자료실의 새 버튼은 읽던 자료에서 같은 작성 창을 여는 기능입니다. 별도 연습 글로 버튼을 확인한 뒤 C1으로 돌아옵니다. C1을 제출한 뒤에는 아직 작성 중인 C3로 공통 비교·확인 기능을 보강합니다.

### 저장하면 위키와 채팅에도 바로 나오나요?

현재 **실무 기록 저장**은 검토 대기 자료를 등록하는 동작입니다. 개인 DB 초안 저장은 이번에 새로 만들 기능입니다. 기록 처리가 완료되고 작성자와 다른 검토자가 공개를 승인하면, 해당 범위를 읽을 수 있는 사용자의 채팅에서 참고 자료로 검색될 수 있습니다. 저장만 했거나 개인 초안인 상태는 채팅 검색 대상이 아닙니다.

실무 기록이 별도의 위키 글로 자동 게시되는 것은 아닙니다. 위키 글로 정리하려면 초안 작성과 게시 검토를 따로 거칩니다. 이번 개발 실습에서는 새 기록을 검토 대기까지 연결하고, 공개 기록 조회는 이미 승인된 샘플로 확인합니다. [기록 공개 후 채팅에서 확인하는 방법](../wiki-chat-guide.md#실무-기록을-남기고-채팅에서-참고하기)도 참고하세요.

## 오늘 완성할 기능과 진행 방법

각 교시에서 **첫 기능 → 후속 두 기능 → 내 업무에 적용**까지 진행합니다. ‘내 업무에 적용’도 기본 실습입니다. 공통 기능을 마친 뒤 적용 장에서 요구를 정하고 실제 동작을 더 개발합니다. 그다음 추가 도전으로 넓힙니다.

**1장은 개발 이유와 목표, 2장은 실제 작업 순서와 교시 사이의 연결을 설명합니다.** 아래 표는 같은 위키를 이어 개발하는 순서입니다. ‘내 초안’은 2교시에 추가할 탭이며 기존 메뉴로 찾지 마세요.

| 교시 | 시작할 화면 | 개발할 동작 | 완성 결과 | 이어서 할 일 |
| --- | --- | --- | --- | --- |
| 1 | 실무 기록 → 작성 버튼 / 관리 → 도메인 | 작성 폼을 모달로 옮기고 / 유형별 작성 안내·예시 추가 | 버튼으로 창을 열고 / 검수·장애 대응 안내 확인 | 같은 작성 창에 / 초안 저장 추가 |
| 2 | 1교시에서 만든 작성 창 | 초안 저장·목록·수정·삭제 / 복사·프로젝트별 보기 추가 | 프로젝트 A·프로젝트 B 글을 따로 보관하고 / 골라서 이어 쓰기 | 저장한 글에 / 근거 연결 |
| 3 | 실무 기록 → 내 초안 / 자료실의 참고 자료 연결 | C1의 근거·미리 보기·검토 요청 / C3로 나란히 보기·확인 목록 보강 | 제출 완료에서 C1·C3 다시 열기 / 검토 대기 상태 확인 | 제출한 기록에서 / 남은 일 관리 |
| 4 | 내 초안 → 제출 완료 / 팀의 경험 → 기존 공개 기록 | 검색·할 일·즐겨찾기 연결 / 미완료 보기·프로젝트별 개수 | 완료·미완료로 되돌리기 / 목록·개수와 계정별 접근 확인 | 바꾼 기능·확인 결과를 / 개발 노트에 정리 |

공통 기능 뒤에는 **해당 교시의 업무 적용 기능**을 더 개발합니다.

- 1교시: 모두 인수인계 유형 등록 → 기록 저장 확인 → 숨기기·다시 사용
- 2교시: 모두 초안 복사 → 프로젝트별 보기
- 3교시: 모두 근거와 나란히 보기 → 제출 전 확인 목록
- 4교시: 모두 미완료 보기 → 프로젝트별 내 할 일 개수

완성한 글은 개인 초안 저장 없이 바로 등록할 수 있게 유지합니다. 4교시의 즐겨찾기는 기존 공개 경험 기록으로 확인합니다.

동작을 정할 때는 **어느 화면에서 무엇을 누르면 어떤 결과가 나와야 하는지** 정합니다. 버튼 이름과 예시 문장만 바꾸는 작업으로 업무 적용을 마치지 않습니다. 수업 중에는 모두 같은 기능을 같은 순서로 개발합니다. 회사에 필요한 추가 요구는 공통 기능을 확인한 뒤 강사와 범위를 정합니다.

### 실제 화면에서 시작하기

기존에는 목록 아래 작성 폼에 실무 기록의 네 입력칸·도메인 안내·AI 정리·탭 임시 복원·근거 선택·저장이 있습니다. 오늘 만들 작성 모달, 유형 관리, 여러 DB 초안, 개인 확인할 일은 아직 있는 기능처럼 찾지 마세요. 관련 DB도 현재 구조를 조사한 뒤 필요한 항목을 추가합니다.

1. 같은 위키 서버에서 로그인하고 **가상 교통관제 자료** 도메인을 고릅니다. ‘교통관제 업무 (개발 예시)’와는 다른 도메인입니다.
2. 자료실에서 **프로젝트 A · 가람시**의 검수 조건·사업 개요와 **프로젝트 B · 누리시**의 상태 조회 조건을 엽니다.
3. 실무 기록에서 공개된 **프로젝트 A 표본 점검에서 날짜 필터를 확인한 경험**을 엽니다. 새 실습 기록으로 복제하지 않습니다.
4. **실무 기록 → + 실무 기록 작성**을 눌러 목록 아래로 이동하고, 새 실무 기록의 도메인·프로젝트를 따로 확인합니다. 관리자 계정에서는 관리 → 도메인 → 가상 교통관제 자료 수정을 펼쳐 실무 기록 기본 양식도 확인합니다.
5. 작성 버튼의 이동 위치와 입력 항목을 AI의 코드 설명과 비교합니다. 화면과 다르거나 확인하지 못한 부분은 강사와 확인합니다.

공개 샘플 원문이 없다면 [샘플 넣기](../sample-data.md)부터 확인합니다. 입력 사례는 작성 창을 분리한 뒤, 7장의 업무 유형별 안내 계획에서 읽습니다.

2회차 즐겨찾기가 미완성이면 그 코드를 이어 완성합니다. 원문은 자료실에서 열어 앞 교시를 진행할 수 있지만 마지막 즐겨찾기 연결을 완료로 표시하지 않습니다.

### 작업 화면을 찾는 순서

‘내 초안’과 ‘내 확인할 일’은 상단의 별도 메뉴가 아닙니다. **실무 기록 화면 안에 순서대로 추가할 탭**입니다. 개발하기 전 스타터킷에서 찾지 마세요.

| 할 일 | 들어갈 위치 | 언제 사용할 수 있나요? |
| --- | --- | --- |
| 새 기록 작성 | 실무 기록 → + 실무 기록 작성 | 현재는 아래 폼으로 이동, 1교시에서 모달로 변경 |
| 유형 안내 관리 | 관리 → 도메인 → 가상 교통관제 자료 수정 | 기존 ‘실무 기록 기본 양식’ 옆에 1교시에서 추가 |
| 보관한 글 이어 쓰기 | 실무 기록 → 내 초안 탭 → 제목 | 2교시에서 탭·목록과 DB 저장을 추가 |
| 원문에서 새로 시작 | 자료실 → 프로젝트 A · 상태 화면 검수 조건 → 이 자료로 기록 시작 | 3교시에서 원문의 새 버튼을 추가 |
| 제출한 기록 읽기 | 실무 기록 → 내 초안 → 제출 완료 → 결과 보기 | 3교시에서 제출 상태와 결과 링크를 추가 |
| 개인 할 일 관리 | 기록 상세에서 입력 → 실무 기록 → 내 확인할 일 탭 | 4교시에서 입력과 탭·목록을 추가 |

**관리 메뉴가 없으면** 관리자 계정인지 확인합니다. 도메인 수정을 펼치면 ‘실무 기록 기본 양식’이 있습니다. 유형별 작성 안내·예시는 아직 없는 기능이며 그 옆에 추가합니다.

**기록을 열었는데 자료실처럼 보이면** 정상입니다. 현재 실무 기록도 자료 상세 화면으로 열리고 위쪽에 ‘← 자료실’이 있습니다. 4교시에는 출발한 팀의 경험·내 확인할 일 탭으로 돌아가는 동작을 보완합니다. 위키 글을 여는 실습과 구분하세요.

### 실습 사례는 필요할 때 읽습니다

[기록 개발 실습 사례](../samples/record-practice.md)에는 가상 예제 네 개가 있습니다. **7장에서는 유형별 작성 안내 표와 프로젝트 A의 검수·장애 대응 예제 두 개만 읽습니다.** 예제 번호 C1–C4는 글을 구분하는 이름이며 앱의 메뉴나 저장된 기록이 아닙니다.

2교시에는 예제의 내용을 새로 만든 내 초안에 저장합니다. 27장에서 프로젝트 B 예제 두 개를 더 준비합니다. 입력을 줄이고 싶다면 그때 사례 페이지의 준비 요청을 사용하세요. JSON은 입력 재료이며 기존 샘플 설치 명령에 넣는 DB 백업이 아닙니다.

검수 글은 근거를 붙여 등록하고, 미완성 글은 초안으로 남깁니다. 본문의 ‘추가 확인할 내용’은 개인 할 일로 자동 복사하지 않고 직접 골라 등록합니다. 각 실습의 준비 상태와 확인 순서는 해당 절차에서 안내합니다.

### 무엇이 어디에 남나요

- **작성 유형과 안내:** 도메인의 공용 설정입니다. 관리자가 고치고 작성자는 선택해 사용합니다. 선택한 유형은 작성한 글과 함께 남깁니다.
- **개인 DB 초안:** 미완성 글 여러 개를 서버에 보관합니다. 내 계정으로 다시 열며 원문 검색·검토함에는 나타나지 않습니다. 기존 탭 임시 복원과 구분합니다.
- **검토 요청한 기록:** 기존 기록 저장 기능으로 검토 대기에 등록합니다. 제출한 초안과 결과 기록을 연결하며 같은 요청으로 중복 기록을 만들지 않습니다.
- **내 확인할 일:** 읽을 수 있는 기록에 내가 남긴 개인 할 일입니다. 완료·미완료로 되돌리기는 내 상태만 바꾸며 기록 본문이나 공개 상태를 변경하지 않습니다.
- **즐겨찾기 내 메모:** 2회차에서 만든 개인 메모입니다. 실무 기록으로 자동 복사하지 않습니다. 즐겨찾기 실습에는 기존 공개 경험 기록을 사용합니다.

새 저장 대상은 AI가 기존 DB를 조사해 설계합니다. 필요한 DB 변경 파일·개발용 DB 적용·서버 저장과 조회를 함께 확인합니다. 권한은 화면뿐 아니라 서버에서 검사합니다. 같은 서버 주소에 다른 브라우저로 로그인해 저장을 확인하고, 배정된 다른 계정으로 개인 정보가 분리되는지 직접 봅니다.

### 다음 단계로 넘어갈 기준

공통 기능과 교시별 업무 적용 기능을 직접 사용해 봅니다. AI가 코드를 읽고 구현·기술 검사를 수행하며, 나는 원하는 동작과 결과를 판단합니다. 동료의 사용을 완료 조건으로 두지 않습니다. AI 정리가 준비되지 않았다면 직접 입력으로 진행합니다.

슬라이드의 후속 요청은 모두 기본이며 워크북에도 같은 순서로 정리되어 있습니다. ‘추가 도전’은 공통과 업무 적용을 마친 뒤 고릅니다. 막히면 강사와 최소 동작부터 연결하고 못한 일은 남겨 두세요.

## 계정을 나눠 확인하기

관리자 예: admin@wiki.local / 일반 사용자 예: writer@wiki.local. 강사가 배정한 계정으로 바꿔도 됩니다. 같은 서버 주소에서 계정을 전환하거나 별도 브라우저·프로필로 확인합니다.

**1교시 · 유형과 작성 안내**

- 관리자: 관리 → 도메인 → 업무 유형별 안내에서 수정·저장·인수인계 등록·숨기기·다시 사용을 확인한다.
- 일반 사용자: 작성 창에서 저장한 안내와 사용 가능한 유형을 확인하고 기록을 저장한다. 관리자 설정은 바꿀 수 없어야 한다.

**2교시 · 개인 초안**

- 일반 사용자: 저장·목록·수정·삭제·복사·프로젝트별 보기를 확인한다.
- 관리자: 자신의 초안만 보이며 일반 사용자의 초안에 접근하지 못한다. 직접 요청 차단은 AI 서버 검사로 확인한다.

**3교시 · 근거와 검토 요청**

- 일반 사용자: 공개 자료에서 별도 연습 초안을 만들고 C1 원본·C3를 근거와 함께 검토 요청한다. C2·C4·C1 복사본·연습 글은 초안으로 남긴다.
- 관리자: 현재 코드에서는 검토 권한도 포함하므로 일반 사용자가 제출한 C1·C3 결과 기록을 읽을 수 있다. 타인의 개인 초안·개인 제출 완료 목록은 열 수 없게 한다.
- 공개 승인·반려는 이번 실습에서 실행하지 않는다. 관리자를 포함해 본인이 등록한 기록의 승인은 금지된다. 화면에서 직접 확인한 결과와 AI 권한 검사 결과를 구분한다.

**4교시 · 검색과 개인 할 일**

- 일반 사용자: C1·C3를 검색하고 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개의 할 일을 저장·수정·완료·미완료로 되돌리기 한다. 미완료 목록과 프로젝트별 숫자를 확인한다.
- 관리자: 제출된 C1은 읽을 수 있지만 작성자의 개인 할 일은 보이지 않아야 한다. 관리자 확인용을 자신의 계정으로 등록해 사용자 목록·집계에 섞이지 않는지 확인한다.
- 관리자 연습 항목을 삭제하고 사용자 세 가지 일을 모두 미완료로 둔다. 직접 요청 차단은 AI 검사 결과로 구분하며 공개 승인·반려는 하지 않는다.

## 준비: 현재 화면과 코드의 동작 확인

내 위키에서 실무 기록 → + 실무 기록 작성을 누르고 입력칸을 살펴봅니다. 같은 위키 프로젝트의 Claude Code에 아래 요청 상자 전체를 한 번에 입력하세요. AI는 코드를 조사하고, 나는 실제 화면과 설명이 맞는지 확인합니다.

```text
지금까지 개발한 위키의 ‘실무 기록’ 메뉴에서 작성·저장 흐름을 확인할 거야. 이 기능의 코드를 확인해. ‘+ 실무 기록 작성’을 누르면 어디로 이동하는지, 입력칸과 ‘실무 기록 저장’ 후 상태·화면을 설명해. 같은 탭의 임시 복원과 DB 저장을 구분하고 내가 눌러 볼 순서를 알려 줘. 없는 기능은 가정하지 마. 아직 코드·DB를 바꾸거나 구현 계획을 세우지 마.
```

**직접 확인:** 작성 버튼이 목록 아래 입력폼으로 이동하는지, AI가 설명한 입력 항목이 화면에 있는지 비교합니다. 다르거나 확인하지 못한 부분은 적어 두고 강사와 함께 확인합니다. 이번에는 기록을 저장하지 않으므로 저장 이후 동작은 코드 조사 결과로 구분해 둡니다. 화면과 설명이 맞으면 다음 단계에서 바꿀 동작을 정합니다.

## 1. 작성 화면과 업무 유형별 안내 만들기

[함께 볼 강의 화면](/lectures/week-03.html#slide-04)

**앞에서 이어받을 것:** 상단 실무 기록 → + 실무 기록 작성으로 목록 아래 폼을 찾습니다. 모달을 만든 뒤 같은 창의 유형 안내와 관리 → 도메인 → 가상 교통관제 자료 수정 화면을 이어 개발합니다.

### 먼저 · 작성 화면을 모달로 분리하기

모달은 현재 화면 위에 열리는 별도 창입니다. 현재는 목록과 긴 작성 폼이 한 페이지에 있고, 작성 버튼을 누르면 아래 폼으로 이동합니다. 목록을 볼 때는 기록에 집중하고, 글을 쓸 때만 창을 여는 방식으로 바꿔 봅니다.

계획을 요청하기 전에 세 가지를 정합니다.

1. **어디서 열까?** 기존 + 실무 기록 작성 버튼으로 열고, 목록 아래에는 폼을 중복으로 두지 않습니다.
2. **쓰던 글은 어떻게 할까?** 빈 창은 바로 닫습니다. 글이 있으면 계속 작성 / 내용을 남기고 닫기를 고르고, 같은 탭에서 다시 열 때 입력값과 선택한 근거를 보여 줍니다.
3. **무엇을 유지할까?** 기존 입력칸·AI 정리·근거 선택·저장은 그대로 씁니다. 작성 창을 옮기는 데 필요한 부분만 바꾸고 나머지 동작은 유지합니다.

아래 계획을 읽고 원하는 동작과 다르면 먼저 고치도록 요청하세요. 확인이 끝나면 실행 요청을 보냅니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

**계획 요청**

```text
실무 기록 메뉴의 목록 아래 작성 폼을 별도 창(모달)으로 옮길 계획을 세워. ‘+ 실무 기록 작성’을 누르면 창을 열고 아래 폼은 없앨 거야. 기존 폼의 입력칸·도메인·프로젝트·AI 정리·근거 선택은 그대로 써.

빈 창은 바로 닫고, 글이 있으면 X·Esc·바깥 클릭 때 ‘계속 작성 / 내용을 남기고 닫기’를 고르게 해. 같은 탭에서 다시 열면 입력값과 고른 근거를 복원해. 창을 좁혀도 입력칸이 보이고 안쪽을 스크롤해 저장 버튼까지 갈 수 있게 해. Tab 키로 입력칸을 옮기게 해. 저장 중에는 다시 저장하거나 닫지 못하게 하고, 실패하면 글을 남기고 성공하면 기록 상세로 이동해. 작성 창의 배치와 조작만 바꾸고 다른 동작은 유지해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획에서 내가 판단할 것**

- **열기** 버튼으로 열고 폼은 한 곳만 둡니다.
- **닫기** 계속 작성 / 내용을 남기고 닫기
- **저장** 성공하면 상세로, 실패하면 글 유지

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 메뉴에서 ‘+ 실무 기록 작성’을 누르면 모달을 열고 목록 아래 폼은 제거해. 기존 폼을 재사용해. 빈 창은 바로 닫고, 글이 있으면 ‘계속 작성 / 내용을 남기고 닫기’를 고르게 해. 같은 탭에서 다시 열면 입력값과 고른 근거를 복원해.

브라우저 창을 좁혀도 입력칸이 보이고, 창 안을 스크롤해 저장 버튼까지 갈 수 있게 해. Tab 키로 입력칸을 옮기고, 닫은 뒤 Enter 키를 누르면 작성 창을 다시 열 수 있게 해. 저장 중에는 다시 저장하거나 닫지 못하게 해. 실패하면 창과 글을 남기고, 성공하면 기존처럼 기록 상세로 이동해. 작성 창을 옮기는 데 필요한 부분만 바꾸고 나머지 동작과 저장 구조는 유지해. 검사 결과와 내가 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 눌러 보기**

1. 목록 아래 입력칸이 사라지고, + 실무 기록 작성을 누르면 창이 열리는지 확인합니다.
2. 제목에 “창 확인용”, 상황에 한 줄을 적고 도메인·프로젝트를 고릅니다. 선택한 근거가 있다면 그 내용도 함께 기억해 둡니다.
3. X·Esc·창 바깥 클릭을 각각 해 봅니다. “계속 작성”을 누르면 같은 창에 글이 남아야 합니다. “내용을 남기고 닫기”를 누른 뒤 같은 탭에서 다시 열어 입력값이 남는지 확인합니다.
4. 기존 **임시 초안 버리기**로 확인용 입력을 비운 뒤, 빈 창은 바로 닫히는지 확인합니다.
5. 브라우저 창을 좁혀 입력칸이 잘리는지 봅니다. 작성 창 안을 스크롤해 마지막 입력칸과 저장 버튼까지 가 봅니다. Tab 키를 눌러 입력칸을 차례로 옮기고, 창을 닫은 뒤 Enter 키로 작성 창을 다시 열 수 있는지 확인합니다.
6. AI에게 저장 실패 시 입력 유지, 저장 중 중복 제출·닫기 방지, 성공 후 기존 이동 경로를 검사하게 하고 결과를 받습니다. 이번 확인용 글은 기록으로 등록하지 않고, 창의 닫기·복원을 확인하는 데 사용합니다.

**저장 기준:** 현재 작성 폼과 같은 탭의 임시 복원을 재사용하므로 이 변경에 새 DB 테이블은 필요하지 않습니다. “내용을 남기고 닫기”는 같은 탭에서 이어 쓰는 기능입니다. 탭을 닫거나 다른 브라우저로 이동한 뒤에도 남기는 저장 기능과 구분합니다.

**이어서:** 작성 창의 열기·닫기·복원을 확인했으면 같은 창에 검수·장애 대응 유형 선택과 안내를 더하는 계획을 세웁니다(슬라이드 7장). 새 폼을 하나 더 만들지 않습니다.

**7장부터 사용할 입력 사례:** [기록 개발 실습 사례](../samples/record-practice.md)를 엽니다. 워크북 메뉴에서는 **실습 자료 → 기록 개발 실습 사례**입니다. ‘업무 유형별 입력칸 작성 안내’과 C1(검수)·C2(장애 대응)를 읽고, 상황·판단과 이유·결과·추가 확인할 내용 옆에 어떤 작성 안내를 보여 줄지 고릅니다. C1–C4는 기능을 만든 뒤 입력해 볼 가상 예제이며, 현재 앱에 저장된 기록이나 초안이 아닙니다. 본문을 자동으로 채우는 기능과 구분하세요.

### 이어서 · 업무 유형별 작성 안내 만들기

1. 작성 창에 검수·장애 대응 유형 선택과 작성 안내·예시를 만듭니다.
2. 관리 탭에서 유형별 안내를 수정·저장하고 작성 창에 반영되게 만듭니다.
3. 선택한 유형을 기록과 함께 저장하고 상세 화면에 표시합니다. 만든 뒤 아래 확인용 글로 직접 확인합니다.

**내가 정할 것:** 관리자가 고칠 작성 안내·예시와 기록 상세에서 유형을 보여 줄 위치

**저장 기준:** 유형별 작성 안내와 예시는 도메인의 공용 설정으로 DB에 저장합니다. 8장에서 작성 창에 표시하고, 9·10장에서 관리자가 안내를 수정·저장할 화면을 만듭니다. 기록을 등록할 때는 고른 업무 유형과 당시 이름을 함께 저장해 상세에 표시합니다. 유형을 만들기 전의 기록은 일반 기록으로 읽으며 본문과 공개 상태는 유지합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
실무 기록 작성 창에 검수·장애 대응 선택과 입력칸별 작성 안내·예시를 더할 거야. docs/training/samples/record-practice.md의 ‘업무 유형별 입력칸 작성 안내’ 표와 C1(검수 범위 확인)·C2(조회 조건 확인)를 참고해. 안내와 예시는 입력칸 옆에 보여 주고 본문을 자동으로 채우지 마. 기존 네 입력칸·필수 조건·도메인 안내·AI 정리는 유지해.

유형 선택·안내 표시, 관리 화면의 안내 수정·저장, 기록에 유형 저장 순서로 계획해. 안내는 도메인의 공용 설정으로 DB에 저장하고 관리자만 고치게 해. 기존 DB를 조사해 필요한 테이블·항목 변경과 개발용 DB 적용 방법을 알려 줘. 작성 중인 글과 기존 기록은 유지해. 코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

### 다음 기능 · 관리 탭에 유형별 안내 편집 기능 만들기

슬라이드 9·10장에서 새로 만드는 기능입니다. 현재 스타터킷에서는 **상단 관리 → 도메인 → 가상 교통관제 자료의 수정**을 펼친 뒤 아래로 내려가면, **핵심 용어 아래에 실무 기록 기본 양식**이 있습니다. 이 입력란은 도메인 공통 안내이며 유형별 편집 기능과 다릅니다. 내 화면이 다르면 AI에게 현재 코드의 위치를 확인하게 합니다. 이번에는 같은 도메인 수정 폼에 **업무 유형별 안내** 영역을 추가합니다.

**먼저 계획 요청**

```text
관리 → 도메인 → ‘가상 교통관제 자료’ 수정에 ‘업무 유형별 안내’ 편집 영역을 만들 거야. 실무 기록 작성 창에 표시하던 검수·장애 대응의 DB 설정을 재사용해. 기존 공통 안내인 ‘실무 기록 기본 양식’은 유지해. 내 화면에 없으면 코드에서 추가할 위치를 설명해.

DB의 유형 이름·입력칸별 작성 안내·예시를 불러와 관리자만 수정하고 저장·취소하게 해. 저장하면 DB에 반영하고 같은 도메인의 작성 창에서 불러오게 해. 필요한 화면·서버·DB 변경과 직접 확인할 순서를 계획해. 코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 기존 공통 안내와 새로 만들 유형별 편집 영역의 위치가 구분되나요?
- 8장에서 저장한 설정을 다시 사용하고 관리자만 수정하나요?
- 취소하면 이전 안내가 남고, 저장하면 작성 창에서 새 안내를 읽나요?

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 관리 → 도메인 → ‘가상 교통관제 자료’ 수정에 ‘업무 유형별 안내’ 편집 영역을 만들어. DB의 검수·장애 대응 이름·입력칸별 작성 안내·예시를 불러와 수정·저장·취소하게 해. 기존 공통 안내는 유지해.

저장하면 DB에 반영하고 서버에서도 관리자만 수정하게 해. 취소하면 이전 값을 보여 주고, 저장 실패 시 편집한 내용은 남겨. 빈 이름·중복 이름은 이유를 안내해. 필요한 DB 변경 파일을 만들고 개발용 DB에 적용해. 작성 화면을 새로고침하고 창을 열면 바꾼 안내가 보여야 해. 저장·취소·접근 제한을 검사하고 내가 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 관리 탭에서 가상 교통관제 자료의 수정을 펼쳐 **새로 만든 업무 유형별 안내**에 검수·장애 대응과 기존 작성 안내가 표시되는지 확인합니다.
2. 검수의 **상황** 입력칸에 보여 줄 안내를 **이번에 비교할 검수 기준은 무엇인가요?**로 고친 뒤 취소합니다. 원래 안내로 돌아오는지 봅니다. 다시 고쳐 이번에는 저장합니다.
3. 실무 기록 화면을 새로고침하고 작성 창에서 가상 교통관제 자료·검수를 선택합니다. 방금 저장한 작성 안내가 보이면 다음 기능으로 넘어갑니다. 장애 대응의 작성 안내와 기존 공통 안내도 그대로인지 봅니다.

**내가 확인할 것**

- 기록을 저장하고 다시 열었을 때 제목 아래에 선택한 유형이 보이나요?

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 기존 실무 기록 저장에 선택한 유형과 저장 당시 이름을 함께 남겨. 필요한 DB 변경 파일을 만들고 개발용 DB에 적용해. 저장 후 여는 기록 상세의 제목 아래에 업무 유형을 표시해. 유형이 없던 글은 ‘일반 기록’으로 보여 줘.

```

### 기록을 저장하고 유형 표시 확인하기

12장의 구현을 마친 뒤 진행합니다. 10장에서 끝낸 관리자 작성 안내 수정·저장은 반복하지 않습니다. 제목은 **유형 확인용 기록**으로 입력하고, 본문은 아래 예시를 사용합니다.

| 입력칸 | 확인용 예시 |
| --- | --- |
| 상황 | 검수 기록을 남기려고 한다. |
| 판단과 이유 | 검수 유형을 선택해 작성하기로 했다. |
| 결과 | 확인용 글을 작성했다. |
| 추가 확인할 내용 | 저장한 유형이 표시되는지 확인한다. |

1. 실무 기록 → 작성 창에서 **가상 교통관제 자료·프로젝트 A·검수**를 고릅니다. 10장에서 저장한 작성 안내 “이번에 비교할 검수 기준은 무엇인가요?”가 보이는지 확인합니다. 다르면 관리자 저장·작성 창 불러오기부터 보완합니다.
2. 제목에 **유형 확인용 기록**을 적고 위 예시의 본문을 입력합니다. 이미 같은 이름의 확인용 기록을 저장했다면 그 기록부터 열어 확인하고 중복해서 만들지 않습니다.
3. **실무 기록 저장**을 누릅니다. 저장 결과의 기록을 열어 제목 아래에 **업무 유형: 검수**가 표시되는지 확인합니다. 저장에 실패했다면 원인과 입력값 유지 여부를 확인한 뒤 다시 시도합니다.
4. 기록 상세를 **새로고침**합니다. 검수 표시와 본문이 남고, 기록이 검토 대기 상태인지 확인합니다.
5. **실무 기록 → 팀의 경험**에서 기존 공개 기록 **프로젝트 A 표본 점검에서 날짜 필터를 확인한 경험**을 엽니다. 업무 유형은 **일반 기록**으로 표시되고 기존 본문·공개 상태는 유지되어야 합니다.

확인용 글은 C1–C4와 별개로 검토 대기에 둡니다. 교육생이 직접 본 결과를 남기고, 유형 이름 변경 후 과거 표시 유지·작성 중 입력 복원 등 AI가 검사한 항목과 구분합니다.

| 함께 진행할 순서 | 개발할 것 | 확인할 결과 |
| --- | --- | --- |
| 1단계 · 인수인계 유형 등록 | 관리자가 유형 이름·입력칸별 작성 안내·예시를 입력해 DB에 저장하고 작성 창에서 선택하게 만들기 | 인수인계와 안내가 표시되고, 이 유형으로 저장한 기록에도 인수인계 표시 |
| 2단계 · 숨기기·다시 사용 | 같은 인수인계 유형을 새 글의 선택에서 숨기고 다시 사용하게 만들기. 관리 목록과 기존 기록은 유지 | 숨기면 새 글에서 선택 불가, 기존 기록 유지, 다시 사용하면 안내와 함께 선택 가능 |

모두 아래 순서로 진행합니다. 각 단계의 계획을 확인하고 실행한 뒤 화면에서 결과를 확인합니다.

**1단계 · 유형 등록을 구현하고 확인**

**먼저 계획 요청**

```text
관리 → 도메인 → 가상 교통관제 자료 수정의 ‘업무 유형별 안내’에 새 유형을 등록하는 기능을 계획해. 관리자가 이름·입력칸별 작성 안내·예시를 저장하면 같은 도메인의 실무 기록 작성 창에서 선택하게 할 거야. 기능을 만든 뒤 내가 ‘인수인계’를 직접 등록할게.

기존 도메인 설정과 기록의 유형 저장을 재사용해. 유형·작성 안내·예시는 DB에 저장하고 서버에서도 관리자만 바꾸게 해. 빈 이름·중복 이름의 안내, 기존 유형과 기록 유지, 필요한 DB 변경과 개발용 DB 적용·검사 순서를 포함해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획에서 판단할 것**

- 유형 추가 버튼과 이름·네 입력칸의 작성 안내·예시를 등록할 위치가 분명한가요?
- 기존 도메인 설정을 재사용하고 서버에서도 관리자만 변경하나요?
- 저장한 유형을 작성 창에서 고르고 기록 상세에서도 확인할 수 있나요?

**확인한 뒤 실행**

```text
확인한 계획대로 관리 → 도메인 → 가상 교통관제 자료 수정의 업무 유형별 안내에 ‘유형 추가’를 만들어. 이름·입력칸별 작성 안내·예시를 DB에 저장하고 실무 기록 작성 창에서 불러와. 기존 설정을 재사용하고 서버에서도 관리자만 변경하게 해. 빈 이름과 같은 도메인의 중복 이름은 이유를 안내해.

필요한 DB 변경 파일을 만들고 개발용 DB에 적용해. 새 유형으로 기록을 저장하면 상세에도 그 유형이 보여야 해. 기존 검수·장애 대응과 저장된 기록은 유지해. 유형이나 예제 기록을 자동으로 등록하지 마. 저장·조회·권한을 검사하고 내가 직접 확인할 순서를 알려 줘.
```

**직접 확인한 뒤 다음 단계로**

1. 관리자로 관리 → 도메인 → 가상 교통관제 자료 수정 → 업무 유형별 안내의 유형 추가를 누릅니다. 이름은 **인수인계**로 입력합니다.
2. **상황** 작성 안내에는 “어떤 업무를 누구에게 넘기나요?”, 예시에는 “검수 자료를 다음 담당자에게 전달하려고 한다.”를 입력합니다.
3. **판단과 이유** 작성 안내에는 “어떤 자료를 먼저 확인해야 하나요?”, 예시에는 “확인한 자료와 남은 일을 구분해 적기로 했다.”를 입력합니다.
4. **결과** 작성 안내에는 “어디까지 전달했나요?”, 예시에는 “전달할 내용을 정리했다.”를 입력합니다.
5. **추가 확인할 내용** 작성 안내에는 “남은 일은?”, 예시에는 “일정과 담당자를 확인해야 한다.”를 입력합니다.
6. 저장하고 관리 화면을 새로고침합니다. 인수인계와 네 칸의 작성 안내·예시가 남는지 확인합니다.
7. 일반 사용자로 실무 기록 → + 실무 기록 작성을 엽니다. 가상 교통관제 자료·프로젝트 A·인수인계를 고르고 등록한 안내·예시가 보이는지 확인합니다.
8. 제목은 **인수인계 확인용 기록**으로 적고 위 예시 네 문장을 각 본문 칸에 직접 입력합니다. 이미 같은 확인용 글이 있으면 그 글을 열어 확인합니다.
9. 실무 기록 저장 후 상세에 인수인계와 본문이 표시되고 새로고침해도 남는지 확인합니다. 기록은 검토 대기로 둔 뒤 숨기기 기능의 계획으로 넘어갑니다.

**2단계 · 숨기기·다시 사용을 구현하고 확인**

**먼저 계획 요청**

```text
관리 → 도메인 → 가상 교통관제 자료 수정의 ‘업무 유형별 안내’에 ‘숨기기’와 ‘다시 사용’을 더할 계획을 세워. 등록한 인수인계 유형과 그 유형으로 저장한 기록으로 확인할 거야. 숨긴 유형은 새 글의 선택 목록에서만 빼고 관리 목록에는 숨김 표시와 다시 사용 버튼을 남길 거야.

유형이나 기존 기록은 삭제하지 마. 저장된 기록의 유형 이름·본문·공개 상태를 유지해. 숨김 상태도 DB에 저장하고 서버에서 관리자만 변경하게 해. 다시 사용하면 작성 창에서 유형과 안내를 다시 보여 줘. 기존 설정을 재사용하고 필요한 DB 변경·개발용 DB 적용·검사 순서를 알려 줘. 코드와 DB는 아직 바꾸지 마.
```

**계획에서 판단할 것**

- 숨겨도 관리 목록과 저장한 기록은 남고, 새 글에서만 선택할 수 없나요?
- 숨김 상태가 DB에 저장되고 관리자만 변경하나요?
- 다시 사용하면 유형과 작성 안내·예시가 함께 돌아오나요?

**확인한 뒤 실행**

```text
확인한 계획대로 관리 → 도메인 → 가상 교통관제 자료 수정의 ‘업무 유형별 안내’에 ‘숨기기’와 ‘다시 사용’을 만들어. 관리자가 유형을 숨기거나 다시 사용하게 해. 숨김 상태도 DB에 저장하고 서버에서도 관리자만 변경하게 해. 필요한 DB 변경 파일을 만들고 개발용 DB에 적용해.

숨긴 유형은 새 글의 선택 목록에서만 빼고, 관리 목록에는 숨김 표시와 다시 사용 동작을 남겨. 유형이나 기존 기록을 삭제하지 마. 이미 저장한 기록의 유형·본문·공개 상태는 유지해. 다시 사용하면 작성 창에서 유형과 안내를 다시 고르게 해. 저장·조회와 기존 기록 유지를 검사하고, 내가 인수인계를 숨겼다가 다시 사용할 순서를 알려 줘.
```

**직접 확인한 뒤 다음 단계로**

1. 관리자로 관리 → 도메인 → 가상 교통관제 자료 수정 → 업무 유형별 안내에서 **인수인계 → 숨기기**를 누릅니다. 새로고침해도 관리 목록에 인수인계와 숨김 표시가 남아야 합니다.
2. 일반 사용자로 실무 기록 작성 창을 엽니다. 새 글에서는 인수인계가 빠지고 검수·장애 대응은 선택할 수 있어야 합니다.
3. 같은 일반 사용자로 **인수인계 확인용 기록**을 엽니다. 인수인계 표시·본문·검토 대기가 그대로인지 확인합니다.
4. 관리자로 인수인계를 **다시 사용**으로 바꾼 뒤 일반 사용자로 작성 창을 새로 엽니다. 인수인계와 안내·예시가 다시 보이고 검수·장애 대응도 선택할 수 있는 상태로 마칩니다.

**직접 확인:** 두 단계 모두 직접 확인합니다. 인수인계 등록·안내 표시·기록 저장, 숨기기·기존 기록 유지·다시 사용까지 확인한 뒤 다음 교시로 넘어갑니다.

**다음으로 이어가기:** 인수인계 등록·숨기기·다시 사용을 모두 확인했으면 다음 교시로 넘어갑니다. 다음 초안 실습에서는 기존 검수·장애 대응을 사용합니다.


**확인:** 새 기록의 검수 표시와 새로고침 후 유지, 기존 기록의 일반 표시와 내용 보존을 직접 확인합니다.

| 먼저 준비할 것 | 직접 해 볼 일 | 이렇게 되면 성공 |
| --- | --- | --- |
| 검수 유형에 쓴 문장 | 장애 대응으로 변경 | 안내만 변경, 입력값 유지 |
| 관리 탭의 업무 유형별 안내 | 작성 안내를 고친 뒤 취소·저장 각각 수행 | 취소는 이전 작성 안내, 저장은 작성 창에 새 작성 안내 표시 |
| 유형 확인용 기록 · 검수 | 기록 저장 후 상세 열기·새로고침 | 업무 유형: 검수 표시, 검토 대기 유지 |
| 유형 없는 기존 공개 기록 | 열어 읽기 | 일반 기록 표시, 기존 본문과 공개 상태 유지 |

**기본을 마쳤다면 — 선택 과제**

- **관리자 정렬:** 자주 쓰는 유형 순서를 바꾸고 작성 화면에도 반영하세요.
- **미리 보기에서 비교:** 검수·장애 대응의 작성 안내를 나란히 비교할 수 있게 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

작성 안내는 각 입력칸에 무엇을 적을지 알려주는 문구입니다. 상황·판단과 이유·결과·추가 확인할 내용의 네 입력칸과 필수 조건은 유지하고, 유형에 따라 안내와 예시를 바꿉니다. 관리자가 안내를 수정·저장할 화면도 개발합니다.

## 2. 여러 초안을 저장하고 이어 쓰기

[함께 볼 강의 화면](/lectures/week-03.html#slide-19)

**앞에서 이어받을 것:** 1교시에서 만든 작성 모달과 검수·장애 대응 유형을 사용합니다. 일반 사용자 계정으로 실무 기록 → + 실무 기록 작성을 엽니다. 초안 저장·내 초안 탭·복사·프로젝트별 보기는 이번에 새로 만듭니다.

1. 미완성 글을 내 계정의 초안으로 DB에 저장합니다.
2. 목록·수정·삭제를 만들고 두 초안으로 각각 확인합니다.
3. 모두 복사를 만든 뒤 프로젝트별 보기를 이어 만듭니다. 마지막에는 일반 사용자와 관리자 계정으로 나눠 확인합니다.

**내가 정할 것:** 미완성 글 저장 기준, 이동할 때의 선택, 초안을 볼 수 있는 계정

**저장 기준:** 초안의 제목·도메인·프로젝트·유형·본문·고른 근거를 작성자 계정과 함께 서버 DB에 저장합니다. 관리자도 다른 사람의 개인 초안을 조회·수정·삭제·복사할 수 없습니다. 초안 저장만으로 팀의 경험이나 검토함에 등록하지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
실무 기록 작성 창에 ‘초안 저장’을 더할 거야. 제목·도메인·프로젝트·유형과 쓰던 글·선택한 근거를 작성자 계정과 함께 DB에 저장할 계획을 세워. 제목과 범위를 정하면 본문에 빈칸이 있어도 저장하게 해. 완성한 글을 등록하는 ‘실무 기록 저장’은 유지하고, 초안 저장만으로 팀의 경험이나 검토함에 등록하지 마.

일반 사용자와 관리자 모두 자기 초안만 다루게 해. 필요한 테이블·항목과 DB 변경 적용 방법, 저장 실패 시 입력값을 지키는 방법을 알려 줘. 목록·수정·삭제·복사·프로젝트별 보기는 이후 순서대로 이어 만들 거야. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **남길 내용** 제목·프로젝트·유형·본문·고른 근거
- **미완성 글** 제목과 범위를 정하면 본문에 빈칸이 있어도 저장
- **개인 초안** 작성자만 접근, 관리자도 타인의 초안은 접근 불가

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 실무 기록 작성 창에 ‘초안 저장’을 만들어. 제목·도메인·프로젝트·유형·현재 글·선택한 근거를 내 계정의 초안으로 DB에 저장해. 본문은 덜 써져도 저장하고, 기존 ‘실무 기록 저장’은 유지해.

성공하면 저장한 제목과 완료 안내를 보여 줘. 실패하면 입력한 글을 남겨. 관리자도 다른 사람의 초안에 접근하지 못하게 서버에서 작성자를 확인해. 필요한 DB 변경 파일을 만들고 개발용 DB에 적용해 저장·조회를 검사해. 기존 탭의 임시 입력도 확인 없이 지우지 마. 저장 성공·실패와 권한 검사 결과, 내가 화면에서 확인할 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 일반 사용자로 작성 창에서 가상 교통관제 자료·프로젝트 A·검수를 고릅니다.
2. 제목에 [가상 실습 C1] 프로젝트 A 검수 범위 확인, 상황에 “검수 준비를 위해 프로젝트 A 검수 조건과 사업 개요를 읽었다.”를 입력합니다. 나머지 칸은 비워 둡니다.
3. 초안 저장 후 제목과 성공 안내를 확인합니다. 목록은 다음 기능에서 만듭니다. DB 저장·실패 처리는 AI 검사 결과도 확인합니다.

**이어서 개발하기**

**1단계 · 초안 복사**

**먼저 계획 요청**

```text
실무 기록 → 내 초안 목록에 ‘복사’를 더할 거야. 원본은 남기고 같은 프로젝트에 독립된 새 초안으로 DB에 저장해. 제목에는 ‘(복사)’를 붙이고 업무 유형·본문·선택한 근거를 가져와. 복사본을 고쳐도 원본은 바뀌면 안 돼. 일반 사용자와 관리자 모두 자기 초안만 복사하게 해.

기존 DB 구조를 재사용할 수 있는지, 필요한 변경과 복사 실패 시 원본을 지킬 방법을 계획해. 코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**계획에서 판단할 것**

**확인한 뒤 실행**


**관리자로 확인**

2. 내 초안 목록에 일반 사용자의 C1–C4와 복사본이 나오지 않아야 합니다. 관리자의 개인 초안도 본인 글만 보여야 합니다.
3. 주소나 요청을 바꾼 조회·수정·삭제·복사 차단은 AI의 서버 검사 결과로 확인합니다. 목록에 보이지 않는 것만으로 권한 검사를 통과했다고 판단하지 않습니다.

**마칠 때**

1. 일반 사용자 계정으로 돌아옵니다. C1–C4와 복사본이 남아 있는지 확인합니다.
2. 다음 교시에는 C1 원본을 이어 씁니다. 직접 확인한 결과·AI 검사 결과·미확인을 따로 남깁니다.

**다음으로 이어가기:** 일반 사용자 계정으로 돌아와 C1 원본을 남겨 둡니다. 다음 교시에는 이 초안의 본문을 완성하고 근거를 붙여 기록으로 등록합니다. C3도 남기며 C2·C4는 미완성 초안으로 유지합니다.


**확인:** 저장·목록·수정·삭제를 확인하고, 이어 복사와 프로젝트별 보기까지 모두 개발합니다.

| 먼저 준비할 것 | 직접 해 볼 일 | 이렇게 되면 성공 |
| --- | --- | --- |
| 일반 사용자 · C1과 C2 | C1만 수정 후 C2 열기 | C1 수정 반영, C2 유지 |
| 미저장 변경 | 닫기에서 취소 / 버리기 | 취소는 작성 중인 글 유지, 버리기는 마지막 저장값 유지 |
| 관리자 또는 다른 사용자 | 타인 초안 목록·직접 요청 확인 | 타인 초안 조회·수정·삭제·복사 불가 |

**기본을 마쳤다면 — 선택 과제**

- **다른 탭에서 동시에 고치기:** 저장 뒤 오래된 화면에서 덮어쓰려 하면 충돌을 알리고 다시 읽게 만드세요.
- **초안에서 이름으로 찾기:** 내 초안이 많아졌을 때 제목 검색과 결과 없음 안내를 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

초안 실습은 작성 권한이 있는 일반 사용자 계정으로 진행합니다. 예: writer@wiki.local. 관리자 예: admin@wiki.local. 강사가 배정한 다른 계정을 써도 됩니다. 같은 위키 주소에 다른 브라우저나 별도 프로필로 로그인해 확인합니다. 같은 브라우저의 탭 두 개는 로그인 상태를 공유할 수 있습니다. 서로 다른 개인 서버의 DB는 자동으로 합쳐지지 않습니다.

## 3. 근거를 붙여 기록 완성하기

[함께 볼 강의 화면](/lectures/week-03.html#slide-33)

**앞에서 이어받을 것:** 실무 기록 → 내 초안을 엽니다. 2교시에서 글을 쓴 일반 사용자로 C1 원본·C3가 남아 있는지 먼저 확인합니다. 이번에는 이 두 글을 완성해 검토 요청까지 연결합니다. 자료실의 새 버튼은 별도 원문 연결 확인용 초안으로 시험한 뒤 C1으로 돌아옵니다. C1 복사본·C2·C4는 제출하지 않습니다.

1. 내 초안의 C1·C3를 확인합니다. 자료를 읽다가 같은 작성 창을 열 수 있도록 새 버튼을 만들고 별도 연습 글로 시험합니다.
2. C1 원본에 두 문단을 연결하고 미리 보기·검토 요청·결과 보기를 만듭니다.
3. C3로 나란히 보기와 확인 목록을 모두 개발합니다. C3 제출·C4 미완성 안내를 확인한 뒤 관리자와 일반 사용자로 결과를 나눠 확인합니다.

**내가 정할 것:** 참고한 자료 정보와 선택한 근거의 구분, 미리 보기에 표시할 값, 제출한 결과를 다시 여는 위치

**저장 기준:** 참고한 자료 정보와 선택한 근거 문단을 구분해 초안 DB에 저장합니다. 검토 요청은 기존 기록 등록 경로를 재사용하며 초안·결과 기록의 연결과 제출 상태를 DB에 남깁니다. 같은 제출을 다시 요청해도 기록은 한 건이어야 합니다. 내 초안의 제출 완료 영역에는 결과 보기 링크를 남깁니다. 미제출 개인 초안은 관리자에게도 공개하지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
자료실의 공개 자료 상세에서 ‘추출한 원문’ 위에 ‘이 자료로 기록 시작’ 버튼을 더할 계획을 세워. 실무 기록의 ‘+ 실무 기록 작성’ 모달과 ‘내 초안’의 DB 저장·다시 열기 코드를 확인해 재사용해. 같은 작성 창에 자료의 도메인·프로젝트와 참고한 자료의 제목·버전을 표시해. 본문과 근거 문단은 내가 직접 입력하고 고를 거야.

새 초안으로 저장하고 기존 초안은 유지해. 쓰던 글이 있으면 기존 저장 후 이동·버리고 이동·취소 안내를 재사용해. 참고한 자료 정보를 초안 DB에 남길 방법, 필요한 테이블·항목 변경, 권한·실패 확인 순서를 알려 줘. 코드와 DB는 아직 바꾸지 마.
```

**계획을 읽고 내가 확인할 것**

- **재사용할 것** 실무 기록 작성 모달 · 내 초안 저장·다시 열기
- **가져올 정보** 참고한 자료의 제목·버전·도메인·프로젝트
- **기존 글 보호** 새 초안으로 저장하고 C1 원본은 유지

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 자료실 → 공개 자료 상세의 ‘추출한 원문’ 위에 ‘이 자료로 기록 시작’을 만들어. 실무 기록 작성 모달에 자료의 도메인·프로젝트를 적용하고 참고한 자료의 제목·버전을 보여 줘. 본문과 근거 문단은 자동으로 채우지 마. 새 초안 저장·미저장 이동 안내는 기존 기능을 재사용해.

초안에 참고한 자료 정보를 DB에 저장해 다시 열어도 표시해. 필요한 DB 변경 파일을 만들고 개발용 DB에 적용해. 서버에서 읽을 수 있는 현재 공개 자료인지 확인해. 기존 초안을 덮어쓰지 말고 실패하면 입력을 남겨. 재열기·기존 글 유지·권한을 검사하고 내가 확인할 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 일반 사용자로 자료실 → 프로젝트 A · 상태 화면 검수 조건 → 이 자료로 기록 시작을 누릅니다.
2. 도메인 가상 교통관제 자료·프로젝트 A가 적용됐는지 보고 검수 유형을 고릅니다. 제목은 원문 연결 확인용, 본문과 근거는 비워 초안 저장합니다.
3. 실무 기록 → 내 초안에서 연습 글을 다시 엽니다. 참고한 자료의 제목·버전이 남고 C1 원본·복사본·C2·C3·C4는 그대로 있어야 합니다. 같은 연습 글이 있으면 다시 만들지 않습니다.
4. 연습 글을 닫고 내 초안에서 C1 원본을 엽니다. 제목 끝에 (복사)가 없는 [가상 실습 C1] 프로젝트 A 검수 범위 확인입니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 후속 두 기능과 아래 두 단계의 업무 적용까지 모두 기본 실습입니다. 강사와 같은 순서로 진행합니다.

### C1 원본을 검토 대기 기록으로 연결

위 요청으로 기능을 만든 뒤 진행합니다. C1 원본의 제목은 [가상 실습 C1] 프로젝트 A 검수 범위 확인입니다. (복사)가 붙은 글과 원문 연결 확인용은 사용하지 않습니다.

| 입력칸 | 확인용 예시 |
| --- | --- |
| 상황 | 프로젝트 A의 검수 조건과 사업 개요를 읽었다. |
| 판단과 이유 | 사업 전체와 검수 표본의 범위를 구분하려고 비교했다. |
| 결과 | 전체 24대, 교육용 검수 표본 3대다. 실제 장비 시험은 하지 않았다. |
| 추가 확인할 내용 | 표본 장비 번호와 검수 일정 담당을 확인해야 한다. |

1. 일반 사용자로 내 초안에서 C1 원본을 엽니다. 프로젝트 A·검수 유형을 확인하고 위 표의 네 본문을 채웁니다.
2. 프로젝트 A 검수 조건의 표본 3대와 사업 개요의 24대 문단을 고릅니다. 서로 다른 범위임을 원문에서 확인합니다.
3. 미리 보기 → 수정 화면 → 다시 미리 보기로 오가며 마지막 입력값과 두 근거가 유지되는지 확인합니다.
4. 검토 요청 후 내 초안 → 제출 완료 → C1 결과 보기로 엽니다. 제목·본문·근거·검토 대기를 확인합니다.
5. 새로고침 후 결과 보기를 다시 눌러 같은 기록인지 확인합니다. 작성 중에는 C2·C3·C4·C1 복사본·원문 연결 확인용이 남아야 합니다.

입력·클릭으로 직접 본 결과와 AI의 중복 요청·실패·응답 끊김 검사 결과를 구분합니다. C1은 재작성하지 않고 C3에서 다음 개발을 이어갑니다.

### 3교시 내 업무에 적용하기

**여기까지 기본 실습입니다.** C1으로 제출 흐름을 확인했습니다. 아직 작성 중인 C3로 비교 화면과 확인 목록을 보강합니다. 새 기능은 모든 실무 기록에 공통으로 적용합니다. C1은 제출 완료에 둡니다. 일반 사용자로 내 초안의 **[가상 실습 C3] 프로젝트 B 사업별 조건 구분**을 엽니다. 프로젝트 B·검수 유형을 확인합니다. 상황은 **프로젝트 B의 상태 조회 조건을 검수 준비에 사용하려고 읽었다.**, 판단과 이유는 **프로젝트 A 조건과 섞지 않도록 프로젝트 이름과 문서를 함께 확인했다.**, 결과는 **도로전광표지 12대, 갱신 120초 이내, 이력 보관 30일이다. 실제 성능 시험은 하지 않았다.**, 추가 확인할 내용은 **실제 검수에 쓸 장비와 확인 순서를 담당자와 정해야 한다.**로 채웁니다. 공개 자료 **프로젝트 B · 누리시 상태 조회 조건**의 승인된 조건과 적용 범위의 본문 문단을 골라 초안 저장합니다. 아직 검토 요청하지 않고 두 기능을 모두 개발합니다.

| 함께 진행할 순서 | 개발할 것 | 확인할 결과 |
| --- | --- | --- |
| 1단계 · 나란히 보기 | 작성 내용과 선택한 근거를 같은 화면에서 비교하고 수정으로 돌아오기 | 근거를 바꿔 읽어도 본문 유지, 정확한 문단 열기 |
| 2단계 · 제출 전 확인 목록 | 작성자가 세 항목을 확인하고 내용을 바꾸면 다시 확인하게 만들기 | 확인 상태 DB 저장, 내용 수정 시 초기화, 공개 승인과 구분 |

모두 아래 순서로 진행합니다. 각 단계의 계획을 확인하고 실행한 뒤 화면에서 결과를 확인합니다.

**1단계 · 본문과 근거 나란히 보기**

**먼저 계획 요청**

```text
실무 기록 작성 창에 ‘근거와 나란히 보기’를 더할 거야. 한쪽에는 작성 중인 본문, 다른 쪽에는 선택한 근거의 제목·버전·문단을 보여 줘. 근거를 번갈아 읽으며 수치와 적용 범위를 비교하는 화면이야. 모든 기록에 적용하고, 확인 사례는 docs/training/samples/record-practice.md의 C3(프로젝트 B 사업별 조건 구분)를 참고해.

읽을 근거를 바꿔도 선택한 근거 목록과 본문은 유지하고 수정으로 돌아가기를 제공해. 작은 화면은 본문·근거를 위아래로 배치해. 근거가 없으면 연결한 근거가 없다고 안내해. 기존 초안·근거 데이터를 재사용하고 필요한 DB 변경과 검사 순서를 알려 줘. 코드와 DB는 아직 바꾸지 마.
```

**계획에서 판단할 것**

- 작성 중인 본문과 선택한 실제 근거를 비교하나요?
- 근거 열람과 선택 해제를 혼동하지 않게 하나요?
- 작은 화면과 근거 없는 글에서도 입력을 유지하나요?

**확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 작성 창에 ‘근거와 나란히 보기’를 만들어. 현재 본문과 선택한 근거의 제목·버전·문단을 함께 보여 줘. 읽을 근거를 바꾸거나 정확한 원문 위치를 열어도 본문과 선택한 근거 목록은 유지해. 수정으로 돌아가기를 제공하고 작은 화면은 위아래로 배치해.

근거가 없는 글도 본문은 보여 주고 연결한 근거가 없다고 안내해. 기존 초안·근거 조회와 권한 검사를 재사용해. DB 변경이 필요하면 변경 파일을 만들어 개발용 DB에 적용해. 본문 유지·근거 전환·권한을 검사하고 내가 ‘[가상 실습 C3] 프로젝트 B 사업별 조건 구분’으로 확인할 순서를 알려 줘.
```

**직접 확인한 뒤 다음 단계로**

1. C3에서 근거와 나란히 보기를 엽니다. 승인된 조건 문단으로 12대·120초·30일을 비교하고, 적용 범위 문단으로 프로젝트 B에만 해당하는지 확인합니다.
2. 두 문단을 번갈아 읽고 정확한 원문 위치를 엽니다. 수정으로 돌아왔을 때 본문과 두 근거가 모두 남아야 합니다.
3. C3를 초안 저장하고 C4를 엽니다. 연결한 근거가 없다는 안내와 쓰던 상황이 남는지 확인합니다. C4의 판단과 이유·결과는 채우지 않고 닫습니다.
4. 내 초안에서 C3를 다시 엽니다. 이어서 이 글로 제출 전 확인 목록을 시험합니다.

**2단계 · 작성자의 제출 전 확인 목록**

**먼저 계획 요청**

```text
실무 기록 작성 창의 미리 보기에 작성자가 확인할 세 항목을 더할 거야. 모든 새 제출에 적용해. ‘프로젝트·업무 유형이 맞다’, ‘확인한 사실과 추측을 구분했다’, ‘근거와 비교했거나 근거 없는 내 경험임을 밝혔다’야. 모두 확인해야 검토 요청하게 하고 초안 저장은 계속 허용해.

체크한 내용이 무엇인지 확인 상태와 함께 DB에 저장해. 제목·범위·유형·메모·본문·근거가 바뀌면 확인을 풀고 다시 확인하게 해. 서버에서도 같은 기준을 검사해. 기존 필수값·검토 권한과 이미 제출한 기록의 본문·검토 상태는 유지해. 필요한 DB 변경과 확인 순서를 계획해. 코드와 DB는 아직 바꾸지 마.
```

**계획에서 판단할 것**

- 작성자가 직접 확인하고 AI는 자동으로 체크하지 않나요?
- 확인 상태가 수정한 내용에 그대로 남지 않나요?
- 필수 입력·공개 승인과 작성자 확인을 구분하나요?

**확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 작성 창의 미리 보기에 세 확인 항목을 만들어. ‘프로젝트·업무 유형이 맞다’, ‘확인한 사실과 추측을 구분했다’, ‘근거와 비교했거나 근거 없는 내 경험임을 밝혔다’야. 작성자가 직접 모두 체크한 현재 내용만 검토 요청하게 해. 초안 저장 없이 작성한 새 글에도 적용해.

확인 상태와 그때의 내용을 구분할 정보를 DB에 저장하고 필요한 변경 파일을 만들어 개발용 DB에 적용해. 제목·범위·유형·메모·본문·근거를 바꾸면 체크를 풀고 재확인을 안내해. 서버에서도 확인 상태와 필수값을 검사해. 초안 저장은 계속 허용하고 근거 없이 쓴 경험도 허용해. 이미 제출한 기록의 본문·검토 상태는 유지해. 내용 수정·저장·재열기를 검사하고 공개는 자동 승인하지 마.
```

**직접 확인한 뒤 다음 단계로**

1. C3를 미리 보고 세 항목을 직접 확인합니다. 내용을 바꾸지 않고 초안 저장·다시 열기 했을 때 확인 상태가 남아야 합니다.
2. C3의 추가 확인할 내용 끝에 “검수 일정도 확인해야 한다.”를 덧붙입니다. 체크가 풀리고 다시 확인하라는 안내가 나와야 합니다.
3. 바뀐 내용을 읽고 세 항목을 다시 확인한 뒤 초안 저장합니다. 다음 계정별 확인에서 C3를 검토 요청합니다.

**직접 확인:** 두 기능을 확인한 뒤 C3는 검토 요청하고 C4는 필수값 안내를 확인해 초안으로 남깁니다. 관리자로 제출된 C1·C3를 읽고, 다른 사용자의 미제출 초안은 열 수 없는지 확인합니다.

**일반 사용자로 확인**

1. writer@wiki.local 또는 배정된 작성 계정으로 C3의 변경 내용을 다시 확인하고 검토 요청합니다. 내 초안 → 제출 완료에서 C1·C3의 결과 보기를 엽니다. 두 글은 서로 다른 프로젝트의 검토 대기 기록이어야 합니다.
2. C2·C4·C1 복사본·원문 연결 확인용은 작성 중에 남습니다. C4에서는 세 확인 항목을 체크해도 판단과 이유·결과가 비어 있으면 제출이 막혀야 합니다. 빈칸을 자동으로 채우거나 성공 처리하지 않습니다.
3. 일반 작성자는 공개 승인할 수 없어야 합니다. 작성자의 세 확인 항목을 모두 체크해도 공개 상태로 바뀌면 안 됩니다.
4. 관리자로 바꾸기 전에 C1·C3 결과 보기로 연 페이지 주소를 각각 복사해 둡니다. 계정 전환은 별도 브라우저를 사용하거나 로그아웃 후 진행합니다.

**관리자로 확인**

1. 같은 서버에서 admin@wiki.local 또는 배정된 관리자로 로그인합니다. 복사해 둔 C1·C3 결과 주소를 열어 제목·본문·근거·검토 대기 상태를 확인합니다.
2. 현재 관리자는 검토 권한도 포함합니다. 이번 실습에서는 승인·반려를 실행하지 않습니다. 본인이 등록한 기록의 승인 차단은 AI 검사 결과로 확인합니다.
3. 다른 사용자의 내 초안과 제출 완료 목록 자체는 열 수 없어야 합니다. 관리자가 읽는 것은 별도 결과 기록이며 미제출 초안 본문이 아닙니다. 직접 요청 차단은 AI 검사 결과와 구분합니다.

**다음 교시로 이어가기**

2. 두 결과 기록은 검토 대기, C2·C4는 초안으로 유지합니다. 실제 승인이나 회사 업무 완료를 뜻하는 것으로 기록하지 않습니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

초안은 나만 이어 쓸 글입니다. 검토 요청을 마치면 검토 담당자도 읽는 검토 대기 기록이 됩니다. C1으로 제출 흐름을 먼저 확인하고, 아직 제출하지 않은 C3로 확인 기능 두 개를 보강합니다. 검토 요청이 공개 승인을 뜻하지는 않습니다.

## 4. 기록 검색과 개인 할 일 관리하기

[함께 볼 강의 화면](/lectures/week-03.html#slide-47)

**앞에서 이어받을 것:** 기록을 쓴 일반 사용자로 실무 기록 → 내 초안 → 제출 완료 → 결과 보기에서 C1·C3를 엽니다. 두 기록은 검토 대기입니다. 팀의 경험에 검색을 더한 뒤 같은 기록을 찾아 개인 할 일을 등록합니다. 즐겨찾기는 이미 공개된 날짜 필터 경험 기록으로 확인합니다.

1. 팀의 경험에 프로젝트·업무 유형·제목·공개 상태 검색과 출발 목록으로 돌아오기를 만듭니다.
2. 기록 상세에서 개인 할 일을 등록하고 실무 기록의 내 확인할 일에서 수정·삭제·완료·미완료로 되돌리기를 만듭니다.
3. 공개 경험 기록은 기존 즐겨찾기에 연결하고, 개인 할 일에서 연결 기록을 읽은 뒤 같은 목록으로 돌아오게 합니다.

**내가 정할 것:** 기록 본문과 개인 할 일의 구분, 내 계정에 저장할 값, 완료·되돌리기와 기록 열람의 차이

**저장 기준:** 개인 할 일은 소유 계정·작업공간·제목·완료 여부·연결 기록과 버전을 DB에 저장합니다. 변경 파일과 개발용 DB 적용을 확인합니다. 검색·즐겨찾기·집계는 기존 저장 구조를 조사해 재사용합니다. 관리자도 타인의 개인 할 일은 조회·수정·집계하지 못하게 하며 기록 열람은 기존 권한을 따릅니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
실무 기록 → 팀의 경험에서 조건으로 기록을 찾고, 상세를 읽은 뒤 같은 목록으로 돌아오게 할 계획을 세워. 이 기능의 코드를 확인해 도메인·프로젝트·제목·공개 상태 조회를 재사용하고, 저장된 업무 유형으로도 찾게 해. 유형이 없는 예전 글은 ‘일반 기록’으로 표시해. 프로젝트를 고르면 같은 도메인의 공통 기록도 함께 보여 줘.

조건을 바꾸면 첫 페이지로 이동하고, 기록을 읽은 뒤 출발한 탭·검색 조건·페이지로 돌아오게 해. 내 초안의 제출 완료에서 열었다면 그 목록으로 돌아와야 해. 개인 초안은 검색에 섞지 말고, 제출한 기록은 기존 열람 권한을 따라. 필요한 DB 변경과 확인할 순서를 알려 줘. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **기존 기능 조사** 목록 조회·기록 열람·저장된 업무 유형
- **검색할 대상** 제출한 기록 · 개인 초안은 제외
- **돌아올 위치** 출발한 탭·검색 조건·페이지

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 계획대로 실무 기록 → 팀의 경험 목록에 도메인·프로젝트·업무 유형·제목·공개 상태 검색을 만들어. 기존 조회 기능을 재사용하고 유형 없는 글은 ‘일반 기록’으로 찾아. 프로젝트 선택 시 같은 도메인의 공통 기록도 함께 표시하고 조건 변경 시 첫 페이지로 이동해.

기록 상세에는 출발한 탭·조건·페이지로 돌아가는 링크를 만들어. 내 초안의 제출 완료와 자료실에서 온 경우도 각각 제자리로 돌아가게 해. 개인 초안은 검색에서 제외하고 기존 열람 권한은 서버에서 확인해. DB 변경이 필요하면 변경 파일을 만들고 개발용 DB에 적용해. 네가 검사한 결과와 내가 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 팀의 경험에서 가상 교통관제 자료·프로젝트 A·검수·검토 대기·검수 범위를 입력해 C1을 엽니다. 돌아온 뒤 조건을 확인합니다.
2. 프로젝트 B·사업별 조건으로 바꿔 C3를 찾아 같은 흐름을 확인합니다. 조건 변경 때 첫 페이지로 이동해야 합니다.
3. 내 초안 → 제출 완료 → 결과 보기로 C1을 연 뒤 돌아오면 제출 완료 목록이어야 합니다.
4. 일반 기록·공개·날짜 필터로 기존 공개 경험 기록도 찾습니다. C2·C4 개인 초안은 목록에 나타나면 안 됩니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 후속 두 기능과 아래 두 단계의 업무 적용까지 모두 기본 실습입니다. 강사와 같은 순서로 진행합니다.

### 다음 기능 · 기록에 개인 할 일을 등록하고 관리하기

**먼저 계획 요청**

```text
실무 기록 상세의 ‘추가 확인할 내용’ 아래에 ‘내 확인할 일’ 입력 영역을 만들 거야. 본문을 자동 복사하지 않고 내가 할 일 제목을 적어 등록하게 해. 실무 기록 화면에는 팀의 경험·내 초안과 오갈 ‘내 확인할 일’ 탭을 추가해.

목록에서 수정·삭제·완료·‘미완료로 되돌리기’를 제공해. 내 계정·작업공간·할 일 제목·완료 여부·연결 기록과 버전을 DB에 저장할 계획을 세워. 관리자도 다른 사람의 개인 할 일은 조회·수정하지 못하게 해. 기록 본문과 공개 상태는 그대로 두고, 필요한 DB 변경과 확인 방법을 알려 줘. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 본문의 추가 확인할 내용과 개인 할 일을 별도로 저장하나요?
- 할 일은 내 계정에 저장하고 관리자에게도 다른 사람의 목록을 보여 주지 않나요?
- 완료와 미완료로 되돌리기가 할 일 상태만 바꾸나요?

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 상세의 ‘추가 확인할 내용’ 아래에 할 일 제목 입력·등록을 만들고, 실무 기록 메뉴에 ‘내 확인할 일’ 탭을 더해. 목록에서 제목 수정·삭제 확인과 취소·완료·‘미완료로 되돌리기’를 제공해. 빈 제목은 막고 저장 중 중복 등록도 막아.

소유 계정·작업공간·제목·완료 여부·연결 기록과 버전을 DB에 저장해. 변경 파일을 만들고 개발용 DB에 적용해. 서버에서도 내 할 일인지 확인하고 등록할 때는 연결 기록을 읽을 수 있는지 확인해. 관리자도 타인의 할 일에 접근하지 못하게 해. 기록 본문·공개 상태는 바꾸지 마. 타인 항목 직접 조회·수정·삭제 차단과 저장·삭제 취소·완료·되돌리기를 검사하고 내가 확인할 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 일반 작성 계정으로 C1 결과 기록을 엽니다. 표본 장비 번호 확인, 검수 일정 담당 확인 두 일을 등록합니다. C3에는 검수 장비·순서 확인을 등록합니다.
2. 내 확인할 일에서 첫 제목을 표본 장비 번호 3개 확인으로 고칩니다. 삭제를 눌렀다가 취소해 남는지 보고, 완료했다가 미완료로 되돌립니다.
3. C1에 삭제 확인용을 추가해 삭제합니다. 연습 항목만 없어지고 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개가 남아야 합니다.
4. 같은 서버·계정으로 다른 브라우저에서 열어 세 가지 일과 수정한 제목을 확인합니다. C1·C3의 본문과 검토 대기는 유지합니다.

### 다음 기능 · 공개 기록 즐겨찾기와 할 일의 기록 링크 연결하기

**먼저 계획 요청**

```text
실무 기록 상세에 즐겨찾기 별표·폴더 선택을 연결하고, ‘내 확인할 일’에서는 연결 기록을 열게 할 거야. 자료실·홈의 기존 즐겨찾기와 폴더 코드를 확인해 재사용해. 현재 읽을 수 있는 공개 버전만 추가하고 같은 폴더에 같은 버전을 중복 저장하지 않게 해. 공개 버전이 없는 검토 대기 기록에는 공개 후 이용할 수 있다고 안내해.

내 확인할 일에는 연결한 기록을 여는 링크와 같은 탭·조건으로 돌아오는 길을 더해. 기록 접근이 사라지면 기록 제목·본문을 숨기고 열 수 없다고 안내하되, 내 할 일은 정리할 수 있게 해. 기존 메모·읽음 동작을 재사용하고 DB 변경 필요 여부와 검사 방법을 알려 줘. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 이미 만든 즐겨찾기·폴더를 재사용하나요?
- 검토 대기 기록과 공개된 기록을 구분하나요?
- 할 일에서 기록을 읽고 같은 목록으로 돌아오나요?

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 상세에 기존 즐겨찾기 별표·폴더 선택을 연결해. 현재 열람 가능한 공개 버전을 사용하고 같은 폴더의 중복을 막아. 공개 버전이 없는 기록에는 ‘공개 후 즐겨찾기에 추가할 수 있습니다’라고 표시해. 기존 개인 메모와 읽음 동작은 재사용해.

내 확인할 일에서 연결 기록을 열고 같은 탭·조건으로 돌아오게 해. 서버에서 기록 열람 권한을 다시 확인하고 접근할 수 없으면 제목·본문 대신 안내를 보여 줘. 내 할 일 수정·삭제는 계속 허용해. 할 일 완료만으로 원문·공개 상태·읽음 표시를 바꾸지 마. DB 변경이 필요하면 변경 파일과 개발용 DB 적용까지 진행해. 공개 기록과 대기 기록의 차이를 검사해.
```

**다음 기능 전에 직접 확인**

1. 팀의 경험에서 가상 교통관제 자료·프로젝트 A·일반 기록·공개로 찾습니다. 제목 검색어는 날짜 필터입니다.
2. 프로젝트 A 표본 점검에서 날짜 필터를 확인한 경험을 열어 기존 즐겨찾기 폴더에 넣습니다. 폴더가 없다면 기존 폴더 만들기 기능으로 검수 참고를 만듭니다. 이미 추가했다면 다시 넣지 않고 한 건인지 확인합니다.
3. C1·C3에는 공개 후 이용 안내가 나오는지 확인합니다. 즐겨찾기에 넣으려고 공개 승인하지 않습니다.
4. 내 확인할 일의 C1 연결 기록을 열고 돌아옵니다. 같은 목록이어야 하며 할 일 완료와 즐겨찾기 읽음 표시는 서로 바뀌지 않아야 합니다.

**만든 뒤 직접 눌러 보기**

### 제출한 두 기록으로 개인 할 일 확인하기

개인 할 일 구현에서 등록한 세 가지 일과 즐겨찾기 연결에서 사용한 공개 기록을 이어 확인합니다. C1·C3는 검토 대기이며 같은 할 일을 새로 등록하지 않습니다.

| 입력칸 | 확인용 예시 |
| --- | --- |
| 프로젝트 A · 가람시 / C1 | 표본 장비 번호 3개 확인 |
| 프로젝트 A · 가람시 / C1 | 검수 일정 담당 확인 |
| 프로젝트 B · 누리시 / C3 | 검수 장비·순서 확인 |

1. 내 확인할 일에서 프로젝트 A의 ‘표본 장비 번호 3개 확인’·‘검수 일정 담당 확인’, 프로젝트 B의 ‘검수 장비·순서 확인’이 남아 있는지 확인합니다. 앞에서 수정한 제목을 다시 고치지 않습니다.
2. 세 가지 일을 모두 미완료로 둡니다. 같은 서버·계정으로 다른 브라우저에서 열어 제목과 상태가 그대로인지 확인합니다.
3. 프로젝트 A의 할 일에서 C1 연결 기록을 열어 본문과 검토 대기 상태를 확인한 뒤 같은 목록으로 돌아옵니다. 프로젝트 B의 C3도 같은 방법으로 엽니다.
4. 기존 즐겨찾기 폴더에서 ‘프로젝트 A 표본 점검에서 날짜 필터를 확인한 경험’을 다시 엽니다. 앞에서 넣은 기록을 중복으로 추가하지 않습니다.
5. C1·C3에는 공개 후 즐겨찾기를 이용할 수 있다는 안내가 나와야 합니다. 공개 승인 없이 두 기록은 검토 대기로 둡니다.

실제 문의·장비 점검·공개 승인을 수행하지 않습니다. 이미 만든 세 가지 일을 재사용하고 같은 일을 중복 등록하지 않습니다.

### 4교시 내 업무에 적용하기

**여기까지 기본 실습입니다.** 실무 기록 → 내 확인할 일에서 이어갑니다. C1의 표본 장비 번호 3개 확인·검수 일정 담당 확인, C3의 검수 장비·순서 확인을 모두 미완료로 준비합니다. 프로젝트별 개수는 내 확인할 일에 등록한 항목을 셉니다. 프로젝트 A의 할 일 하나를 완료하면 프로젝트 A의 미완료는 1개가 되고 프로젝트 B는 1개로 유지됩니다. 기존 할 일이 있다면 실제 개수에 합산합니다. 새 할 일을 반복 등록하지 않습니다.

| 함께 진행할 순서 | 개발할 것 | 확인할 결과 |
| --- | --- | --- |
| 1단계 · 미완료 보기 | 프로젝트·유형·완료 조건으로 내 할 일을 찾고 완료 후 빈 목록에서 전체 보기로 이동 | 프로젝트 B의 할 일 하나 완료 → 0개 안내 → 전체 보기 → 미완료로 되돌리기 |
| 2단계 · 프로젝트별 개수 | 내 전체·미완료·완료 개수를 누르면 같은 조건의 목록 열기 | 프로젝트 A의 할 일 하나 완료 시 프로젝트 A는 2·1·1, 프로젝트 B는 1·1·0 유지 |

모두 아래 순서로 진행합니다. 각 단계의 계획을 확인하고 실행한 뒤 화면에서 결과를 확인합니다.

**1단계 · 미완료 할 일 보기**

**먼저 계획 요청**

```text
실무 기록의 ‘내 확인할 일’에 도메인·프로젝트·업무 유형과 ‘전체 / 미완료 / 완료’ 조건을 더할 거야. 기록 검색과 달리 프로젝트 A를 고르면 프로젝트 A에 연결한 내 할 일만 보여 줘. 공통 기록의 할 일은 ‘공통’으로 따로 고르게 해. 조건은 연결한 기록의 범위와 유형을 사용해.

미완료 목록에서 완료한 일은 빠지고, 완료 목록에서 ‘미완료로 되돌리기’를 누르면 다시 미완료에 나타나야 해. 0개면 ‘남은 일이 없습니다’와 ‘전체 보기’를 보여 줘. 조건을 바꾸면 첫 페이지로 가고 기록을 읽고 돌아와도 조건을 유지해. 기존 DB·권한을 재사용할 계획과 확인 순서를 알려 줘. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획에서 판단할 것**

- 프로젝트 A를 골랐을 때 프로젝트 B·공통 할 일이 섞이지 않나요?
- 완료한 일을 다시 찾고 미완료로 되돌릴 수 있나요?
- 마지막 일을 완료해도 전체 목록으로 돌아갈 수 있나요?

**확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 → 내 확인할 일 탭에 도메인·프로젝트·업무 유형·전체/미완료/완료 조건을 만들어. 프로젝트 선택은 해당 프로젝트의 내 할 일만 보여 주고 공통은 별도 선택으로 제공해. 조건 변경 시 첫 페이지로 이동하고 기록을 읽고 돌아와도 조건을 유지해.

미완료에서 완료한 일은 빠지고 완료 목록에서는 ‘미완료로 되돌리기’를 제공해. 0개면 남은 일이 없다는 안내와 전체 보기 버튼을 표시해. 전체 보기는 도메인·프로젝트·유형을 유지하고 완료 조건만 전체로 바꿔. 기존 DB 저장·소유자 확인을 재사용하고 필요한 DB 변경은 변경 파일을 만들어 개발용 DB에 적용해. 목록 변화와 빈 상태를 검사해.
```

**직접 확인한 뒤 다음 단계로**

1. 내 확인할 일에서 가상 교통관제 자료·프로젝트 B·검수·미완료를 고릅니다. 검수 장비·순서 확인 한 개가 보여야 합니다.
2. 그 일을 완료합니다. 목록이 비고 남은 일이 없다는 안내가 나와야 합니다. 프로젝트 A의 두 일은 바뀌면 안 됩니다.
3. 전체 보기를 눌러 프로젝트 B 조건이 유지되는지 확인합니다. 완료한 프로젝트 B의 할 일을 미완료로 되돌린 뒤 미완료 목록에서 다시 찾습니다.
4. 프로젝트 B의 연결 기록을 읽고 돌아옵니다. 프로젝트 B·검수·미완료 조건이 남아 있어야 합니다.

**2단계 · 프로젝트별 내 할 일 개수**

**먼저 계획 요청**

```text
실무 기록 → 내 확인할 일 탭 상단에 프로젝트별 ‘전체·미완료·완료’ 개수를 보여 줄 거야. 선택한 도메인·업무 유형에서 내 할 일만 세고 공통은 별도 행으로 구분해. 화면의 현재 페이지뿐 아니라 조건에 맞는 전체 데이터를 세어 줘.

개수 표는 프로젝트·완료 조건을 바꿔도 유지하고, 숫자를 누르면 아래 목록의 프로젝트·완료 조건을 그 숫자에 맞게 바꿔. 완료·되돌리기·삭제 후 숫자와 목록을 함께 갱신해. 다른 사람의 할 일이나 회사 전체 업무 진행률은 포함하지 않아. 기존 DB를 재사용할 방법과 확인할 순서를 계획해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획에서 판단할 것**

- 프로젝트마다 내 전체·미완료·완료를 구분하나요?
- 숫자를 누르면 그 숫자에 해당하는 목록이 열리나요?
- 완료·되돌리기·삭제 뒤 숫자와 목록이 함께 바뀌나요?

**확인한 뒤 실행**

```text
확인한 계획대로 실무 기록 → 내 확인할 일 탭 상단에 프로젝트별 전체·미완료·완료 개수를 만들어. 선택한 도메인·업무 유형의 내 할 일 전체를 DB에서 집계하고, 프로젝트·완료 조건은 아래 목록에만 적용해. 공통은 별도 행으로 보여 줘. 숫자를 누르면 그 프로젝트·완료 조건으로 첫 페이지를 열어.

완료·미완료로 되돌리기·삭제 후 개수와 목록을 함께 갱신해. 다른 계정의 할 일은 집계하지 마. 필요한 DB 변경은 변경 파일을 만들고 개발용 DB에 적용해. 기능 검사는 별도 테스트 데이터로 하고, 내가 저장한 할 일은 바꾸지 마. 한 프로젝트의 완료·되돌리기·삭제가 해당 개수와 목록에 반영되고 다른 프로젝트·계정은 유지되는지 검사해. 검사 결과와 내가 직접 눌러 볼 순서를 알려 줘.
```

**직접 확인한 뒤 다음 단계로**

1. 기능 구현·검사는 AI가 별도 테스트 데이터로 수행합니다. 교육생은 이미 등록한 세 가지 일을 새로 만들지 않고 모두 미완료인지 직접 확인합니다. 가상 교통관제 자료·검수 조건에서 프로젝트 A 전체 2·미완료 2·완료 0, 프로젝트 B 전체 1·미완료 1·완료 0이어야 합니다. 기존 할 일이 있으면 실제 개수에 합산합니다.
2. 프로젝트 A의 미완료 2를 누르고 표본 장비 번호 3개 확인만 완료합니다. 프로젝트 A는 2·1·1, 프로젝트 B는 1·1·0이어야 합니다.
3. 프로젝트 A의 완료 1을 눌러 해당 일을 미완료로 되돌립니다. 프로젝트 A는 2·2·0으로 돌아와야 합니다.
4. 프로젝트 B의 유일한 일을 완료해 프로젝트 B의 미완료가 0인지 확인한 뒤 전체 보기에서 미완료로 되돌립니다. 새로고침과 같은 계정의 다른 브라우저에서도 같은 개수여야 합니다.

**직접 확인:** 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개로 조건·개수·빈 목록·되돌리기를 확인하고 일반 사용자·관리자의 개인 할 일이 분리되는지 확인합니다.

**일반 사용자로 확인**

1. writer@wiki.local 또는 배정된 작성 계정으로 내 확인할 일의 세 항목과 프로젝트별 개수를 확인합니다. 같은 서버·계정의 다른 브라우저에서도 저장한 제목·완료 상태를 확인합니다.
2. C1·C3 연결 기록의 본문·검토 대기를 확인하고 개인 할 일 목록으로 돌아옵니다. 즐겨찾기에서는 기존 공개 날짜 필터 경험 기록을 엽니다.
3. C1·C3 결과 기록 주소를 보관합니다. 관리자와의 비교 전 세 가지 일을 모두 미완료로 되돌립니다.

**관리자로 확인**

1. 같은 서버에 admin@wiki.local 또는 배정된 관리자로 로그인합니다. 내 확인할 일에 일반 사용자의 세 항목과 숫자가 나타나면 안 됩니다. 관리자 본인의 기존 할 일은 보일 수 있습니다.
2. 보관한 C1 결과 주소를 엽니다. 관리자는 검토 권한으로 기록 본문을 읽을 수 있지만 작성자의 개인 할 일은 보이지 않아야 합니다. 공개 승인·반려는 하지 않습니다.
3. C1에 관리자 확인용이라는 관리자 개인 할 일을 한 개 등록합니다. 관리자 목록에서만 보이는지 확인합니다. 일반 사용자로 돌아와 자신의 프로젝트 A의 할 일 두 개·프로젝트 B의 할 일 한 개와 숫자가 유지되는지 확인합니다.
4. 타인 할 일 ID로 직접 조회·수정·삭제하는 요청의 차단은 AI가 검사합니다. 화면에서 직접 본 결과와 AI 서버 검사 결과를 구분해 남깁니다.

**마무리할 상태**

1. 관리자 확인용 항목은 관리자 계정에서 삭제한 뒤 일반 사용자로 돌아옵니다. 사용자의 세 가지 일은 모두 미완료로 둡니다.
2. C1·C3는 검토 대기, C2·C4는 개인 초안, 날짜 필터 경험 기록은 기존 공개 상태를 유지합니다. 마지막 장에서 오늘 만든 기능을 이어 확인합니다.

**다음으로 이어가기:** 일반 사용자로 돌아와 세 가지 일을 모두 미완료로 둡니다. 마지막 장에서 개인 초안·제출 기록·할 일·공개 기록 즐겨찾기를 이어 확인합니다.


**확인:** 기록 검색·개인 할 일·즐겨찾기 연결 뒤 미완료 보기와 프로젝트별 개수까지 모두 확인합니다.

| 먼저 준비할 것 | 직접 해 볼 일 | 이렇게 되면 성공 |
| --- | --- | --- |
| 프로젝트 A의 미완료 할 일 두 개·프로젝트 B의 미완료 할 일 한 개 | 프로젝트 A의 할 일 하나 완료 후 미완료로 되돌리기 | 프로젝트 A의 목록·개수만 변경, 프로젝트 B와 기록 본문·공개 상태 유지 |
| 프로젝트 B의 미완료 한 개 | 완료 → 전체 보기 → 미완료로 되돌리기 | 0개 안내 후 같은 프로젝트에서 다시 찾기 |
| 일반 사용자와 관리자 | 내 확인할 일과 연결 기록 열기 | 개인 할 일은 소유자만, 기록은 기존 열람 권한 적용 |

**기본을 마쳤다면 — 선택 과제**

- **여러 할 일 한 번에 정리:** 현재 목록에서 고른 항목만 완료하고 프로젝트 변경 시 선택을 해제하세요.
- **홈에서 이어가기:** 내 미완료 할 일을 홈에서 열고, 변경 후 개수와 목록이 일치하게 만드세요.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

본문의 추가 확인할 내용, 개인 할 일의 완료, 기록 공개 상태를 구분합니다. 할 일 완료는 실제 회사 업무 완료나 공개 승인이 아닙니다. 기록 검색은 공통 기록도 포함하지만 개인 할 일의 프로젝트 조건은 해당 프로젝트만 보여 줍니다.
