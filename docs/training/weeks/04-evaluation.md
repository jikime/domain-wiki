# 4단계 · 위키 생성 결과·답변 품질과 중간 점검

**이번에 할 일:** 질문과 원문을 비교해 잘된 답과 보완할 답을 구분합니다.

**이번 실습에 필요한 말:** 기준 결과 = 바꾸기 전 기록 · 검색 근거 = 찾은 자료 · 미확인 = 아직 확인하지 못함

[입력할 창이 헷갈리면](../start-here.md#어디에-입력하나요) · [도움 요청하기](../start-here.md#결과가-다르면-이렇게-도움을-요청하세요) · [다시 사용하기](../daily-use.md)

## 1. 이번 실습의 목표와 준비

위키의 작성 규칙과 생성 결과를 원문으로 확인하고 AI에게 보완을 요청합니다. 자료를 못 찾았는지, 답이 틀렸는지, 다른 범위의 자료가 섞였는지 구분해 기록합니다. 이 기록을 기능 개선 전후를 비교할 기준으로 씁니다. 준비물은 3단계 자료 상태, 검수 조건 **v1**, [평가 질문 12개](../samples/evaluation-questions.csv), T5·T7 [기록 양식](../templates.md)입니다. 신규 RFP·개정본·강사 답안을 검색 자료에 올리지 않습니다.

## 2. 진행 순서

| 순서 | 강사 안내 | 교육생 실습·확인 |
| --- | --- | --- |
| 1 | 평가 조건과 공개 상태 확인 | 모델·범위·버전 기록 |
| 2 | 검색과 답변을 따로 평가하는 시연 | Q03·Q09 비교, 실패 유형 연습 |
| 3 | 12개 질문 평가 지원 | 실습 A, 기준 결과 수집 |
| 4 | 위키 생성 결과·AI 보완 요청·과제 범위 코칭 | 실습 B, 위키 초안 비교·공통 개선 요청 작성 |
| 5 | 중간 점검, 공통·팀 과제 확정 | 완료 기준·우선순위·담당 기록 |

## 3. 핵심 설명

**위키 생성·갱신.** 서비스 AI는 공개 원문과 목적·작성 규칙을 바탕으로 위키를 만듭니다. 교육생은 수치와 적용 범위가 맞는지, 예외와 근거가 빠지지 않았는지 확인하고 누락된 내용을 구체적으로 전달합니다. 프롬프트·작업자·버전의 역할만 설명하며 관련 코딩은 요구하지 않습니다.

**키워드 검색.** 입력한 단어와 등록된 동의어를 바탕으로 제목·본문 등을 찾습니다. 원문이 공개되어 있고 질문 범위 안에 있어야 후보가 됩니다.

**문단과 선택적인 임베딩.** 문단은 원문 근거를 연결하고 필요한 내용을 찾는 단위입니다. 임베딩은 의미가 비슷한 자료를 찾도록 돕는 선택적 수치 표현이며 사실을 판정하지 않습니다. 현재 스타터킷은 임베딩 없이 키워드 검색을 사용할 수 있습니다.

**현재 OpenAI 임베딩과 pgvector의 연결.** 교육 준비 환경의 모델은 `text-embedding-3-small`입니다. 공개 원문·게시된 위키를 이 모델로 변환해 PostgreSQL에 보관하고, 질문도 같은 모델로 변환한 뒤 pgvector로 유사도를 비교합니다. 그 결과를 키워드 검색과 함께 사용하고, 선택된 근거로 답변 생성 모델이 답합니다. 임베딩 모델과 답변 생성 모델의 역할은 다릅니다. [공통 연결 설명](../project-guide.md#현재-임베딩-모델과-pgvector)을 검색 시연에서 복습합니다.

교육생은 이미 준비된 검색 결과와 실제 근거를 확인합니다. 임베딩 호출·벡터 저장·검색 코드 작성이나 모델 교체 실습은 요구하지 않습니다. 설정·연결 실패로 키워드 검색을 사용한 경우에는 표시된 상태를 T5에 기록하고, 해당 결과만으로 의미 검색이 정상 작동했다고 판단하지 않습니다.

**RAG의 위치.** 질문과 관련된 위키·원문을 찾아 답변에 제공하는 흐름입니다. 위키 생성·갱신의 필수 선행 구현이 아니며 이 수업에서 벡터 DB·검색 파이프라인을 만드는 과제는 없습니다. 자료·추출·범위가 잘못되면 모델 변경만으로 해결되지 않을 수 있습니다.

**검색과 생성의 분리.** 근거 문서가 검색되지 않은 경우와, 검색되었지만 AI가 수치를 잘못 해석한 경우는 조치가 다릅니다. 전자는 상태·범위·검색 입력부터 보고, 후자는 제공 근거·질문·해석을 확인합니다.

**코드가 통과하는 조건과 업무 정답.** 인용 ID가 실제 근거에 연결되어 있어도 답변의 주장이 원문 의미와 일치하는지는 별도로 읽어야 합니다. ‘화면 갱신 60초’를 ‘장애 복구 60초’로 쓰면 같은 숫자라도 오류입니다.

## 4. 실습 A · 기준 평가 12개

> **입력할 곳:** 브라우저의 위키 채팅·근거 화면과 평가 기록표. 질문은 정해진 문구로 입력합니다.
>
> **정상 결과 예시:** 답변마다 실제 근거와 확인 결과가 기록됩니다. 가상 검수 조건의 이력 보관 90일과 회의록의 180일 검토 의견을 구분했는지 봅니다.

근거를 여는 조작은 [실제 사용 따라 하기의 5단계](../wiki-chat-guide.md#5-답변이-참고한-근거를-확인합니다)를 참고합니다. 이번 기준 평가에서는 아래에 정한 질문과 범위를 유지하며, 특정 위키로 범위를 바꾸거나 답변을 새 위키로 게시하지 않습니다.

1. 원문 01–05와 실무 기록, 위키의 현재 공개 상태를 확인합니다. 검수 조건은 v1을 사용합니다.
2. T5 상단에 코드 기준, 자료 버전, 연결 방식(API·Claude Code CLI·Codex CLI), 용도별 모델, 임베딩 설정, 도메인·프로젝트, 실행 시각을 기록합니다. 웹 검색은 끄고 내부 자료를 대상으로 평가합니다. 같은 모델 이름이어도 API·CLI의 입력 구조가 다를 수 있으므로 평가 도중 연결을 바꾸지 않습니다.
3. 팀별로 질문 12개를 나누어 실행하되 질문 문구와 지정 범위는 유지합니다. 모델 사용 한도와 CLI 대기열 혼잡을 피하도록 각 팀에서 한 요청씩 보냅니다. 인증·한도·시간 초과는 연결 실패로 기록하고 업무 답변의 사실 오류와 구분합니다.
4. 자료 검색 또는 근거 목록에서 기대 자료가 보이는지 먼저 기록합니다. 그다음 답변의 숫자와 부정 표현, 예외 조건을 읽고 해당 프로젝트와 버전이 맞는지 확인합니다.
5. T7에 실제 답변 요약과 근거를 남기고 0–2점 기준으로 평가합니다.
6. Q04·Q12에서 90일 승인 기준과 180일 검토 의견을 구분했는지 확인합니다.
7. Q08·Q09에서 자료에 없는 날짜나 장애 복구 시간을 만들어 내지 않았는지 확인합니다.
8. 두 팀이 점수가 다른 질문 2개를 골라 원문을 함께 읽고 판단 이유를 맞춥니다.

검색 지표는 ‘기대 근거를 확인한 질문 수 / 기대 근거 확인 대상 질문 수’로 계산하고 실제 분모를 적습니다. 답변 점수는 12개 질문의 점수 합계와 최대 24점을 함께 적습니다. 작은 가상 표본의 점수를 회사 전체 정확도로 표현하지 않습니다.

## 5. 실습 B · 위키 보완 요청과 개선 과제

> **입력할 곳:** 개발용 AI에 보완을 요청하고, 브라우저에서 새 위키 초안·용어 입력을 비교합니다.
>
> **정상 결과 예시:** 수치와 근거를 유지한 초안, 동의어 입력의 실제 저장 결과, 다음 단계에 개선할 조건을 남깁니다. 이 비교용 초안은 게시하지 않습니다.

같은 원문으로 위키 초안을 비교한 뒤 실패 유형을 분류하고 공통 코드 개선 요청을 정합니다. 12개 질문의 기준 평가 이후에 진행하고, 현재 게시된 위키와 원문 v1은 유지합니다.

위키 초안을 비교하면서 [프롬프트 수정·재실행](../prompt-practice.md#5-한-번-실행한-뒤-어떻게-고치나요) 연습도 겸합니다. 교육생은 개발용 AI의 대화창에 기존 초안에서 실제로 확인한 문장·누락과 원문 위치를 넣어 첫 보완 요청을 직접 작성·전송합니다. 제안 또는 새 초안을 확인한 뒤 후속 요청을 작성·실행하고 T3·T5에 두 결과를 비교합니다. 오류가 없으면 ‘확인된 조건과 미정인 조건을 구분해 표시’처럼 확인할 구성을 보완합니다. **기준 평가 질문 12개의 문장은 수정하지 않으며**, 이 연습의 결과를 기준 평가 점수에 합치지 않습니다.

1. 3단계 위키에서 적용 범위·확인된 조건·예외·추가 질문이 구분되는지 봅니다.
2. AI에게 ‘같은 원문에서 확인한 사실을 유지하며 적용 범위와 미확인 조건을 분리할 작성 규칙을 제안해 주세요’라고 요청합니다. 현재 목적·위키 구조 설정을 기록한 뒤 제안을 필요한 범위로 반영합니다.
3. 같은 공개 원문 v1로 새 AI 초안을 생성하고 기존 위키와 비교합니다. 새 초안은 게시하지 않습니다. 수치 60초·90일·표본 3대, 장애 복구 시간 미정, 실제 근거 연결을 확인합니다.
4. 누락이 있으면 위치·기대 조건·원문을 AI에 전달해 보완을 요청합니다. 작업 완료 후 원래 설정을 복원하고 보완 규칙은 T3, 비교 결과는 T5에 보관합니다. 기준 평가의 게시본·자료·모델은 바꾸지 않습니다.

AI 처리 지연 시 준비된 초안으로 검토·보완 요청까지 수행하고 실제 생성은 미확인으로 기록합니다. 이어서 아래 실패 분류와 5단계 공통 요구사항을 정합니다.

실패를 다음 표로 분류합니다. 분류가 불확실하면 가설로 표시합니다.

| 유형 | 예 | 첫 확인 |
| --- | --- | --- |
| 자료 부족 | 종료일이 없음 | 원문에 답이 있는지 |
| 추출 오류 | 수치·표 항목이 빠짐 | 원문과 추출 텍스트 비교 |
| 상태·범위 | A 질문에 B 자료 사용 | 공개 상태·프로젝트·역할 |
| 용어·입력 | 동의어가 한 덩어리로 저장됨 | 관리 화면 저장 결과 |
| 검색 후보 | 필요한 공개 문단을 못 찾음 | 검색어·용어·색인 상태 |
| 생성·해석 | 60초를 장애 복구로 해석 | 전달 근거·질문·답변 비교 |

1. 재현 가능한 문제 한 개를 고릅니다. 실패가 없으면 아래 공통 입력 문제를 사용합니다.
2. 관리 화면에서 현재 용어 설정을 기록한 뒤 동의어에 `VMS; 전광표지， VMS`를 넣습니다.
3. 저장하고 다시 열어 현재 구현이 이 문자열을 쉼표 하나로만 나누는지 확인합니다. 단순 검색 성공 여부만으로 입력이 올바르다고 판단하지 않습니다.
4. 기존의 쉼표 입력과 비교하고, 실습 뒤 원래 설정으로 되돌립니다.
5. T1·T3에 ‘쉼표·전각 쉼표·세미콜론 지원, 앞뒤 공백과 동일 항목 중복 정리, 기존 검증 유지’라는 완료 기준을 적고 개발용 AI에게 현재 코드의 최소 변경 계획을 요청합니다. 교육생은 업무 범위를 판단하고 구현은 다음 단계에 AI가 수행합니다.
6. 팀별 응용은 ‘실무 기록 작성 안내 구체화’ 또는 ‘위키의 적용 조건·확인 질문 구성 개선’ 중 하나로 정합니다. 이미 있는 설정으로 해결되는 부분을 먼저 선택합니다.

## 6. 중간 점검

강사는 각 팀과 5단계의 공통 코드 과제, 팀 응용 한 개, 완료 기준을 확정합니다. 새 테이블·인증·권한 체계 변경이나 대규모 검색 재설계가 필요한 과제는 후속 목록으로 옮깁니다. 5단계의 공통 기능 개선과 함께 확인할 수 있는 범위를 선택합니다.

예상 논의: ‘검색 결과를 늘리기 위해 A와 B의 범위를 합칠까요?’에는 ‘필요한 업무 범위를 먼저 정하고, 범위가 다른 근거를 섞어 점수를 올리지 않는다’고 설명합니다.

## 7. 완료 기준

위키 초안 비교·AI 보완 요청, 평가 결과 12개, 실패 유형과 근거, 공통 개선 요청 1개, 팀 응용 1개를 남깁니다. ‘검색 실패와 답변 해석 오류를 어떻게 구분하나요?’, ‘조건이 바뀐 평가를 그대로 비교해도 되나요?’에 답합니다. 다음 단계에는 여기서 정한 입력 사례를 개발과 검증에 그대로 사용합니다.
