# 자료를 회사 업무 위키로 정리하기

자료실 검색을 자료별로 묶고 업무 절차 위키의 작성 화면을 개선합니다. 본문 위치별 수정 의견과 보완 과정을 연결한 뒤, 원문이 개정되면 관련 위키를 찾아 고치는 기능을 만듭니다.

[강의 화면](/lectures/week-04.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 3회차까지 개발한 내 위키와 같은 코드를 연 Claude Code에서 이어갑니다. 공개 원문, 위키 작성·검토 계정과 검수 조건 v1을 확인합니다.

**남길 결과:** 자료별 검색·문단 열기·목록 복귀·기존 즐겨찾기 연결 / 업무 절차 목차·근거 비교·빈 절 안내·이어 쓰기 / 본문 위치별 수정 의견·보완 답글·재요청·남은 의견 / 원문 개정의 재확인 목록·전후 비교·보완·게시 상태

각 교시의 네 가지 개발 단계를 모두 진행합니다. **계획 요청 → 내가 확인·수정 → 실행 요청 → 화면에서 직접 확인**을 반복한 뒤 같은 사례로 전체 업무를 이어 해 봅니다. 계획과 실행은 따로 보내고, 상자 하나는 한 번에 입력합니다. 추가 도전은 공통 기능을 마친 뒤 진행합니다.

## 먼저 준비할 것

- 같은 개인 위키와 개발용 Claude Code를 사용합니다. 앱 채팅에 개발 요청을 넣지 않습니다.
- 도메인 **가상 교통관제 자료**, 프로젝트 **A · 가람시**, 공개 원문 **사업 개요·검수 조건 v1**을 확인합니다. 검수 조건은 60초·90일입니다. 샘플이 없다면 [샘플 넣기](../sample-data.md)를 먼저 진행합니다.
- 기본 실습 계정은 작성 `writer@wiki.local`, 검토 `reviewer@wiki.local`, 열람 `reader@wiki.local`입니다. 내가 계정을 바꾸어 각 역할을 확인합니다. 비밀번호는 본인 환경의 계정 안내를 따릅니다.
- 샘플 원문과 기존 위키는 `writer@wiki.local`의 자료로 준비됩니다. 이번에는 이 계정으로 초안 작성·원문 개정·위키 보완을 이어갑니다. 다른 작성 계정을 쓰면 기존 샘플을 수정할 수 있는지 먼저 확인하세요. 자료 등록자 또는 검토자에게 권한이 필요한 작업도 있습니다.
- 검토함은 검토 계정에서 엽니다. 관리자라도 자신이 작성한 버전을 직접 승인하지 않습니다.
- 저장 검색 조건·즐겨찾기는 앞서 내 위키에 개발한 기능입니다. 처음 받은 스타터킷이나 샘플 데이터에 포함된 기본 기능이 아닙니다.
- 3회차의 검토 대기 기록과 개인 초안은 그대로 둡니다. 이번에는 새 업무 절차 위키를 작성합니다.

## 같은 사례로 이어가기

[업무 절차 실습 사례](../samples/wiki-practice.md)에 본문·근거·검토 의견·개정 파일과 역할별 순서를 모았습니다. 강의 화면에도 필요한 입력과 확인 순서가 있습니다.

| 교시 | 시작 상태 | 끝나면 남길 것 |
| --- | --- | --- |
| 1 | 공개 원문 v1 | 자료별 검색·원문 탐색·기존 개인 기능 연결 |
| 2 | 두 원문의 실제 문단 | 네 절과 근거가 있는 업무 절차 초안 |
| 3 | 업무 절차 초안 | 의견을 보완해 게시한 v1 근거의 위키 |
| 4 | 게시 위키·원문 v1 | 원문 v2, 보완해 게시한 두 위키와 남은 영향 |

처음부터 v2를 공개하지 않습니다. 이미 개정된 환경은 강사와 시작 상태를 맞추고, 과거 상태를 만들려고 기존 자료를 삭제하지 않습니다. 회사 용어 편집은 뒤의 관리 실습에서 다룹니다.

## 준비: 개발할 메뉴와 기존 기능 확인

아래 상자 전체를 개발용 AI에 한 번 입력합니다. 새 기능을 만들기 전에 실제 화면과 설명을 비교하세요.

```text
자료실의 공개 지식 검색, 위키의 작성·초안 저장, 검토함의 위키 게시 요청을 개선할 거야. 해당 코드에서 검색 결과 단위·원문 링크·본문과 근거의 저장·작성자와 검토자 동작을 확인해. 내가 앞서 개발한 즐겨찾기·저장 검색 조건이 있는지 확인하고 연결 방법도 설명해. 실제 메뉴와 버튼으로 내가 눌러 볼 순서를 알려 줘. 없는 기능은 가정하지 마. 코드와 DB는 아직 바꾸지 마.
```

**직접 확인:** 작성 계정에서 원문·위키 작성 메뉴를 확인합니다. 검토함은 검토 계정으로 엽니다. 지금은 등록·승인하지 않습니다.

## 1. 자료별 검색과 원문 탐색

[함께 볼 강의 화면](/lectures/week-04.html#slide-04)

**앞에서 이어받을 것:** 공개 샘플과 앞서 만든 저장 검색 조건·즐겨찾기

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 이미 입력·저장한 사례를 이어 사용해 아래 전체 업무를 확인합니다. 같은 제목의 문서나 의견을 중복 생성하지 않습니다.

**내가 정할 것:** 자료를 묶는 기준, 원문에서 돌아올 검색 조건, 기존 즐겨찾기 버튼의 위치

**저장 기준:** 검색 묶음·펼침·복귀는 화면·URL 상태입니다. 기존 개인 기능의 사용자별 DB를 재사용합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
자료실의 ‘공개 지식 검색’ 결과를 같은 자료별로 묶을 거야. 기존 검색 응답과 화면을 조사해 종류·자료 ID·버전 ID가 같은 결과만 묶는 계획을 세워. 제목이 같다는 이유로 합치지 마. 현재 페이지에서 받은 결과만 묶고 첫 결과의 순서를 유지해. 전체 검색 결과 수와 이 페이지의 자료 묶음 수를 구분해 보여 줘. 기존 검색 조건·페이지 처리와 열람 권한을 유지해. 화면·서버의 변경 범위와 DB 변경이 필요한지, 확인할 사례를 설명해. 코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **같은 자료란?** 제목이 아니라 자료·버전·종류가 같은 결과
- **어디까지 묶나요?** 현재 페이지에서 받은 결과
- **개수의 뜻은?** 전체 검색 결과와 현재 페이지 묶음을 구분

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
자료실의 공개 지식 검색에 확인한 자료별 묶음을 만들어. 현재 페이지의 결과에서 종류·자료 ID·버전 ID가 같은 것만 묶고, 제목·종류·버전·이 페이지의 일치 문단 수를 표시해. 묶음 순서는 첫 결과의 순서를 따르게 해. 기존 전체 검색 결과 수와 페이지 이동은 유지하고 묶음 수를 별도로 표시해. 화면 표시를 위해 새 DB 테이블을 만들지는 마. 다른 프로젝트·같은 제목·다른 버전을 잘못 합치지 않는지 검사하고 내가 직접 확인할 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 가상 교통관제 자료·프로젝트 A·공개 원문에서 ‘검수’를 검색합니다. 상태 화면 검수 조건의 여러 결과가 한 묶음으로 보이는지 확인하세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 기능도 모두 공통 실습입니다. 각 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다. 첫 기능만으로 교시를 마치지 않습니다.

### 다음 기능 · 일치 문단 펼치고 원문 열기

**먼저 계획 요청**

```text
자료실에 만든 자료별 검색 묶음에 ‘일치 문단 보기’를 더할 거야. 펼치면 이 페이지에서 검색된 문단의 내용·위치를 보여 주고, 각 문단의 기존 원문 링크를 열게 계획해. 단순히 자료 제목으로 다시 검색하지 말고 실제 버전·문단 주소를 유지해. 원문 종류와 게시 위키의 링크 형식이 다르면 각각 기존 경로를 사용해. 제목만 있는 문단도 실제 결과대로 표시해. 접기·펼치기와 키보드 조작, 빈 문단 처리까지 확인할 순서를 정해. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 무엇을 펼치나요?: 검색 결과에 들어온 일치 문단
- 어디로 이동하나요?: 해당 버전의 해당 문단
- 확인할 자료: 검수 조건의 승인된 검수 조건 문단

**계획을 확인한 뒤 실행**

```text
자료실의 자료별 검색 묶음에 ‘일치 문단 보기’와 접기를 만들어. 각 결과의 본문 일부·위치·원문 열기를 표시해. 기존 검색 응답의 링크를 사용해 같은 자료의 정확한 버전과 문단으로 이동하게 해. 공개 원문과 게시 위키를 구분하고 새 창에서 열기도 가능하게 해. 펼침 상태는 화면 상태로 관리하고 DB에 따로 저장하지 마. 여러 문단·제목 문단·키보드 열기를 검사하고 내가 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. ‘검수’를 검색해 검수 조건의 문단을 펼칩니다. 원문 열기를 눌러 제목·버전·해당 문단이 일치하는지 보세요.

### 다음 기능 · 원문에서 검색 목록으로 돌아오기

**먼저 계획 요청**

```text
자료실 검색 결과에서 원문을 열었다가 같은 목록으로 돌아올 수 있게 할 거야. 검색어·도메인·프로젝트·종류·페이지와 펼친 자료를 어떻게 이어 줄지 계획해. 원문 상세에는 검색에서 들어왔을 때 ‘검색 결과로 돌아가기’를 더해. 기존 버전·문단 링크와 직접 주소로 연 경우의 자료실 링크를 유지해. 돌아갈 주소는 같은 작업공간의 검색 경로만 허용해. 일시적인 탐색 상태와 기존 DB 저장 검색 조건을 구분하고 새 테이블 없이 가능한 방법부터 설명해. 코드와 DB는 아직 바꾸지 마. 기존 실무 기록에서 원문을 읽고 돌아오는 경로도 유지해.
```

**내가 확인할 것**

- 돌아갈 조건: 검색어·범위·종류·페이지
- 열었던 위치: 펼친 자료 묶음 복원
- 직접 주소로 열면?: 기존 자료실 진입을 유지

**계획을 확인한 뒤 실행**

```text
자료실과 원문 상세에 확인한 검색 복귀 기능을 만들어. 원문을 읽고 ‘검색 결과로 돌아가기’를 누르면 검색어·도메인·프로젝트·종류·페이지와 펼친 묶음이 복원되게 해. 직접 주소로 연 원문에는 기존 자료실 링크를 사용해. 돌아갈 주소는 같은 작업공간의 허용된 검색 경로만 받아. 기존 버전·문단 링크를 바꾸지 마. 새로고침·뒤로 가기·직접 링크 열기와 검색 복귀를 검사하고 내가 확인할 순서를 알려 줘. 기존 실무 기록에서 원문을 읽고 돌아오는 경로도 유지해.
```

**다음 기능 전에 직접 확인**

1. 프로젝트 A의 ‘검수’ 결과에서 원문을 열고 검색 결과로 돌아옵니다. 프로젝트 B로 검색한 뒤에도 같은 순서로 확인하세요.

### 다음 기능 · 저장한 조건과 즐겨찾기 연결하기

**먼저 계획 요청**

```text
자료실의 새 검색 묶음에 기존 저장 검색 조건과 즐겨찾기를 연결할 거야. 먼저 내 코드에 있는 저장 단위와 DB를 확인해. 검색 조건을 불러오면 그 범위의 묶음이 나오고, 원문을 즐겨찾기에 넣을 때는 기존 자료·버전 연결과 내 메모·읽음 표시를 재사용해. 묶음 전체와 문단별 버튼이 중복 등록을 만들지 않도록 표시 위치를 정해. 결과 없음과 조건 변경도 계획해. 없는 개인 기능은 있다고 가정하지 말고 필요한 연결을 알려 줘. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 저장한 조건: 프로젝트 A + 검수 키워드로 재검색
- 즐겨찾기: 앞서 만든 저장 단위·메모를 재사용
- 결과 없음: 현재 조건을 확인하고 다시 검색

### 1. 계획 요청


내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.


**저장 기준:** 수정 의견·답글·처리 이력은 위키·대상 버전·사용자에 연결해 DB 저장합니다. 초안·검토·게시 상태는 기존 구조를 유지합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
위키 상세의 검토 화면에 본문 위치별 수정 의견을 만들 거야. 검토자가 절 제목과 문장을 선택해 의견을 남기고 작성자가 그 위치를 보게 계획해. 대상 위키·버전·절 제목·인용 문장·의견·작성자를 DB에 연결해 저장해. 현재 검토 의견·반려·승인은 그대로 사용하고 새 의견을 저장했다고 반려하지 마. 작성자와 검토 권한자만 볼 범위, 위치가 사라진 경우의 안내, 필요한 테이블 변경과 개발 DB 적용 순서를 설명해. 코드와 DB는 아직 바꾸지 마.
```

**계획을 읽고 내가 확인할 것**

- **의견을 남길 곳** 절 제목과 그 안의 구체적인 문장
- **DB에 남길 것** 대상 버전·위치·의견·작성자
- **반려와 구분** 의견 저장만으로 상태를 바꾸지 않기

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행


**만든 뒤 직접 확인**

**만든 뒤 직접 확인**

1. 검수 조건 v2를 공개한 뒤 개정·철회 영향 확인을 엽니다. 새 업무 절차와 기존 ‘프로젝트 A의 범위와 검수 기준’이 보완 대상으로 보이는지 확인하세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 기능도 모두 공통 실습입니다. 각 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다. 첫 기능만으로 교시를 마치지 않습니다.

### 다음 기능 · 이전 근거와 현재 원문 비교하기

**먼저 계획 요청**

```text
자료실의 위키 재확인 목록에서 이전 근거와 현재 공개 원문을 비교할 거야. 위키가 실제 연결했던 구버전 문단을 왼쪽에, 현재 원문에서 내가 고른 문단을 오른쪽에 보여 주는 계획을 세워. 버전·위치·공개 상태를 표시하고 같은 제목이나 줄 번호만으로 문단을 자동 대응시키지 마. 현재 문단을 못 찾으면 선택할 검색을 안내해. 구버전 조회 권한과 기존 링크를 유지하고 화면 상태만으로 가능한지 설명해. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 이전 근거: 연결했던 v1의 실제 문단
- 현재 원문: v2에서 직접 고른 공개 문단
- 바뀐 것과 유지: 갱신 60초 → 30초 · 보관 90일

**계획을 확인한 뒤 실행**

```text
자료실의 위키 재확인 목록에 확인한 근거 비교 화면을 만들어. 실제 연결한 이전 문단과 내가 선택한 현재 공개 문단을 나란히 보여 줘. 각 자료의 제목·버전·위치를 표시하고 원문으로 이동하게 해. 현재 문단이 아직 선택되지 않았으면 빈칸과 선택 안내를 보여 줘. 구버전 링크나 개인 메모를 새 원문으로 바꾸지 마. 60초와 30초, 그대로인 90일을 비교하고 작은 화면의 전환과 목록 복귀를 검사해.
```

**다음 기능 전에 직접 확인**

1. 갱신 주기 문단을 비교한 뒤 보관 기간 문단도 비교합니다. 바뀐 문단과 그대로인 문단의 버전이 모두 v2인지 확인하세요.

### 다음 기능 · 근거를 고치고 위키 검토로 이어가기

**먼저 계획 요청**

```text
자료실의 근거 비교에서 ‘이 위키 보완하기’를 눌러 기존 위키 편집기로 이어갈 거야. 어떤 위키와 근거를 고칠지 보여 주고, 편집기에서는 현재 공개 문단을 다시 선택해 저장하게 계획해. 기존 위키의 본문·관계와 버전 저장·검토 요청을 재사용해. 오래된 근거를 바꾸지 않은 채 저장하려 할 때는 해당 자료와 조치 방법을 안내해. 비교 화면을 열었다고 본문·근거를 자동 교체하지 마. 필요한 화면 연결과 확인 방법을 설명해. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 고칠 곳: 갱신 기준 본문과 연결한 근거
- 유지할 것: 위키 관계 · 원래 버전 · 개인 기록
- 다음 상태: 초안 저장 → 검토 요청 → 별도 승인

**계획을 확인한 뒤 실행**

```text
자료실 근거 비교에 ‘이 위키 보완하기’를 만들고 해당 위키의 기존 편집기로 연결해. 원문 제목·이전 버전·현재 공개 버전을 안내하고 근거 선택 영역을 찾기 쉽게 해. 작성자가 본문을 고치고 구버전 근거를 해제한 뒤 현재 공개 문단을 골라 새 초안을 저장하게 해. 기존 버전 저장과 검토 요청을 재사용하고 자동 게시하지 마. 기존 위키 연결은 유지해. 잘못된 근거 안내·새 초안 저장·재확인 목록 복귀를 검사해.
```

**다음 기능 전에 직접 확인**

1. 업무 절차의 60초를 30초로 고치고 검수 조건의 v1 근거를 모두 v2의 해당 문단으로 바꿉니다. 사업 개요 근거는 그대로 둡니다.

### 다음 기능 · 보완 상태로 목록과 개수 확인하기

**먼저 계획 요청**

```text
자료실의 위키 재확인 목록에 ‘보완 필요·검토 중·반영 완료’ 필터와 개수를 더할 거야. 이 원문 개정의 영향을 받은 접근 가능한 위키를 기준으로 중복 없이 계산해. 새 초안 저장만으로 완료하지 말고 현재 공개 근거를 연결한 버전이 게시됐는지 확인해. 반려·다시 개정·동시 변경 때 상태가 어떻게 돌아갈지 계획해. 목록 새로고침과 필터 URL, 기존 조회 제한을 사용자에게 알리는 방법도 설명해. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 초안과 검토 중: 저장만으로 반영 완료가 되지 않음
- 반영 완료: 현재 공개 근거로 보완한 버전 게시
- 개수의 범위: 이 개정에 연결된 열람 가능한 위키

**계획을 확인한 뒤 실행**

```text
자료실의 위키 재확인 목록에 확인한 상태 필터·개수·새로고침을 만들어. 같은 원문 개정과 열람 범위에서 목록·개수가 일치하게 해. 새 초안만 저장했으면 보완 필요로 안내하고 검토 요청 후에는 검토 중, 현재 공개 근거의 보완본이 게시돼야 반영 완료로 보여 줘. 반려되거나 다시 오래된 근거가 되면 재확인할 상태로 돌아가게 해. 계산 결과를 근거로 표시하고 임의 완료 체크는 만들지 마. 조회 제한이 있으면 표시하고 역할별 목록·게시 후 갱신을 검사해.
```

**다음 기능 전에 직접 확인**

1. 업무 절차를 보완·게시한 뒤 목록을 새로고침합니다. 기존 범위와 검수 기준 위키도 보완해 게시하고, 두 위키의 상태와 개수를 확인하세요.

### 업무 순서대로 확인

앞의 단계에서 만든 결과로 전체 흐름을 확인합니다. 이미 입력·저장한 사례는 다시 만들지 않고 이어 사용하세요.

1. 이미 보완한 업무 절차의 30초·90일과 검수 조건 v2 근거를 확인합니다. 아직 남은 보완·검토 요청만 마칩니다.
2. 기존 범위 위키의 v2 표기·30초 두 곳·현재 근거를 확인합니다. 24대·제외 범위·90일·협의 메모는 유지합니다. 게시했다면 새 버전을 또 만들지 않습니다.
3. reviewer로 아직 대기 중인 변경만 검토합니다. reader로 두 게시 위키·현재 근거·관련 위키 링크를 읽고 재확인 목록의 결과와 맞춰 봅니다.

재확인 목록에 다른 항목이 남았다면 제목과 다음 작업을 기록합니다.

**확인:** 두 위키를 현재 공개 근거로 보완해 게시하고 목록 상태를 확인했습니다.

**기본을 마쳤다면 — 선택 과제**

- **개정별 이력 보기:** 어느 원문 개정 때문에 어떤 위키를 고쳤는지 필터로 다시 찾게 합니다.
- **재개정 확인:** 다음 원문 버전이 또 공개되면 완료됐던 위키가 다시 보완 대상으로 잡히는지 별도 실습 환경에서 확인합니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.
