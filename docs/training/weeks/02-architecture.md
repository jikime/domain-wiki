## 3. 핵심 설명

**파일·함수·값.** 파일은 관련 코드를 담는 단위이고 함수는 입력을 받아 처리하는 단위입니다. `title`은 제목 값을 담고, `saveRecord`는 받은 실무 기록을 저장하는 역할입니다. 모든 코드를 외우기보다 어떤 값이 어떤 함수로 이동하는지 봅니다.

**클라이언트·서버.** 실무 기록 입력은 브라우저에서 처리하고 저장 요청은 서버로 전달합니다. 서버는 계정·역할·입력 형식을 다시 확인합니다. 화면에서 저장 버튼을 숨기는 것만으로 권한 검사가 완성되지는 않습니다. Next.js에서는 화면 파일에도 서버에서 실행하는 부분이 있으므로 ‘화면 파일은 모두 브라우저에서 실행된다’고 설명하지 않습니다. [Next.js 공식 설명](https://nextjs.org/docs/app/getting-started/server-and-client-components)

**API·JSON.** API는 프로그램 사이의 요청 약속입니다. JSON은 제목과 상황 같은 값을 이름·값의 구조로 전달하는 형식입니다. API 주소, 요청 방식, 전달 값, 응답 결과를 함께 확인합니다.

**서비스의 API와 모델의 API·CLI.** 브라우저는 위키 서버의 API를 호출합니다. 그다음 서버가 모델을 직접 HTTP API로 부르거나 Claude Code·Codex CLI를 실행합니다. 모델 연결을 CLI로 바꾸어도 브라우저가 서버를 거치는 구조와 권한 검사는 유지됩니다. 실행 방식과 인증·과금 방식은 다르므로 ‘CLI 선택 = 무료 구독 사용’으로 설명하지 않습니다.

**TypeScript와 실행 중 검증.** 타입은 개발 중 값의 형태를 확인하는 데 도움을 줍니다. 서버가 외부에서 받은 입력을 확인하는 검증은 별도로 필요합니다. 이 프로젝트는 Zod 스키마로 필수값과 길이 등을 검사합니다. [TypeScript 공식 안내](https://www.typescriptlang.org/docs/handbook/intro.html)

**DB·원본·작업자.** DB는 계정·상태·관계를 저장합니다. 원본 파일은 별도 저장 위치에 보관합니다. 문서 작업자는 시간이 걸리는 추출·AI 처리를 담당합니다. 서버 화면이 켜져도 작업자가 없으면 문서 처리가 진행되지 않을 수 있습니다.

**Git 변경 내역.** 현재 파일과 기준 파일의 차이를 보는 것이 `diff`입니다. AI가 바꾼 범위가 요청과 일치하는지 확인한 뒤 기록합니다. [Git 공식 설명](https://git-scm.com/docs/git-diff)

14:20–15:00 구조 설명 중 8분은 모델 연결을 읽는 데 사용합니다. 강사는 관리자 화면의 대화·지식 생성 연결 표시와 `src/server/ai/client.ts`의 `streamModel`, `src/server/ai/cli.ts`를 차례로 보여 줍니다. 교육생은 T2에 ‘위키 서버→선택한 API 또는 CLI→응답’ 경로를 적습니다. 환경 설정이나 계정 로그인을 현장에서 바꾸지는 않습니다. 연결 등록·선택·저장 화면은 [후속 설계안](../project-guide.md#8-모델-연결의-현재-기능과-설정-화면-권장안)이며 현재는 조회·연결 확인 기능만 제공한다는 점을 짚습니다.

## 4. 실습 A · 실무 기록 저장 흐름 추적

1. 실무 기록 화면에서 제목과 상황·판단과 이유·결과·추가 확인할 내용을 찾습니다.
2. 편집기 전체 검색 또는 다음 명령으로 화면 파일을 찾습니다. `rg`가 없으면 편집기 검색을 사용합니다.

```bash
rg -n '작성 당시 메모|saveRecord|recordInput' src
```

3. `src/components/record-editor.tsx`에서 `fetch`와 `JSON.stringify`를 찾아 전송되는 필드를 적습니다. `domainId`, `projectId`, `rawNote`, `chunkIds`가 어떤 값인지 설명합니다.
4. `src/app/api/workspaces/[workspaceId]/[resource]/route.ts`에서 `records` 처리와 `saveRecord` 연결을 찾습니다.
5. `src/server/services/records.ts`에서 `requireWriter`, `recordInput.parse`, `checkEvidence`, `uploadSource`의 순서를 확인합니다.
6. `src/lib/proposals.ts`에서 `recordInput`을 찾아 필수 항목을 확인합니다. 상황·판단·결과는 필수이며 추가 확인 내용은 비어 있을 수 있습니다.
7. T2에 ‘입력→요청→권한·입력 확인→원문 생성→처리·검토’ 흐름을 적습니다. 실제 저장은 자료 등록 서비스를 재사용한다는 점을 설명합니다.

기대 결과: 코드 전체를 해석하지 않아도 관련 화면·API·서버 함수와 값 3개 이상을 연결합니다. 저장된 실무 기록이 공식 규정과 구분된 작성자 진술임을 확인합니다.

## 5. 실습 B · 작성 당시 메모 도움말 개선

문제: 교육생이 원본 메모에 무엇을 적어야 하는지 모릅니다. 기존 도움말에 ‘프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요.’를 추가합니다. AI 정리가 메모를 바꾸지 않는다는 기존 안내를 유지합니다.

1. 교육용 사본의 변경 상태를 확인합니다. 기준 커밋이 준비된 사본에서 개인 실습 브랜치를 만듭니다.

```bash
git status --short
git switch -c training/week02
```

같은 이름의 브랜치가 이미 있으면 새로 만들지 않고 강사가 알려 준 개인 브랜치를 사용합니다. 기존 변경이 있으면 먼저 내용을 확인하고 임의로 지우지 않습니다.

2. AI에게 T3 양식으로 변경 계획을 요청합니다. 대상은 `src/components/record-editor.tsx`의 ‘작성 당시 메모’ 도움말입니다. 저장 필드·API·DB·스타일 변경은 필요하지 않다고 명시합니다.
3. AI의 계획과 실제 변경을 읽습니다. 기존 `FieldDescription` 안의 문장만 바뀌었는지 확인합니다.
4. 실무 기록 화면을 다시 열어 문구를 확인합니다. 메모를 입력하고 다른 필드로 이동해 입력 동작이 유지되는지 봅니다.
5. 아래 명령으로 변경을 확인합니다.

```bash
git diff -- src/components/record-editor.tsx
git diff --check
```

6. T5에 변경 이유와 확인한 화면을 남깁니다. 문구 수정만을 위해 새 자동 테스트를 만들지는 않습니다.
7. 확인 후 해당 파일만 스테이징하고 저장합니다. 소스 사본의 다른 변경이나 환경 파일을 함께 넣지 않습니다.

```bash
git add src/components/record-editor.tsx
git diff --cached
git commit -m "교육 실습: 실무 메모 작성 안내 보완"
```

되돌리기를 체험할 때는 AI에게 광범위한 초기화를 요청하지 않습니다. 아직 커밋하지 않은 본인 문구 변경을 편집기에서 원문으로 되돌리거나, 본인의 해당 커밋만 취소하는 방법을 강사와 확인합니다.

## 6. 응용과 예상 오류

응용 과제는 같은 도움말에 수치·단위를 함께 적도록 한 문장을 더하는 것입니다. 먼저 완료 기준을 작성하고 같은 검증 순서를 독립적으로 수행합니다. 입력 필드 추가는 이번 회차의 응용 범위를 넘으므로 후속 과제로 기록합니다.

| 증상 | 진단 | 조치 |
| --- | --- | --- |
| 수정한 문구가 보이지 않음 | 접속 주소·실행 사본·수정 파일 확인 | 같은 사본의 화면을 다시 열기 |
| 저장이 안 됨 | 문구 외 코드가 바뀌었는지, 오류 메시지 확인 | 변경 내역에서 불필요한 수정 제거 |
| 폴더 이름의 대괄호 때문에 명령 실패 | 동적 경로가 셸에서 해석되는지 확인 | 경로를 따옴표로 감싸기 |
| AI가 여러 파일을 재설계함 | 요청과 변경 범위 비교 | 도움말 수정만 남기도록 범위를 좁히기 |

## 7. 완료 기준

T2 코드 지도, 도움말 변경 전후, 관련 파일의 변경 내역, 확인 결과를 제출합니다. ‘이 변경이 DB 구조를 바꿨나요?’, ‘서버의 입력 검증은 어느 파일에 있나요?’에 답합니다. 다음 주에는 코드를 바꾸기 전에 관리 화면의 도메인 설정으로 해결할 수 있는 부분을 다룹니다.
