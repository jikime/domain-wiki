## 1. 이번 시간의 목표와 준비

domain-wiki의 기술이 어떤 목적과 용도로 사용되는지 이해하고, AI에게 첫 화면 변경을 요청해 결과를 확인합니다. 교육생은 업무 동작과 변경 범위를 설명하면 됩니다. 기술 문법·함수 작성·코드 줄별 해석·터미널 명령 암기는 과제가 아닙니다.

준비물은 1주차에 설치·실행한 같은 개인 프로젝트 사본과 개발용 AI, T0 환경 기록표, T1 문제 카드입니다. [프로젝트 업무·기술·아키텍처 안내](../project-guide.md), T2·T3·T5 [기록 양식](../templates.md)을 사용합니다. 시작할 때 T0와 [실행 안내](../getting-started.md)로 같은 DB·웹 서버·작업자를 확인합니다. 1주차의 설치 미완료 항목은 강사에게 알려 지원 상태를 확인합니다.

## 3. 핵심 설명

[공통 안내의 기술 표](../project-guide.md#3-사용-기술의-목적과-용도)를 화면과 함께 보여 줍니다. 40분은 기술 목적 12분, 실행·데이터 흐름 20분, 서비스 모델 연결 8분으로 나눕니다. 각 기술로 예제를 구현하는 시간은 두지 않습니다.

**화면과 서버.** Next.js·React는 화면과 서버 연결을 구성합니다. 화면의 입력이 서버로 전달되며 서버는 로그인·역할·입력 조건을 확인합니다. Next.js 화면 구성에는 서버에서 실행하는 부분도 있습니다.

**dev·worker·DB의 역할.** `npm run dev`는 화면과 API 백엔드를 함께 제공하는 Next.js 웹 서버입니다. `npm run worker`는 문서 추출·위키 생성·임베딩 색인 같은 오래 걸리는 작업을 처리하며 별도 사용자 접속용 웹 주소가 없습니다. 이 두 프로그램과 PostgreSQL DB가 기본 실행 구성입니다. pgvector와 pg-boss는 같은 DB를 사용하고, 기본 생성 연결은 Claude Code CLI를 실행하고 임베딩용 OpenAI 연결은 외부 API를 호출합니다. [실행 구성 표](../project-guide.md#실행-명령과-세-가지-구성)를 기존 구조 설명 20분 중 약 4분에 짚습니다. 코딩·설치 과제는 추가하지 않습니다.

**자료형과 입력 검증.** TypeScript는 개발 중 코드의 값 형태를 확인하고, Zod는 서버가 실제 받은 입력이 조건에 맞는지 검사합니다. ‘제목 필수’, ‘입력 길이 제한’처럼 필요한 규칙을 AI에게 알려 주면 됩니다.

**저장과 작업자.** PostgreSQL·Drizzle은 데이터와 관계를 저장·조회하고, 원본 파일은 별도로 보관합니다. 오래 걸리는 문서 추출과 위키 생성은 작업자가 처리합니다. pg-boss는 처리할 일을 보관하는 작업 큐입니다.

**임베딩과 pgvector.** 현재 교육 준비 환경은 OpenAI의 `text-embedding-3-small`로 글을 벡터라는 숫자 배열로 바꾸고, PostgreSQL의 pgvector로 저장·비교하도록 설정되어 있습니다. 작업자는 공개 원문·게시된 위키의 벡터를 저장하고, 서버는 질문도 같은 모델로 변환해 관련 자료를 찾습니다. ‘OpenAI는 벡터 생성, pgvector는 저장·비교, 서버·작업자는 연결’로 역할을 설명합니다. [연결 흐름](../project-guide.md#현재-임베딩-모델과-pgvector)을 기존 구조 설명 20분 중 약 3분에 다루며 구현 실습은 추가하지 않습니다.

**서비스 AI와 개발용 AI.** 서비스 AI는 위키와 답변을 만들고, 개발용 AI는 프로젝트 코드를 수정합니다. 서비스의 브라우저는 위키 서버 API를 호출하고 서버가 설정된 모델 API 또는 CLI를 사용합니다. 현재 모델 연결은 환경 변수로 선택하며, 관리자 화면은 조회·연결 확인 기능입니다. 연결 선택·저장 화면은 후속 설계안입니다.

**화면 스타일과 변경 기록.** 기존 shadcn/ui 부품과 스타일을 재사용하도록 AI에게 요청합니다. Git은 변경 이력을 남기는 도구이며, 교육생은 AI가 정리한 변경 범위와 결과 위치를 확인합니다.

## 4. 실습 A · 저장 흐름을 AI에게 설명받기

> **입력할 곳:** 개발용 AI 대화창. 위키 화면은 설명과 비교할 때 엽니다.
>
> **정상 결과 예시:** “화면에서 입력하고 서버가 조건을 확인해 저장한다”는 흐름을 자신의 말로 설명합니다. 파일명과 코드 문법은 외우지 않습니다.

1. 실무 기록 화면에서 제목·메모·상황 등을 확인하고 저장하면 어떤 결과가 필요한지 설명합니다.
2. 개발용 AI에게 다음 요청을 전달합니다.

```text
이 domain-wiki에서 실무 기록을 저장하면 어떤 과정을 거치는지 설명해 주세요.
실제 코드를 확인하고 화면, 서버의 입력·권한 검사, 저장, 후속 문서 처리의 역할을 정리해 주세요.
코드 문법이나 줄별 해설 대신 각 부분이 필요한 이유를 업무 용어로 설명해 주세요.
관련 파일은 제가 찾아볼 수 있는 위치 안내로만 표시하고, 이번에는 수정하지 마세요.
```

3. AI가 제시한 흐름을 화면의 저장·처리·검토 상태와 연결합니다. 확인하지 못한 부분을 추정으로 표시했는지도 봅니다.
4. T2에 사용자 동작, 처리하는 부분의 역할, AI가 알려 준 위치를 남깁니다. 파일·함수 이름을 외우거나 직접 검색해 찾는 능력은 평가하지 않습니다.
5. ‘제목을 비워도 저장되게 바꾸면 어떤 규칙에 영향이 있나요?’처럼 업무 조건의 영향을 AI에게 묻습니다. 이 단계에서는 실제 검증 규칙을 바꾸지 않습니다.

강사는 실무 기록이 기존 자료 등록을 재사용해 작성자 진술 원문으로 저장된다는 점을 확인해 줍니다. 참고 위치는 [record-editor.tsx](../../../src/components/record-editor.tsx), [records.ts](../../../src/server/services/records.ts), [proposals.ts](../../../src/lib/proposals.ts)입니다.

기대 결과: ‘입력은 화면에서 하고, 서버가 조건을 확인한 뒤 자료로 보관한다. 공개에는 검토가 필요하다’는 흐름을 설명합니다.

## 5. 실습 B · AI에게 작성 안내 개선 요청하기

> **입력할 곳:** 개발용 AI에 변경을 요청하고, 브라우저의 실무 기록 화면에서 결과를 확인합니다.
>
> **정상 결과 예시:** ‘작성 당시 메모’에 요청한 안내가 보이고 기존 입력·화면 이동이 유지됩니다. AI의 완료 메시지만 보지 말고 화면을 다시 엽니다.

이 실습의 약 10분은 [다섯 가지 작성 기준](../prompt-practice.md#3-업무-요청에-필요한-다섯-가지)으로 요청 초안 작성·실행·후속 요청에 사용합니다. 3분 동안 아래 예시를 가리고 작성하고, AI의 계획에서 빠진 조건 한 가지를 찾아 후속 요청으로 전송합니다. 조건이 충분하면 확인할 화면 동작을 추가합니다. 실제 구현·화면 확인은 나머지 실습 시간에 이어 갑니다.

문제: 작성 당시 메모에 무엇을 적어야 하는지 알기 어렵습니다. ‘프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요.’라는 안내를 추가합니다. AI 정리가 원본 메모를 바꾸지 않는다는 기존 의미를 유지합니다.

1. 변경 전 화면을 확인하고 T3에 불편한 점·원하는 안내·완료 기준을 적습니다.
2. 자신의 요청을 먼저 전송합니다. 다음 예시와 비교해 빠진 조건을 찾되, 예시를 읽은 것만으로 작성·실행을 마친 것으로 기록하지 않습니다.

```text
실무 기록의 '작성 당시 메모' 도움말을 개선해 주세요.
'프로젝트, 확인 조건, 관찰한 결과를 구분해 적어 주세요.'를 추가하고
메모가 없어도 작성할 수 있으며 AI 정리가 메모 원문을 바꾸지 않는다는 기존 안내는 유지해 주세요.
기존 화면 스타일을 사용하고 입력 항목·저장 방식·권한은 유지해 주세요.
먼저 현재 코드와 변경 범위를 확인해 계획을 설명해 주세요.
```

3. 계획에서 안내 문구와 관련 화면만 바뀌는지 확인한 뒤 구현을 요청합니다. 코드 수정은 AI가 수행합니다.
4. AI에게 변경 파일·변경 이유·실행한 확인·미확인 항목을 정리하도록 요청합니다. 단순 문구 변경에 별도 테스트 작성 과제를 붙이지 않습니다.
5. 교육생은 실제 화면을 다시 열어 문구를 읽고 메모 입력과 다른 항목 이동이 그대로 되는지 확인합니다.
6. 보이지 않거나 의미가 달라졌다면 실제 결과를 AI에게 전달해 보완을 요청합니다.
7. T3에 첫 요청·후속 요청과 실제 응답, T5에 변경 전후 화면·교육생이 확인한 입력을 기록합니다. AI에게 해당 변경의 이력과 결과 위치를 정리하도록 요청합니다.

## 6. 응용과 예상 오류

빠르게 마친 교육생은 같은 도움말에 수치·단위를 함께 적도록 AI에게 추가 요청하고 결과를 확인합니다. 별도 문법·컴포넌트 작성 과제는 두지 않습니다.

| 증상 | 교육생이 전달할 정보 | AI·강사가 확인할 것 |
| --- | --- | --- |
| 수정한 안내가 보이지 않음 | 접속 주소·화면·기대 문구 | 수정 사본과 실행 서버의 일치 |
| 저장이 안 됨 | 입력과 오류 메시지 | 문구 외 변경 여부·기존 검증 |
| AI가 큰 재설계를 제시함 | 이번 완료 기준과 원하는 범위 | 최소 변경으로 다시 계획 |
| AI가 완료했다고 하나 화면이 다름 | 실제 화면과 기대 결과의 차이 | 반영 경로·변경 내역·미실행 검사 |

## 7. 완료 기준

T2 구조 지도, T3 요청, AI의 변경 요약, T5 실제 화면 확인을 남깁니다. ‘어떤 기술이 입력 조건을 확인하나요?’, ‘왜 안내 문구 변경에 DB 구조 변경이 필요하지 않나요?’를 역할 중심으로 설명합니다. 코드를 직접 작성하거나 변경 줄을 해설할 필요는 없습니다.

마무리에는 ‘저장 API는 dev와 worker 중 어디에서 처리하나요?’, ‘화면은 열리는데 문서 처리가 대기하면 어느 구성을 확인하나요?’를 같은 역할 설명 안에서 묻습니다. 실행 명령·포트 암기나 프로세스를 직접 중단하는 실습은 요구하지 않습니다.

다음 주에는 같은 프로젝트에서 회사 용어·양식·원문을 적용하고, 위키 생성에 필요한 업무 조건을 정합니다.
