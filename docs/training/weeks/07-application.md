# 통합 위키로 업무를 확인하고 운영 인계하기

같은 위키로 후속 단계 인수인계를 준비하고, 메모 저장을 안정화합니다. 자료 갱신과 운영 점검을 직접 해 본 뒤 최종 버전·담당·남은 일을 인계합니다.

[강의 화면](/lectures/week-07.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 6회차 통합 기준에서 내 전용 교육 DB와 자료를 이어 씁니다. 최종 코드 반영 때도 같은 DB의 기록·메모·갱신 결과를 유지합니다. 다른 교육생과 한 DB를 공동 수정하지 않습니다.

**남길 결과:** 근거·미정 사항을 구분한 인수인계 준비 기록 / 저장 실패·수정 충돌·계정 전환을 확인한 메모 기능 / 자료 개정과 역할별 운영 점검 결과 / 최종 버전·공용 반영 상태·담당과 남은 과제

업무 적용·운영 점검은 화면에서 직접 수행합니다. 기능 보완은 **계획 요청 → 내가 판단·수정 → 실행 요청 → 직접 확인** 순서입니다. 위키 채팅의 질문, Claude Code의 개발 요청, 내 문서의 기록 양식을 구분하세요.

## 시작 전에 준비할 것

- 6회차에서 확인한 통합 커밋과 개발 DB, 작성 writer@wiki.local·검토 reviewer@wiki.local·관리 admin@wiki.local·열람 reader@wiki.local 계정을 준비합니다. 비밀번호는 배정받은 값을 사용합니다.
- 공개 검수 조건 v2·두 게시 위키·후속 단계 요청 원문과 RFP 보고서가 필요합니다. 기존 운영 30초·90일, 후속 요청 45초·180일입니다. 초기 샘플의 60초 v1만 있으면 앞 회차 준비부터 확인합니다.
- RFP의 이전 회신과 현재 R5·R6 질문, 검색 조건·즐겨찾기·개인 메모·실무 기록·할 일·질문 모음·답변 확인·그래프 비교·용어·안내 기능을 이어 씁니다. 현재 스타터킷 캡처가 이 기능의 구현 완료를 뜻하지는 않습니다.
- [운영 인수인계 실습 사례](../samples/handover-practice.md)의 입력과 확인 순서를 사용합니다. 슬라이드에도 같은 업무 상황과 문장을 제공합니다.
- [운영 연습 원문 v1](../samples/handover-source-v1.md)은 별도 자료로 등록·공개한 상태로 준비합니다. [v2](../samples/handover-source-v2.md)는 자료 갱신 실습에서 같은 자료에 추가합니다. 기존 검수 조건·후속 요청을 덮어쓰지 않습니다.
- 강사는 채택한 안정화 변경·최종 기준·통합 사본·개발 DB를 준비합니다. 공용 주소·실제 운영 담당·기존 보관과 복구 확인 기록은 준비 여부를 구분합니다. 개인 DB의 자료가 코드 병합으로 자동 이동하지 않습니다.

| 결과 | 기준과 근거를 비교한 준비 기록을 남겼다. |
| 추가 확인할 내용 | 연계 책임·자료 항목과 허용 중단·전환 확인 방법을 정해야 한다. |

기록에는 실제 확인한 원문 문단을 연결합니다. 업무 조건 확인, 앱 기능 안정화, 실제 회사 인수는 각각 구분합니다.

## 통합 환경에서 이어가기

강사가 제공한 코드 사본·실행 주소·전용 개발 DB를 확인합니다. 교육생마다 DB를 분리하고 그 안에서 작성·검토·관리·열람 역할을 바꿉니다. 공통 계정 이름이 같다고 한 DB를 함께 수정하지 않습니다. 기준 커밋과 내 실제 통합 커밋은 각각 기록하며, 코드 내용·DB 적용·자료 상태를 함께 대조합니다.

최종 코드를 반영할 때도 이번에 만든 준비 기록·할 일·메모와 갱신한 연습 원문 v2·문의 안내가 있는 DB를 이어 씁니다. 새 코드 사본을 만든다고 빈 DB로 바꾸지 않습니다. 다른 DB가 꼭 필요하면 옮길 교육 자료·소유자·버전과 확인 순서를 먼저 정합니다.

## 준비: 통합 기능과 운영 메뉴 확인

실제 대상 메뉴와 저장 연결을 조사하고 내 화면에서 확인합니다.

```text
통합 위키의 자료실 즐겨찾기·내 메모, 실무 기록·개인 할 일, 채팅 질문 모음·답변 확인, 그래프 비교, RFP 항목·질문 답변과 관리의 운영 메뉴를 확인해. 기존 기능·빠진 기능과 저장할 DB를 구분하고 내가 열 화면을 알려 줘. 검수 조건 v2·후속 요청·보고서 준비 여부는 실제 화면에서 확인할 항목으로 남겨. 기능이나 자료가 있다고 가정하지 말고 코드·DB·운영 설정은 아직 바꾸지 마.
```

**직접 확인:** 통합 버전·역할 계정·공개 원문·보고서·즐겨찾기 준비를 확인합니다.

## 1. 후속 단계 인수인계 준비하기

[함께 볼 강의 화면](/lectures/week-07.html#slide-04)

**앞에서 이어받을 것:** 6회차 통합 기준에서 내 전용 교육 DB와 자료를 이어 씁니다. 최종 코드 반영 때도 같은 DB의 기록·메모·갱신 결과를 유지합니다. 다른 교육생과 한 DB를 공동 수정하지 않습니다.

**업무 상황:** 운영 담당에게 프로젝트 A의 기존 운영 기준과 후속 요청, 미정 조건을 설명할 준비를 합니다. 먼저 사용할 메뉴와 이유를 정하고 아래 공통 결과를 모두 남깁니다.

1. 자료실에서 검수 조건 v2와 후속 요청의 제목·버전·갱신·보관 문단을 확인합니다. 지식 그래프의 비교 목록에서 업무 절차와 범위·검수 기준 위키를 엽니다.
2. 아래 질문을 위키 채팅에 보낸 뒤 근거를 직접 읽습니다. RFP 내부 가상 회신은 보고서에서 따로 확인합니다.
3. 실무 기록에 ‘[가상 실습] 프로젝트 A 후속 단계 인수인계 준비’를 작성합니다. 상황은 두 기준의 혼재, 판단은 적용 범위 구분, 결과는 근거 비교, 추가 확인은 R5·R6 미정 조건입니다. 원문의 해당 문단을 근거로 선택한 뒤 저장하고 같은 기록을 다시 엽니다.
4. 내 할 일 ‘연계 책임 주체·세부 자료 항목 확인’, ‘허용 중단 시간·전환 확인 방법 확인’을 미완료로 남깁니다.
5. 후속 요청 원문 즐겨찾기의 내 메모에 **후속 요청 45초·180일. 연계 책임과 전환 조건은 확인 필요.**를 저장합니다. 같은 항목을 중복 등록하지 않습니다.

1. 아래 공통 작업을 모두 진행합니다.
2. 앞 단계의 기록을 다시 열어 확인하고 중복 입력하지 않습니다.
3. 실제 결과와 남은 일을 구분해 기록합니다.

**내가 정할 것:** 앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

**저장 기준:** 기록·할 일·즐겨찾기·답변 확인은 기존 DB 연결을 사용합니다. RFP 내부 회신과 공개 검색 자료를 구분합니다.

**입력할 곳:** 내 위키 → 채팅 · 가상 교통관제 자료 / 프로젝트 A

**위키의 채팅에 입력하는 질문입니다. 개발용 AI와 구분하세요.**

### 위키 채팅에 입력

```text
프로젝트 A의 기존 운영 기준과 후속 단계 요청을 비교해 줘. 기존 상태 화면 검수 조건 v2와 후속 단계 요청 문서를 구분해서, 표시 갱신 주기·이력 보관 기간·미정인 연계와 운영 전환 조건을 표로 정리해. 각 항목에 문서 제목·버전·근거를 붙이고 자료에 없으면 확인 필요로 남겨. 후속 요청을 기존 운영의 확정 개정으로 쓰지 마.
```

**만든 뒤 직접 눌러 보기**

### 끝까지 이어서 확인

앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

1. 두 기준의 원문·버전과 채팅 근거를 다시 읽습니다. 그래프 비교의 두 게시 위키도 같은 기준인지 봅니다.
2. 저장한 준비 기록과 근거를 다시 열고 R5·R6의 남은 질문, 내 할 일 두 개가 미완료인지 확인합니다.
3. 후속 요청 원문의 즐겨찾기와 저장한 메모를 다시 엽니다. 다음 실습에서는 이 메모의 저장을 보완합니다.

기록·질문을 읽었다고 실제 장비 점검이나 회사 운영 인수가 완료되지는 않습니다.

**확인:** 새 업무 결과와 안정화에 사용할 메모를 준비했습니다.

**기본을 마쳤다면 — 선택 과제**



한 가지만 골라도 됩니다. 막히면 기본 기능부터 강사와 함께 완성하세요.

실제로 수행한 결과와 준비되지 않아 확인하지 못한 항목을 구분합니다.

## 2. 즐겨찾기 메모 저장 안정화하기

[함께 볼 강의 화면](/lectures/week-07.html#slide-13)

**앞에서 이어받을 것:** 앞 업무에서 저장한 후속 요청 원문의 즐겨찾기 메모

**같은 메모로 확인:** 처음 문장은 ‘후속 요청 45초·180일. 연계 책임과 전환 조건은 확인 필요.’입니다. 탭1에는 ‘연계 책임 주체를 확인할 것.’, 탭2에는 ‘전환 확인 방법을 정할 것.’을 더합니다.

- 실패 확인: 편집 화면에서 ‘세부 자료 항목도 확인 필요.’ 추가 → 개발자 도구 Network의 Offline → 저장 → 입력 보존 확인 → 원래 온라인 설정 복귀 → 서버 값 재조회 → 필요한 내용 저장. 오프라인 중 새로고침하지 않습니다.
- 충돌 확인: 앞 단계에서 저장한 같은 버전의 메모를 두 탭에 열기 → 탭1 저장 → 새로고침하지 않은 탭2 저장 → 충돌과 두 내용 확인 → 두 문장을 합쳐 저장 → 두 탭에서 최종값 재조회.
- 계정 확인: 같은 서버에 같은 계정으로 별도 브라우저 로그인 → 저장값 읽기 → 다른 계정에서 개인 메모 접근 제한 확인. 서버·DB를 중지하거나 다른 사람의 메모를 삭제하지 않습니다.

1. 아래 공통 작업을 모두 진행합니다.
2. 앞 단계의 기록을 다시 열어 확인하고 중복 입력하지 않습니다.
3. 실제 결과와 남은 일을 구분해 기록합니다.

**내가 정할 것:** 앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

**저장 기준:** 기존 사용자·작업공간·즐겨찾기별 메모 DB를 유지합니다. 새 갱신 번호와 조건부 저장이 필요하면 변경 파일·적용·조회까지 확인합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
자료실 즐겨찾기의 내 메모 편집과 저장을 보완할 거야. 사용자·작업공간·즐겨찾기 연결을 확인하고 저장 중·완료·실패·결과 미확인을 구분할 계획을 세워. 실패하면 입력을 남기고 응답이 끊겼다면 서버 값을 재조회해 저장 여부를 확인하게 해. 재시도는 같은 메모를 갱신하며 중복 행을 만들지 않게 해. 현재 잘 되는 동작은 유지하고 필요한 DB 변경과 검사 범위를 설명해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **저장 완료** 서버 결과를 확인한 뒤 표시
- **실패·미확인** 입력 보존·서버 값 재조회
- **반복 저장** 같은 메모 갱신·중복 방지

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
즐겨찾기 내 메모에 확인한 저장 상태와 재시도 흐름을 적용해. 처리 중 연속 저장을 막고 확정된 응답 뒤에 완료를 보여 줘. 실패·결과 미확인에서는 입력을 지우거나 화면을 닫지 마. 서버 재조회와 사용자의 확인 뒤 다시 저장하게 해. 기존 메모 DB와 소유 범위를 유지하고 필요한 구조 변경만 파일로 남겨 개발 DB에 적용해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 메모에 ‘세부 자료 항목도 확인 필요.’를 더하고 오프라인에서 저장합니다. 입력이 남아야 합니다. 온라인 복귀 후 서버 값을 확인해 저장하고, 다음 두 탭 시험은 이 저장값에서 시작하세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 선택 과제는 기본 기능 뒤에 진행합니다.

### 다음 기능 · 두 탭에서 고친 내용을 덮어쓰지 않기

**먼저 계획 요청**

```text
즐겨찾기 내 메모를 같은 계정의 두 탭에서 수정할 때 충돌을 알려 줄 거야. 읽은 버전과 DB의 현재 버전을 서버에서 원자적으로 비교해 다르면 저장을 거절하는 계획을 세워. 갱신 번호 같은 기준을 기존 메모에 추가하고 최신 내용과 내가 쓴 내용을 함께 보여 줘. 사용자가 합칠 문장을 정한 뒤 최신 버전 기준으로 저장하게 해. 여러 서버에서도 단순 화면 비교만으로 통과하지 않게 해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 충돌 기준: 내가 읽은 버전과 DB 현재 버전
- 보존할 내용: 최신 저장문·내 작성문 모두
- 최종 판단: 내가 합칠 내용을 정한 뒤 저장

**계획을 확인한 뒤 실행**

```text
즐겨찾기 메모에 확인한 수정 충돌 처리를 만들어. 필요한 버전 필드·구조 변경을 개발 DB에 적용하고 조건부 갱신이 성공한 경우만 저장 완료로 표시해. 충돌하면 내 입력을 보존하며 최신 값을 다시 읽어 보여 줘. 사용자가 내용을 정한 뒤 다시 저장하고 그 사이 또 바뀌면 다시 충돌로 알려. 강제 덮어쓰기나 자동 합치기는 하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 탭1과 탭2에서 같은 메모를 엽니다. 탭1 저장 뒤 오래된 탭2를 저장해 충돌을 확인하고 두 문장을 합쳐 저장하세요.


**다음 기능 전에 직접 확인**

1. 오프라인 복귀·두 탭 충돌·다른 계정 확인을 다시 수행합니다. 이미 저장한 최종 문장은 읽어 확인하고 불필요한 새 메모를 만들지 마세요.

## 3. 자료 갱신과 운영 점검하기

[함께 볼 강의 화면](/lectures/week-07.html#slide-26)

**앞에서 이어받을 것:** 앞 통합본과 별도 공개된 운영 연습 원문 v1

**자료 준비:** [운영 연습 v1](../samples/handover-source-v1.md)을 별도 사업 자료로 등록하고 공개한 상태에서 시작합니다. 도메인은 가상 교통관제 자료, 프로젝트는 A입니다. 기존 검수 조건·후속 요청 원문은 바꾸지 않습니다.

1. writer로 같은 연습 자료의 **새 원본 버전 등록**에서 [v2 파일](../samples/handover-source-v2.md)을 올립니다. 제목은 ‘[가상 실습] 운영 안내 변경 연습’, v2는 문의에 자료 제목·버전·증상·기대·실제 결과를 남기도록 바뀝니다.
2. reader로 승인 전 공개 v1을 확인합니다. reviewer가 검토함에서 추출문·변경 내용을 읽고 별도로 공개 승인한 뒤 reader로 v2를 확인합니다.
3. 관리 → 작업·사용량·보존 관리에서 문서 처리 상태·최근 모델 오류·모델/임베딩 사용량을 읽습니다. 실제 오류가 없다면 없음, 재시도는 미실행으로 기록합니다. 자료 실패는 해당 원문의 오류와 처리 재시도, 모델 문제는 관리의 모델 연결과 실제 오류를 확인합니다.
4. 직원 계정의 역할과 모델 연결 위치를 확인합니다. 앞에서 만든 자료실 이용 안내에 **문의에는 자료 제목·버전·증상·기대·실제 결과를 남기세요.**를 덧붙이고 writer·reader로 다시 읽습니다.
5. DB·원본 파일·코드·설정 보관 위치·담당·기존 복구 확인 기록을 아래 양식에 남깁니다. 교육용 샘플 백업을 전체 운영 백업으로 보지 않습니다.

1. 아래 공통 작업을 모두 진행합니다.
2. 앞 단계의 기록을 다시 열어 확인하고 중복 입력하지 않습니다.
3. 실제 결과와 남은 일을 구분해 기록합니다.

**내가 정할 것:** 앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

**저장 기준:** 원문 버전·검토는 기존 기능을 사용합니다. 문의 안내는 기존 도메인·메뉴별 DB에 저장하고 운영 인계 문서는 지정한 문서 위치에 보관합니다.

**입력할 곳:** 내 기록 문서 → 운영 인계

**내 문서에 적을 양식입니다. 개발 AI에 보내는 요청이 아닙니다.**

### 내 기록 문서에 남기기

```text

문서 처리·모델 상태: [실제 화면 / 현재 상태 / 다음 행동]
재시도·모델 점검: [실행함·미실행 / 이유 / 결과]
계정·문의 안내: [역할별 결과 / 안내 위치 / 담당]
보관·복구: [DB·원본·코드·설정의 보관 위치 / 담당 / 확인 기록 유무]

```

### 끝까지 이어서 확인

앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

1. reader로 연습 원문의 공개 v2와 변경 문장을 다시 엽니다. v2를 다시 등록하지 않습니다.
2. 관리자로 작업·사용량·보존 관리와 모델 연결을 찾습니다. 실제 오류 없음과 재시도 미실행을 구분해 적습니다.
3. writer·reader로 자료실 안내를 읽고 문의할 내용·담당을 찾습니다. 보관·복구 미확인 항목도 남깁니다.

실제 운영 담당의 참여·인수가 없으면 교육용 역할 확인까지만 완료입니다.

**확인:** 자료 갱신 결과와 운영 확인 기록을 최종 인계로 넘깁니다.

**기본을 마쳤다면 — 선택 과제**



한 가지만 골라도 됩니다. 막히면 기본 기능부터 강사와 함께 완성하세요.

실제로 수행한 결과와 준비되지 않아 확인하지 못한 항목을 구분합니다.

## 4. 최종 반영과 운영 인계하기

[함께 볼 강의 화면](/lectures/week-07.html#slide-35)

**앞에서 이어받을 것:** 안정화 코드·DB 변경과 운영 점검 결과, 강사가 지정한 통합 환경

반영할 기준·안정화 변경·최종 커밋, 코드 사본은 강사가 준비한 실제 값을 사용합니다. DB는 이번 업무에서 쓴 교육생별 전용 통합 DB를 유지해 기록·메모·운영 연습 결과를 이어 씁니다. 다른 DB가 필요하면 자료 이전 범위를 먼저 확인합니다. 공용 반영은 담당 절차에서 수행하고, 이 개발 요청은 교육용 통합 환경까지만 다룹니다.

1. 아래 계획과 실행 요청으로 확인한 안정화 변경을 반영합니다.
2. writer·reviewer·admin·reader로 같은 서버에서 원문·보고서·기록·개인 메모·안내와 접근 제한을 확인합니다.
3. 홈에서 시작해 처음 맡은 인수인계 준비 업무를 다시 수행합니다. 새 자료와 메모를 중복 등록하지 않습니다.
4. 인계 문서에 개인·통합 확인, 공용 반영, 실제 운영 인수, 보관·복구 확인, 남은 업무·기능·도입 준비를 구분합니다. 각 항목에는 실제 주소·버전·담당·다음 행동·완료 기준을 적습니다.

**최종 인계 기록 양식 — 내 문서에 작성**

```text
개인·통합 확인: [서버 / 최종 커밋 / DB 적용 / 실제 업무 결과]
공용 반영: [실제 주소 / 반영 버전 / 확인자 / 완료·미완료]
운영 인수: [실제 담당 / 받은 절차·위치 / 직접 확인 결과 / 미인수 항목]
보관·복구: [DB·원본·코드·설정 위치 / 기존 확인 기록 / 미확인]
남은 업무·기능·도입 준비: [문제 / 담당 또는 지정할 사람 / 다음 행동 / 완료 기준]
```

1. 아래 공통 작업을 모두 진행합니다.
2. 앞 단계의 기록을 다시 열어 확인하고 중복 입력하지 않습니다.
3. 실제 결과와 남은 일을 구분해 기록합니다.

**내가 정할 것:** 앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

**저장 기준:** 반영한 코드 커밋·DB 적용 목록과 업무 결과를 연결합니다. 공용 반영·운영 인수 상태는 실제 확인 근거와 함께 기록합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
즐겨찾기 내 메모 안정화 변경을 내 교육용 통합본에 반영할 거야. 제공한 시작·추가·최종 비교 기준과 대상 코드 사본을 확인해. 이번 업무에서 쓴 내 전용 DB·기록·메모·연습 원문·안내를 그대로 이어 쓸 계획을 세워. origin·upstream, 작업 보관·차이·충돌·DB 적용 순서를 설명해. 다른 DB가 필요하면 자료 이전 계획부터 제시해. 공용 배포·운영 데이터 이관은 하지 말고 코드·DB는 아직 바꾸지 마.
```

**계획을 읽고 내가 확인할 것**

- **반영 대상** 지정 통합 사본·개발 DB
- **채택 변경** 확인한 메모 안정화·필요한 DB 변경
- **확인 결과** 실제 최종 커밋·적용·검사

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
확인한 개인 변경을 별도 브랜치에 보관하고 upstream 이력을 fetch해 지정 통합 사본에 채택한 안정화 변경만 반영해. 이번 실습의 전용 DB와 기존 기록·메모를 유지하며 필요한 DB 변경만 적용해. 코드 내용·DB 이력·저장 실패·충돌·계정 분리를 검사해. 기준과 내 실제 커밋·적용 파일·미실행을 기록해. 환경 파일·개인 자료는 커밋하지 말고 운영 환경·Docker는 바꾸지 마. 직접 확인할 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 통합본에서 같은 후속 요청 즐겨찾기의 메모를 열고 저장·충돌·계정 분리를 확인합니다. 개인 DB의 메모가 저절로 옮겨졌다고 가정하지 마세요.

**만든 뒤 직접 눌러 보기**

### 끝까지 이어서 확인

앞 단계에서 만든 결과를 이어 사용하고 확인합니다.

1. 최종 통합본에서 준비 기록·근거·메모·안내를 다시 엽니다. 실제 적용 커밋·DB 변경과 맞는지 확인합니다.
2. 운영 절차의 주소·담당·보관 위치와 확인 기록을 읽습니다. 실제 담당의 인수가 없으면 미인수로 남깁니다.
3. R5·R6 업무 질문과 기능·공용 준비의 남은 일을 구분합니다. 맡을 사람·다음 행동·완료 기준을 적습니다.

실제 회사 운영 인수는 준비된 담당과 환경에서 확인한 범위만 완료입니다.

**확인:** 교육 이후에도 같은 위키를 개선하고 운영할 기준을 남겼습니다.

**기본을 마쳤다면 — 선택 과제**



한 가지만 골라도 됩니다. 막히면 기본 기능부터 강사와 함께 완성하세요.

공용 환경이 준비되지 않았다면 통합 확인까지 완료하고 남은 도입 조건을 남깁니다.

## 화면에서 확인한 뒤 코드 보관하기

인계 기록을 완성한 뒤 포함할 변경과 확인 결과를 대조합니다. 공용 반영은 지정 담당 절차를 따릅니다.

**먼저 보관할 변경 확인**

```text
즐겨찾기 내 메모 안정화와 최종 통합에서 바뀐 코드·DB 변경 파일을 정리해. 실제 실행한 검사와 미실행 항목을 구분하고 인계 문서의 버전과 맞춰 줘. 커밋에 포함할 변경과 제외할 환경 파일·개인 자료를 먼저 보여 줘. 아직 커밋하거나 push하지 마.
```

**포함할 코드·DB 변경과 제외할 설정을 확인한 뒤 실행**

```text
확인한 코드·DB 변경과 교육용 문서만 현재 작업 브랜치에 커밋해. 환경 파일·개인 자료·비밀 값은 제외하고 관련 없는 변경은 보존해. 최종 커밋과 실제 검사 결과를 알려 줘. 원격 push·공용 배포·운영 데이터 이관은 하지 마.
```

## 이어서 할 일

회사가 정한 담당이 남은 과제를 이어 확인합니다. 새 불편이 생기면 대상 기능과 기대 결과부터 정하고 계획·개발·직접 확인을 반복합니다. 바꾼 내용과 직접 확인한 결과는 회사 개발 노트의 같은 작업 카드에 적으세요.
