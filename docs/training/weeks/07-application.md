## 1. 이번 시간의 목표와 준비

팀마다 **현재 소스의 작은 기능 개선 한 가지를 AI에게 구현 요청**하고, 교육생은 변경 전후 동작과 업무 활용 결과를 확인합니다. 새 RFP를 기존 지식에 적용하는 실습도 이어 갑니다. 준비물은 6주차의 정상 코드와 자료 v2, 선정한 팀 과제, 신규 요청 문서, T3·T5·T9 [양식](../templates.md)과 [평가 기준](../assessment.md)입니다.

기능은 6주차에 범위를 정하고 이번 시간에 AI가 구현합니다. 교육생은 요구사항·계획 판단·화면 확인·보완 요청을 맡으며 직접 코딩하지 않습니다. 설정값 변경이나 기존 기능 시연만으로 코드 과제를 완료한 것으로 보지 않습니다. 강사가 핵심 요청·판단·확인을 대신한 경우에는 도움 수준을 기록하고 교육생이 다른 조건으로 요청·확인을 다시 수행합니다. AI의 코드 작성은 기본 수행 방식입니다.

## 3. 핵심 설명

**기능 개발의 완료.** 코드가 바뀌고 실제 화면의 동작도 달라져야 합니다. 파일 저장이나 AI의 완료 설명만으로 판단하지 않습니다. 정상 입력과 빈 값·삭제·잘못된 입력을 함께 확인합니다.

**입력과 표시.** 입력·삭제에 따라 화면의 안내도 달라져야 합니다. 필요한 화면 동작을 교육생이 정하고 계산·연결 방법은 AI가 구현합니다. 기존 입력 검증·권한·근거 규칙이 유지되는지 실제 결과로 확인합니다.

**RFP의 근거 구분.** 새 문서의 명시 요구, 기존 사업의 사례, 우리가 해석한 내용과 확인 질문을 나눕니다. 기존 A의 조건을 새 요청의 조건으로 바꾸어 적지 않습니다.

**개발 결과와 업무 결과.** 질문 개수 표시가 맞는 것과 RFP 분석 내용이 맞는 것은 별도로 확인합니다. UI 개선이 모델 답변의 정확도나 업무 요구의 충족을 보장하지 않습니다.

## 4. 팀 코드 개선 과제

> **입력할 곳:** 개발용 AI에 구현을 요청하고 브라우저의 RFP 또는 실무 기록 화면에서 확인합니다.
>
> **정상 결과 예시:** A 과제는 확인 질문이 빈 불명확 항목 1개를 누락 1개로 표시합니다. B 과제는 ‘현장 점검’ 입력 시 길이 5를 표시합니다. 선택한 과제만 진행합니다.

각 팀은 아래에서 하나를 고릅니다. **현재 소스에는 이 표시 기능이 없으며, 교육생이 AI에게 추가를 요청할 과제**입니다. 두 팀이 같은 과제를 선택해도 각자의 요청과 화면 확인 결과를 남깁니다.

| 과제 | 해결할 문제 | AI가 확인할 위치 | 완료 기준 |
| --- | --- | --- | --- |
| A · RFP 확인 질문 누락 개수 | 추론·불명확 항목에 확인 질문을 빠뜨린 채 저장을 시도함 | [rfp-editor.tsx](../../../src/components/rfp-editor.tsx)의 보고서 항목 표시 영역 | 질문이 비어 있는 추론·불명확 항목 수를 표시하고 입력·유형 변경·추가·삭제에 맞춰 갱신 |
| B · 실무 메모 입력 길이 | 긴 협의 메모를 작성하며 입력 한도까지 얼마나 남았는지 알기 어려움 | [record-editor.tsx](../../../src/components/record-editor.tsx)의 작성 당시 메모 안내 | 현재 길이와 기존 12,000 제한을 표시하고 입력·삭제·다시 열기에 맞춰 갱신 |

A의 빈 질문은 질문이 없거나 공백만 입력한 경우입니다. 명시 요구·기준·사례 항목은 질문이 없더라도 이 개수에 넣지 않습니다. 표시 문구 예는 ‘확인 질문이 필요한 항목 2개’입니다. 저장 버튼이나 서버 검증을 새 규칙으로 바꾸는 과제는 아닙니다.

B는 기존 12,000 입력 제한과 같은 기준으로 현재 길이를 보여 줍니다. 기존 입력창·스타일·저장·AI 정리 동작을 유지하도록 요청합니다. 계산 방법은 AI가 결정하며 교육생은 실제 표시를 확인합니다.

### 요청·계획 확인·AI 구현

첫 약 10분은 [프롬프트 작성·실행](../prompt-practice.md)을 스스로 진행합니다. 아래 예시를 가리고 팀의 요청 초안을 작성한 뒤 팀원이 목표·결과·유지 조건·확인 입력을 읽어 봅니다. 초안을 실제로 전송하고 계획을 확인한 뒤 각 교육생은 자신이 발견한 조건 또는 확인 요청을 한 번 이상 직접 작성·전송합니다. 같은 사본의 코드 구현 요청은 순서를 정해 진행합니다. T3에 각자의 문장·전송·응답을 기록합니다.

1. 교육생은 변경 전 화면을 보고 T3에 사용자 문제·기대 동작·확인할 입력을 적습니다. 수정 파일은 AI가 찾아 안내하게 합니다.
2. 직접 작성한 초안을 AI에게 전달합니다. 아래 예시는 전송한 뒤 누락 조건을 확인하는 참고로 사용합니다.

```text
현재 domain-wiki의 RFP 작성 화면을 개선해 주세요.
추론·불명확 항목 중 확인 질문이 없거나 공백뿐인 항목의 개수를 보여 주세요.
질문 입력, 항목 유형 변경, 추가·삭제에 따라 표시가 즉시 맞아야 합니다.
명시 요구·기준·사례는 이 개수에서 제외하고 기존 저장 조건·권한·스타일은 유지해 주세요.
현재 코드를 확인하고 변경 범위·확인 방법을 설명해 주세요.
```

B팀은 ‘실무 기록의 작성 당시 메모에 현재 길이와 기존 12,000 한도를 보여 주고, 입력·삭제·다시 열기에 맞춰 갱신해 주세요’로 바꿉니다.

3. 계획이 업무 의도와 맞으면 AI에게 구현과 관련 형식·타입 검사를 요청합니다. 새 DB·API·의존성이 필요한지 제안되면 이번 작은 표시 기능의 범위에 맞게 조정합니다.
4. AI에게 변경 파일·역할·사용자 동작의 변화·실행한 검사·미확인 항목을 정리하게 합니다. 기술 명령과 코드 수정은 AI가 수행합니다.
5. 팀원은 요청 작성자·계획 확인자·결과 확인자를 교대합니다. 모든 교육생이 요구·판단·보완 요청 중 한 가지와 개별 화면 확인에 참여합니다.

### 동작 확인

| 과제 | 확인할 입력·조작 | 기대 결과 |
| --- | --- | --- |
| A | 명시 요구만 있고 확인 질문은 없음 | 누락 개수 0 |
| A | 불명확 항목의 질문이 빈 값 또는 공백뿐임 | 해당 항목을 1개로 계산 |
| A | 추론·불명확 두 항목 중 하나에 질문 입력 | 2개에서 1개로 변경 |
| A | 질문 없는 항목의 유형 변경·추가·삭제 | 현재 항목 목록에 맞게 개수 갱신 |
| A | 질문 없는 불명확 항목 저장 시도 후 질문을 넣어 저장 | 기존 서버 거부 유지, 나머지 근거 조건도 충족하면 저장 |
| B | 빈 메모 → ‘현장 점검’ 입력 → 일부 삭제 | 0 → 5 → 삭제한 뒤의 길이 표시 |
| B | 일반 한글로 12,000 한도까지 입력 | 표시와 기존 입력 제한 일치 |
| B | 저장한 기록 다시 열기 | 저장된 메모의 길이 표시, 기존 내용 유지 |

A의 화면 개수는 원문 인용·권한 등 모든 저장 조건을 판정하지 않습니다. 비교에는 같은 자료와 계정을 사용하고, 6주차에 확인한 동의어 저장도 대표 입력 한 건으로 확인합니다. T5에는 AI의 코드 검사 보고와 교육생의 화면·기존 동작 확인을 나누어 적습니다.

## 5. 팀 실습 · 새 RFP에 적용

> **입력할 곳:** 브라우저의 RFP 작성 화면에서 새 요청 문서와 실제 근거를 선택합니다.
>
> **정상 결과 예시:** 명시 요구에는 새 RFP의 원문 구절이, 불명확 항목에는 확인 질문이 연결됩니다. 과거 사업의 조건을 새 요구로 단정하지 않습니다.

개발 결과를 검증한 뒤 30분 동안 진행합니다. 신규 문서는 강사가 수업 시작에 제공하며, 기존 원문을 덮어쓰지 않고 새 RFP 원문으로 등록·공개합니다.

1. R1–R6을 읽고 명시 요구와 협의가 필요한 범위를 표시합니다.
2. RFP 화면에서 공개된 신규 요청 문서를 선택합니다.
3. **명시 요구 1개와 불명확 항목 1개**를 작성합니다. 명시 요구는 해당 RFP의 실제 문단과 원문 구절을 연결하고, 불명확 항목에는 확인 질문을 남깁니다.
4. R5의 대상 기관·자료 항목·연계 주기·책임, R6의 허용 중단 시간·전환 확인 방법을 질문 후보로 사용합니다. 문서에 없는 답을 채우지 않습니다.
5. 저장·검토 요청 후 다른 검토자가 확인합니다. 전체 R1–R6의 검토 여부와 미완료 항목을 기록합니다.
6. A팀은 질문 입력 전후 개수 표시를 실제 RFP에서 확인합니다. B팀은 이 검토에서 발견한 협의 내용을 실무 메모로 작성하며 길이 표시를 확인합니다.

기준·과거 사례 항목 추가는 여유가 있을 때 진행합니다. 근거·분류·확인 질문 규칙은 [business.ts](../../../src/lib/business.ts)와 [rfp.ts](../../../src/server/services/rfp.ts)를 따르며, 저장을 통과시키기 위해 검증을 삭제하지 않습니다.

## 6. 개인 수행 확인

각 교육생은 팀 과제에서 자신이 맡은 부분을 T5에 이름과 함께 남깁니다.

1. 자신이 작성·전송한 첫 요청 또는 후속 요청을 보여 주고, 결과를 보고 그 문장을 쓴 이유와 기대한 화면 동작을 설명합니다.
2. 다른 교육생과 다른 입력·조작 하나를 직접 실행하고 기대 결과와 비교합니다.
3. 오류가 있으면 AI에 전달한 재현 정보와 보완 결과를 남기고, 없으면 빈 값·삭제 등 확인한 동작을 설명합니다.
4. 신규 RFP의 명시 요구 또는 불명확 항목 하나를 원문과 대조합니다.

팀의 완성 화면만으로 개인 수행을 대신하지 않습니다. 강사의 직접 지원이 있었다면 같은 유형의 다른 입력으로 재수행합니다.

## 7. 시연과 결과 검토

팀 시연은 **업무 문제 → AI 요청·계획 판단 → 변경 전후 화면 → 정상·경계 입력 → RFP 적용 결과** 순서로 진행합니다. AI가 정리한 변경 위치는 인계용으로 남기고 코드 문법·계산식 설명은 요구하지 않습니다.

개인 설명 10분은 업무 문제 2분, AI 요청·판단 3분, 다른 입력 확인 3분, 인계 설명 2분으로 사용합니다. AI 사용은 기본 수행 방식이며 직접 코드를 작성했는지는 평가하지 않습니다.

## 8. 인계와 완료 기준

팀마다 AI가 구현한 코드 개선 1개, AI 요청·변경 요약·검사 보고, 교육생의 정상·경계 입력·기존 동작 확인, RFP 필수 항목 2개와 검토 상태를 남깁니다. 코드 개선을 미완료한 경우에는 설정 변경이나 보고서 작성만으로 대체 완료하지 않습니다. 범위를 표시 기능의 최소 동작까지 줄이고 강사의 도움 수준·남은 문제를 기록합니다.

T9에는 [원본 저장소](https://github.com/jikime/domain-wiki), 결과 코드의 위치·커밋, 새 기능과 확인 방법, [실행 안내](../getting-started.md)를 적습니다. 다른 팀이 해당 코드와 검증 입력을 찾아 같은 동작을 확인합니다. DB·원본 파일의 관리 위치도 별도로 남깁니다.

AI는 용도별 연결·모델, 인증·과금·사용 범위, 한도와 관리 담당, 최근 확인 결과를 기록합니다. 설정 변경 뒤 웹 서버·작업자 재시작이 필요하며 키·로그인 토큰은 인계 문서에 적지 않습니다.

관리자 화면의 모델 연결 등록·선택·저장, 새 DB 구조, 배포 자동화처럼 범위가 큰 기능은 T8의 후속 과제로 남깁니다. 팀별 후속 과제 3개에는 사용자 문제·담당자·완료 기준을 적습니다. 자세한 판정은 [평가와 인계](../assessment.md)를 따릅니다.
