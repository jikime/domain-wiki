# 7주차 · 업무 적용 워크숍과 성과 공유

시간: 운영 360분 / 학습 330분 / 휴게 30분. 시작·종료 시간은 고객과 별도로 협의합니다. 아래 시각은 수업 시작부터의 경과 시간입니다.

## 1. 이번 시간의 목표와 준비

교육생은 처음 보는 요구사항을 기존 지식과 비교하고, 근거·추론·확인 질문을 구분합니다. 개인 수행과 팀 시연을 통해 변경·검증·인계 능력을 확인합니다. 준비물은 6주차까지의 프로젝트, 강사가 배포하는 신규 요청 문서, T7·T8·T9 [양식](../templates.md)과 [평가 기준](../assessment.md)입니다.

강사는 신규 RFP를 수업 시작 시 프로젝트 A의 사업 자료로 공개할 수 있도록 준비합니다. 사전 공개로 답을 외우게 하지 않습니다. AI와 공식 자료는 사용할 수 있으며 강사가 직접 해결 코드를 입력한 경우 도움 수준을 기록합니다.

## 3. 핵심 설명

**RFP 명시 요구.** 이번 요청 문서 자체가 요구한 내용입니다. 과거 사업의 조건으로 바꾸어 적지 않습니다.

**관련 기준·과거 사례.** 공통 지침과 기존 사업의 경험은 적용 가능성을 확인할 자료입니다. 가상 지침은 이 교육 예제에서만 사용하는 자료이며 실제 법적 의무로 표현하지 않습니다.

**분석·추론·불명확한 범위.** 원문에 쓰인 내용과 우리가 해석한 내용을 구분합니다. 불명확한 대상·주기·책임은 확인 질문으로 남깁니다.

**기능 완성과 업무 적용.** 저장과 게시가 성공해도 검토 내용이 맞는지는 따로 확인합니다. 같은 숫자라도 측정 대상과 조건이 다르면 충족을 단정할 수 없습니다.

**인계.** 다른 사람이 코드·자료·설정·평가 방법을 찾아 같은 상태에서 시작할 수 있게 정리하는 것입니다. API 키와 DB 원본을 코드 저장소에 함께 넣는 것을 뜻하지 않습니다.

## 4. 개인 적용 과제

강사는 각 교육생에게 아래 유형을 하나씩 배정합니다. 모든 교육생은 T1·T5 또는 T6 기록과 근거를 남깁니다.

| 유형 | 수행 | 완료 증거 |
| --- | --- | --- |
| 요구 비교 | 신규 R1·R2와 기존 A 조건 비교 | 숫자·대상·원문 버전·추가 확인 정리 |
| 범위 검토 | R4의 제외 범위와 R5의 불명확한 연계 구분 | 명시 내용과 질문 구분 |
| 작은 변경 | 새로운 업무 용어·양식 조건 적용 | 변경 전후와 기존 입력 확인 |
| 오류 진단 | 강사가 제시한 미공개·잘못된 범위 사례 진단 | 가설·확인·수정·재확인 |
| 지식 갱신 | 새 요구사항에 맞는 짧은 위키 초안과 근거 연결 | 원문·추론 분리, 동료 검토 상태 |

난이도는 사전 학습 결과에 맞추되 단순 복사만으로 완료되지 않도록 입력이나 조건을 바꿉니다. 이미 만든 답안 파일을 제출하는 것으로 개인 수행을 대체하지 않습니다.

## 5. 팀 실습 · RFP 보고서

1. 신규 문서에서 R1–R6을 읽고 명시 요구·불명확한 범위를 표시합니다.
2. 업무 도구의 RFP 화면에서 공개된 신규 문서를 선택합니다. 기존 사업 개요나 실무 기록을 신규 RFP 원문으로 잘못 고르지 않습니다.
3. 팀별로 명시 요구 2개, 관련 기준 또는 과거 사례 1개, 불명확한 범위 또는 추론 1개 이상을 작성합니다. 전체 요구 6개의 누락 여부는 팀 검토표에 남깁니다.
4. 명시 요구의 근거는 **선택한 RFP 자체의 실제 문단**에서 고릅니다. ‘원문 구절’은 선택 문단에 있는 표현을 그대로 사용합니다.
5. 관련 기준은 도메인 공통의 가상 지침 문단을, 과거 사례는 사업 자료 또는 작성자 진술을 연결합니다. 문서 유형과 프로젝트 범위를 확인합니다.
6. 불명확한 범위·추론에는 확인 질문을 반드시 남깁니다. R5의 대상 기관·자료 항목·연계 주기·책임, R6의 중단 시간·전환 확인 방법을 질문 후보로 사용할 수 있습니다.
7. 저장하고 검토 요청합니다. 다른 검토자가 인용·분류·적용 조건을 확인해 게시하거나 수정 요청합니다.
8. 작성·검토 완료 범위와 남은 항목을 기록합니다. 게시 여부와 내용의 정확성을 따로 확인합니다.

## 6. 코드와 연결되는 확인 사항

현재 보고서는 `src/lib/business.ts`의 분류와 입력 구조를 사용하고, `src/server/services/rfp.ts`에서 근거를 검사합니다. 명시 요구·기준·사례에는 원문 구절과 근거 문단이 필요합니다. 인용 구절이 문단에 없거나 명시 요구에 다른 자료를 연결하면 저장을 거부할 수 있습니다. 이를 회피하려고 검증 코드를 삭제하지 않습니다.

AI가 만든 인용이 틀리면 원문에서 정확한 구절을 다시 선택합니다. ‘관련 기준’에 일반 참고 메모를 넣은 경우에는 실제 자료 성격과 분류를 다시 확인합니다. 게시를 통과시키려고 자료 유형을 임의로 바꾸지 않습니다.

## 7. 시연과 개인 설명

팀 시연은 ‘업무 문제 → 변경 → 같은 입력의 전후 결과 → 근거 → 남은 제한’ 순서로 진행합니다. 서비스 전체 메뉴를 순서대로 보여 주는 데 시간을 쓰지 않습니다.

개인 설명에서는 다음 네 가지를 확인합니다.

1. 내가 직접 수행한 변경 또는 진단은 무엇인가?
2. 어느 원문·코드·공식 자료를 근거로 판단했는가?
3. 성공·실패 입력으로 무엇을 확인했는가?
4. 다른 조건에서 다시 적용하거나 되돌리려면 무엇이 필요한가?

## 8. 인계와 완료 기준

T9에 코드 기준, 실행 방법, 설정 이름과 담당자, 원본·DB 관리 위치, 검토 절차, 대표 질문, 남은 문제를 정리합니다. AI는 용도별 연결 방식·모델, 확인된 인증·과금 방식, 임베딩·검색 설정, 한도, 최근 연결 확인 결과와 관리 담당을 남깁니다. 키·CLI 로그인 토큰은 적지 않습니다. 현재 설정 변경 후에는 웹 서버·작업자 재시작이 필요하다는 점도 인계합니다. 다른 팀이 안내를 읽고 파일과 대표 질문을 실제로 찾아 봅니다.

관리자 화면의 연결 등록·선택·저장 기능은 후속 과제 후보입니다. 이 항목을 선택한다면 회사별 적용 범위·권한, 비밀 값 분리, 연결 상태 표시와 새 요청부터의 설정 적용을 완료 기준으로 적습니다. 제안한 화면을 이미 구현된 기능으로 인계하지 않습니다.

T8에는 우선 개선 과제 3개를 정하고 각각 사용자·완료 기준·담당자를 적습니다. 새 데이터 연계, 배포, 운영 자동화처럼 범위가 큰 일은 필요한 조건을 먼저 적습니다. 교육 후 지원을 자동으로 포함하는 일정으로 쓰지 않습니다.

교육생별 수행 기록, 팀 RFP 결과, 변경·평가 기록, 인계 카드가 최종 산출물입니다. 자세한 판정과 보완 방법은 [평가와 인계](../assessment.md)를 따릅니다.
