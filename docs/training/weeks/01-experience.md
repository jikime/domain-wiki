## 1. 이번 시간의 목표와 준비

교육생은 **자기 PC에 개발 도구를 설치하고, 실제로 실행되는 도메인 위키 업무환경을 만듭니다.** Git·Node.js·Claude Code·Docker·디자인 하네스 설치를 모두 수업 안에서 진행합니다. Windows는 **Git for Windows·Git Bash와 Docker용 WSL2**도 함께 준비합니다. Ubuntu는 설치하지 않습니다. 자료 한 건을 등록·공개하고 근거 질문을 수행한 뒤, 다음 시간에 같은 환경을 다시 열 수 있도록 기록합니다.

수업 전 준비물은 PC·전원, 사용할 계정, 설치 권한과 다운로드 가능한 네트워크입니다. 도구 설치·로그인·소스 다운로드·첫 실행을 미리 끝내야 수강할 수 있는 것은 아닙니다. 이미 설치된 도구는 같은 실습 환경에서 동작하는지 확인하고 필요한 설정을 보완합니다.

교재는 [기본 개발 환경 준비](../environment-setup.md)와 [도메인 위키 받기와 실행](../getting-started.md)을 옆에 열어 둡니다. [T0 내 PC 업무환경 기록표](../templates.md#t0-내-pc-업무환경-기록표)와 T1 업무 문제 카드를 사용합니다. 첫 요청과 후속 요청은 [T3](../templates.md#t3-ai-개발-요청)에 간단히 남깁니다. 설치·설정 명령은 강사의 안내를 따라 실행하고, Claude Code가 준비되면 기술 점검과 설정 지원을 AI에 요청합니다. 직접 코딩이나 명령 암기는 요구하지 않습니다.

여기서 업무환경은 내 PC에서 자료·위키·질문 기능을 사용하는 실습 환경입니다. 공통 실습에는 가상 업무 자료를 사용합니다. 본인 업무의 적용 주제는 T1에 적고, 회사 자료는 사용 범위가 확인된 뒤 별도 적용합니다.

## 3. 설치하면서 함께 이해할 것

**도구의 역할.** Git은 소스와 변경 이력을 다루고, Node.js는 웹 서버와 작업자를 실행합니다. Docker는 DB를 실행하고, Claude Code는 파일 조사·설정·구현·검사를 돕습니다. 디자인 하네스는 AI가 디자인 기준을 따라 작업하도록 역할과 절차를 제공합니다. Windows의 WSL2는 Docker Desktop이 Linux 컨테이너를 실행할 기반입니다. 개발 도구와 프로젝트는 Windows에 둡니다.

**실행 위치.** Windows는 Git Bash에서 Git·Node.js를 확인하고 Claude Code 설치·로그인·하네스·위키 실습을 진행합니다. PowerShell은 Docker용 WSL2 준비에만 사용합니다. macOS는 Terminal을 사용합니다. 웹 서버에는 화면과 API가 함께 있고, 작업자는 문서·AI 작업을 처리하며, 두 프로그램은 같은 DB를 사용합니다.

**개발용 AI와 서비스 AI.** Claude Code의 개인 개발 인증과 위키의 채팅·문서 생성 연결은 별도입니다. 개발 도구가 응답했다고 위키 AI까지 준비된 것으로 표시하지 않습니다. 개인 PC 실습의 서비스 AI도 Claude Code CLI·sonnet을 기본으로 사용합니다. 같은 사용자 인증을 사용할 수 있지만, 위키의 설정과 실제 호출 성공은 별도로 확인합니다. 자세한 목적과 구조는 [공통 안내](../project-guide.md)와 2주차에서 다룹니다.

**자료·위키·질문.** 원문은 근거가 되는 자료, 위키는 근거를 연결해 정리한 지식, 답변은 질문에 맞춰 생성한 결과입니다. ‘처리 완료’와 ‘공개 완료’는 다르며, 답변은 실제 원문과 비교해야 합니다. 도메인·프로젝트는 자료의 업무 범위를 정하고 개별 사용자만의 비밀 공간을 만드는 기능은 아닙니다.

## 4. 실습 A · 기본 도구를 내 PC에 설치하기

> **입력할 곳:** 설치 화면과 일반 터미널. Windows의 관리자 PowerShell은 WSL2 준비 단계에만 사용합니다.
>
> **정상 결과 예시:** `node --version`에 `v22.`로 시작하는 버전이 나옵니다. 숫자를 외울 필요는 없으며 [설치 단계별 확인표](../environment-setup.md#설치-단계별로-다음에-넘어가도-되는지-확인하기)를 봅니다.

### 14:10–15:00 · 편집기·Git·Node.js

1. [터미널과 작업 위치](../environment-setup.md#2-터미널과-작업-위치-정하기)를 읽고 VS Code를 설치합니다. Windows는 Git Bash, macOS는 Terminal을 사용할 것을 확인합니다.
2. [Git 설치](../environment-setup.md#3-git-설치)를 진행합니다. Windows는 Git for Windows 설치 후 시작 메뉴의 Git Bash에서 버전·현재 폴더를 확인합니다. macOS는 Terminal에서 Git을 확인합니다.
3. Windows는 VS Code의 기본 터미널을 Git Bash로 선택합니다. 2절의 폴더 준비 명령으로 `~/Projects`를 만들고 현재 위치를 확인합니다.
4. [Node.js 22·npm 설치](../environment-setup.md#4-nodejs-22와-npm-설치)를 진행하고, 같은 터미널에서 두 버전을 확인합니다.
5. T0에 운영체제·터미널·설치 결과를 적습니다. 설치 위치나 버전이 다르면 강사에게 해당 결과를 보여 주고 보완합니다.

### 15:10–16:00 · Docker·Claude Code·디자인 하네스

1. [Docker Desktop·Compose](../environment-setup.md#5-docker-desktop과-compose-준비)를 설치합니다. Windows는 Ubuntu 없이 Docker용 WSL2를 준비하고, Git Bash에서 Docker의 Client·Server 연결을 확인합니다.
2. [Claude Code](../environment-setup.md#6-개발용-claude-code-설치)를 설치하고 설치 진단을 확인합니다. Windows는 Git Bash에서 WinGet으로 설치하고, 새 Git Bash에서 실행합니다.
3. [위키 소스 받기와 첫 요청](../environment-setup.md#7-위키-소스-받기와-claude-code-첫-요청)에 따라 저장소를 내려받고 프로젝트에서 Claude Code에 로그인합니다. AI가 실제 프로젝트를 읽고 설명하는지 확인합니다. 이 단계의 약 8분은 [세 줄 요청](../prompt-practice.md#2-처음에는-세-줄로-시작하기) 작성·전송과 후속 요청에 사용합니다. 궁금한 대상 선택 2분 → 첫 요청 전송·응답 확인 2분 → 설명에 추가할 조건 작성·재전송 2분 → 두 결과 확인·T3 기록 2분으로 진행합니다. 응답이 늦으면 마지막 확인 시간에 이어서 마무리합니다.
4. [디자인 하네스](../environment-setup.md#8-디자인-하네스-설치와-기존-기준-연결)를 이 프로젝트에 설치합니다. CLAUDE.md의 지침 참조, 스킬·에이전트 인식, 기존 hince 기준 설명까지 확인합니다.
5. 개발용 AI의 응답과 하네스 인식 결과를 T0에 남깁니다. 아직 위키 DB나 서비스 AI가 실행되지 않았다면 해당 항목은 미확인으로 둡니다.

이미 설치된 도구를 지우고 다시 설치할 필요는 없습니다. 현재 도구를 같은 실습 폴더에서 사용할 수 있는지 확인하고, 처음 설치하는 교육생과 같은 완료 기준을 적용합니다.

## 5. 실습 B · 내 PC에 실제 업무환경 만들기

> **입력할 곳:** 일반 터미널 두 개에서 웹 서버와 작업자를 실행한 뒤 브라우저를 엽니다.
>
> **정상 결과 예시:** 로그인 화면이 열리고, 로그인 후 자신의 작업공간이 보입니다. 자료 처리와 AI 응답은 다음 실습에서 별도로 확인합니다.

### 처음 한 번 설정하고 실행하기

1. 편집기와 터미널이 모두 자신의 `domain-wiki` 사본을 가리키는지 확인합니다. 같은 이름의 다른 프로젝트와 혼동하지 않도록 T0에 실제 경로를 적습니다.
2. [처음 한 번 설정](../getting-started.md#2-처음-한-번-설정)에 따라 의존성·개인 환경 파일·교육용 DB·계정을 준비합니다. 이미 준비한 항목은 강사·AI가 확인하고 필요한 단계만 진행합니다.
3. 해당 사본의 `AI_TRANSPORT=claude-code`, `AI_MODEL=sonnet`과 같은 사용자의 CLI 로그인을 확인합니다. 임베딩 API 설정은 별도로 확인하며 키 값은 기록표나 AI 대화에 붙여 넣지 않습니다.
4. [앱 실행](../getting-started.md#3-앱-실행)에 따라 같은 프로젝트의 터미널 두 개에서 웹 서버와 작업자를 실행합니다. Windows는 둘 다 Git Bash를 사용합니다.
5. 브라우저에서 `http://localhost:3010`을 열고 교육용 계정으로 로그인합니다. 작성·검토·이용 계정을 구분하고 비밀번호를 기록표에 적지 않습니다.

설정 중 AI의 도움이 필요하면 다음처럼 요청합니다.

```text
이 프로젝트를 내 PC의 교육용 업무환경으로 실행하려고 합니다.
docs/training/getting-started.md를 읽고 설치·설정 상태를 확인해 주세요.
현재 사본의 로컬 환경에서 빠진 준비와 실행을 한 단계씩 도와주세요.
기존 DB·원문 파일·다른 프로젝트를 삭제하거나 초기화하지 마세요.
웹 서버·작업자·DB의 실행 상태와 각각 확인할 화면을 알려 주세요.
비밀번호·API 키는 읽어서 출력하지 말고 제가 입력할 위치만 알려 주세요.
확인된 결과와 미확인 항목을 구분해 주세요.
```

### 업무 공간·자료 위치·연결 확인하기

1. 초기 설정으로 생성된 작업공간에 들어갑니다. 기본 표시명은 ‘우리 업무 위키 · 개발 공간’일 수 있습니다. 이 공간을 자신의 교육용 업무 공간으로 사용하고 T0에 실제 이름을 적습니다.
2. 강사와 [공통 자료 배치](../samples/README.md)에 맞는 교육용 도메인·프로젝트 A/B를 준비하고 확인합니다. 기본 설치의 개발 예시 프로젝트와 교재의 프로젝트 A는 다릅니다. 교육용 배치는 첫 설치 명령만으로 자동 완성되지 않으므로 강사·AI가 현재 상태에 맞춰 지원합니다.
3. 편집기에서 `docs/training/samples/01-project-a.md`를 찾습니다. 위키의 자료실에 등록할 파일과 설치·실행 교재를 구분합니다.
4. 서비스 AI의 실제 연결 결과와 웹 서버·작업자 상태를 강사와 확인합니다. 문서 처리의 최종 확인은 다음 실습의 원문 한 건으로 수행합니다.
5. T0에 접속 주소, 작업공간·프로젝트, 파일 위치, 실행 결과와 남은 문제를 적습니다. 자신의 업무에 적용하고 싶은 대상과 문서 종류는 T1에 기록합니다.

기대 결과는 **자기 PC에서 위키 화면에 로그인하고, 자료 처리와 업무 질문을 이어갈 수 있는 상태**입니다. 강사 화면을 보는 것만으로 개인 환경 완료를 표시하지 않습니다.

## 6. 실습 C · 자료 한 건으로 업무 흐름 확인하기

> **입력할 곳:** 브라우저의 자료실에서 등록·검토하고, 위키 채팅창에 질문합니다.
>
> **정상 결과 예시:** 사업 개요의 도로전광표지 수량 ‘24대’를 답변과 원문에서 대조합니다. 종료일은 자료에 없으므로 날짜를 단정하지 않는 답변이 맞습니다.

강사는 준비한 환경에서 원문·처리·공개·게시된 위키의 근거를 약 5분간 보여 줍니다. 교육생은 이어서 자신의 PC에서 아래 핵심 흐름을 수행하고, 마지막 확인 시간에 결과를 마무리합니다.

1. 작성 계정으로 프로젝트 A에 [사업 개요](../samples/01-project-a.md)를 ‘사업 자료’로 등록합니다. 제목의 가상 교육 자료 표시를 유지합니다.
2. 원문 상세의 처리 완료를 확인하고 ‘도로전광표지 24대’, ‘현장 장비 교체 제외’가 추출되었는지 봅니다. 대기 상태가 이어지면 중복 업로드하기 전에 작업자 상태를 확인합니다.
3. 다른 검토 계정으로 원문과 추출 내용을 비교하고 공개 승인합니다. 작성자 본인 승인 제한을 유지합니다. 역할별 조작은 동료·강사와 함께 확인합니다.
4. 이용 계정으로 프로젝트 A를 선택하고 ‘도로전광표지는 몇 대인가요?’를 질문합니다. 답변의 근거를 열어 원문의 ‘24대’와 비교합니다.
5. ‘최종 사업 종료일은 언제인가요?’도 확인합니다. 자료에 없는 날짜를 단정하면 근거 없는 답변으로 기록합니다.
6. 자료·위키·답변이 각각 무엇인지 설명하고, T0에 문서 처리·공개·AI 응답 확인 결과를 남깁니다.

서비스 AI 연결이 안 되면 원문에서 답을 확인하되 실제 응답은 미확인으로 기록합니다. 원문 처리·공개 성공을 AI 연결 성공으로 바꾸어 적지 않습니다. 설치가 늦어진 경우 강사의 준비된 환경에서 업무 흐름을 확인하고, 내 PC의 미완료 항목은 별도로 남깁니다.

## 7. 먼저 마친 경우 · 짧은 위키 만들기

[실제 사용 따라 하기](../wiki-chat-guide.md)의 1–5단계를 보며 작성·근거 선택·검토·게시 후 채팅까지 이어갈 수 있습니다. 이미 만든 위키가 있다면 그대로 사용하고, 답변을 새 초안으로 저장하는 6단계는 시간이 남을 때 살펴봅니다.

개인 환경과 필수 확인을 끝낸 교육생은 ‘프로젝트 A의 사업 범위’라는 짧은 위키 초안을 작성합니다. 포함 범위·제외 범위·확인할 사항 세 부분에 공개 원문 근거를 연결하고 검토를 요청합니다. 다른 검토자가 게시하거나 수정 요청한 상태를 기록합니다.

개인 위키 초안 작성은 이번 시간의 선택 활동입니다. 모든 교육생은 강사 시연으로 원문과 위키의 관계를 확인하며, 설치 시간을 확보하기 위해 기존의 긴 위키 작성·추가 질문 비교는 필수 제출에서 제외합니다.

## 8. 기술 이슈와 확인 순서

| 증상 | 먼저 확인할 것 | 이번 시간의 조치 |
| --- | --- | --- |
| 설치가 막히거나 명령을 찾을 수 없음 | 설치 권한·재부팅·Git Bash·Docker용 PowerShell·현재 경로 | [설치 오류 안내](../environment-setup.md#10-설치-중-막혔을-때)로 강사와 확인 |
| Docker·AI·하네스 준비가 안 됨 | Desktop·WSL2 백엔드·인증·프로젝트 설치 위치 | 해당 도구의 단계로 돌아가 보완, 미완료 상태 기록 |
| 화면이 열리지 않음 | 내 PC 주소·웹 서버·같은 사본의 설정 | [실행 안내](../getting-started.md)로 확인 |
| 자료가 처리 대기에서 멈춤 | 웹 서버와 별도로 작업자가 실행 중인지 | 강사·AI에 상태와 시각 전달 |
| 등록 자료가 검색되지 않음 | 처리 완료·공개 상태·선택 프로젝트 | 공개 후 같은 범위로 다시 검색 |
| 승인 버튼이 보이지 않음 | 본인 작성 여부·검토 역할·처리 상태 | 다른 검토 계정 사용 |
| AI가 답을 단정함 | 원문에 실제 문장·수치·조건이 있는지 | 근거와 오류를 기록하고 수정 |

장비 제약으로 원격 환경을 사용하면 T0에 ‘원격 대체’라고 표시합니다. 이어갈 실습과 내 PC 설치의 미완료 항목·지원 담당을 구분합니다.

## 9. 완료 기준과 다음 시간 연결

- 직접 작성한 첫 프롬프트와 결과를 보고 보완한 후속 프롬프트를 실행하고, 실제 확인 결과를 T3에 남깁니다.
- 내 PC의 Git·Node.js·Docker·Claude Code·디자인 하네스 설치와 동작을 확인합니다. Windows는 Git for Windows·Git Bash와 Docker용 WSL2를 각각 확인합니다.
- 자신의 위키 사본에서 웹 서버·작업자·DB를 연결하고 교육용 계정으로 로그인합니다.
- 원문 한 건의 처리·공개와 답이 있는 질문 한 개·답이 없는 질문 한 개를 확인합니다.
- 원문·위키·답변의 차이와 실제 근거 위치를 설명합니다. 개인 위키 초안은 선택 결과입니다.
- T0에 설치·실행 결과, 프로젝트·접속 위치, 다시 사용하는 순서, 미완료 항목과 지원 담당을 남깁니다.
- T1에 업무 상황·입력·현재 결과·기대 결과·완료 기준을 작성합니다.

마지막 40분에는 브라우저를 닫았다가 같은 주소로 다시 접속해 같은 자료가 보이는지 확인합니다. AI·강사가 정리한 DB·웹 서버·작업자 실행 순서와 종료 방법도 T0에 남깁니다. 브라우저 재접속을 서버 재시작까지 검증한 것으로 기록하지 않습니다. 아직 확인하지 못한 항목은 완료로 표시하지 않습니다.

다음 주에는 이번에 만든 개인 환경과 T0·T1을 이어 사용합니다. 기술의 목적과 구조를 설명받고 개발용 AI에게 첫 화면 변경을 요청합니다. 기존 데이터나 프로젝트를 다시 초기화하지 않습니다.
