## 1. 이번 시간의 목표와 준비

작은 기능 변경의 계획·구현·검증을 한 번 끝까지 수행합니다. 공통 과제는 **동의어 입력의 구분자 지원과 중복 정리**입니다. 4주차의 변경 전 결과, 개인 코드 사본·관리 권한, T3·T5 양식을 준비합니다.

현재 `src/components/settings-form.tsx`는 도메인 입력 줄을 `|`로 나눈 뒤 동의어 부분을 `,`로만 나눕니다. 이번에 바꾸는 것은 **동의어 부분의 분리**입니다. 줄 구조, 용어 설명, API 데이터 형태, 서버의 권한·길이·개수 검증은 유지합니다.

## 3. 핵심 설명

**완료 기준.** ‘잘 처리한다’는 표현 대신 입력과 기대 배열을 적습니다. 예: `VMS; 전광표지， VMS` → `VMS`, `전광표지` 두 항목입니다.

**순수 함수.** 입력 문자열을 받아 배열을 반환하고 DB·네트워크·화면을 직접 바꾸지 않는 함수입니다. 입력 처리를 분리하면 결과를 빠르게 확인할 수 있습니다.

**정규식·배열·중복 제거.** 여러 구분자를 하나의 규칙으로 나누고, 각 항목의 앞뒤 공백을 없애며, 빈 항목과 같은 문자열의 중복을 정리합니다. 이 실습은 대소문자나 뜻이 비슷한 단어까지 임의로 합치지 않습니다.

**단위 검사와 화면 검사.** 함수 결과가 맞아도 화면이 옛 코드를 호출하면 기능은 바뀌지 않습니다. 함수 검사 뒤 실제 저장과 다시 열기까지 확인합니다. 서버 검증을 없애 결과를 맞추지 않습니다.

**회귀.** 새 입력이 성공하면서 기존 쉼표 입력도 유지되어야 합니다. 새 기능만 확인하고 기존 동작을 놓치지 않습니다.

## 4. 변경 계약

| 항목 | 이번 실습의 기준 |
| --- | --- |
| 허용 구분자 | 쉼표 `,`, 전각 쉼표 `，`, 세미콜론 `;` |
| 공백 | 각 항목의 앞뒤 공백 제거, 내부 공백 유지 |
| 빈 항목 | 구분자가 연속되거나 끝에 있어도 제거 |
| 중복 | 공백 정리 후 완전히 같은 문자열은 첫 항목만 유지 |
| 보존 | 입력 순서, 원래 대소문자, 다른 뜻의 단어 |
| 서버 검증 | 동의어 2–80자·최대 10개, 용어 설명 필수 유지 |
| 범위 밖 | 세로 구분선 자체를 포함한 용어 형식, 새 DB 필드, 의미 판단 |

## 5. 실습 A · 계획과 구현

1. `git status --short`로 시작 상태를 확인하고 4주차의 재현 입력을 준비합니다.
2. AI에게 다음 요청을 제공합니다.

```text
교육용 도메인의 동의어 입력을 개선하려고 합니다.
현재 src/components/settings-form.tsx에서 aliases.split(",")를 사용합니다.
쉼표, 전각 쉼표, 세미콜론을 구분자로 처리하고 앞뒤 공백·빈 항목·정확히 같은 중복을 정리해 주세요.
용어 줄의 | 구조와 API 형태, 서버 검증·권한은 유지해 주세요.
src/lib/term-aliases.ts에 splitAliases(value: string): string[] 순수 함수를 두고 기존 폼에서 사용하려고 합니다.
관리 화면 도움말도 지원 구분자와 맞춰 주세요.
먼저 관련 코드 확인과 최소 변경 계획, 검증 입력을 설명해 주세요.
```

3. 계획을 읽고 추가 의존성·DB 변경이 들어 있으면 필요성을 확인합니다. 이 과제는 기존 문자열 처리로 구현할 수 있습니다.
4. `src/lib/term-aliases.ts`에 함수를 만듭니다. AI 코드에서 각 줄이 어떤 입력을 어떻게 처리하는지 설명해 봅니다.
5. `src/components/settings-form.tsx`에서 함수 import를 추가하고 기존 동의어 분리 부분만 함수 호출로 바꿉니다. 줄의 `term`, `definition` 처리는 유지합니다.
6. `src/app/w/[workspaceId]/admin/page.tsx`의 핵심 용어 도움말에 지원 구분자를 반영합니다. 기존 Field·Textarea·도움말 연결을 유지합니다.
7. 제공된 입력 검사기를 **교육생이 만든 파일을 대상으로** 실행합니다.

```bash
node docs/training/exercises/check-aliases.mjs src/lib/term-aliases.ts
```

이 명령은 순수 함수의 계약을 확인합니다. 검사가 실패하면 실제 입력·기대 배열·받은 배열을 비교합니다. 강사용 참고 답안을 검사한 결과를 본인 구현의 결과로 제출하지 않습니다.

## 6. 실습 B · 화면 연결과 회귀 확인

1. 관리 화면에서 `도로전광표지 | 교육용 장비 용어 | VMS; 전광표지， VMS`를 저장합니다.
2. 다시 열어 동의어가 `VMS, 전광표지`의 두 항목으로 보이는지 확인합니다.
3. 기존 쉼표 입력, 동의어가 없는 줄, 연속 구분자 입력도 확인합니다.
4. 한 글자 동의어나 11개의 서로 다른 동의어는 서버가 거부하는지 확인합니다. 함수가 잘못된 항목을 몰래 자르거나 삭제해 성공처럼 만드는 방식은 사용하지 않습니다. 실패 입력 뒤 정상 설정을 다시 저장합니다.
5. 공개된 01 자료에서 VMS와 도로전광표지로 같은 대상 자료를 찾습니다. 데이터·연결 방식·모델·임베딩 설정은 4주차와 같게 유지합니다.
6. 변경한 파일의 형식·타입을 확인합니다. 다음 명령은 앱 실행과 별도로 수행하며, 새 파일도 Git 상태에서 확인합니다.

```bash
git diff --check
npx biome check src/lib/term-aliases.ts src/components/settings-form.tsx "src/app/w/[workspaceId]/admin/page.tsx"
npm run typecheck
```

저장소 전체의 기존 오류가 나오면 해당 변경 때문에 생겼는지 나누어 기록합니다. 이 실습만을 위해 전체 통합시험·반복 빌드를 기본으로 실행하지 않습니다.

7. 팀 응용은 4주차에 정한 실무 기록 안내 또는 위키 구조를 20분 안에서 개선하고 같은 예제로 검토합니다. 완료가 늦으면 공통 과제 검증을 우선합니다.
8. 변경 파일만 스테이징하고 `git diff --cached`에서 신규 함수까지 읽습니다. 검사와 화면 결과를 T5에 적은 뒤 커밋합니다.

## 7. 예상 오류와 질문

| 오류 | 원인 후보 | 확인 |
| --- | --- | --- |
| 함수 검사 성공, 화면은 이전 결과 | 폼이 새 함수를 사용하지 않음 | import와 함수 호출, 접속 사본 확인 |
| 새 파일이 변경 내역에 안 보임 | 아직 추적하지 않은 파일 | `git status`와 스테이징 후 diff 확인 |
| 빈 항목 때문에 저장 실패 | 분리 후 빈 문자열 유지 | 검사기의 빈 입력·연속 구분자 사례 확인 |
| 잘못된 긴 입력도 저장됨 | 기존 검증을 삭제했을 가능성 | `src/lib/validation.ts` 변경 여부 확인 |
| 검색 순위가 기대와 다름 | 검색은 여러 조건의 영향을 받음 | 입력 분리·저장 성공과 검색 순위를 분리 |

## 8. 완료 기준

새 함수, 폼 연결, 도움말, 입력 검사 결과, 화면의 정상·실패 입력 결과를 남깁니다. 공통 과제는 입력 계약 충족 여부로 평가합니다. 검색 정확도가 전반적으로 개선되었다는 주장은 별도 평가 없이 하지 않습니다.
