# 채팅과 지식 그래프로 근거 확인하기

질문을 다시 쓰고 답변의 근거를 확인하며, 두 위키를 비교하는 기능을 개발합니다. 확인한 구현은 코드와 DB 변경까지 첫 통합본으로 연결합니다.

[강의 화면](/lectures/week-05.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 4회차에서 게시한 검수 업무 절차·범위 위키와 공개 원문 v2를 이어 사용합니다. 같은 위키 코드를 연 Claude Code와 실제 앱을 나란히 엽니다.

**남길 결과:** 범위를 함께 저장하는 내 질문 모음 / 답변·근거에 연결된 개인 확인 기록 / 두 게시 위키의 비교와 탐색 복귀 / 코드·DB 적용을 확인한 첫 통합본

개발·통합의 공통 단계를 **계획 요청 → 내가 확인·수정 → 실행 요청 → 직접 확인** 순서로 진행합니다. 요청 상자 하나는 한 번에 입력하고 계획과 실행은 따로 보냅니다. 코드와 DB 통합·결과 정리 활동을 모두 새 기능 개발로 세지는 않습니다.

## 먼저 준비할 것

- 같은 개인 위키와 Claude Code를 사용합니다. **업무 질문은 앱 채팅**, **개발 요청은 Claude Code**에 입력합니다.
- 4회차에서 공개한 검수 조건 v2와 보완·게시한 **프로젝트 A 검수 업무 절차**, **프로젝트 A의 범위와 검수 기준**을 확인합니다. 현재 기준은 30초·90일이며 B는 120초·30일입니다.
- 기본 계정은 writer@wiki.local로 진행하고 reviewer@wiki.local·reader@wiki.local로 역할을 직접 확인합니다. 비밀번호는 본인 환경의 안내를 따릅니다.
- 앱의 AI 연결이 준비돼 있어야 합니다. 답변에 실제 근거가 나오는지 확인하며 실패한 답변을 완료 사례로 꾸미지 않습니다.
- 통합은 개인 개발본과 다른 사본·개발 DB에서 진행합니다. 대표 저장소·브랜치·커밋, 추가 변경 커밋, 작업 사본 경로, 대상 DB는 강사가 미리 준비한 실제 값을 받습니다.

## 같은 사례로 이어가기

[질문·근거·위키 비교 실습 사례](../samples/chat-graph-practice.md)에 입력 문장과 확인 순서를 모았습니다. 필요한 내용은 강의 화면에도 있습니다.

| 교시 | 공통 작업 | 다음에 사용할 결과 |
| --- | --- | --- |
| 1 | 질문·범위 저장, 불러오기, 수정·복제·검색 | 세 질문과 첫 A 질문의 실제 답변 |
| 2 | 개인 메모·상태·근거 연결·확인 목록·검토 의견 연결 | 확인한 답변과 추가 확인할 질문 |
| 3 | 두 위키 담기·비교·원문 복귀·목록 보관 | 다시 열 수 있는 게시 위키 비교 |
| 4 | 개인 작업 보관·기준 가져오기·추가 변경·업무 확인 | 코드·DB를 확인한 첫 통합본 |

교재의 답변·그래프 캡처는 개정 전 샘플의 실제 화면입니다. 캡처의 60초를 실습 기준으로 사용하지 않습니다. 앞서 게시한 v2의 30초·90일을 새 대화에서 확인합니다. 기존 대화·개인 기록·원문 버전을 삭제하지 않습니다.

## 통합 환경에서 이어가기

강사가 제공한 코드 사본·실행 주소·전용 개발 DB를 확인합니다. 교육생마다 DB를 분리하고 그 안에서 작성·검토·관리·열람 역할을 바꿉니다. 공통 계정 이름이 같다고 한 DB를 함께 수정하지 않습니다. 기준 커밋과 내 실제 통합 커밋은 각각 기록하며, 코드 내용·DB 적용·자료 상태를 함께 대조합니다.

첫 통합의 대표 구현에는 2~4회차 기능과 오늘의 질문 모음·답변 확인·위키 비교가 필요합니다. 질문 고정하기는 강사가 미리 시험해 제공할 추가 변경입니다. 통합 DB에는 공개 원문 v2·두 게시 위키·역할 계정이 있어야 하며, 필요한 개인 질문·확인 기록은 통합 환경에서 교육용으로 준비합니다. 개인 DB를 그대로 복사하거나 초기 샘플로 덮어쓰지 않습니다.

## 준비: 채팅·그래프의 기존 기능 확인

아래 전체를 개발용 AI에 입력한 뒤 실제 메뉴와 비교합니다.

```text
지금 개발한 위키의 채팅과 지식 그래프를 개선할 거야. 채팅의 질문 범위·최근 대화·참고 자료·답변 의견·위키 초안 저장과 그래프의 필터·위키 목록·문서 미리보기 동작을 확인해. 현재 코드에 질문 모음이나 개인 확인 기록이 있는지도 확인하고 새로 필요한 기능과 구분해. 내가 눌러 볼 메뉴·버튼 순서를 알려 줘. 없는 기능은 가정하지 마. 코드와 DB는 아직 바꾸지 마.
```

**직접 확인:** 기존 기능의 위치와 사용할 계정을 확인합니다. 개발 요청은 앱 채팅에 넣지 않습니다.

## 1. 질문 저장과 범위 재사용

[함께 볼 강의 화면](/lectures/week-05.html#slide-04)

**앞에서 이어받을 것:** v2 원문과 두 게시 위키를 사용할 수 있는 개인 위키

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 앞 단계에서 저장한 항목으로 아래 업무를 이어 확인합니다. 실패한 동작은 같은 대화에서 보완 계획부터 요청합니다.

**내가 정할 것:** 앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

**저장 기준:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅에 내 질문 모음을 만들 거야. 질문 입력 옆에 저장 버튼을 두고 이름·질문·도메인·프로젝트·자료 탐색 깊이·원문만 사용·웹 검색 설정을 저장할 계획을 세워. 자료나 위키에서 들어온 한정 범위도 빠뜨리지 마. 작업공간과 로그인 사용자별 DB 저장 구조, 중복 제출 처리와 목록 위치를 설명해. 기존 최근 대화 목록과 저장 검색 조건은 그대로 사용해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **저장할 내용** 질문 문장 + 적용할 범위 + 이름
- **저장할 곳** 현재 사용자·작업공간의 DB
- **기존 기능** 최근 대화와 저장 검색 조건은 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
채팅에 확인한 질문 저장과 내 질문 목록을 만들어. 이름·질문·현재 범위를 로그인 사용자와 작업공간에 연결해 DB에 저장해. 필요한 테이블·변경 파일을 만들고 개발 DB에 적용해. 질문 내용이 비어 있으면 저장하지 말고, 중복 클릭으로 같은 항목이 여러 개 생기지 않게 해. 새로고침 후 목록과 다른 계정의 접근 제한을 검사해. 질문을 저장하는 동작으로 AI에게 전송하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 프로젝트 A 범위에서 첫 질문을 입력하고 이름을 ‘A 검수 기준’으로 저장합니다. 새로고침해 같은 항목이 남는지 보세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · 질문과 범위를 확인한 뒤 불러오기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에서 저장한 질문을 불러올 거야. 질문과 도메인·프로젝트·한정 자료·탐색 설정을 먼저 보여 주고 확인 후 새 대화의 입력칸과 범위에 적용하게 계획해. 작성 중인 문장이 있으면 교체 전에 확인해. 기존 대화의 질문 범위와 기록을 바꾸지 마. 삭제되거나 접근할 수 없는 범위는 전체 범위로 몰래 바꾸지 말고 이유와 다시 고를 곳을 안내해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 적용 전: 질문 문장과 프로젝트를 먼저 확인
- 적용 후: 새 대화 입력칸과 범위만 채움
- 전송: 내가 질문 보내기를 눌러 실행

**계획을 확인한 뒤 실행**

```text
채팅에 확인한 질문 불러오기를 만들어. 저장한 문장·범위를 미리 보여 주고 적용을 눌러야 새 대화의 입력칸과 범위를 채워. 입력 중인 문장의 교체는 확인받고 취소하면 그대로 둬. 기존 대화는 유지하고, 사용자가 질문 보내기를 눌러야 전송해. 불러온 범위를 현재 계정으로 다시 확인해. 범위가 유효하지 않으면 적용을 막고 수정할 곳을 안내해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 프로젝트 B를 선택한 화면에서 ‘A 검수 기준’을 불러옵니다. A 범위를 확인해 적용하고, 전송 전까지 새 답변이 생기지 않는지 보세요.

### 다음 기능 · 질문 수정·복제·삭제 연결하기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에 수정·복제·삭제를 더할 거야. 수정에서는 이름·문장·범위를 편집하고 저장과 취소를 나눠. 복제는 새 항목으로 만들고 원래 질문을 유지해. 삭제는 대상 이름을 확인받되 이미 나눈 대화나 답변 기록은 지우지 마. 현재 사용자 소유 여부를 서버에서 확인하는 계획을 세워. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 수정과 취소: 질문만 변경 · 취소 시 원래 값
- 복제: A 원본을 남기고 B용 질문 저장
- 삭제: 질문 모음 항목만 제거

**계획을 확인한 뒤 실행**

```text
채팅의 내 질문 모음에 확인한 수정·복제·삭제를 만들어. 같은 저장 구조를 재사용하고 취소하면 원래 값이 남게 해. 복제 후 이름·질문 문장·프로젝트를 바꾸어 별도 저장하게 해. 내 질문만 삭제하고 기존 대화·답변은 남겨. 수정·삭제 성공 후 목록을 갱신하고 저장 실패 시 입력을 보존해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

### 다음 기능 · 질문 목록 검색과 프로젝트 필터

**먼저 계획 요청**


**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

1. 저장한 공통 세 질문을 찾습니다. 수정·취소와 ‘삭제 연습’ 복제본 삭제 결과를 확인합니다. 이미 삭제한 항목을 다시 만들지는 않습니다.

**확인:** 저장한 A 질문과 실제 완료된 답변을 준비했습니다.

## 2. 답변 근거와 개인 확인 기록

[함께 볼 강의 화면](/lectures/week-05.html#slide-17)

**앞에서 이어받을 것:** 앞에서 완료된 A 검수 기준의 실제 답변

1. 이번 교시의 네 기능을 계획 → 확인 → 실행 순서로 모두 개발합니다.
2. 각 실행 요청의 사례를 직접 눌러 확인합니다.
3. 앞 단계에서 저장한 항목으로 아래 업무를 이어 확인합니다. 실패한 동작은 같은 대화에서 보완 계획부터 요청합니다.

**내가 정할 것:** 앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

**저장 기준:** 메모·확인 상태·인용 관계는 실제 답변과 사용자에 연결합니다. 답변 본문을 별도 복제하지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅의 완료된 답변에 내 확인 메모와 상태를 만들 거야. 미확인·확인함·추가 확인을 구분하고 메모와 확인 시각을 답변 ID·대화 ID·작업공간·사용자에 연결해 DB에 저장하는 계획을 세워. 문장 내용만으로 답변을 식별하지 마. 기존 답변에 의견 남기기는 검토자에게 보내는 기능이므로 개인 메모와 분리해. 실패·진행 중 답변은 확인 완료로 만들지 마. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **대상** 완료된 답변 한 건
- **기록** 내 메모·상태·확인 시각
- **구분** 검토함에 보내는 의견과 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
채팅의 완료된 답변에 확인한 내 확인 메모와 상태를 만들어. 메모와 상태는 로그인 사용자의 해당 답변에 DB 저장하고 필요한 변경 파일을 개발 DB에 적용해. 저장·수정·취소를 구분하고 저장 실패 시 메모를 남겨. 같은 계정으로 다시 열면 복원하고 다른 계정에서는 조회·수정하지 못하게 해. 이 표시는 내가 확인한 기록이며 위키 게시나 공식 승인 상태를 바꾸지 않아. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 확인**

1. 첫 질문의 답변에서 30초·90일 근거를 읽고 ‘갱신은 표시 갱신이며 복구 시간이 아님’이라는 내 메모를 남깁니다. 실제 확인한 뒤 확인함으로 저장하세요.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · 확인한 근거와 답변 다시 열기

**먼저 계획 요청**

```text
채팅의 내 확인 기록에 직접 읽은 근거를 연결할 거야. 해당 답변이 실제 사용한 인용 목록에서 고르고 원래 자료 종류·버전·문단을 보존해. 저장할 관계와 기존 참고 자료 패널을 다시 여는 경로를 계획해. 인용 번호는 답변마다 다르므로 번호만 저장하지 마. 현재 접근할 수 없는 근거는 내용을 복사해 노출하지 말고 상태를 안내해. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 연결 대상: 해당 답변이 실제 사용한 근거
- 다시 열기: 원래 답변·자료·버전·문단
- 확인할 차이: 게시 위키와 원문 근거를 구분

**계획을 확인한 뒤 실행**

```text
채팅의 내 확인 기록에서 해당 답변의 사용 근거를 고르고 다시 열게 해. 답변과 실제 인용 식별자로 DB에 연결하고 필요한 변경 파일을 개발 DB에 적용해. 기존 참고 자료 패널과 원문 열기를 재사용하고 원래 버전 주소를 바꾸지 마. 현재 답변의 확인 기록에서 저장한 근거를 다시 열게 해. 별도 확인 목록은 다음 단계에서 만들 거야. 접근 제한이나 원문 개정 상태는 기존 검사를 따라 안내해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 답변이 실제 인용한 자료나 위키 중 읽은 근거를 고릅니다. 갱신·보관이 한 근거에 있으면 하나만 연결합니다. 다른 대화에서 돌아와 같은 답변을 확인하세요.

### 다음 기능 · 추가 확인할 답변 모아 보기

**먼저 계획 요청**

```text
채팅에 내 답변 확인 목록을 만들 거야. 상태·프로젝트·메모 검색으로 찾고, 질문 요약·확인 상태·메모·마지막 확인 시각을 보여 줘. 개인 확인 기록이 없는 내 완료 답변도 미확인 목록에 포함해. 대화 소유와 현재 열람 가능 여부를 확인하고 목록에서 원래 답변·근거로 이동하게 계획해. 개수와 목록의 범위도 맞춰. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 미확인: 아직 확인 기록이 없는 완료 답변
- 추가 확인: 자료만으로 판단할 수 없는 질문
- 목록에서 이어가기: 답변과 근거를 다시 열어 확인

**계획을 확인한 뒤 실행**

```text
채팅의 내 답변 확인 목록을 만들어. 내 완료 답변 중 기록이 없으면 미확인으로 표시하고, 확인함·추가 확인 필터와 프로젝트·메모 검색을 함께 적용해. 원래 대화의 해당 답변으로 이동하게 해. 메모나 상태를 고치면 목록·개수를 갱신해. 삭제되거나 제한된 대화는 현재 권한 규칙에 따라 처리하고 답변 본문을 개인 기록에 복제하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. ‘A 자동 복구 확인’ 질문을 보내고 답변과 근거를 읽습니다. 복구 시간은 문서에 없으므로 ‘담당자에게 복구 기준 확인’ 메모와 추가 확인 상태로 남기세요.

### 다음 기능 · 개인 메모와 검토 의견 연결 구분

**먼저 계획 요청**

```text

```

**내가 확인할 것**

- 내 메모: 나에게만 보이는 확인 기록
- 검토 의견: 보낼 내용을 읽고 직접 전송
- 위키 초안: 기존 답변·근거 저장 기능 사용

**계획을 확인한 뒤 실행**

```text
채팅의 내 확인 기록에서 검토 의견 작성으로 이어지는 버튼을 만들어. 기존 의견 폼에 보낼 내용을 미리 보여 주고 수정·취소할 수 있게 해. 사용자가 의견 보내기를 눌러야 기존 검토함에 전달되게 해. 개인 메모와 상태는 별도로 유지하고 자동 승인하지 마. 기존 위키 초안 저장은 답변과 그 근거만 사용하며 내 메모나 다른 대화를 함께 넣지 않는지 검사해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

## 4. 대표 구현과 첫 통합

### 1. 계획 요청


- **통합 기준** 강사가 지정한 대표·추가 변경 커밋
- **작업 위치** 개인 개발본과 다른 사본·개발 DB

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

```text

```

**만든 뒤 직접 확인**

1. 시작·추가·최종 기준, 내 사본·주소·전용 DB와 준비된 자료를 대조합니다. 기준 커밋과 내 실제 커밋은 각각 기록하세요.

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 세 단계도 모두 공통 실습입니다. 계획을 확인하고 실행한 뒤 제시한 사례를 직접 확인합니다.

### 다음 기능 · 강사 기준 가져와 별도 사본 준비

**먼저 계획 요청**

```text
통합 기준표의 대표 구현을 별도 작업 사본에서 확인할 거야. origin은 내 fork, upstream은 강사가 확인한 기준 저장소인지 비교해. fetch로 변경 이력만 가져온 뒤 대표 커밋과 내 작업의 차이·DB 적용 차이를 설명하는 계획을 세워. 기존 작업을 강제로 초기화하지 마. 별도 사본·브랜치와 지정된 통합 개발 DB만 사용하고 기존 사본의 설정은 덮어쓰지 마. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- origin: 내 fork 저장소
- upstream: 강사가 안내한 기준 저장소
- fetch: 이력 가져오기 · 내 작업에 병합은 별도

**계획을 확인한 뒤 실행**

```text
확인한 upstream 이력을 fetch하고 대표 커밋의 별도 브랜치·작업 사본을 준비해. 기존 경로·브랜치는 덮지 마. 제공한 실행 주소·포트와 전용 개발 DB 연결을 비밀값 출력 없이 확인해. 필요한 패키지·DB 변경을 확인한 순서로 적용하고 웹·추출 작업자가 해당 DB를 쓰는지 확인해. 원문 v2·두 게시 위키·역할 계정을 확인할 순서를 알려 줘. 개인·운영 DB나 Docker는 바꾸지 말고 추가 변경은 아직 합치지 마.
```

**다음 기능 전에 직접 확인**

1. 별도 사본을 실행하고 대표 구현의 질문 저장·답변 메모·위키 비교가 열리는지 확인합니다. 내 개인 사본의 코드와 자료가 유지되는지도 봅니다.

### 다음 기능 · 추가 기능의 코드와 DB 변경 합치기

**먼저 계획 요청**

```text
통합 사본의 내 질문 모음에 강사가 지정한 추가 변경인 질문 고정하기를 합칠 거야. 대표 구현과 추가 커밋에서 질문 저장 구조·사용자 권한·DB 변경 순서를 비교해. 고정한 질문이 목록 위에 나오고 해제하면 일반 정렬로 돌아가는 동작을 기준으로 중복 코드와 충돌 해결안을 설명해. 이미 적용한 DB 변경 파일은 고쳐 쓰지 말고 새 보완 파일이 필요한지 판단해. 개인 질문 데이터는 다른 사람과 합치지 마. 코드와 DB는 아직 바꾸지 마. 내가 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 채택할 변경: 내 질문 고정·해제·상단 정렬
- 코드와 DB: 충돌과 저장 구조를 함께 확인
- 보존할 것: 기존 질문·적용 이력·개인 개발본

**계획을 확인한 뒤 실행**

```text
통합 계획에서 확인한 질문 고정하기 변경만 별도 사본에 반영해. 충돌은 확인한 동작과 기존 저장 구조에 맞춰 해결하고 한쪽 파일 전체로 덮지 마. 필요한 새 DB 변경 파일을 남기고 지정된 통합 개발 DB에만 적용해. 기존 적용 이력은 유지해. 질문 고정·해제·상단 정렬과 기존 저장·수정·삭제를 확인하고 코드 커밋과 DB 적용 결과를 각각 기록해. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 통합 사본에서 A 질문을 고정하고 B 질문도 저장합니다. 새로고침해 A가 위에 남는지, 고정을 해제해도 질문과 기존 메모가 남는지 확인하세요.

### 다음 기능 · 같은 통합 기준으로 업무 흐름 확인

**먼저 계획 요청**

```text
통합 사본의 질문 모음·답변 확인·위키 비교와 기존 자료실·위키 기능을 확인할 거야. 제공한 최종 기준과 코드 내용·DB 변경 목록을 비교해. 병합 방식에 따라 내 커밋 번호가 달라도 내용과 적용 이력이 맞는지 판단하고 강제 초기화하지 마. 작성·검토·열람 계정의 확인 순서와 필요한 차이 반영을 계획해. 원격 push나 회사 배포는 하지 마. 코드와 DB는 아직 바꾸지 마.
```

**내가 확인할 것**

- 같은 기준: 코드 커밋 + DB 적용 목록
- 직접 수행: 질문 → 근거 → 메모 → 위키 비교
- 남길 결과: 통과·실패·미확인·다음 조치

**계획을 확인한 뒤 실행**

```text
확인한 통합 기준과 내 사본의 차이만 별도 사본에 반영하고 지정한 개발 DB 적용 상태를 맞춰. 불필요한 DB 재적용이나 데이터 병합은 하지 마. 자동 검사를 한 뒤 로그인 계정과 시작 메뉴·누를 버튼·예상 결과를 알려 줘. 내가 직접 확인한 결과를 받은 뒤 통과·실패·미확인과 남은 일을 기록해. 코드 버전이 같다는 이유만으로 DB 적용과 업무 확인을 완료로 표시하지 마. 필요한 검사를 하고 내가 화면에서 눌러 볼 순서를 알려 줘.
```

**다음 기능 전에 직접 확인**

1. 각자 통합 사본에서 A 질문을 보내고 근거·개인 메모·두 위키 비교를 확인합니다. 다른 역할의 계정으로 개인 목록이 섞이지 않는지도 직접 확인하세요.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

1. 기준과 내 실제 커밋·DB 적용을 기록합니다. 앞 단계에서 저장·고정한 A 질문을 다시 열어 고정 상태를 확인하고, 없는 항목만 준비합니다.
2. 같은 통합본에서 이미 확인한 A 답변·근거·메모를 다시 엽니다. 아직 질문하지 않았다면 한 번 전송해 30초·90일 근거와 내 확인 기록을 남깁니다.
3. 두 게시 위키를 비교하고 원문에서 돌아옵니다. 다른 역할에서 개인 기록이 섞이지 않는지 확인하고 통과·실패·미확인을 적습니다.

다른 교육생이 써 주는 것을 기다리지 않습니다. 각자 본인의 통합 사본에서 확인합니다.

**확인:** 같은 기준의 첫 통합본과 직접 확인한 결과를 남겼습니다.

**기본을 마쳤다면 — 선택 과제**

- **충돌 원인 비교:** 같은 기능의 다른 저장 방식이 어떤 차이를 만드는지 비교합니다.
- **통합 검사 자동화:** 질문 저장·고정·다른 계정 차단을 반복 검사할 절차를 만듭니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

공통 네 기능을 모두 확인한 뒤에만 추가 도전을 진행합니다.
