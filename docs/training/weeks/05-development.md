# 채팅과 지식 그래프로 근거 확인하기

질문을 다시 쓰고 답변의 근거를 확인하며, 두 위키를 비교하는 기능을 개발합니다. 확인한 구현은 코드와 DB 변경까지 첫 통합본으로 연결합니다.

[강의 화면](/lectures/week-05.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 4회차에서 게시한 검수 업무 절차·범위 위키와 공개 원문 v2를 이어 사용합니다. 같은 위키 코드를 연 Claude Code와 실제 앱을 나란히 엽니다.

**남길 결과:** 범위를 함께 저장하는 내 질문 모음 / 답변·근거에 연결된 개인 확인 기록 / 두 게시 위키의 비교와 탐색 복귀 / 코드·DB 적용을 확인한 첫 통합본

각 실습은 **계획 요청 → 내가 확인·수정 → 실행 → 직접 확인**을 한 장에서 진행합니다. 먼저 계획 요청만 보내고 원하는 동작인지 확인합니다. 맞으면 같은 Claude Code 대화에 **‘계획한 대로 실행해줘.’**를 보냅니다. 두 복사 버튼은 따로 사용하고, 실행 후에는 같은 장 하단의 사례로 확인합니다. 교시 마지막에는 만든 기능을 이어 사용합니다.

## 먼저 준비할 것

- 같은 개인 위키와 Claude Code를 사용합니다. **업무 질문은 앱 채팅**, **개발 요청은 Claude Code**에 입력합니다.
- 4회차에서 공개한 검수 조건 v2와 보완·게시한 **프로젝트 A 검수 업무 절차**, **프로젝트 A의 범위와 검수 기준**을 확인합니다. 현재 기준은 30초·90일이며 B는 120초·30일입니다. 기본 샘플 설치만으로 v2와 검수 업무 절차가 생기지는 않습니다. 빠졌다면 4회차의 개정·게시 결과부터 준비합니다.
- 기본 계정은 writer@wiki.local로 진행하고 reviewer@wiki.local·reader@wiki.local로 역할을 직접 확인합니다. 비밀번호는 본인 환경의 안내를 따릅니다.
- 앱의 AI 연결이 준비돼 있어야 합니다. 답변에 실제 근거가 나오는지 확인하며 실패한 답변을 완료 사례로 꾸미지 않습니다.
- 통합은 개인 개발본과 다른 사본·개발 DB에서 진행합니다. 대표 저장소·브랜치·커밋, 추가 변경 커밋, 작업 사본 경로, 대상 DB는 강사가 미리 준비한 실제 값을 받습니다.

## 같은 사례로 이어가기

[질문·근거·위키 비교 실습 사례](../samples/chat-graph-practice.md)에 입력 문장과 확인 순서를 모았습니다. 필요한 내용은 강의 화면에도 있습니다.

| 교시 | 공통 작업 | 다음에 사용할 결과 |
| --- | --- | --- |
| 1 | 질문·범위 저장, 불러오기, 수정·복제·검색 | 세 질문과 첫 A 질문의 실제 답변 |
| 2 | 개인 메모·상태·근거 연결·확인 목록·검토 의견 연결 | 확인한 답변과 추가 확인할 질문 |
| 3 | 두 위키 담기·비교·원문 복귀·목록 보관 | 다시 열 수 있는 게시 위키 비교 |
| 4 | 개인 작업 보관·기준 가져오기·추가 변경·업무 확인 | 코드·DB를 확인한 첫 통합본 |

교재의 답변·그래프 캡처는 개정 전 샘플의 실제 화면입니다. 캡처의 60초를 실습 기준으로 사용하지 않습니다. 앞서 게시한 v2의 30초·90일을 새 대화에서 확인합니다. 기존 대화·개인 기록·원문 버전을 삭제하지 않습니다.

## 통합 환경에서 이어가기

강사가 제공한 코드 사본·실행 주소·전용 개발 DB를 확인합니다. 교육생마다 DB를 분리하고 그 안에서 작성·검토·관리·열람 역할을 바꿉니다. 공통 계정 이름이 같다고 한 DB를 함께 수정하지 않습니다. 기준 커밋과 내 실제 통합 커밋은 각각 기록하며, 코드 내용·DB 적용·자료 상태를 함께 대조합니다.

첫 통합의 대표 구현에는 2~4회차 기능과 오늘의 질문 모음·답변 확인·위키 비교가 필요합니다. 질문 고정하기는 강사가 미리 시험해 제공할 추가 변경입니다. 통합 DB에는 공개 원문 v2·두 게시 위키·역할 계정이 있어야 하며, 필요한 개인 질문·확인 기록은 통합 환경에서 교육용으로 준비합니다. 개인 DB를 그대로 복사하거나 초기 샘플로 덮어쓰지 않습니다.

질문은 A 두 개를 먼저 저장하고 복제 기능으로 B를 만듭니다. 통합 사본에서는 추가 변경 전에 A·B 질문, A 답변 메모와 두 위키 비교를 준비합니다. 그 뒤 Claude Code의 작업 폴더를 통합 사본으로 옮기고, 같은 기록이 변경 후에도 남는지 확인합니다.

## 준비: 채팅·그래프의 기존 기능 확인

아래 전체를 개발용 AI에 입력한 뒤 실제 메뉴와 비교합니다.

```text
지금 개발한 위키의 채팅과 지식 그래프를 개선할 거야. 채팅의 질문 범위·최근 대화·참고 자료·답변 의견·위키 초안 저장과 그래프의 필터·위키 목록·문서 미리보기 동작을 확인해. 현재 코드에 질문 모음이나 개인 확인 기록이 있는지도 확인하고 새로 필요한 기능과 구분해. 내가 눌러 볼 메뉴·버튼 순서를 알려 줘. 없는 기능은 가정하지 마. 코드와 DB는 아직 바꾸지 마.
```

**직접 확인:** 기존 기능의 위치와 사용할 계정을 확인합니다. 개발 요청은 앱 채팅에 넣지 않습니다.

## 1. 질문 저장과 범위 재사용

[함께 볼 강의 화면](/lectures/week-05.html#slide-04)

**앞에서 이어받을 것:** v2 원문과 두 게시 위키를 사용할 수 있는 개인 위키

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 같은 장 하단의 사례로 직접 눌러 보고 예상과 다른 동작을 고칩니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

**저장 기준:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅에 내 질문 모음을 만들 계획을 세워. 질문 입력 옆에 저장 버튼과 내 질문 목록을 두고 이름·질문·도메인·프로젝트·탐색 깊이·원문만 사용·웹 검색 설정을 저장해. 자료·위키에서 들어온 한정 범위도 포함해. 사용자·작업공간별 테이블과 변경 파일, 개발 DB 적용을 계획에 넣어. 빈 질문과 중복 클릭은 저장을 막고, 저장만으로 AI에게 전송하지 마. 새로고침 뒤 복원과 다른 계정의 접근 제한도 검사해. 기존 최근 대화와 저장 검색 조건은 유지해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **저장할 내용** 질문 문장 + 적용할 범위 + 이름
- **저장할 곳** 현재 사용자·작업공간의 DB
- **기존 기능** 최근 대화와 저장 검색 조건은 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. A 질문 두 개 저장: 프로젝트 A에서 ‘A 검수 기준’과 ‘A 자동 복구 확인’을 각각 저장합니다. 질문 이름과 입력 문장이 함께 남아야 합니다.
2. 저장과 전송 구분: 저장 버튼만 눌렀을 때 새 답변이 생기지 않아야 합니다. 목록에 같은 질문이 중복으로 생기지 않았는지도 봅니다.
3. 새로고침 후 다시 보기: 새로고침해 두 질문의 문장과 A 범위가 남는지 확인합니다. B 질문은 복제 기능을 만든 뒤 추가합니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

### 다음 기능 · 질문과 범위를 확인한 뒤 불러오기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에서 저장한 질문을 불러올 계획을 세워. 문장·도메인·프로젝트·한정 자료·탐색 설정을 미리 보여 주고 적용을 눌러야 새 대화의 입력칸과 범위를 채워. 입력 중인 문장이 있으면 교체 전에 확인하고 취소하면 남겨. 기존 대화의 범위·기록은 유지하고 질문 보내기를 눌러야 전송해. 현재 계정으로 범위를 다시 확인하고 삭제·접근 제한이면 적용을 막아. 전체 범위로 바꾸지 말고 이유와 수정할 곳을 안내해. 적용·취소·전송 전 상태를 검사할 방법도 포함해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 적용 전: 질문 문장과 프로젝트를 먼저 확인
- 적용 후: 새 대화 입력칸과 범위만 채움
- 전송: 내가 질문 보내기를 눌러 실행

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. A 질문 고르기: B 범위에서 ‘A 검수 기준’을 고릅니다. 적용 전 안내에는 저장된 문장과 프로젝트 A가 보여야 합니다.
2. 입력 교체 취소하기: 입력칸에 문장이 있다면 교체 확인에서 취소해 봅니다. 작성 중인 문장은 그대로 남아야 합니다.
3. 확인 후 적용하기: 다시 A 질문을 골라 적용합니다. 새 대화의 문장과 범위가 A로 채워지되, 아직 답변은 생성되지 않아야 합니다.

### 다음 기능 · 질문 수정·복제·삭제 연결하기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에 수정·복제·삭제를 더할 계획을 세워. 기존 저장 구조를 사용하고 수정은 이름·문장·범위를 바꾸되 취소하면 원래 값을 남겨. 복제는 원본을 유지한 새 항목으로 만들고 이름·문장·프로젝트를 바꿔 저장하게 해. 삭제는 대상 이름을 확인받고 질문 항목만 지워. 기존 대화·답변은 남겨. 내 질문인지 서버에서 확인하고, 성공하면 목록을 갱신하며 저장 실패 시 입력을 보존해. 이 동작을 확인할 검사도 계획해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 수정과 취소: 질문만 변경 · 취소 시 원래 값
- 복제: A 원본을 남기고 B용 질문 저장
- 삭제: 질문 모음 항목만 제거

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. B용으로 복제하기: ‘A 검수 기준’을 복제해 이름·문장·프로젝트를 ‘B 검수 기준’으로 바꿔 저장합니다. B가 이미 있으면 기존 항목을 사용합니다.
2. 원본과 취소 확인하기: A 질문은 그대로인지 봅니다. B 질문의 수정을 열어 값을 바꾼 뒤 취소하면 이전 값이 남아야 합니다.
3. 연습 항목만 삭제하기: 별도 ‘삭제 연습’ 복제본으로 삭제를 확인합니다. A 두 개와 B 한 개, 기존 대화·답변은 남겨 둡니다.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

## 2. 답변 근거와 개인 확인 기록

[함께 볼 강의 화면](/lectures/week-05.html#slide-13)

**앞에서 이어받을 것:** 앞에서 완료된 A 검수 기준의 실제 답변

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 같은 장 하단의 사례로 직접 눌러 보고 예상과 다른 동작을 고칩니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 앞 단계에서 만든 기능을 같은 사례로 이어 확인합니다. 이미 저장한 항목은 다시 만들지 않고 사용하세요.

**저장 기준:** 메모·확인 상태·인용 관계는 실제 답변과 사용자에 연결합니다. 답변 본문을 별도 복제하지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅의 완료된 답변에 내 메모와 미확인·확인함·추가 확인 상태를 만들 계획을 세워. 메모·상태·확인 시각을 답변 ID·대화 ID·작업공간·사용자에 연결해 DB에 저장하고 변경 파일의 개발 DB 적용을 포함해. 같은 문장도 서로 다른 답변으로 구분해. 저장·수정·취소, 저장 실패 시 입력 보존, 다시 열기와 다른 계정의 접근 제한을 검사해. 실패·진행 중 답변은 확인함으로 바꾸지 마. 검토자에게 보내는 기존 의견과 분리하고 위키 게시나 공식 승인 상태는 바꾸지 마. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **대상** 완료된 답변 한 건
- **기록** 내 메모·상태·확인 시각
- **구분** 검토함에 보내는 의견과 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 원문과 대조하기: 참고 자료에서 현재 기준 30초·90일을 확인합니다. 30초는 화면 표시 갱신이며 장애 복구 시간이 아닙니다.
2. 메모와 상태 저장하기: ‘갱신은 표시 갱신이며 복구 시간이 아님’을 메모하고, 직접 확인했다면 확인함으로 저장합니다.
3. 같은 답변 다시 열기: 새로고침해 같은 답변의 메모와 상태가 남는지 봅니다. 수정 후 취소하면 저장했던 메모가 남아야 합니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

### 다음 기능 · 확인한 근거와 답변 다시 열기

**먼저 계획 요청**

```text
채팅의 내 확인 기록에 직접 읽은 근거를 연결할 계획을 세워. 해당 답변의 실제 인용에서 고르고 답변·인용 식별자로 DB에 연결해. 변경 파일과 개발 DB 적용도 포함해. 인용 번호만 저장하지 말고 자료 종류·버전·문단과 원래 주소를 보존해. 기존 참고 자료 패널과 원문 열기를 재사용해 같은 답변의 기록에서 다시 열게 해. 접근 제한·원문 개정은 기존 규칙으로 안내하고 숨겨진 본문은 노출하지 마. 연결·다시 열기를 검사해. 이번에는 개별 답변의 기록 안에서 동작하게 해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 연결 대상: 해당 답변이 실제 사용한 근거
- 다시 열기: 원래 답변·자료·버전·문단
- 확인할 차이: 게시 위키와 원문 근거를 구분

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 실제 인용에서 고르기: 답변에 실제로 나온 위키나 원문 중 읽은 근거를 고릅니다. 갱신·보관이 한 근거에 있으면 하나만 연결합니다.
2. 원래 자료 다시 열기: 연결한 근거를 열어 자료 종류와 버전·문단이 맞는지 봅니다. 위키 인용이면 위키에 연결된 원문도 대조합니다.
3. 답변으로 돌아오기: 다른 대화를 보거나 화면을 다시 연 뒤 같은 A 답변으로 돌아옵니다. 연결해 둔 근거를 다시 열 수 있어야 합니다.

### 다음 기능 · 추가 확인할 답변 모아 보기

**먼저 계획 요청**

```text
채팅에 내 답변 확인 목록을 만들 계획을 세워. 질문 요약·상태·메모·확인 시각을 보여 주고 상태·프로젝트·메모 필터를 함께 적용해. 프로젝트는 각 답변을 만들 당시의 저장된 범위를 사용해. 대화의 현재 범위를 바꿔도 과거 답변 분류는 유지해. 기록이 없는 내 완료 답변은 미확인으로 표시해. 소유·열람 조건에 맞춰 목록과 개수를 구하고 원래 답변·근거로 이동하게 해. 메모·상태 변경 후 갱신과 범위 변경을 검사해. 답변 본문을 복제하지 말고 삭제·접근 제한은 기존 규칙을 따라. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 미확인: 확인 기록이 없는 내 완료 답변
- 프로젝트 기준: 각 답변을 만들 당시의 범위
- 목록에서 이어가기: 답변과 근거를 다시 열어 확인

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

```text
지식 그래프의 선택한 위키 상세에 비교에 담기와 최대 두 개의 비교 목록을 만들 계획을 세워. 담은 제목·프로젝트를 보여 주고 위키 ID로 중복을 막아. 두 개가 찼으면 하나를 빼고 담도록 안내해. 담기·빼기·모두 비우기를 우선 화면 상태로 구현해. 목록을 비워도 위키나 그래프 관계는 삭제하지 마. 실제 게시 상태와 열람 권한을 확인하고 기존 위키 검색·노드 선택·미리보기와 관계 계산은 유지해. 중복·개수 제한·목록 비우기를 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **대상** 현재 읽을 수 있는 게시 위키 두 개
- **중복** 제목이 아닌 위키 ID로 판단
- **기존 기능** 그래프 탐색·미리보기는 재사용

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 첫 위키 담기: ‘프로젝트 A 검수 업무 절차’를 선택해 비교에 담습니다. 목록에 제목과 프로젝트가 보여야 합니다.
2. 두 번째 위키 담기: ‘프로젝트 A의 범위와 검수 기준’을 담습니다. 같은 위키를 다시 눌러도 중복 항목이 생기지 않아야 합니다.
3. 빼고 다시 담기: 한 항목을 빼도 원래 위키는 남아야 합니다. 다시 담아 두 개를 준비합니다. 세 번째 항목은 하나를 빼라는 안내가 나와야 합니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

## 4. 대표 구현과 첫 통합

[함께 볼 강의 화면](/lectures/week-05.html#slide-30)

**앞에서 이어받을 것:** 각자의 개발 결과와 강사가 준비한 대표·추가 커밋, 별도 통합 사본·개발 DB

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 같은 장 하단의 사례로 직접 눌러 보고 예상과 다른 동작을 고칩니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 앞 장에서 확인한 결과를 모아 다음 회차의 출발 상태를 정합니다. 같은 질문·역할 검사를 다시 실행하지 않습니다.

**저장 기준:** 코드 변경과 DB 변경 파일·적용 순서를 함께 반영합니다. 개인 데이터와 운영 DB는 이 실습의 통합 대상이 아닙니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅 질문 모음·답변 확인·그래프 비교의 개인 개발본을 통합 전에 보관할 계획을 세워. 내 브랜치·미커밋 변경·DB 적용·origin·upstream을 확인하고 제공된 시작·추가·최종 커밋과 별도 사본·주소·전용 DB를 대조해. 없는 값은 추측하지 마. 교육에서 바꾼 코드·DB 변경 파일만 개인 브랜치에 커밋하되 이미 보관했으면 중복 커밋하지 마. 환경 파일·비밀번호·개인 DB·업로드 파일은 제외해. 커밋 번호와 통합 대상을 비밀값 없이 남기고 원문 v2·두 게시 위키·역할 계정을 확인할 목록을 정해. 병합·push는 하지 마. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **내 작업** 기능·코드 커밋·DB 적용 상태
- **통합 기준** 강사가 지정한 대표·추가 변경 커밋
- **작업 위치** 개인 개발본과 다른 사본·개발 DB

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 보관한 커밋 확인하기: Claude Code가 알려 준 개인 브랜치·커밋 번호와 포함 파일 설명을 봅니다. 이미 커밋했다면 새 커밋을 만들지 않습니다.
2. 보관 범위 확인하기: 교육 코드·DB 변경 파일만 포함했는지 확인합니다. 환경 파일·비밀번호·개인 DB·업로드 파일은 포함하지 않습니다.
3. 통합 대상 대조하기: 대표·추가·최종 기준 커밋과 별도 폴더·주소·전용 DB가 제공됐는지 봅니다. 아직 병합하거나 원격에 올리지 않습니다.

### 다음 기능 · 강사 기준 가져와 별도 사본 준비

**먼저 계획 요청**

```text
제공된 통합 기준표의 대표 구현을 별도 사본에 준비할 계획을 세워. origin은 내 fork, upstream은 강사 저장소인지 대조하고 없으면 연결할 방법을 정해. fetch할 커밋과 개인 작업의 차이를 설명해. 기존 경로·브랜치·설정을 보존하며 대표 커밋의 별도 브랜치·사본을 만들고 제공된 포트·전용 개발 DB만 사용해. 패키지·DB 변경의 적용 순서와 웹·작업자 연결 검사를 포함해. 원문 v2·두 게시 위키·역할 계정 확인 방법과 다음 Claude Code에서 열 폴더·브랜치를 알려 줘. 비밀값은 출력하지 말고 개인·운영 DB와 Docker는 건드리지 마. 추가 변경은 아직 합치지 마. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- origin: 내 fork 저장소
- upstream: 강사가 안내한 기준 저장소
- fetch: 이력 가져오기 · 내 작업에 병합은 별도

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 실행 환경 대조하기: 제공된 주소에서 통합 사본이 열리는지 보고 원문 v2·두 게시 위키·역할 계정을 확인합니다. 개인 개발본과 DB를 구분합니다.
2. 변경 전 기록 남기기: 통합 DB에 A·B 질문과 고정 전 순서, A 실제 답변·메모·근거, 두 위키 비교 목록을 준비합니다. 이미 있으면 그대로 사용합니다.
3. Claude Code 폴더 옮기기: 이제 별도 통합 사본 폴더를 Claude Code에서 엽니다. 기준표의 폴더·브랜치·주소·DB 정보를 전달하되 비밀번호는 넣지 않습니다.

### 다음 기능 · 추가 기능의 코드와 DB 변경 합치기

**먼저 계획 요청**

```text
별도 통합 사본의 내 질문 모음에 제공된 질문 고정하기 변경을 합칠 계획을 세워. 현재 폴더·브랜치·주소·전용 DB가 기준표와 맞는지 먼저 확인해. 대표 코드와 추가 커밋의 저장 구조·권한·DB 변경 순서를 비교하고 충돌 해결안을 설명해. 한쪽 파일 전체로 덮지 말고 확인한 동작에 맞춰 해결해. 필요한 새 DB 변경 파일을 지정된 통합 개발 DB에만 적용하고 기존 적용 이력은 유지해. 고정·해제·상단 정렬, 기존 저장·수정·삭제와 추가 변경 전 질문·답변 메모·비교 목록 보존을 검사해. 코드 커밋과 DB 적용 결과를 각각 남겨. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 채택할 변경: 내 질문 고정·해제·상단 정렬
- 코드와 DB: 충돌과 저장 구조를 함께 확인
- 보존할 것: 기존 질문·적용 이력·개인 개발본

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 아래쪽 질문 고정하기: 통합 전에 준비한 목록에서 아래쪽 질문을 고정합니다. 맨 위로 이동해야 하며 이미 맨 위인 질문만으로 판단하지 않습니다.
2. 새로고침 후 해제하기: 새로고침해 고정과 순서를 확인한 뒤 해제합니다. 고정 전 정렬로 돌아가야 합니다.
3. 같은 기록 다시 열기: 추가 변경 전 A 질문·답변 메모·근거·두 위키 비교가 그대로인지 확인합니다. 코드 커밋과 DB 적용 결과도 구분해 남깁니다.

### 다음 기능 · 같은 통합 기준으로 업무 흐름 확인

**먼저 계획 요청**

```text
별도 통합 사본의 질문 모음·답변 확인·위키 비교·기존 자료실·위키를 최종 기준과 대조할 계획을 세워. 커밋 번호가 달라도 코드 내용·DB 변경 목록·적용 이력을 비교하고 필요한 차이만 반영해. 강제 초기화·불필요한 DB 재적용·개인 데이터 병합·push·회사 배포는 하지 마. 자동 검사와 작성·검토·열람 계정별 시작 메뉴·버튼·기대 결과를 정해. 추가 변경 전 질문·답변·메모·비교 기록으로 보존 여부를 확인하게 해. 내 실제 확인 결과를 받은 뒤 통과·실패·미확인을 기록하고 코드가 같다고 업무 확인을 완료 처리하지 마. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 같은 기준: 코드 커밋 + DB 적용 목록
- 직접 수행: 질문 → 근거 → 메모 → 위키 비교
- 남길 결과: 통과·실패·미확인·다음 조치

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 작성 계정으로 이어 보기: 변경 전 A 질문·답변·메모·비교를 그대로 엽니다. 같은 질문을 다시 보내거나 새 기록으로 바꾸지 않습니다.
2. 역할을 바꿔 확인하기: 검토자는 보낸 의견을, 열람자는 공개 자료·게시 위키와 자신의 비교 목록을 확인합니다. 다른 계정의 개인 기록은 보이지 않아야 합니다.
3. 실제 결과 알려 주기: AI에게 직접 누른 결과를 알려 통과·실패·미확인을 나눠 남깁니다. 코드 기준 일치와 실제 업무 확인은 각각 기록합니다.

### 업무 순서대로 확인

앞 장에서 확인한 결과를 모아 다음 회차의 출발 상태를 정합니다. 같은 질문·역할 검사를 다시 실행하지 않습니다.

1. 통합 사본의 실제 주소·커밋·DB 적용 결과를 기록합니다. 제공된 최종 기준과 내 통합 커밋은 구분합니다.
2. 앞 장에서 확인한 질문·답변·메모·비교의 보존 결과를 남깁니다. 새로 만든 기록으로 보존 확인을 대체하지 않습니다.
3. 작성·검토·열람 계정에서 이미 확인한 결과와 남은 문제를 구분합니다. 다음 회차에서 이어 볼 기록을 남깁니다.

다른 교육생이 써 주는 것을 기다리지 않습니다. 각자 본인의 통합 사본에서 확인합니다.
