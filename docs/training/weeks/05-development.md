# 채팅과 지식 그래프로 근거 확인하기

질문을 다시 쓰고 답변의 근거를 확인하며, 두 위키를 비교하는 기능을 개발합니다. 확인한 구현은 코드와 DB 변경까지 첫 통합본으로 연결합니다.

[강의 화면](/lectures/week-05.html) · [회사 개발 노트](../company-project.md)

**시작 전에 준비할 것:** 실습에 사용할 공개 자료와 게시 위키를 확인합니다. 같은 위키 코드를 연 Claude Code와 실제 앱을 나란히 엽니다.

**남길 결과:** 범위를 함께 저장하는 내 질문 모음 / 답변·근거에 연결된 개인 확인 기록 / 두 게시 위키의 비교와 탐색 복귀 / 코드·DB 적용을 확인한 첫 통합본

각 실습은 **계획 요청 → 내가 확인·수정 → 실행 → 직접 확인**을 한 장에서 진행합니다. 먼저 계획 요청만 보내고 원하는 동작인지 확인합니다. 맞으면 같은 Claude Code 대화에 **‘계획한 대로 실행해줘.’**를 보냅니다. 두 복사 버튼은 따로 사용하고, 실행 후에는 같은 장 하단의 사례로 확인합니다. 교시 마지막에는 만든 기능을 이어 사용합니다.

## 먼저 준비할 것

- 같은 개인 위키와 Claude Code를 사용합니다. **업무 질문은 앱 채팅**, **개발 요청은 Claude Code**에 입력합니다.
- 자료실에서 프로젝트 A·B의 공개 자료를 확인합니다. 위키 비교 실습에는 게시 위키 두 개가 필요합니다. 이 교재는 **프로젝트 A 검수 업무 절차**, **프로젝트 A의 범위와 검수 기준**을 예로 듭니다. 없는 자료는 강사와 함께 준비하고, 정해진 답을 만들기 위해 원문을 바꾸지 않습니다.
- 기본 계정은 writer@wiki.local로 진행하고 reviewer@wiki.local·reader@wiki.local로 역할을 직접 확인합니다. 비밀번호는 본인 환경의 안내를 따릅니다.
- 앱의 AI 연결이 준비돼 있어야 합니다. 답변에 실제 근거가 나오는지 확인하며 실패한 답변을 완료 사례로 꾸미지 않습니다.
- 통합은 개인 개발본과 다른 사본·개발 DB에서 진행합니다. 대표 저장소·브랜치·커밋, 추가 변경 커밋, 작업 사본 경로, 대상 DB는 강사가 미리 준비한 실제 값을 받습니다.

## 같은 사례로 이어가기

[질문·근거·위키 비교 실습 사례](../samples/chat-graph-practice.md)에 입력 문장과 확인 순서를 모았습니다. 필요한 내용은 강의 화면에도 있습니다.

| 교시 | 공통 작업 | 다음에 사용할 결과 |
| --- | --- | --- |
| 1 | 질문·범위 저장, 불러오기, 수정·복제·검색 | 세 질문과 첫 A 질문의 실제 답변 |
| 2 | 개인 메모·상태·근거 연결·확인 목록·검토 의견 연결 | 두 답변의 실제 확인 기록과 보낸 의견 |
| 3 | 두 위키 담기·비교·원문 복귀·목록 보관 | 다시 열 수 있는 게시 위키 비교 |
| 4 | 개인 작업 보관·기준 가져오기·추가 변경·업무 확인 | 코드·DB를 확인한 첫 통합본 |

답변의 갱신 주기·보관 기간은 내 앱에서 연 원문과 대조합니다. 캡처의 숫자를 정답으로 외우거나, 답을 맞추려고 자료를 수정하지 않습니다.

## 통합 환경에서 이어가기

강사가 제공한 코드 사본·실행 주소·전용 개발 DB를 확인합니다. 교육생마다 DB를 분리하고 그 안에서 작성·검토·관리·열람 역할을 바꿉니다. 공통 계정 이름이 같다고 한 DB를 함께 수정하지 않습니다. 기준 커밋과 내 실제 통합 커밋은 각각 기록하며, 코드 내용·DB 적용·자료 상태를 함께 대조합니다.

첫 통합의 대표 구현에는 2~4회차 기능과 오늘의 질문 모음·답변 확인·위키 비교가 필요합니다. 질문 고정하기는 강사가 미리 시험해 제공할 추가 변경입니다. 통합 DB에는 공개 원문·두 게시 위키·역할 계정이 있어야 하며, 필요한 개인 질문·확인 기록은 통합 환경에서 교육용으로 준비합니다. 개인 DB를 그대로 복사하거나 초기 샘플로 덮어쓰지 않습니다.

개발 요청은 기능을 만드는 요청입니다. 기능이 완성되면 교육생이 앱에서 ‘A 검수 기준’과 ‘A 자동 복구 확인’을 직접 입력해 저장하고, 복제 기능으로 ‘B 검수 기준’을 만듭니다. 기존 질문은 그대로 둡니다. 통합 사본에서는 추가 변경 전에 ‘A 검수 기준’·‘B 검수 기준’, A 답변의 메모·근거·검토 의견과 두 위키 비교를 직접 준비합니다. 그 뒤 Claude Code의 작업 폴더를 통합 사본으로 옮기고, 같은 기록이 변경 후에도 남는지 확인합니다.

## 장 사이에서 이어갈 상태

- 기본 실습은 writer 계정입니다. reader·reviewer로 확인을 마치면 writer로 돌아옵니다.
- 저장한 질문의 이름과 실제 질문 문장은 다릅니다. 최근 대화·내 확인 목록에서는 갱신 주기·보관 기간 질문과 자동 복구 질문의 문장으로 답변을 구분합니다. 같은 질문을 다시 보내 이전 답변을 대신하지 않습니다.
- 14·15장은 앞으로 기록할 내용의 예시입니다. 16장에서 메모·상태, 17장에서 근거 연결, 18장에서 확인 목록, 19장에서 의견 작성 연결을 개발한 뒤 사용합니다.
- 24~26장의 비교 목록은 아직 계정별 DB 저장 전입니다. 개발 중 화면이 다시 열려 비면 같은 두 위키를 다시 담습니다. 27장에서 담기·빼기와 DB 저장을 연결한 뒤 새로고침·다른 브라우저·계정 분리를 확인합니다.
- 34장에서 별도 통합 앱에 준비한 기록의 위치와 내용을 적고 Claude Code도 통합 폴더로 옮깁니다. 35장 이후에는 그 환경에서 작업합니다.
- 36장에서 실제 검사 결과를 `docs/practice/week-05-integration.md`에 저장하고 37~39장에서 읽어 정리합니다. 다음 회차에도 같은 통합 앱과 결과 파일을 사용합니다.

## 준비: 채팅·그래프의 기존 기능 확인

아래 전체를 개발용 AI에 입력한 뒤 실제 메뉴와 비교합니다.

```text
지금 개발한 위키의 채팅과 지식 그래프를 개선할 거야. 채팅의 질문 범위·최근 대화·참고 자료·답변 의견·위키 초안 저장과 그래프의 필터·위키 목록·문서 미리보기 동작을 확인해. 현재 코드에 질문 모음이나 개인 확인 기록이 있는지도 확인하고 새로 필요한 기능과 구분해. 내가 눌러 볼 메뉴·버튼 순서를 알려 줘. 없는 기능은 가정하지 마. 코드와 DB는 아직 바꾸지 마.
```

**직접 확인:** 기존 기능의 위치와 사용할 계정을 확인합니다. 개발 요청은 앱 채팅에 넣지 않습니다.

## 1. 질문 저장과 범위 재사용

[함께 볼 강의 화면](/lectures/week-05.html#slide-04)

**앞에서 이어받을 것:** 공개 자료를 참고해 채팅할 수 있는 개인 위키

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 기능 구현이 끝나면 아래 입력 사례를 앱에서 직접 저장·전송하고 결과를 확인합니다. 개발 요청만으로 개인 실습 기록이 생기지는 않습니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 7장에서 직접 저장한 A 질문 두 개와 9장에서 복제한 B 질문을 사용합니다. 없는 항목은 해당 장의 입력 순서로 준비하세요.

**저장 기준:** 질문·범위·이름을 사용자·작업공간별 DB에 저장합니다. 기존 대화와 저장 검색 조건은 분리합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅에 내 질문 모음을 만들 계획을 세워. 질문 입력 옆에 저장 버튼과 내 질문 목록을 두고 이름·질문·도메인·프로젝트·탐색 깊이·원문만 사용·웹 검색 설정을 저장해. 자료·위키에서 들어온 한정 범위도 포함해. 사용자·작업공간별 테이블과 변경 파일, 개발 DB 적용을 계획에 넣어. 빈 질문과 중복 클릭은 저장을 막고, 저장만으로 AI에게 전송하지 마. 새로고침 뒤 복원과 다른 계정의 접근 제한도 검사해. 기존 최근 대화와 저장 검색 조건은 유지해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **저장할 내용** 질문 문장 + 적용할 범위 + 이름
- **저장할 곳** 현재 사용자·작업공간의 DB
- **기존 기능** 최근 대화와 저장 검색 조건은 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 앱에서 첫 질문 저장하기: 채팅에서 도메인 ‘가상 교통관제 자료’와 프로젝트 A를 고릅니다. 사례표의 첫 질문 문장을 입력하고 이름을 ‘A 검수 기준’으로 저장합니다. 개발 요청이 이 항목을 대신 만들어 주지는 않습니다.
2. 두 번째 질문 저장하기: 사례표의 자동 복구 질문 문장으로 입력칸을 바꾸고 ‘A 자동 복구 확인’으로 저장합니다. 두 항목의 이름·문장·프로젝트가 각각 맞는지 확인하며 질문 보내기는 누르지 않습니다.
3. 새로고침 후 확인하기: 두 질문과 저장한 범위가 남고, 답변이 생성되지 않았는지 봅니다. 이미 저장한 항목은 내용을 확인해 사용합니다. B 질문은 복제 기능을 만든 뒤 추가합니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

### 다음 기능 · 질문과 범위를 확인한 뒤 불러오기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에서 저장한 질문을 불러올 계획을 세워. 문장·도메인·프로젝트·한정 자료·탐색 설정을 미리 보여 주고 적용을 눌러야 새 대화의 입력칸과 범위를 채워. 입력 중인 문장이 있으면 교체 전에 확인하고 취소하면 입력 문장과 현재 범위를 모두 남겨. 기존 대화의 범위·기록은 유지하고 질문 보내기를 눌러야 전송해. 현재 계정으로 범위를 다시 확인하고 삭제·접근 제한이면 적용을 막아. 전체 범위로 바꾸지 말고 이유와 수정할 곳을 안내해. 적용·취소·전송 전 상태를 검사할 방법도 포함해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 적용 전: 질문 문장과 프로젝트를 먼저 확인
- 적용 후: 새 대화 입력칸과 범위만 채움
- 전송: 내가 질문 보내기를 눌러 실행

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 프로젝트를 B로 바꾸기: 새 대화에서 프로젝트 B를 고른 뒤 내 질문 모음의 ‘A 검수 기준’을 선택합니다. B용 저장 질문을 찾는 단계가 아닙니다. 적용 전 문장과 프로젝트 A가 보여야 합니다.
2. 입력 교체 취소하기: 새 대화의 프로젝트를 B로 두고 입력칸에 ‘작성 중인 질문’이라고 적습니다. ‘A 검수 기준’을 불러오다가 취소하면 입력 문장과 프로젝트 B가 모두 남아야 합니다.
3. 확인 후 적용하기: 다시 ‘A 검수 기준’을 골라 적용합니다. 새 대화의 문장과 프로젝트가 A로 채워지되 답변은 생성되지 않아야 합니다.

### 다음 기능 · 질문 수정·복제·삭제 연결하기

**먼저 계획 요청**

```text
채팅의 내 질문 모음에 수정·복제·삭제를 더할 계획을 세워. 기존 저장 구조를 사용하고 수정은 이름·문장·범위를 바꾸되 취소하면 원래 값을 남겨. 복제는 원본을 유지한 새 항목으로 만들고 이름·문장·프로젝트를 바꿔 저장하게 해. 삭제는 대상 이름을 확인받고 질문 항목만 지워. 기존 대화·답변은 남겨. 내 질문인지 서버에서 확인하고, 성공하면 목록을 갱신하며 저장 실패 시 입력을 보존해. 이 동작을 확인할 검사도 계획해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 수정과 취소: 질문만 변경 · 취소 시 원래 값

**계획을 확인한 뒤 실행**

계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. B 질문 저장하기: 앱의 내 질문 모음에서 ‘A 검수 기준’을 복제합니다. 이름은 ‘B 검수 기준’, 질문 문장은 사례표의 B 질문, 프로젝트는 ‘프로젝트 B · 누리시’로 바꿔 저장합니다. 이미 같은 항목이 있으면 내용을 확인해 사용합니다.
2. 수정 저장과 취소 확인하기: ‘B 검수 기준’을 복제해 ‘삭제 연습’으로 저장합니다. 이 복제본의 이름을 ‘삭제 확인용’으로 수정·저장한 뒤 다시 수정을 열어 다른 이름을 입력하고 취소합니다. 저장했던 ‘삭제 확인용’이 남아야 합니다.

### 다음 기능 · 질문 목록 검색과 프로젝트 필터

**먼저 계획 요청**

채팅의 내 질문 목록에 이름·문장 검색과 프로젝트 필터를 더할 계획을 세워. 두 조건을 함께 적용하고 로그인 사용자·작업공간 범위에서 목록과 개수를 구해. 전체 질문이 없을 때와 검색 결과가 없을 때를 구분하고 조건 지우기를 제공해. 수정·복제·삭제 뒤 목록과 개수를 갱신하고 새로고침 후에도 저장한 질문을 찾게 해. 화면 필터를 저장할 별도 DB 테이블은 만들지 마. 조건 조합과 빈 결과, 다른 계정의 질문이 섞이지 않는지 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 검색 대상: 질문의 이름과 문장
- 필터: 프로젝트 A·B 또는 전체
- 빈 결과: 조건을 지워 다시 찾기

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 검색 조건 함께 적용하기: 프로젝트 A와 검색어 ‘검수’를 고릅니다. 이번 사례에서는 ‘A 검수 기준’이 나오고 ‘A 자동 복구 확인’과 ‘B 검수 기준’은 제외돼야 합니다. 다른 기존 질문도 조건에 맞으면 나올 수 있습니다.
2. 없는 검색어 넣기: 저장한 질문에 없는 검색어로 바꿉니다. 결과 0개와 조건을 지우는 방법이 보여야 합니다.
3. 조건 지우기: 검색어와 프로젝트 조건을 지우면 이번에 저장한 세 질문과 기존 질문이 다시 보이고, 표시 개수가 실제 목록과 맞아야 합니다. 개수를 맞추려고 기존 질문을 지우지 않습니다.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

7장에서 직접 저장한 A 질문 두 개와 9장에서 복제한 B 질문을 사용합니다. 없는 항목은 해당 장의 입력 순서로 준비하세요.

**확인:** 세 질문과 갱신 주기·보관 기간 질문의 실제 답변을 다시 열 수 있습니다.

## 2. 답변 근거와 개인 확인 기록

[함께 볼 강의 화면](/lectures/week-05.html#slide-13)

**앞에서 이어받을 것:** 앞에서 완료된 A 검수 기준의 실제 답변

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 기능 구현이 끝나면 아래 입력 사례를 앱에서 직접 저장·전송하고 결과를 확인합니다. 개발 요청만으로 개인 실습 기록이 생기지는 않습니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 16~19장에서 직접 저장한 메모·상태·근거와 전송한 의견을 사용합니다. 목록이 비었다면 해당 단계의 저장·전송부터 확인하세요.

**저장 기준:** 메모·확인 상태·인용 관계는 실제 답변과 사용자에 연결합니다. 답변 본문을 별도 복제하지 않습니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
채팅의 완료된 답변에 내 메모와 미확인·확인함·추가 확인 상태를 만들 계획을 세워. 메모·상태·확인 시각을 답변 ID·대화 ID·작업공간·사용자에 연결해 DB에 저장하고 변경 파일의 개발 DB 적용을 포함해. 같은 문장도 서로 다른 답변으로 구분해. 저장·수정·취소, 저장 실패 시 입력 보존, 다시 열기와 다른 계정의 접근 제한을 검사해. 실패·진행 중 답변은 확인함으로 바꾸지 마. 검토자에게 보내는 기존 의견과 분리하고 위키 게시나 공식 승인 상태는 바꾸지 마. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **대상** 완료된 답변 한 건
- **기록** 내 메모·상태·확인 시각
- **구분** 검토함에 보내는 의견과 별개

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 같은 답변 열기: 최근 대화에서 ‘프로젝트 A의 현재 상태 화면 갱신 주기와 이력 보관 기간은?’으로 시작하는 질문의 완료 답변을 엽니다. 저장한 질문 이름이 대화 제목에 그대로 나타난다고 가정하지 않습니다. 아직 답변이 없으면 질문을 한 번 보내고 완료된 뒤 진행합니다.
2. 판단을 직접 저장하기: 갱신 주기·보관 기간을 원문과 대조하고 읽은 내용과 남은 의문을 내 메모에 적습니다. 확인이 끝났으면 확인함, 더 알아볼 내용이 있으면 추가 확인으로 저장합니다.
3. 수정·취소·재접속 확인하기: 메모에 원문 제목을 보완해 저장합니다. 다시 수정 화면을 열어 다른 문장을 입력하고 취소한 뒤 새로고침합니다. 마지막에 저장한 메모·상태가 같은 답변에 남아야 합니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

### 다음 기능 · 확인한 근거와 답변 다시 열기

**먼저 계획 요청**

```text
채팅의 내 확인 기록에 직접 읽은 근거를 연결할 계획을 세워. 해당 답변의 실제 인용에서 고르고 답변·인용 식별자로 DB에 연결해. 변경 파일과 개발 DB 적용도 포함해. 인용 번호만 저장하지 말고 자료 종류·버전·문단과 원래 주소를 보존해. 기존 참고 자료 패널과 원문 열기를 재사용해 같은 답변의 기록에서 다시 열게 해. 접근 제한·원문 개정은 기존 규칙으로 안내하고 숨겨진 본문은 노출하지 마. 연결·다시 열기를 검사해. 이번에는 개별 답변의 기록 안에서 동작하게 해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 연결 대상: 해당 답변이 실제 사용한 근거
- 다시 열기: 원래 답변·자료·버전·문단
- 확인할 차이: 게시 위키와 원문 근거를 구분

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 실제 인용에서 고르기: 답변에 실제로 나온 위키나 원문 중 읽은 근거를 고릅니다. 갱신·보관이 한 근거에 있으면 하나만 연결합니다. 인용이 없다면 모델 연결·공개 자료 상태를 강사와 확인하고, 연결하지 않은 근거를 확인 완료로 처리하지 않습니다.
2. 원래 자료 다시 열기: 연결한 근거를 열어 자료 종류와 버전·문단이 맞는지 봅니다. 위키 인용이면 위키에 연결된 원문도 대조합니다.
3. 같은 답변으로 돌아오기: 최근 대화에서 갱신 주기·보관 기간 질문의 같은 답변을 다시 엽니다. 저장한 메모와 근거를 찾을 수 있어야 합니다. 별도의 내 확인 목록은 다음 장에서 만듭니다.

### 다음 기능 · 추가 확인할 답변 모아 보기

**먼저 계획 요청**

```text
채팅에 내 답변 확인 목록을 만들 계획을 세워. 질문 요약·상태·메모·확인 시각을 보여 주고 상태·프로젝트·메모 필터를 함께 적용해. 프로젝트는 각 답변을 만들 당시의 저장된 범위를 사용해. 대화의 현재 범위를 바꿔도 과거 답변 분류는 유지해. 기록이 없는 내 완료 답변은 미확인으로 표시해. 소유·열람 조건에 맞춰 목록과 개수를 구하고 원래 답변·근거로 이동하게 해. 메모·상태 변경 후 갱신과 범위 변경을 검사해. 답변 본문을 복제하지 말고 삭제·접근 제한은 기존 규칙을 따라. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 미확인: 확인 기록이 없는 내 완료 답변
- 프로젝트 기준: 각 답변을 만들 당시의 범위
- 목록에서 이어가기: 답변과 근거를 다시 열어 확인

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 두 번째 답변 만들기: writer의 내 질문 모음에서 ‘A 자동 복구 확인’을 새 대화에 불러와 한 번 전송합니다. 답변을 받은 직후 미확인 목록에 보이는지 먼저 확인합니다. 그런 다음 원문을 읽고 메모·상태를 저장합니다. 근거로 확인했으면 확인함, 판단이 남았으면 추가 확인으로 둡니다.
2. 필터와 이동 확인하기: 프로젝트 A와 방금 저장한 상태, 메모에 실제로 쓴 단어를 함께 적용합니다. ‘프로젝트 A의 장애 자동 복구 시간은?’으로 시작하는 질문을 찾아 답변을 엽니다. 조건을 지우면 앞서 받은 검수 기준 답변도 찾을 수 있어야 합니다.
3. 대화 범위 바꾸기: 현재 대화의 프로젝트를 B로 바꿔도 기존 답변은 A 목록에 남아야 합니다. 새 질문은 보내지 않고 확인 후 프로젝트를 A로 돌립니다.

### 다음 기능 · 개인 메모와 검토 의견 연결 구분

**먼저 계획 요청**

```text
채팅의 내 확인 기록에 검토 의견 작성 버튼을 더할 계획을 세워. 내가 고른 메모만 기존 답변 의견 폼으로 옮기고 질문·실제 답변 요약을 직접 보완하게 해. 검토자는 개인 대화 전체를 볼 수 없다는 점을 안내해. 보낼 내용과 기존 답변 평가를 읽고 수정한 뒤 의견 보내기를 눌러야 전달해. 의견 작성 취소 버튼을 두고 취소하면 보내지 마. 이미 보낸 의견은 기존 수정 흐름을 사용해. 내 메모·상태는 유지하며 개인 메모를 위키 초안에 자동 포함하지 마. 취소·전송·수정과 검토함에 보이는 내용을 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 보낼 내용: 질문·답변 요약·추가 확인할 내용
- 답변 평가: 정상 답변과 수정이 필요한 답변 구분
- 전송과 취소: 취소는 미전송 · 기존 의견은 수정

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 의견 내용 직접 작성하기: ‘A 자동 복구 확인’ 답변의 메모에서 검토 의견 작성을 엽니다. 실제 질문·답변 요약과 확인 요청을 적습니다. 기준을 찾지 못했다면 별도 문서가 있는지, 기준을 찾았다면 그 적용 범위가 맞는지 확인을 요청할 수 있습니다.
2. 평가와 취소 확인하기: 원문에 맞게 답했다면 ‘도움이 되었어요’, 내용이나 근거가 틀렸다면 해당 수정 요청 평가를 고릅니다. 취소하면 의견이 전송되지 않고 내 메모가 남아야 합니다.
3. 보낸 의견 다시 확인하기: 다시 열어 실제 질문·답변 요약·요청을 적고 한 번 보냅니다. ‘의견이 접수되었습니다 · 수정하기’로 보낸 내용을 다시 열어 수정·저장도 확인합니다. 같은 답변의 기존 의견 한 건이 갱신되고 내 메모는 남아야 합니다.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

16~19장에서 직접 저장한 메모·상태·근거와 전송한 의견을 사용합니다. 목록이 비었다면 해당 단계의 저장·전송부터 확인하세요.

1. 내 확인 목록에서 프로젝트 A를 고르고 상태·메모 검색은 지웁니다. 갱신 주기·보관 기간 질문의 답변을 열어 저장한 메모와 읽은 근거를 확인합니다.
2. 자동 복구 시간 질문의 답변도 엽니다. 직접 저장한 상태와 판단을 읽습니다. 목록의 질문 요약으로 구분하며 저장한 질문 이름이 표시된다고 가정하지 않습니다.
3. reviewer로 바꿔 검토함에서 방금 보낸 의견을 찾습니다. 질문·실제 답변 요약·수정한 요청이 맞는지 확인합니다. 개인 메모는 공유되지 않아야 하며 끝나면 writer로 돌아옵니다.

여기서 위키 초안을 새로 만들거나 게시하지 않습니다. 기존 게시 위키 두 개를 비교하는 작업으로 이어갑니다.

**확인:** 실제 질문 문장으로 두 답변을 다시 찾고, 검토함에 보낸 의견과 개인 메모를 구분할 수 있습니다.

**기본을 마쳤다면 — 선택 과제**

- **확인 항목 나누기:** 한 답변의 여러 주장별로 확인 상태를 나눕니다.
- **기준 변경 안내:** 근거 개정 후 예전에 확인한 답변을 다시 볼 목록을 만듭니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

계획·실행·핵심 확인을 한 장에서 진행합니다. 교시 마지막에는 만든 기능을 연결해 사용합니다.

## 3. 관련 위키 비교와 탐색 복귀

[함께 볼 강의 화면](/lectures/week-05.html#slide-22)

**앞에서 이어받을 것:** 보완·게시한 업무 절차와 범위 위키, 앞서 남긴 답변 확인 기록

1. 계획 요청과 확인 항목을 읽고, 맞으면 같은 대화에 ‘계획한 대로 실행해줘.’를 보냅니다.
2. 기능 구현이 끝나면 아래 입력 사례를 앱에서 직접 저장·전송하고 결과를 확인합니다. 개발 요청만으로 개인 실습 기록이 생기지는 않습니다.
3. 교시 마지막에는 이미 만든 결과를 연결해 사용합니다. 같은 항목을 다시 만들지 않습니다.

**내가 정할 것:** 27장에서 DB에 저장한 writer의 비교 목록을 이어 사용합니다. 두 위키를 다시 만들거나 같은 계정 검사를 반복하지 않습니다.

**저장 기준:** 비교 목록은 위키 ID·순서를 개인 DB에 보관하고 본문은 현재 게시본을 조회합니다.

**입력할 곳:** 내 위키 코드를 연 Claude Code · 같은 대화

### 1. 계획 요청

```text
지식 그래프의 선택한 위키 상세에 비교에 담기와 최대 두 개의 비교 목록을 만들 계획을 세워. 담은 제목·프로젝트를 보여 주고 위키 ID로 중복을 막아. 두 개가 찼으면 하나를 빼고 담도록 안내해. 담기·빼기·모두 비우기를 우선 화면 상태로 구현해. 목록을 비워도 위키나 그래프 관계는 삭제하지 마. 실제 게시 상태와 열람 권한을 확인하고 기존 위키 검색·노드 선택·미리보기와 관계 계산은 유지해. 중복·개수 제한·목록 비우기를 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**계획을 읽고 내가 확인할 것**

- **대상** 현재 읽을 수 있는 게시 위키 두 개
- **중복** 제목이 아닌 위키 ID로 판단
- **기존 기능** 그래프 탐색·미리보기는 재사용

내 결정과 다르면 계획부터 고칩니다. 확인하기 전에는 아래 실행 요청을 보내지 않습니다.

### 2. 확인한 뒤 실행

```text
계획한 대로 실행해줘.
```

**만든 뒤 직접 확인**

1. 첫 위키 담기: ‘프로젝트 A 검수 업무 절차’를 선택해 비교에 담습니다. 목록에 제목과 프로젝트가 보여야 합니다.
2. 두 번째 위키 담기: ‘프로젝트 A의 범위와 검수 기준’을 담습니다. 같은 위키를 다시 눌러도 중복 항목이 생기지 않아야 합니다.
3. 비운 뒤 다시 준비하기: 한 항목 빼기와 모두 비우기를 확인해도 원래 위키는 남아야 합니다. 마지막에는 같은 두 위키를 다시 담습니다. 세 번째 게시 위키가 있으면 최대 두 개 제한도 확인하며 없으면 이 검사는 미확인으로 적습니다.

**이어서 개발하기**

기본 기능을 확인한 뒤 이어갑니다. 각 요청 상자는 한 번에 입력하되, 계획과 실행을 함께 보내지 않습니다. 이미 완성한 동작은 확인하고 건너뜁니다. 아래 기능도 같은 순서로 진행합니다. 계획에 동의하면 짧은 실행 요청을 보내고, 직접 확인한 뒤 이어갑니다.

### 다음 기능 · 본문·적용 범위·근거 나란히 읽기

**먼저 계획 요청**

```text
지식 그래프의 비교 목록에서 두 위키를 나란히 읽을 계획을 세워. 각 열에 제목·도메인·프로젝트·현재 게시 버전·본문·연결 원문 근거를 보여 줘. 기존 미리보기·본문 표시를 재사용하고 새 초안이 있어도 게시본만 비교해. 공통 근거는 실제 자료·버전·문단 ID로 판단하고 원문 주소를 보존해. 작은 화면에서는 두 위키를 전환해 읽게 하고 편집·승인은 기존 경로를 사용해. AI가 사실을 임의 판정하거나 관계를 만들지 마. 게시본·근거 링크·작은 화면 동작을 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 비교 내용: 적용 범위·게시 본문·원문 근거
- 같은 값: 같은 숫자라도 적용 대상·의미·근거가 같은지 확인
- 관계의 뜻: 본문 링크·계산한 관련성·근거는 다름

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 비교할 두 문서 준비하기: 업무 절차와 범위 위키를 담고 나란히 엽니다. 개발 중 화면이 새로 열려 목록이 비었다면 다시 담습니다. 제목·프로젝트·게시 버전으로 각 문서를 구분합니다.
2. 게시본과 근거 대조하기: 두 위키의 갱신 주기·보관 기간을 연결된 원문과 비교합니다. 새 초안이 있는 문서라면 게시본과 혼동하지 않는지도 확인합니다. 검사를 위해 불필요한 초안을 새로 만들지는 않습니다.
3. 좁은 화면에서 읽기: 창 폭을 줄여 두 문서를 전환해 봅니다. 선택한 위키와 원문 링크가 유지되고 본문을 읽을 수 있어야 합니다.

### 다음 기능 · 원문을 읽고 같은 비교로 돌아오기

**먼저 계획 요청**

```text
지식 그래프 비교에서 원문의 정확한 버전·문단을 읽고 같은 비교로 돌아올 계획을 세워. 두 위키·도메인·프로젝트·검색·중심 위키·읽던 쪽을 URL 등 복귀 정보에 담아 원문에서 돌아올 때 복원해. 개인 목록의 DB 보관과 구분해. 현재 권한·게시 상태를 다시 확인하고 게시본이 달라졌으면 알린 뒤 갱신해. 그래프에서 온 경우만 같은 작업공간의 허용된 내부 그래프 경로로 돌아가게 해. 자료실·실무 기록의 기존 복귀, 위키 상세의 목록 링크, 직접 연 원문의 자료실 링크는 유지해. 필터 밖 항목·직접 진입·권한 변경도 안내하고 기존 경로와 복귀를 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 이어갈 상태: 두 위키·범위·검색·읽던 쪽
- 원문 위치: 각 위키에 연결된 정확한 문단
- 다시 확인: 접근 가능 여부와 현재 게시본

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. 원문을 열기 전 상태 확인하기: 두 위키를 담아 비교 화면을 엽니다. 현재 프로젝트·검색어·중심 위키·읽던 쪽을 적은 뒤 한쪽 근거의 정확한 버전·문단을 엽니다.
2. 같은 비교로 돌아오기: 복귀 버튼으로 돌아와 두 위키·프로젝트·검색·중심 위키·읽던 쪽이 그대로인지 봅니다.
3. 기존 복귀도 확인하기: 자료실에서 원문을 열고 자료실로 돌아옵니다. 본인이 볼 수 있는 근거 연결 실무 기록이 있으면 그 기록에서도 확인하고, 없으면 그 경로는 미확인으로 남깁니다. 끝나면 그래프에서 같은 두 위키를 다시 준비합니다.

### 다음 기능 · 내 비교 목록 저장하고 다시 열기

**먼저 계획 요청**

```text
지식 그래프의 내 비교 목록을 DB에 저장할 계획을 세워. 사용자·작업공간·위키 ID·선택 순서·마지막으로 본 게시 버전을 보관하고 본문은 복제하지 마. 테이블 변경 파일과 개발 DB 적용을 포함해. 앞에서 만든 담기·빼기·비우기를 DB 저장과 연결하고 저장 성공·실패를 표시해. 선택 순서를 보관하고 다시 열면 현재 읽을 수 있는 게시본을 조회해. 게시본 변경·근거 개정은 알리고 게시 철회나 접근 제한이면 본문을 숨긴 채 목록에서 정리하게 해. 목록을 비워도 원래 위키는 남겨. 같은 계정의 다른 브라우저 복원과 다른 계정의 목록 분리를 검사해. 코드와 DB는 아직 바꾸지 마. 계획을 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것**

- 보관할 것: 내가 고른 위키 ID·순서
- 다시 열 때: 현재 게시본과 권한 확인
- 비우기: 개인 비교 목록만 제거

**계획을 확인한 뒤 실행**

```text
계획한 대로 실행해줘.
```

**다음 기능 전에 직접 확인**

1. DB에 저장할 목록 준비하기: 개발 후 writer로 업무 절차와 범위 위키를 담아 저장 성공을 확인합니다. 화면 선택만 남아 있다면 담기·빼기 동작으로 실제 저장합니다. 새로고침해 같은 순서의 두 문서가 복원돼야 합니다.
2. 다른 브라우저에서 같은 목록 열기: 같은 서버·작업공간에 같은 writer로 로그인합니다. 저장한 두 위키가 보여야 합니다. 여기서는 목록을 바꾸지 않습니다.
3. reader의 목록 분리 확인하기: reader로 로그인해 writer의 목록이 없는지 봅니다. reader로 읽을 수 있는 위키 하나를 담아 새로고침하고 자신의 항목만 남는지 확인합니다. writer로 돌아오면 원래 두 위키가 그대로 있어야 합니다.

**만든 뒤 직접 눌러 보기**

### 업무 순서대로 확인

27장에서 DB에 저장한 writer의 비교 목록을 이어 사용합니다. 두 위키를 다시 만들거나 같은 계정 검사를 반복하지 않습니다.

1. writer로 저장한 두 위키를 엽니다. 목록이 비면 27장의 저장 결과부터 확인합니다. 문서 제목·적용 프로젝트·현재 게시 버전을 대조합니다.
2. 한쪽 원문 문단을 열고 비교로 돌아옵니다. 다른 쪽도 같은 순서로 확인해 두 위키와 탐색 조건이 유지되는지 봅니다.
3. 계정별 목록 확인은 앞 장 결과를 사용합니다. 두 위키에서 다르게 설명한 점과 남은 질문을 내 메모장에 적습니다. 앱의 비교 메모 기능을 새로 만들라는 뜻은 아닙니다.

본문이나 원문 링크가 열리지 않으면 게시 상태·권한·저장된 경로를 확인하고, 그 항목은 미확인으로 남깁니다.

**확인:** 두 위키 비교와 개인 목록 보관을 직접 확인했습니다.

**기본을 마쳤다면 — 선택 과제**

- **비교 기준 메모:** 두 문서를 비교하는 이유와 확인 결과를 함께 보관합니다.
- **여러 비교 묶음:** 비교 목록에 이름을 붙여 업무별로 여러 묶음을 저장합니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

계획·실행·핵심 확인을 한 장에서 진행합니다. 교시 마지막에는 만든 기능을 연결해 사용합니다.

2. 작성·검토·열람 계정에서 직접 확인한 결과가 적혀 있는지 봅니다. AI의 자동 검사만으로 직접 확인을 통과 처리한 항목이 있으면 고칩니다.
3. 실패·미확인 항목에 막힌 화면과 다음에 할 일을 적습니다. 다음 회차에 이 파일과 같은 통합 앱을 열어 이어갑니다.

다른 교육생이 써 주는 것을 기다리지 않습니다. 각자 본인의 통합 사본에서 확인합니다.

**확인:** 같은 기준의 첫 통합본과 직접 확인한 결과를 남겼습니다.

**기본을 마쳤다면 — 선택 과제**

- **충돌 원인 비교:** 같은 기능의 다른 저장 방식이 어떤 차이를 만드는지 비교합니다.
- **통합 검사 자동화:** 질문 저장·고정·다른 계정 차단을 반복 검사할 절차를 만듭니다.

필요한 과제를 선택하거나 다음 기능으로 이어가세요. 막히면 첫 동작부터 강사와 함께 완성합니다.

계획·실행·핵심 확인을 한 장에서 진행합니다. 교시 마지막에는 만든 기능을 연결해 사용합니다.

## 화면에서 확인한 뒤 코드 보관하기

같은 회사 개발 노트에 질문·답변 확인·위키 비교와 통합 결과를 남깁니다. 코드 커밋·DB 적용·직접 확인 결과를 구분합니다.

**먼저 보관할 변경 확인**

```text
채팅의 내 질문 모음·답변 확인 기록, 지식 그래프 비교와 첫 통합 결과를 정리할 거야. 변경 파일·DB 변경과 적용 상태·기준 커밋·직접 확인할 역할과 사례를 확인해. 내가 확인한 결과와 자동 검사, 미확인을 나눠 남길 계획을 세워. 비밀번호와 개인 대화 본문은 기록하지 마. 파일과 DB는 아직 바꾸지 마.
```

**포함할 코드·DB 변경과 제외할 설정을 확인한 뒤 실행**

```text
확인한 계획대로 개인 개발본과 통합본의 코드 커밋·DB 적용 목록·직접 확인 결과·남은 일을 개발 노트에 남겨. 실제 실행하지 않은 검사는 완료로 적지 마. 기존 기록은 유지하고 다음 RFP·관리 실습의 출발 상태를 정리해.
```
