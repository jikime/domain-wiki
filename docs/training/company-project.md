# 회사 개발 노트

각자의 기록 문서에 복사해 사용하고 통합할 때 필요한 항목을 회사 문서로 모읍니다. 이 워크북 화면에는 기록이 저장되지 않습니다. 목표는 한 번 정리하고, 작업이 생길 때마다 카드 한 장을 추가하세요. 코드·화면·대화는 위치를 연결하면 됩니다.

## 회사 위키의 목표

| 항목 | 우리 팀의 결정 |
| --- | --- |
| 사용자와 끝낼 업무 | |
| 현재 불편 / 완성할 모습 | |
| 사용할 자료·범위·대표 질문 | |
| 이미 있는 기능 / 개발할 기능 | |
| 개발 사본·팀 저장소·기준 버전 | |
| 코드 통합 / 회사 자료 준비 담당 | |
| 공용 환경 / 시스템·AI 운영 담당 | |
| 자료·위키의 별도 검토 담당 | |

## 이어 쓰는 작업 카드

```text
작업 이름 / 담당:
문제: [화면·입력·현재 결과]
완료 기준: [바뀔 동작과 확인 입력]
유지할 조건: [저장·권한·기존 기능]
AI 계획: [바뀔 동작·저장 방법·권한·확인 순서]
내 확인·수정: [내가 결정한 것·고친 계획·이번 실행 범위]
AI 요청·결정: [대화 위치·실행한 단계]
DB 반영: [기존 구조 활용 또는 변경 파일·적용한 개발 DB·결과]
변경 결과: [코드 버전·화면·자료 위치]
AI 검사: [실행한 검사·결과·하지 못한 검사]
직접 확인: [입력 → 기대 결과 → 실제 결과]
상태: [계획 중 / 계획 확인 / 개발 중 / 직접 확인 중 / 완료]
남은 일: [막힌 내용·도움받을 사람·다음 행동]
통합·공용 반영: [채택할 변경·코드 버전·DB 적용 순서·담당·실제 결과]
```

‘개발 중’인 카드는 계속 이어 씁니다. 기능 구현, 지식 보완, 오류 수정 모두 이 형식으로 충분합니다. 빈칸을 전부 채우는 대신 이번 작업에 필요한 내용만 적으세요. 코드 조사와 변경 버전 정리는 AI의 도움을 받습니다. 직접 확인한 사실과 아직 확인하지 못한 부분을 구분하세요.

**예시 — 확인 질문 누락 표시**

- 문제: RFP의 불명확 항목에서 확인 질문을 빠뜨립니다.
- 완료 기준: 빈 질문 1개 → ‘1개’, 질문 입력 → ‘0개’, 삭제 → 다시 ‘1개’입니다.
- 유지할 조건: 기존 저장 검증과 권한은 그대로 둡니다.
- 다음 개선: 직원이 누락 항목을 찾기 어렵다면 해당 항목으로 이동하는 동작을 검토합니다.

예시는 개발 후보입니다. 이미 있는 기능인지 먼저 확인하고 회사 요구에 맞게 바꿉니다.

## 개발과 함께 확인할 회사 환경

첫 화면을 바꾸며 코드 보관 위치·공용 환경·접속 담당을 정합니다. 회사 자료를 적용할 때는 직원 로그인을 확인하고, 기능을 통합하면 공용 주소에서 대표 업무를 수행합니다. 이어서 시범 사용과 운영 인계를 확인합니다.

## 회사 적용과 인계

| --- | --- | --- |
| 직원 접속 주소·계정·권한 | | |
| 통합 코드·DB 변경 이력·적용 버전·되돌릴 기준 | | |
| 회사 자료·게시 위키·대표 업무 | | |
| 자료 처리·AI 응답·개선 기능 | | |
| 자료 검토·갱신·사용 문의 | | |
| 시스템·AI 연결·사용량·비용 관리 | | |
| DB·원본·설정 백업과 별도 환경의 복원 확인 | | |
| 장애 접수·대체 담당·운영 안내 | | |

자세한 확인 순서는 [회사 적용과 운영](operations.md)을 봅니다. 비밀번호와 API 키는 쓰지 않고 관리 위치와 담당자를 적습니다.

개발 결과, 실제 회사 자료 적용, 공용 운영 확인은 각각 증거를 남깁니다. 부족한 부분은 다음 담당자와 해결 기한을 정합니다. 새 자료와 직원의 사용 의견이 들어오면 이 목록에서 다음 개발을 고릅니다.

코드를 합친다고 각자의 DB 데이터까지 합쳐지지는 않습니다. 같은 기능의 대표 구현을 고르고 DB 구조와 적용 이력을 함께 확인합니다. 자료 이관은 소유자·프로젝트 대응·중복 처리·담당을 따로 정한 범위만 진행합니다. 같은 서버에서 다른 브라우저로 저장을 확인한 결과와 다른 교육생의 서버를 합치는 작업을 구분하세요.
