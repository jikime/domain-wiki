# 기능 개발 예제

실제 화면에서 발견한 회사의 불편을 우선합니다. 아래 예제는 회사의 필요에 따라 고를 후보입니다. 현재 강의의 기본 과제와 선택 과제는 각 실습 워크북을 따릅니다. 현재 코드에서 이미 되는 기능을 조사한 뒤 작은 변경부터 시작하세요.

## 기존 기록 입력칸에 회사 예시 붙이기

**열 화면:** 실무 기록 → 새 실무 기록. 상황·판단과 이유·결과·추가 확인할 내용의 네 칸은 이미 있습니다. 입력칸 옆에 읽을 수 있는 회사 예시를 붙이는 것부터 시작합니다.

| 기존 입력칸 | 붙일 예시 · 가상 사례 |
| --- | --- |
| 상황 | A 현장 점검 중 이력 목록이 비어 보였습니다. |
| 판단과 이유 | 기록 누락으로 단정하기 전에 날짜 범위를 확인했습니다. |
| 결과 | 조회 기간을 바꾸자 해당 기록을 확인할 수 있었습니다. |
| 추가 확인할 내용 | 다른 사례에서도 날짜·사업 범위·공개 상태를 먼저 확인합니다. |

**먼저 계획 요청**

```text
실무 기록의 네 입력칸에 무엇을 써야 할지 직원이 어려워해.
현재 코드와 기존 기능을 조사하고 아래 변화의 계획부터 알려 줘.
원하는 변화: 각 칸 옆에 회사 예시를 붙이기. 입력값·초안·AI 정리·저장·검토는 유지해 줘.
저장할 정보·권한·유지할 동작·직접 확인할 순서를 설명해. DB 변경이 필요한지도 알려 줘.
코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것:** 원하는 동작·유지할 기능·저장 필요 여부·직접 확인할 입력을 설명해 보세요. 다른 점은 계획부터 고칩니다.

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 이번 변경을 구현해.
각 칸 옆에 회사 예시를 붙여 줘. 입력값·초안·AI 정리·저장·검토는 유지해 줘.
확인할 예: ‘판단과 이유’에는 날짜 범위를 먼저 확인한 행동과 그 이유를 함께 보여 줘.
필요한 DB 변경이 있다면 개발용 DB 적용과 저장·조회까지 연결하고 기존 데이터는 유지해. 실행한 검사·미확인 항목·내가 확인할 순서를 알려 줘.
```

**완료 확인:** 빈 화면과 작성 중인 화면에서 예시가 보이고, 기존 글이 보존되며 저장 후 다시 열 수 있습니다. 예시를 입력값으로 저장하지 않습니다. 직원의 필요가 확인된 경우에만 빈 칸에 예시를 넣는 동작을 후속으로 검토합니다.

AI가 조사할 위치: [실무 기록 화면](../../src/components/record-editor.tsx). 실제 연결은 현재 코드에서 다시 확인하며 기존 shadcn/ui 폼과 디자인 지침을 따릅니다.

## 검색 결과의 단위를 알기 쉽게 표시하기

**열 화면:** 자료실 → 공개 지식 검색. 공개 검색은 원문 문단과 게시 위키를 찾고, 자료 관리 목록은 문서 단위를 보여 줍니다. 캡처의 문서 6건·검색 결과 55개는 서로 다른 단위이며 현재 데이터에 따라 달라집니다.

**먼저 계획 요청**

```text
자료실의 검색 결과 수를 등록한 문서 수로 오해해.
현재 코드와 기존 기능을 조사하고 아래 변화의 계획부터 알려 줘.
원하는 변화: 실제 계산 단위를 조사해 결과 수 옆에 안내를 붙이기. 검색·필터·권한은 유지해 줘.
저장할 정보·권한·유지할 동작·직접 확인할 순서를 설명해. DB 변경이 필요한지도 알려 줘.
코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것:** 원하는 동작·유지할 기능·저장 필요 여부·직접 확인할 입력을 설명해 보세요. 다른 점은 계획부터 고칩니다.

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 이번 변경을 구현해.
실제 계산 단위를 조사해 결과 수 옆에 안내를 붙여 줘. 검색·필터·권한은 유지해 줘.
확인할 예: 공개 검색은 ‘문단·위키 기준’, 자료 관리는 ‘등록 자료 기준’으로 구분해.
필요한 DB 변경이 있다면 개발용 DB 적용과 저장·조회까지 연결하고 기존 데이터는 유지해. 실행한 검사·미확인 항목·내가 확인할 순서를 알려 줘.
```

**완료 확인:** 빈 검색·검색어 입력·자료 유형 변경에서도 안내와 실제 결과 단위가 맞습니다. 먼저 문구를 바꾸고, 여전히 찾기 어렵다면 결과 보기 전환이나 문서별 묶음을 후속으로 검토합니다. 자료별 묶음과 문단 탐색으로 이어 개발할 때는 [검색 고도화 실습](weeks/04-evaluation.md)의 범위·페이지 기준을 따릅니다.

## 이동할 때 도메인·프로젝트 선택 유지하기

**열 화면:** 자료실에서 범위 선택 → 상단 실무 기록 → 새 실무 기록. 앞 화면에서 고른 범위와 새 기록의 기본 범위가 같은지 확인합니다. 실제로 달라지는 경로를 작업 카드에 남기세요.

**먼저 계획 요청**

```text
자료실에서 선택한 사업이 새 실무 기록으로 이어지지 않아.
현재 코드와 기존 기능을 조사하고 아래 변화의 계획부터 알려 줘.
원하는 변화: 선택을 이어 주는 최소 변경을 구현하기. 직접 접속과 권한 검증은 유지해 줘.
저장할 정보·권한·유지할 동작·직접 확인할 순서를 설명해. DB 변경이 필요한지도 알려 줘.
코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것:** 원하는 동작·유지할 기능·저장 필요 여부·직접 확인할 입력을 설명해 보세요. 다른 점은 계획부터 고칩니다.

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 이번 변경을 구현해.
선택을 이어 주는 최소 변경을 구현해 줘. 직접 접속과 권한 검증은 유지해 줘.
확인할 예: 교육 도메인·A 선택 → 기록에도 같은 범위. 없는 ID는 허용된 기본값으로 처리해.
필요한 DB 변경이 있다면 개발용 DB 적용과 저장·조회까지 연결하고 기존 데이터는 유지해. 실행한 검사·미확인 항목·내가 확인할 순서를 알려 줘.
```

**완료 확인:** 정상 이동·직접 접속·다른 도메인으로 변경·잘못된 값에서 일관되게 동작합니다. 작성 중인 글과 기존 초안을 자동으로 덮어쓰지 않도록 확인합니다.

## RFP의 확인 질문 누락 표시하기

**열 화면:** 업무 도구 → RFP 분석 보고서 → 새 분석 작성. 유형·근거·확인 질문 입력칸은 이미 있습니다. 누락 개수를 표시하는 기능은 개발 후보입니다.

처음 쓰는 팀은 아래 두 항목으로 기존 화면부터 익힙니다. 공개된 **프로젝트 A 사업 개요**를 연습 원문으로 고르고 직접 작성·수정에서 입력합니다. 이는 기능 체험용이며 새 업무 적용에 사용할 신규 요청 문서는 따로 둡니다.

| 항목 | 구분 | 원문·근거 | 확인 질문 |
| --- | --- | --- | --- |
| 도로전광표지 24대 | RFP 명시 요구 | 사업 개요의 실제 수량 문장·문단 선택 | 해당 수량은 원문에서 확인 |
| 최종 검수표 확인 | 불명확 | 최종 사업 종료일과 상세 검수표가 정해지지 않았다는 문장 | 누락 표시 관찰 때는 빈칸, 저장 전에는 ‘상세 검수표는 언제 확정되나요?’ 입력 |

유형·제목·의미·적용 범위·원문 구절·근거를 채우고 질문을 넣거나 지워 보세요. 필요한 질문을 채운 뒤 저장·다시 열기를 확인합니다. AI 초안은 연결이 준비됐을 때 별도로 확인하며 직접 작성 성공을 AI 성공으로 보지 않습니다.

**먼저 계획 요청**

```text
RFP의 추론·불명확 항목에서 확인 질문을 빠뜨려.
현재 코드와 기존 기능을 조사하고 아래 변화의 계획부터 알려 줘.
원하는 변화: 질문이 없거나 공백뿐인 항목 수를 표시하기. 다른 유형은 제외하고 기존 저장 검증은 유지해 줘.
저장할 정보·권한·유지할 동작·직접 확인할 순서를 설명해. DB 변경이 필요한지도 알려 줘.
코드와 DB는 아직 바꾸지 마. 내가 확인한 뒤 실행을 요청할게.
```

**내가 확인할 것:** 원하는 동작·유지할 기능·저장 필요 여부·직접 확인할 입력을 설명해 보세요. 다른 점은 계획부터 고칩니다.

**계획을 확인한 뒤 실행**

```text
확인한 계획대로 이번 변경을 구현해.
질문이 없거나 공백뿐인 항목 수를 표시해 줘. 다른 유형은 제외하고 기존 저장 검증은 유지해 줘.
확인할 예: 불명확 항목의 빈 질문 1개 → 질문 입력 후 0개 → 삭제하면 1개야.
필요한 DB 변경이 있다면 개발용 DB 적용과 저장·조회까지 연결하고 기존 데이터는 유지해. 실행한 검사·미확인 항목·내가 확인할 순서를 알려 줘.
```

| 입력·조작 | 기대 결과 |
| --- | --- |
| 추론·불명확 항목의 빈 질문 또는 공백만 입력 | 누락 1개 |
| 실제 질문 입력 / 다시 삭제 | 0개 / 1개 |
| 유형을 명시 요구·기준·사례로 변경 | 누락에서 제외 |
| 항목 추가·삭제·다시 열기 | 현재 값에 맞는 개수 |

AI가 조사할 위치: [RFP 화면](../../src/components/rfp-editor.tsx). 개수 표시는 저장 조건 전체를 판단하지 않습니다. 누락 항목으로 이동하는 동작은 실제 필요에 따라 이어 만듭니다.

## 다른 후보가 필요한 경우

- **용어 입력:** 동의어의 쉼표·전각 쉼표·세미콜론을 구분하고 공백·중복을 정리합니다. 기존 길이 2–80자·최대 10개·저장·권한 규칙을 지킵니다. `VMS; 전광표지， VMS`는 두 항목이어야 합니다.
- **메모 길이:** 현재 길이와 기존 12,000 제한을 표시합니다. 빈칸은 0, `현장 점검`은 5이며 기존 제한과 같은 계산 기준을 씁니다. 입력·삭제·다시 열기와 AI 정리를 확인합니다.

동의어 [검사기](exercises/check-aliases.mjs)를 쓴다면 실제 함수를 `src/lib/term-aliases.ts`에 두고 폼에 연결합니다. 참고 답안만 검사하지 않습니다. 어떤 후보든 [요청 순서](prompt-practice.md)로 계획을 합의하고 [작업 카드](company-project.md)에 결과를 이어 씁니다.
