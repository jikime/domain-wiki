# 실습·개발·평가 기록 양식

필요한 양식을 복사해 개인이나 팀의 작업 문서에 붙여 넣습니다. 어떤 업무를 해결하려 했는지, AI에게 무엇을 요청했고 어떻게 판단했는지, 화면에서 어떤 결과를 확인했는지 적습니다. 코드 위치와 검사 명령, 변경 내역은 AI가 정리한 내용을 붙입니다. 코드 작성·문법 해설은 기록 항목에 포함하지 않습니다. 빈칸은 실습 결과를 적기 위한 항목입니다. 계정 비밀번호·API 키·승인되지 않은 회사 자료는 기록하지 않습니다.

## T0. 내 PC 업무환경 기록표

1단계 수업에서 설치·실행한 결과를 기록하고 이후 수업에서도 같은 환경을 찾는 데 사용합니다. 각 항목은 ‘완료·미완료·해당 없음·원격 대체’와 실제 확인 결과를 함께 적습니다. 명령을 외워서 쓰는 양식이 아니며, 기술 위치·실행 순서는 AI·강사의 도움을 받아 기록합니다.

| 항목 | 내 환경과 실제 확인 결과 |
| --- | --- |
| 교육생 | |
| 내 PC 또는 원격 대체 여부 | |

| 디자인 하네스 버전·스킬·에이전트 인식 | |
| CLAUDE.md의 AGENTS.md·hince 문서 참조 | |
| 내 domain-wiki 프로젝트 폴더·편집기 | |

| 작성·검토·이용 계정의 역할 확인 | |
| DB·웹 서버·작업자 실행 확인 | |
| 서비스 AI 연결·모델·실제 응답 여부 | |

| 다시 사용할 때의 실행 순서·종료 방법 | |
| 내 업무에 적용할 주제·T1 카드 위치 | |
| 미완료 항목·지원 담당·다음 확인 방법 | |

비밀번호·API 키·토큰·비밀 값이 포함된 DB 접속 문자열은 적지 않습니다. 원격 환경 사용을 내 PC 설치 완료로 표시하지 않으며, 브라우저 재접속·서버 실행·AI 응답은 각각 확인한 범위만 기록합니다.

| 실제로 발생한 결과 | |

## T2. 업무 동작과 기술·구조의 연결

| 사용자 동작 | 화면·서버·작업자 중 담당 부분 | 사용하는 기술과 목적 | 저장·근거·후속 작업 | AI가 안내한 관련 위치 | 내가 확인한 화면·상태 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

전체 코드와 요청 전문을 직접 분석할 필요는 없습니다. AI에게 실제 위치와 역할을 설명받고, 교육생은 그 흐름이 사용한 화면·처리 상태와 어떻게 연결되는지 적습니다.

## T3. AI 개발 요청

처음에는 [세 줄 요청](prompt-practice.md#2-처음에는-세-줄로-시작하기)으로 시작합니다. 아래 상세 틀은 실제 화면·코드 변경을 요청할 때 필요한 항목을 채워 사용합니다. 구조 설명이나 위키 작성 기준 제안도 같은 기록표에 남길 수 있습니다.

```text
현재 상황:
재현 입력과 실제 결과:
기대 결과와 완료 기준:
사용한 화면과 업무 상황:
알고 있는 관련 위치(모르면 AI가 확인):
변경 가능한 범위:
유지할 동작과 제약:
확인할 정상·실패 입력:

현재 프로젝트를 확인해 재사용할 기능과 최소 변경 계획을 설명해 주세요.
파일 조사·코드 수정·필요한 기술 검사는 AI가 수행해 주세요.
제가 계획을 확인하고 구현을 요청하면 변경 파일의 역할과 검사 결과를 정리해 주세요.
제가 화면에서 확인할 입력과 기대 결과도 알려 주세요.
확인하지 못한 결과는 미확인으로 표시해 주세요.
```

교육생은 계획이 업무 의도와 맞는지 확인한 뒤 구현을 요청합니다. 넓은 재설계가 나오면 완료 기준으로 범위를 다시 좁힙니다. 결과가 다르면 실제 입력·기대 결과·실제 결과를 추가해 보완을 요청합니다. 기술 문법이나 함수 이름을 몰라도 요청할 수 있습니다.

### 프롬프트 작성·실행 기록

각 단계에서 대표 실습을 한 번 골라, 그때 보낸 첫 요청과 후속 요청을 기록합니다. 요청 원문은 대화 위치로 연결해도 됩니다. 교육생마다 본인이 쓴 문장 한 곳과 직접 확인한 결과를 남깁니다.

| 기록할 것 | 첫 요청 | 수정·후속 요청 |
| --- | --- | --- |
| 작성자·단계·실습 | | |
| 입력 위치·대상 프로젝트 또는 자료 | | |
| 내가 작성해 전송한 요청문 | | |
| 전송·응답 확인 여부, 응답 위치 또는 일부 | | |
| 기대 기준과 실제 확인 결과 | | |
| 추가·수정한 조건과 그 이유 | 처음 요청의 목표 | |
| 남은 문제 또는 새로 확인한 조건 | | |

응답이 없으면 로그인·연결·처리 상태를 기록하고 성공으로 표시하지 않습니다. 처음부터 맞은 답을 틀렸다고 기록할 필요는 없습니다. 예시·출력 형식·다른 입력 확인을 추가한 이유를 적으면 됩니다. 실제 화면·원문·설정의 비교는 T5로 연결합니다.

## T4. 업무 근거·AI 설명 확인

| 확인할 문제 | 업무 원문 또는 AI 설명의 출처 | 원문 버전·AI가 확인한 기술 기준 | 우리 상황에 적용되는 조건 | 내가 확인한 사실·역할 | 남은 질문 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

업무 사실은 교육생이 실제 원문을 열어 확인합니다. 기술 문서·설치 버전·현재 구현 조사는 AI·강사가 담당하고, 교육생은 기술의 용도와 변경 영향을 설명받습니다. 기술 예제를 직접 구현하는 활동은 두지 않습니다.

## T7. 평가 결과표

| 질문 ID | 질문 범위·버전 | 기대 근거 검색 여부 | 실제 답변 요약 | 근거·범위 점수 0–2 | 실패 유형 | 다음 조치 |
| --- | --- | --- | --- | ---: | --- | --- |
| | | | | | | |

2점은 필요한 사실·근거·적용 범위를 모두 확인한 경우, 1점은 일부 누락 또는 불명확한 경우, 0점은 잘못된 사실·범위 또는 근거 없는 단정입니다. 답이 없는 질문은 근거 부족을 설명하고 확인 질문을 남기면 2점입니다. 검색 성공률과 답변 점수는 별도로 집계합니다.

AI에게 코드 위치와 커밋, 실행하고 복구하는 방법을 정리해 달라고 요청합니다. 교육생은 결과가 있는 위치와 업무에서 확인할 방법을 살펴봅니다. 위치와 담당자를 적고 비밀 값은 적지 않습니다. 원본 저장소 주소와 본인 결과의 보관 위치를 구분하고, 원격에 제출하지 않았다면 ‘로컬 보관’으로 표시합니다. 실행 절차는 [Git에서 받기·첫 실행](getting-started.md)을 기준으로 실제 환경의 차이를 보완합니다. 코드 커밋만으로 DB와 원본 파일이 복구되는 것은 아닙니다.
