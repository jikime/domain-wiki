# 실습·개발·평가 기록 양식

각 양식을 복사해 교육생 또는 팀의 작업 문서에 사용합니다. 빈칸은 실습 결과를 적기 위한 항목입니다. 계정 비밀번호·API 키·승인되지 않은 회사 자료는 기록하지 않습니다.

## T1. 업무 문제 카드

| 항목 | 작성 내용 |
| --- | --- |
| 작성자·날짜·주차 | |
| 업무 상황과 대상 사용자 | |
| 현재 입력과 화면 | |
| 실제로 발생한 결과 | |
| 기대하는 결과 | |
| 업무에 주는 영향 | |
| 원문·화면·오류 등 확인한 근거 | |
| 이번 실습의 완료 기준 | |
| 이번 범위에 넣지 않을 일 | |

예: ‘검색을 좋게 한다’ 대신 ‘교육용 도메인에서 VMS와 전광표지를 동의어로 등록할 때 세미콜론으로 구분해도 두 항목으로 저장되고 기존 쉼표 입력이 유지된다’라고 작성합니다.

## T2. 화면과 코드의 연결

| 사용자 동작 | 화면 파일·구성요소 | API 요청 | 서버 함수·검증 | 저장·후속 작업 | 확인한 증거 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

API 경로는 개발자 도구에서 확인하되 인증 쿠키와 요청 헤더 전문을 공유하지 않습니다. 값이 이동하는 순서와 필요한 검증을 설명합니다.

## T3. AI 개발 요청

```text
현재 상황:
재현 입력과 실제 결과:
기대 결과와 완료 기준:
관련 화면·파일·함수:
현재 코드·설치 버전에서 확인한 내용:
변경 가능한 범위:
유지할 동작과 제약:
확인할 정상·실패 입력:

먼저 원인 후보와 확인할 코드, 최소 변경 계획을 설명해 주세요.
계획에 따라 변경한 뒤 변경 파일과 검증 결과를 정리해 주세요.
확인하지 못한 결과는 미확인으로 표시해 주세요.
```

교육생은 계획을 읽고 의도한 범위인지 확인합니다. 넓은 재설계가 나오면 해당 실습의 완료 기준으로 다시 좁힙니다.

## T4. 자료·기술 문서 확인

| 찾으려는 문제 | 자료 제목·주소·위치 | 발행·수정 시점 또는 설치 버전 | 우리 상황에 적용되는 조건 | 원문에서 확인한 사실 | 작은 적용 결과 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

AI가 제시한 주소는 직접 열어 봅니다. 업무 지식은 공식 자료·검토된 내부 원문을 확인하고, 코드 지식은 현재 버전에 맞는 공식 문서와 실제 구현을 함께 확인합니다.

조건이 다르면 그 차이를 먼저 적습니다. 자료 개정이나 API·CLI 전환 효과를 코드 개선 효과로 기록하지 않습니다. 계정명·인증 토큰·API 키는 비교표에 적지 않습니다.

실패한 가설도 남깁니다. ‘재시작해서 해결’로 끝내지 않고 어떤 프로세스가 어떤 설정을 다시 읽었는지 적습니다.

## T7. 평가 결과표

| 질문 ID | 질문 범위·버전 | 기대 근거 검색 여부 | 실제 답변 요약 | 근거·범위 점수 0–2 | 실패 유형 | 다음 조치 |
| --- | --- | --- | --- | ---: | --- | --- |
| | | | | | | |

2점은 필요한 사실·근거·적용 범위를 모두 확인한 경우, 1점은 일부 누락 또는 불명확한 경우, 0점은 잘못된 사실·범위 또는 근거 없는 단정입니다. 답이 없는 질문은 근거 부족을 설명하고 확인 질문을 남기면 2점입니다. 검색 성공률과 답변 점수는 별도로 집계합니다.

## T8. 후속 개발 과제

| 우선순위 | 업무 문제·사용자 | 변경 후보 | 완료 기준 | 담당자 | 확인할 자료·의존 조건 | 다음 검토일 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

다음 검토일은 실제 담당자와 합의한 날짜를 적습니다. 교육 후 지원이 자동 제공되는 일정으로 표시하지 않습니다.
