# 회사 위키 개발 강의의 기본 구성 원칙

교육생은 각자의 환경에서 스타터킷을 회사 업무에 맞게 직접 수정하고, 강사의 코칭을 받으며 자신의 위키를 발전시킨다. 실습 결과는 본인이 직접 실행해 판단한다. 이후 각자가 만든 결과를 하나의 회사 위키로 합쳐 계속 운영하는 것이 과정의 목표다. 강의자료는 설명할 순서와 교육생이 할 일을 함께 보여 준다. 모든 차수의 슬라이드를 만들고 검토할 때 이 원칙을 적용한다.

## 개별 개발과 직접 확인

실습은 **현재 화면 확인 → 계획 요청 → 내가 확인·수정 → 실행 요청 → 직접 확인·보완**을 반복하고, 이후 각자의 결과를 회사 위키로 통합하는 흐름이다. 실습 중 동료의 사용이나 승인을 완료 조건으로 두지 않는다. 강사는 작업의 범위를 좁히고, 막힌 부분과 판단하기 어려운 변경을 코칭한다.

교육생은 회사 업무의 불편, 원하는 변화, 유지할 조건과 완료 기준을 정한다. 코드 조사·수정·필요한 기술 검사는 AI가 수행한다. 교육생에게 파일을 열어 코드를 대조하거나 경로를 설명하도록 요구하지 않는다. 필요한 때 코드 설명을 함께 볼 수 있지만, 코드 독해를 실습의 완료 조건으로 삼지 않는다.

AI에는 실행한 검사와 결과, 실행하지 못한 부분을 남기게 한다. 교육생은 화면에서 실제 업무를 수행해 기대 결과와 비교한다. 저장·권한·데이터 구조처럼 판단하기 어려운 변경은 강사와 기술 검토를 진행한다.

스스로 확인할 때는 수정 전에 정한 목표와 실제 결과를 비교한다. 문구 변경이라면 의도한 문구가 보이는지, 링크 변경이라면 직접 눌렀을 때 예상한 곳으로 이동하는지 확인한다. AI의 완료 보고만으로 판단하지 않고 교육생이 직접 화면을 조작한다.

나중에 작업을 합칠 수 있도록 바꾼 내용·확인 결과·남은 일을 기록한다. 개별 결과가 동작하는지 확인하는 실습과 여러 사람의 작업을 통합하는 작업은 별도 단계로 다룬다. 통합할 범위와 방법은 해당 단계에서 강사의 코칭을 받으며 정한다.

## 한 장에서 전할 핵심

한 장마다 꼭 전할 말을 한 문장으로 정한다. 제목과 화면을 보고 그 뜻을 이해할 수 있어야 한다. 도입에서는 만들 결과를, 실제 화면에서는 논의할 문제를, 실습에서는 수행할 작업을 중심에 둔다.

슬라이드를 설명한 뒤 교육생에게 무엇이 남아야 하는지도 정한다. ‘어느 화면을 왜 바꿀지 안다’, ‘입력할 곳을 찾는다’, ‘직접 조작해 결과를 확인한다’처럼 이해하거나 수행할 행동으로 적는다.

## 교육생이 할 일을 쉬운 말로 쓰기

문장을 읽으면 무엇을 만들고 어디를 눌러 볼지 알 수 있게 쓴다. ‘꺼내 쓰기’는 ‘저장한 조건으로 다시 검색하기’나 ‘즐겨찾기에서 자료 열기’로, ‘업무 규칙’은 ‘홈에 고정하기’나 ‘안 읽은 자료만 보기’로 풀어 쓴다. ‘상태 유지’처럼 줄이지 말고 그대로 남아야 할 검색어·프로젝트·페이지를 적는다.

2회차는 검색 조건 저장·즐겨찾기·즐겨찾기 폴더·내 메모·읽음 표시를 구분한다. 검색은 조건을, 즐겨찾기는 자료 링크를 저장한다. 즐겨찾기 폴더는 즐겨찾기를 업무별로 나눈다. 기능 선택 A/B는 사용하지 않으며, 예제 프로젝트는 항상 ‘프로젝트 A’처럼 부른다.

실제 화면의 ‘도메인’, ‘원문’, ‘버전’ 같은 이름은 유지하되 처음 나올 때 필요한 뜻을 짧게 설명한다. 도메인은 회사의 업무 분야, 원문은 등록한 원래 자료, 버전은 문서를 수정해 보관한 차례다. ‘조건을 해제한다’는 ‘선택한 검색 조건 하나를 지운다’로 풀고, 자료 삭제와 즐겨찾기에서 빼기를 구분한다.

쉬운 말로 바꿔도 해야 할 기능과 완료 기준을 줄이지 않는다. 교육생 안내는 존댓말로 쓰고 Claude Code에 넣을 요청은 반말 지시형을 유지한다. 강사는 실제 화면과 예시를 짚으며 같은 표현으로 설명한다.

## 말할 순서를 화면에 배치하기

설명에 필요한 핵심 단어를 말할 순서대로 배치한다. 도입과 정리에는 큰 단어 세 개를 기본으로 삼고, 각 단어 아래에 구체적인 행동을 짧게 붙인다. 강사는 단어를 보며 자신의 말로 설명한다.

2회차 도입은 하루의 완성 모습을 보여 주고, 찾기·모으기·읽고 메모·홈 연결의 네 교시를 안내한 뒤 사용할 업무와 자료를 정하는 순서다. 첫 장은 전체 차수를 대표하므로 교시와 같은 네 항목으로 구성한다. 제목·키워드는 교육생 화면의 표현과 맞춘다. 준비 요청은 기존 기능이 있는지 확인하는 용도로만 사용한다.

장마다 같은 세 단어를 반복하지 않는다. 실제 화면은 짚어볼 위치와 질문 하나, 요청 예시는 입력할 곳과 요청문, 작업 화면은 순서와 완료 기준이 잘 보이도록 구성한다.

## 화면별 역할

| 화면 | 먼저 보일 내용 | 교육생에게 남길 것 |
| --- | --- | --- |
| 도입 | 핵심 한 문장과 진행 순서 | 무엇을 왜 만드는지 이해 |
| 실제 화면과 논의 | 실제 캡처, 짚어볼 위치, 질문 | 현재의 불편과 바꿀 목표 선택 |
| 요청 예시 | 입력할 곳, 자연스러운 요청문, 원하는 변화·유지할 조건·완료 기준 | 자기 작업에 맞춘 요청 |
| 직접 작업 | 작업 순서, 완료 기준, 워크북 연결 | 직접 구현하고 조작한 결과 |
| 확인과 정리 | 처음의 불편, 변경 결과, 이어 할 일 | 확인한 상태와 다음 작업 기록 |

실제 제품 화면은 로그인해 확인한 캡처를 사용한다. 현재 상태와 앞으로 개발할 목표를 구분하고, 예시의 명칭과 입력은 실제 화면에서 찾을 수 있게 한다.

화면의 역할에 따라 배치를 고른다. 도입·정리에는 중앙에 핵심과 키워드를 모으고, 개발 목표는 현재 화면과 목표 예시를 같은 크기로 비교한다. 실제 화면을 논의할 때는 캡처와 짚어볼 위치를 크게 보여 주고, 작업 중에는 순서와 완료 기준을 함께 띄운다.

2회차 첫 장은 현재 홈 카드와 즐겨찾기 폴더·메모·읽음 개수가 있는 완성 예시를 좌우로 비교한다. 아래 네 칸은 네 교시와 일치한다. 2장은 앞 교시의 결과가 다음 교시의 입력이 되는 순서를, 3장은 사용할 업무·자료와 개발 환경을 보여 준다. 목표에는 ‘이번에 만들 화면 · 예시’와 ‘앞으로 만들 모습입니다’를 표시한다. 도식을 실제 캡처처럼 소개하지 않는다. 16:9 화면을 기준으로 글·이미지·간격이 함께 커지도록 하며, 한 장씩 볼 때는 상단 탐색을 접는다.

## AI에게 요청하는 방법

클로드 코드에 입력하는 프롬프트는 “바꿔 줘”, “확인해”, “알려 줘”처럼 짧은 반말 지시형으로 쓴다. 상황 설명도 “불편해”, “확인했어”처럼 같은 톤으로 맞춘다. 교육생에게 설명하는 슬라이드·워크북 안내와 강사의 말은 존댓말을 유지한다.

요청은 현재 불편·원하는 변화·유지할 조건·완료 기준을 중심으로 정리한다. 이 네 가지는 빠진 내용을 생각할 질문이며, 매번 채워야 하는 고정 양식이 아니다. 화면 캡처와 예시는 도움이 될 때 붙이고, 답변 형식도 필요한 경우에만 지정한다. 답변의 모양과 개발의 완료 기준을 구분한다.

새 기능과 저장·권한 변경은 먼저 계획만 요청하고 교육생이 확인한 뒤 실행한다. 계획 요청에 코드와 DB를 아직 바꾸지 말고 확인을 기다리라고 명시한다. 작은 변경은 짧은 계획으로 확인하고, 이미 합의한 범위를 이어갈 때 계획 전체를 다시 작성하지 않는다. 프로젝트를 여는 방법과 공통 작업 규칙은 미리 준비해 두고, 교육생이 매 요청마다 기술 지침을 반복 작성하게 하지 않는다.

첫 실습에서는 작은 변경을 화면에서 확인하는 경험까지 이어 간다. 이후 예상과 다른 결과를 보완하고, 실제 업무에서 남은 불편을 골라 다음 변경을 만든다. 같은 작은 변경을 찾기·계획·수정·확인으로 나누어 네 교시에 걸쳐 진행하지 않는다.

## 강사용 메모

강사용 메모는 교육생에게 보이는 슬라이드와 같은 순서로 쓴다. 앞부분에는 다음 내용만 짧게 둔다.

- **꼭 전할 말:** 이 장의 핵심 한 문장
- **시작할 말:** 설명을 꺼낼 짧은 문장
- **설명 순서:** 화면의 핵심 단어와 단어별 한 문장
- **사례 하나:** 지금 보고 있는 위키에서 찾을 수 있는 예
- **마무리할 말:** 다음 설명이나 작업으로 연결하는 문장
- **전환 시점:** 설명을 마치고 다음 화면이나 직접 작업으로 넘어갈 기준

추가 설명은 ‘시간이 남으면’에 둔다. 이야기가 길어지면 핵심 단어와 꼭 전할 말로 돌아온다. 문장을 그대로 외울 필요는 없으며 막히면 메모를 읽어도 된다. 강사의 설명 시간과 전환 판단을 적은 메모는 공개 워크북·강의 HTML·다운로드에 포함하지 않는다. 교육생 화면과 워크북에는 고정 시간표를 넣지 않는다. 강사는 설명·개발·확인에 쓸 시간을 진행 상황에 맞춰 조절한다.

## 가치 있는 실습과 진행 속도

교육생 화면에는 ‘설명 10분 · 실습 35분 · 확인 5분’, 교시별 분량, 남은 시간이나 총 실습 시간 같은 고정 배분을 표시하지 않는다. 교시 번호와 현재 할 일, 완료 기준을 안내한다. 시간 운영은 강사가 교육생의 준비·개발·확인 상태와 휴식을 함께 고려해 조절한다. 요청문 하나와 일정 시간을 일대일로 묶지 않는다.

실습은 **짧은 시작 → 기본 기능 완성 → 내 업무에 적용 → 선택 도전**으로 설계한다. 시작 과제는 화면이 바뀌는 경험을 주며, 기본 과제는 회사 업무에 쓸 작은 결과를 남겨야 한다. 바꿀 내용과 확인 기준은 교육생이 정하고 AI가 구현·검사를 맡는다. 같은 문구 변경을 여러 교시에 걸쳐 반복하지 않는다.

기본을 마친 교육생에게는 실제 업무에서 이어지는 선택 과제 두세 개를 보여 준다. 기능 추가만 요구하지 않고 다른 입력·범위에서 확인하며 필요한 안내를 보완하는 작업도 포함한다. 선택 과제는 모두 수행할 숙제가 아니다. 막힌 교육생은 작은 동작 하나로 범위를 좁히고 강사의 코칭을 받아 완성한다. 오류가 생겨야만 진행할 수 있는 실습을 만들지 않는다.

2회차는 업무별 검색과 조건 저장 → 즐겨찾기와 폴더 → 내 메모와 읽음 관리 → 홈의 폴더·개수·원문 연결을 DB 저장까지 이어 개발한다. 일괄 읽음 변경과 홈 고정은 기본 연결 뒤 선택 과제다. 각 교시에는 서로 다른 세 동작과 선택 과제를 두고, 앞에서 만든 자료와 코드를 계속 사용한다. 기능 수나 요청 개수로 실습 시간을 보장하지 않는다. AI가 한 번에 끝낸 기능은 반복하지 않고, 먼저 마친 교육생에게는 같은 기능에 더할 과제를 준다. 기록이나 대기만으로 교시를 채우지 않는다.

기능 묶음에는 업무 상황·완성 모습·개발 순서·유지할 조건·완료 기준을 둔다. 기존 검색·필터·공개 규칙을 활용하고 실제로 부족한 동작을 더한다. 강사의 시간 운영 기준과 실습 리허설 결과는 별도로 관리한다. 약속한 시간을 채우기 위해 AI 대기나 오류를 기대하지 않는다.

설명은 교육생이 작업을 시작할 수 있는 지점에서 마친다. 실습 화면에는 순서·기본 완료 기준·선택 과제를 함께 두고, 작업하는 동안 띄워 둔다. 강사는 공통 문제가 있을 때만 짧게 설명하고 개별 코칭을 이어간다. 대표 과제는 수업 전에 직접 진행해 난이도를 조정하며, 실제 소요 시간을 교육생 모두에게 보장하지 않는다.

워크북은 실행 순서·한 번에 입력할 요청 예시·확인 기준·선택 과제를 같은 원고에서 제공한다. 시작 실습·첫 동작·후속 개발의 요청은 서로 다른 작업임을 구분한다. 각 요청 상자는 한 번에 입력하되 계획과 실행을 함께 보내지 않는다. 계획을 확인·수정한 뒤 실행하고 직접 확인한 다음 후속 기능의 계획으로 이어간다. 슬라이드를 보지 않고 읽어도 시작할 위치와 순서를 알 수 있어야 한다. 자료를 읽거나 기록을 작성하는 시간이 실제 개발과 사용을 대신하지 않게 한다.

## 설명 연습

슬라이드 한 장을 보고 핵심 단어 순서대로 짧게 말해 본다. 꼭 전할 말이 들어갔는지 확인하고, 마지막에 교육생이 무엇을 이해하거나 할지 연결한다. 막힌 부분은 단어의 순서나 강사용 메모를 고친 뒤 다시 설명한다.

## 전체 차수와 장별 검토 순서

1. 하루의 완성 결과와 네 교시의 필수 개발 과제를 먼저 정한다.
2. 앞 교시의 결과가 다음 교시의 입력으로 쓰이는지 확인한다. 같은 작업의 설명·확인만으로 한 교시를 만들지 않는다.
3. 도입 1–3장·교시별 목표·계획·확인 후 실행·직접 작업·마지막 정리를 같은 흐름으로 맞춘다.
4. 워크북의 다음 요청·확인 절차와 비공개 강사 노트를 함께 갱신한다.
5. 전체 흐름을 확인한 뒤 필요한 장을 자세히 다듬는다. 파일 반영과 사용자의 확인 완료는 구분한다.

전체 회차의 흐름을 함께 구성한다. 개발 교시는 현재 화면·계획·실행·직접 작업의 네 장이며 장수를 16장으로 고정하지 않는다. 이후 개별 장을 수정할 때에도 앞뒤 과제와 시간 운영에 미치는 영향을 확인한다. 교시별 개발 분량은 기능 수·요청 수로 보장하지 않고 별도 리허설과 실제 진행으로 조정한다.

## 장별 확인 질문

1. 이 장에서 꼭 전할 말이 하나로 잡히는가?
2. 화면을 보면 설명할 순서가 떠오르는가?
3. 설명을 마치면 교육생이 무엇을 이해하거나 해야 하는지 분명한가?

강사 노트는 공통 원고로부터 모든 회차를 생성하며 교육생에게 공개하지 않는다. [강사용 진행 안내](../training/instructor/lecture-guide.md)에서 회차별 노트를 연다.

## 기능 설명과 직접 확인 절차 연결하기

기능마다 저장할 대상, 누를 버튼, 화면의 결과를 구분한다. 원문 문서 제목과 사용자가 적는 ‘내 메모’를 섞지 않는다. 읽음 표시는 누가 무엇을 읽었는지와 직접 바꾸는 방법을 설명한다. 설명용 문서 이름은 실제 샘플 자료와 연결해 찾을 수 있게 한다.

워크북에는 AI에 보낼 개발 요청과 만든 뒤 사람이 눌러 볼 절차를 나누어 둔다. `practice.walkthroughs`의 시작 조건·순서·주의점을 공통 생성기가 내보낸다. 같은 예시를 반복해 길게 설명하기보다 해당 단계에서 직접 확인할 절차를 제공한다. 원문을 열고 목록으로 돌아오는 확인과 새로고침 후 저장 내용이 남는지 확인하는 절차를 분리한다.


## 기존 기능과 개발 목표의 이름 구분

기존 ‘자료 모아보기’는 자료실로 이동하는 카드다. 새로 만들 즐겨찾기와 즐겨찾기 폴더를 기존 메뉴처럼 설명하지 않는다. 폴더는 즐겨찾기를 업무별로 나누며 원본 파일을 옮기지 않는다. 첫 장에서 기존 화면과 앞으로 만들 동작을 구분한다.

버튼을 설명할 때는 실제로 열리는 다음 화면을 적는다. 폴더 이름과 안 읽음 개수는 각각 자료 목록을 열고, 그 목록에서 자료 제목을 눌러 원문을 연다. 수동 읽음 표시를 ‘읽으면 자동 반영’이라고 줄이지 않는다. 고정 해제·폴더 삭제·즐겨찾기에서 빼기·원문 삭제의 차이를 유지한다. 자료 예시는 실제 샘플 제목과 본문에 있는 내용으로 쓴다.


## 개발 요청의 조건을 쉽게 쓰기

‘기존 링크·버전·열람 권한 유지’처럼 명사를 나열하는 대신, 자료 제목을 눌렀을 때 무엇이 열려야 하는지와 누가 볼 수 있는지를 쓴다. ‘다시 열어도 남게’는 새로고침·같은 브라우저 재접속처럼 확인할 행동으로 풀어 쓴다. ‘만들고 검사해’에는 검사할 동작과 교육생에게 안내할 확인 순서를 붙인다. 설명을 줄이면서 기존 동작의 조건까지 지우지 않는다. 별도 문단과 오른쪽 안내로 구분해도 복사할 요청에는 필요한 조건을 남기고 한 번에 입력하게 한다.


## 계획을 읽고 교육생이 판단할 것

원하는 동작인지, 무엇을 누구의 기록으로 저장할지, 누가 보고 바꿀 수 있는지, 기존 기능 중 무엇을 유지할지, 어떤 조작으로 확인할지 설명하게 한다. 이름만 바꿔 복사하는 활동에 머물지 않는다. 결정과 다른 점은 계획을 고친 뒤 실행 요청을 보낸다. 계획·실행을 별도 장과 별도 요청 상자로 보여 준다.

자료 등록·위키 채팅·환경 준비·운영 기록에는 개발 계획을 억지로 붙이지 않는다. 내 기록 문서, 터미널, 위키 채팅, Claude Code 중 수행할 곳을 구분한다. 계획과 실행 장이 늘어도 설명 시간을 늘리지 않고 판단할 핵심만 짚은 뒤 직접 작업한다.

## DB 저장과 실제 적용

2회차부터 검색 조건·즐겨찾기·폴더·내 메모·수동 읽음 등 지속적으로 사용할 개인 기록은 서버 DB에 저장한다. 로그인 사용자·작업공간·도메인과 자료 열람 권한은 서버에서 확인한다. 홈 개수는 기록으로 계산하고, 일시적인 검색 페이지나 미리보기까지 모두 새 테이블에 저장하지 않는다.

새 기능마다 새 테이블을 지시하지 않는다. 기존 구조를 활용할지, 필요한 항목·테이블 변경이 있는지 AI가 조사한다. 구조 변경 파일 작성, 실제 개발용 DB 적용, 화면·서버의 저장·조회·수정·삭제 연결을 각각 확인한다. 기존 데이터와 이미 적용된 DB 변경 이력은 유지한다.

새로고침은 DB 저장의 충분한 증거가 아니다. 같은 위키 서버 주소에 다른 브라우저로 같은 계정으로 로그인하고, 다른 계정에서는 개인 기록을 보거나 고칠 수 없는지 확인한다. 서로 다른 교육생의 개인 서버는 자동으로 연결되지 않는다. 교육생에게 SQL이나 코드 독해를 요구하지 않고 무엇이 누구의 기록으로 남는지 판단하게 한다.

## 회차가 진행될수록 발전시킬 결과

| 회차 | 누적할 결과 |
| --- | --- |
| 1 | 기존 업무 흐름·개발 환경·계획을 확인한 첫 변경 |
| 2 | DB에 저장되는 개인 검색·즐겨찾기·메모와 홈 연결 |
| 3 | 회사 자료와 기록의 작성·저장 전 확인·다시 찾기 |
| 4 | 자료별 검색 묶음·문단 탐색·회사 용어 입력과 검색 안내 |
| 5 | 남은 연결·역할별 검증·코드와 DB 통합·공용 반영 준비 |
| 6 | 실패와 재시도·자료 개정·저장 갱신·운영 안내 |
| 7 | 새 업무 검증·필수 보완·운영 인계·후속 개발 |

동의어 검색, 실무 기록의 네 입력칸·초안·AI 정리·저장, 자료와 위키의 별도 검토는 기존 기능이다. 현재 코드를 조사하고 이미 있는 부분은 재사용한다. 새 과제는 기존 기능에 더할 동작으로 설명한다.

통합할 때 같은 기능의 대표 구현과 가져올 추가 변경을 정한다. 코드 병합과 DB 구조·적용 이력 정리는 별도로 확인한다. 지정한 통합 개발 환경에 한 변경씩 적용하고, 개인 DB 데이터는 자동으로 합치지 않는다. 데이터 이관이 필요하면 소유자·프로젝트 대응·중복 처리·담당을 따로 정한다.

개발 결과는 본인이 배정된 역할별 계정으로 확인한다. 자료 공개·위키 게시의 별도 검토 담당과 권한 규칙은 유지한다. 실제 회사 시범 사용·운영 인수는 준비된 경우 별도로 기록한다. 공용 반영은 담당자가 합의한 운영 절차로 수행한다.

계획 요청·교육생 판단·실행 요청·직접 확인이 슬라이드와 워크북·강사 노트에서 일치해야 한다. 파일 반영, 사용자 내용 확인, 실제 기능 개발 리허설, 회사 도입 완료를 구분해 보고한다.
