# 회사 위키 개발 과정 4회차부터 7회차 구성안

자료실과 실무 기록에서 시작한 개발을 위키·채팅·지식 그래프·업무 도구·검토함·관리로 넓힌다. 교육생은 각자의 위키를 같은 순서로 개선하고 직접 확인한다. 5회차부터 채택한 구현을 차례로 합쳐, 마지막에는 회사 담당자가 이어 운영할 수 있는 위키를 남긴다.

**4~7회차 상세 교재까지 반영했다.** 공통 원고에서 각각 54장·55장·58장·45장의 슬라이드·워크북·장별 강사 노트를 생성하고 입력 사례를 추가했다. 전체 구성 저장, 세부 교재 반영, 교육생 개발, 회사 도입은 각각 구분한다.

회차 전환에 필요한 실제 준비는 [강사용 통합 준비표](../training/instructor/integration-readiness.md)로 확인한다. 코드 기준뿐 아니라 공개 자료·보고서 상태·실행 주소·학생별 전용 DB를 맞춘다. 교재와 준비표가 있다고 해당 구현·DB·공용 환경까지 준비된 것은 아니다.

## 전체 흐름

| 회차 | 중심 메뉴 | 해결할 업무 불편 | 남길 결과 |
| --- | --- | --- | --- |
| 1~3 | 홈·자료실·실무 기록·관리 | 자료를 다시 찾기 어렵고 업무 경험이 흩어진다 | 검색 조건·즐겨찾기·개인 메모, 작성 안내·개인 초안·근거·개인 할 일 |
| 4 | 자료실·위키·검토함 | 원문을 찾아도 회사의 업무 절차로 정리하고 갱신하기 어렵다 | 자료별 검색, 업무 절차 위키, 수정 의견 처리, 개정 확인 |
| 5 | 채팅·지식 그래프 | 질문 범위와 답변 근거를 확인하기 어렵고 관련 지식을 함께 보기 어렵다 | 개인 질문 모음, 답변 확인 기록, 관련 위키 비교, 첫 통합본 |
| 6 | 업무 도구·관리·검토함 | 분석 결과의 미확인 사항과 회사 설정을 계속 관리하기 어렵다 | RFP 항목 확인·질문 답변 관리, 회사 용어·운영 안내 편집, 추가 통합본 |
| 7 | 전체 메뉴 | 여러 기능을 연결해 실제 업무를 하고 운영을 이어갈 준비가 필요하다 | 새 업무 수행 결과, 안정화한 통합본, 운영 인계와 남은 도입 과제 |

4회차에서 정리·게시한 지식을 5회차에서 질문하고 비교한다. 6회차에서는 그 지식을 참고해 요청 문서를 검토하고 미확인 사항을 관리한다. 7회차에서는 같은 기능을 새 업무에 적용해 운영까지 확인한다.

## 메뉴를 교육에 포함하는 방법

메뉴 이름은 현재 상단 탐색을 따른다. 메뉴의 역할을 먼저 이해하고, 실제 화면의 불편을 찾아 기능 묶음을 개발한다. 모든 하위 도구를 같은 깊이로 개발하지는 않는다. 공통 실습에서 만드는 기능과 사용만 해 보는 기존 기능을 구분한다.

| 메뉴 | 기존에 활용할 기능 | 교육에서 다룰 범위 |
| --- | --- | --- |
| 홈 | 도메인 안내·업무 진입 | 2회차의 즐겨찾기·검색 연결을 계속 사용하고 7회차에서 전체 업무의 시작점으로 확인 |
| 자료실 | 공개 검색·원문·버전·문단 링크 | 4회차의 자료별 검색과 개정 확인, 6회차의 요청 문서 등록 |
| 실무 기록 | 경험 작성·저장·공개 검토 | 3회차 개발 결과를 유지하고 7회차에서 새 업무의 판단과 남은 일을 기록 |
| 위키 | 작성·근거 선택·초안·게시 검토·개정 | 4회차에서 업무 절차 작성과 보완 흐름을 개선하고 5~7회차에서 사용 |
| 채팅 | 질문 범위·대화·근거 패널·답변 의견·위키 초안 저장 | 5회차에서 반복 질문과 근거 확인 과정을 개선하고 7회차에서 새 업무 질문 |
| 지식 그래프 | 관련 위키 탐색·검색·필터·문서 미리보기 | 5회차에서 관련 문서 비교와 탐색 복귀를 개선. 그래프 엔진을 다시 만들지 않음 |
| 업무 도구 | 심층 조사·프로젝트 탐색·RFP 분석 보고서·공식 자료 수집 | 위치와 용도를 함께 안내하고, 개발은 모두 RFP 분석 보고서의 후속 확인 과정으로 통일 |
| 검토함 | 공개·게시 검토, 담당·오류 처리, 품질 점검 | 4회차에서 작성자 보완과 검토자 판단을 연결. 6~7회차에서 기존 담당·처리 기능도 직접 사용 |
| 관리 | 도메인·프로젝트·직원 계정·모델 연결·작업·사용량·보존 관리 | 3회차 안내 설정을 유지하고 6회차에서 회사 용어·운영 안내를 개선. 7회차에서 운영 위치 확인 |

`교육 워크북`은 보조 자료 진입점이다. 내 활동·프로젝트·내 계정은 상단의 독립 주 메뉴와 구분해 필요한 업무에서 연결한다. 검토함과 관리는 해당 권한을 가진 계정으로 확인한다. 웹 클리퍼나 MCP 외부 연결을 새 개발 과제로 추가하지 않는다.

## 4회차 자료를 회사 업무 위키로 정리하기

**목표:** 찾은 자료를 읽기 쉽게 정리하고, 근거가 있는 업무 절차를 작성·검토·게시한 뒤 자료가 바뀌었을 때 고칠 곳을 찾는다.

**출발점:** 2회차의 검색 조건·즐겨찾기와 3회차의 실무 기록 기능이 있는 개인 위키. ‘가상 교통관제 자료’ 도메인의 공개 샘플을 사용한다. 실무 기록은 경험이고, 이번에 작성할 위키는 자료를 근거로 정리한 업무 절차라는 차이를 먼저 설명한다.

| 교시 | 시작 화면과 문제 | 함께 개발할 기능 묶음 | 직접 확인하고 다음에 넘길 결과 |
| --- | --- | --- | --- |
| 1 | 자료실 → 공개 지식 검색. 같은 자료의 여러 문단이 흩어져 보임 | 자료·종류·버전별 결과 묶기 → 일치 문단 펼쳐 보기와 원문 위치 열기 → 같은 검색 조건·페이지로 복귀하고 기존 즐겨찾기 연결 | ‘검수’로 검색해 필요한 문단을 고른다. 같은 제목의 다른 자료를 합치지 않고, 전체 검색 수와 현재 페이지의 묶음 수를 구분한다. 다음 교시에서 쓸 원문 두 개를 확인한다. |
| 2 | 위키 → 위키 작성. 빈 본문에서 업무 절차를 어떻게 정리할지 막힘 | 업무 절차 목차를 확인 후 넣기 → 본문과 선택한 근거를 함께 보며 작성 → 비어 있는 절을 안내하고 해당 위치로 이동 | 적용 범위·확인 순서·판단 기준·추가 확인을 갖춘 ‘[가상 실습] 프로젝트 A 검수 업무 절차’를 초안으로 저장한다. 기존 본문은 목차 적용으로 덮어쓰지 않는다. 기존 위키 연결 기능으로 관련 게시 위키를 연결하고, 다음 교시에 이 초안의 검토를 요청한다. |
| 3 | 위키 상세·검토함. 반려 이유를 읽어도 본문의 어디를 고칠지 찾기 어려움 | 위키 버전·본문 위치에 연결된 수정 의견 → 작성자의 보완 여부와 변경 위치 확인 → 재요청할 버전과 이전 의견을 함께 보기 | 교육용 작성 계정으로 요청하고 다른 검토 계정으로 의견을 남긴다. 작성 계정으로 보완·재요청한 뒤 검토 계정으로 게시를 판단한다. 의견의 보완 표시가 승인으로 바뀌지는 않는다. |
| 4 | 자료실 원문·위키 목록. 원문이 개정되면 어떤 위키를 다시 확인할지 찾기 어려움 | 기존 개정·영향 조회를 연결한 재확인 대상 목록 → 변경 전후 근거와 연결된 위키 열기 → 보완·게시 후 재확인 상태 갱신 | 검수 조건 v2를 같은 원문의 새 버전으로 등록·공개한다. 앞에서 만든 업무 절차와 기존 ‘프로젝트 A의 범위와 검수 기준’ 위키를 30초·90일 기준으로 보완하고 별도 게시 검토를 마친다. 이전 버전 링크와 개인 메모는 임의 변경하지 않는다. |

**저장과 역할:** 위키 본문·근거·버전은 기존 저장 구조를 재사용한다. 새 수정 의견은 대상 위키 버전·위치·작성자·처리 내역과 연결한다. 재확인 대상은 실제 원문·위키 연결과 공개 상태를 근거로 계산한다. 목록에서 확인 표시를 눌렀다는 이유만으로 오래된 근거를 유효하게 만들지 않는다.

**범위 조정:** 이전 4회차의 검색 묶음·문단 탐색을 1교시의 한 기능 묶음으로 합친다. 서버의 전체 자료 단위 검색·페이지 재설계는 공통 필수에서 뺀다. 첫 교시가 검색 엔진 개발로 커지는 것을 막고, 위키·검토·개정 개발에 시간을 배분한다. 회사 용어 입력 개선은 6회차 관리 실습으로 옮긴다.

**다음 회차의 입력:** 게시한 업무 절차의 주소·버전, 공개된 검수 조건 v2, 보완 의견 처리 결과, 기존 검색·즐겨찾기가 유지되는 코드와 DB 변경.

## 5회차 채팅과 지식 그래프로 근거 확인하기

**목표:** 회사 업무 질문을 다시 사용하고 답변의 근거를 직접 확인하며, 관련 위키를 비교해 판단한다. 그 과정에서 검증한 구현을 첫 통합본으로 연결한다.

**출발점:** 4회차에서 게시한 업무 절차와 개정된 공개 자료. 채팅의 질문 범위, 근거 패널, 답변 의견, 위키 초안 저장과 그래프의 문서 미리보기는 기존 기능으로 소개한다.

| 교시 | 시작 화면과 문제 | 함께 개발할 기능 묶음 | 직접 확인하고 다음에 넘길 결과 |
| --- | --- | --- | --- |
| 1 | 채팅. 반복 질문을 다시 입력하고 범위를 매번 확인해야 함 | 내 질문 저장·목록·수정·삭제 → 질문에 연결한 도메인·프로젝트 표시 → 불러온 질문과 범위를 확인한 뒤 전송 | ‘프로젝트 A의 현재 갱신 주기와 이력 보관 기간은?’을 저장·수정·재사용한다. 질문을 고르는 것만으로 전송하지 않으며 프로젝트 B로 잘못 질문하지 않는다. 같은 계정으로 다시 열어 목록을 확인한다. |
| 2 | 채팅 → 답변의 원문 근거. 어떤 답변을 확인했는지 남기기 어려움 | 답변별 내 확인 메모·확인 상태 → 확인할 근거와 원래 답변 다시 열기 → 미확인 답변만 모아 이어 확인 | 30초·90일의 근거와 문서에 없는 사항을 구분한다. ‘내가 근거를 확인함’과 답변이 회사의 공식 정답이라는 판단을 구분한다. 기존 답변 의견·위키 초안 저장도 연결해 사용한다. |
| 3 | 지식 그래프 → 문서 미리보기. 관련 문서를 번갈아 열면 비교 대상을 놓침 | 관련 위키를 비교 목록에 담기·빼기 → 적용 프로젝트·게시 버전·근거를 나란히 보기 → 문서를 읽고 같은 탐색·비교 목록으로 복귀 | 프로젝트 A 업무 절차와 연결된 위키를 비교한다. 제목만으로 같은 자료라고 판단하지 않는다. 실제 연결이 없는 관계를 AI 설명으로 만들어 표시하지 않는다. |
| 4 | 각자의 개발 결과와 통합 확인 환경. 같은 기능의 구현이 서로 다름 | 대표 구현 선정과 차이 확인 → 채택한 추가 변경 한 묶음의 코드·DB 반영 → 통합본에서 검색·위키·채팅·비교 연결 확인 | 첫 통합 기준 버전과 반영한 DB 변경을 남긴다. 모두 그 기준을 별도 작업 브랜치에서 받아 역할별로 직접 확인한다. 남은 통합 대상은 6회차로 넘긴다. |

**저장과 역할:** 질문 모음과 답변 확인 기록은 로그인 사용자·작업공간에 속한다. 질문에는 선택한 업무 범위를, 확인 기록에는 대화·답변과 근거 참조를 연결한다. 2회차의 검색 조건은 자료실 검색용이고, 이번 질문 모음은 채팅 질문용이다. 그래프 비교 목록도 사용자·작업공간별로 DB에 보관한다. 위키 식별 정보와 순서를 저장하고 현재 게시 본문을 다시 불러온다. 읽을 수 있는 문서만 비교한다. 첫 통합에서는 모두 질문 고정·해제·상단 정렬의 추가 변경을 합친다. 강사는 기준 커밋·추가 변경 커밋·별도 작업 위치·통합 개발 DB를 사전에 준비한다.

**AI 준비:** 개발용 Claude Code와 앱 채팅 모델을 구분한다. 앱 모델 연결·샘플 처리는 수업 전에 준비한다. 연결되지 않으면 화면 개발과 실제 답변 확인을 나누어 기록하며, 저장된 예시 답변을 실시간 모델 실행 결과로 소개하지 않는다.

**다음 회차의 입력:** 질문과 확인 기록, 비교한 위키, 첫 통합 기준 버전·DB 적용 기록. 그래프용 게시 위키와 실제 연결은 수업 전에 확인한다.

## 6회차 업무 결과물과 회사 설정 관리하기

**목표:** 요청 문서를 분석한 뒤 남는 확인 사항을 끝까지 관리하고, 회사 담당자가 용어와 사용 안내를 직접 수정할 수 있게 만든다. 그 변경을 통합본에 반영한다.

**출발점:** 업무 도구의 기존 RFP 분석 보고서. RFP는 제안 요청 문서이며 이 실습에서는 ‘프로젝트 A · 후속 단계 요청 문서’를 사용한다. 분석 항목·근거·확인 질문·초안 저장·검토는 기존 기능이다. 모든 교육생이 같은 보고서 업무 흐름을 개발한다.

| 교시 | 시작 화면과 문제 | 함께 개발할 기능 묶음 | 직접 확인하고 다음에 넘길 결과 |
| --- | --- | --- | --- |
| 1 | 업무 도구 → RFP 분석 보고서. 항목이 많아 어떤 요구를 확인했는지 구분하기 어려움 | 보고서 항목별 미확인·확인 중·확인 완료 관리 → 미확인 항목 필터·개수 → 원문 근거를 읽고 같은 항목으로 복귀 | 45초·180일의 명시 요구와 미정인 연계 범위를 구분한다. 항목 내용이나 근거가 바뀌면 이전 확인을 그대로 완료로 보지 않도록 처리한다. 다음 교시에는 미해결 질문이 남은 항목을 연다. |
| 2 | 같은 보고서의 확인 질문. 질문을 남긴 뒤 받은 답변과 후속 판단을 관리하기 어려움 | 질문별 확인 대기·답변 기록·보류 → 답변의 출처와 연결 자료 저장 → 답변을 보고 분석 항목을 수정·재확인 | 가상 답변 예시를 기록하고 보류한 질문을 다시 연다. 질문 상태·항목 확인·보고서 승인 상태는 따로 둔다. 질문을 모두 처리해도 보고서를 자동 승인하지 않는다. |
| 3 | 관리 → 도메인·운영 설정. 용어 입력이 어렵고 안내를 바꾸려면 개발자에게 요청해야 함 | 핵심 용어를 행별로 등록·수정·삭제하고 동의어 입력 미리 보기 → 기존 도메인 DB 저장과 검색 적용 확인 → 메뉴별 운영 안내·문의 담당 편집 및 해당 화면 연결 | 관리 계정으로 회사 용어와 안내를 저장하고 일반 사용자로 검색·도움말을 확인한다. 임의의 검색어 확장을 표시하지 않고 서버가 실제 적용한 용어를 보여 준다. 문의 버튼은 안내만 하며 메시지를 자동 발송하지 않는다. |
| 4 | 첫 통합본과 업무 도구·관리 변경. 새 기능을 합치면 권한과 기존 화면에 영향이 생김 | 채택한 업무 도구·관리 변경 반영 → 작성·검토·관리·일반 열람 계정으로 확인 → 기존 기능까지 연결해 통합 문제 수정 | RFP 확인 과정과 회사 설정이 함께 동작하는 통합본을 남긴다. 공용 반영 대상·담당·설정·복구 준비와 실제 반영 상태를 구분한다. |

**저장과 역할:** RFP 확인 내역은 보고서 버전·항목·질문·처리자에 연결한다. 작성자·배정된 검토 역할이 처리하는 업무 기록이며 회사 전체 공개 메모로 만들지 않는다. 보고서 새 버전의 항목은 미확인, 질문은 확인 대기로 시작한다. 이전 답변은 원래 버전에 보존하고 작성자가 연결 대상을 확인해 참고로 연결한다. RFP 검토 요청은 검토함의 담당·오류 처리에서 찾거나 RFP 목록에서 열며, 판단은 보고서 상세에서 한다. 회사 용어·운영 안내는 도메인 공용 설정이고 관리자가 편집한다. 관리자라는 이유만으로 다른 사용자의 개인 질문·대화·메모를 공개하지 않는다.

**다른 업무 도구:** 프로젝트 탐색은 문서 범위를 찾는 데 사용한다. 심층 조사와 공식 자료 수집은 목적·입력·결과·검토 위치를 함께 확인한다. 두 도구를 추가 개발 과제로 나누어 맡기지 않는다. 외부 조회가 필요한 실제 실행은 준비한 모델·허용 사이트·자료 범위 안에서 진행한다.

**다음 회차의 입력:** 항목 확인과 질문 답변이 남은 분석 보고서, 회사 용어·운영 안내, 추가 통합본, 역할별 확인 결과와 공용 운영 준비 목록.

## 7회차 통합 위키로 업무를 확인하고 운영 인계하기

**목표:** 완성한 기능을 새 업무 상황에 연결하고, 실패하거나 자료가 달라져도 계속 사용할 수 있는지 확인한다. 회사 담당자가 실제 운영을 이어받는다.

**출발점:** 6회차 통합본과 보고서. 새 업무는 ‘프로젝트 A 후속 단계의 운영 인수인계를 준비한다’로 통일한다. 수업용 업무 상황 카드로 요청·확인할 근거·남길 결과를 먼저 제시한다. 교육생이 메뉴 순서와 이유를 정한 뒤 공통 확인 절차로 빠진 결과를 보완한다. 실제 회사 업무 수행과 가상 기능 확인을 구분한다.

| 교시 | 시작 화면과 문제 | 함께 수행할 실습 | 직접 확인하고 남길 결과 |
| --- | --- | --- | --- |
| 1 | 홈에서 새 업무 시작. 기능은 있지만 어떤 순서로 쓰면 되는지 판단해야 함 | 필요한 자료 검색·즐겨찾기 → 위키·채팅·그래프로 근거 확인 → RFP의 남은 질문과 실무 기록·개인 할 일 연결 | 후속 요청의 45초·180일과 기존 운영 기준 30초·90일을 구분한 업무 결과를 남긴다. 미정인 항목은 확인 질문으로 남기고 실제 사용을 막는 문제를 재현한다. |
| 2 | 통합본의 저장·수정 화면. 실패·재접속·동시 수정에서 작업이 유실될 수 있음 | 실패 시 입력 보존·저장 결과 재확인 → 두 탭의 수정 충돌 안내와 재조회 → 목록·개수·계정 전환 뒤 내용 일치 | 공통 확인 대상으로 ‘즐겨찾기 내 메모’를 사용한다. 기존에 되는 동작은 유지하고 누락된 연결을 보완한다. 실제 오류 유무와 무관하게 준비된 실패·충돌 사례로 동작을 확인한다. |
| 3 | 관리·검토함·운영 안내. 담당자가 혼자 운영 절차를 따라갈 수 있어야 함 | 자료 갱신·별도 검토 요청 → 작업·모델 오류 확인과 허용된 재시도 → 계정·백업 위치·복구 절차 확인 후 필요한 안내 보완 | 운영 담당자가 실제로 수행한 항목과 설명만 확인한 항목을 구분한다. 코드·DB 구조뿐 아니라 운영 데이터·원본 파일·설정의 보관 위치와 담당을 인계한다. |
| 4 | 회사 운영 대상 환경. 최종 버전과 운영 책임이 분명해야 함 | 같은 업무 전체 시연 → 공용 주소에서 역할별 핵심 기능 확인 → 최종 버전·담당·남은 과제 인계 | 개인 실행·통합 검증·공용 반영·운영 인수 상태를 따로 남긴다. 도입 미완료 항목에는 담당·다음 행동·완료 기준을 정한다. |

7회차에는 새 대형 기능을 추가하지 않는다. 1교시의 업무 적용과 3~4교시의 운영 실습을 개발 시간으로 부풀리지 않고, 2교시의 안정화 개발과 구분해 시간을 배분한다. 실제 회사 환경이나 운영 인수자가 준비되지 않았다면 통합 환경에서 수행한 결과까지만 완료로 남긴다.

## 각자 개발한 결과를 합치는 방식

모두 같은 필수 과제를 수행하므로 같은 화면과 DB를 서로 다르게 구현할 수 있다. 여러 저장소를 통째로 순서대로 병합하지 않는다. 강사가 확인한 대표 구현을 기준으로, 회사에 필요한 추가 변경을 골라 합친다.

1. **4회차까지 통합 준비:** 기준 커밋, 바꾼 화면, DB 변경 파일, 직접 확인한 결과를 각자 남긴다. 통합 환경·담당·공용 운영 대상은 수업 전에 준비한다.
2. **5회차 첫 통합:** 대표 구현과 채택할 차이를 정한다. 추가 변경 한 묶음을 코드와 DB까지 적용하고 모두 같은 기준 버전을 직접 확인한다.
3. **6회차 추가 통합:** 업무 도구·관리 변경을 이어 합친다. 검색부터 보고서까지 동작하고 역할별 접근이 맞는지 확인한다.
4. **7회차 최종 반영:** 새 업무 결과와 안정화 변경을 반영한다. 실제 공용 반영·운영 인수까지 확인한다.

교육생의 `origin`은 자신의 fork이고 `upstream`은 강사의 기준 저장소다. 최신 변경을 가져오는 것과 내 작업에 병합하는 것은 별도 단계로 안내한다. 수정 중인 작업을 보관하고 차이·충돌을 확인한 뒤 별도 브랜치에 반영하며, 강사 기준으로 강제 초기화하지 않는다. 통합 기준 브랜치·버전은 수업 전에 강사가 명시한다.

코드 병합과 DB 적용을 따로 확인한다. 이미 적용된 DB 변경 파일을 임의로 덮어쓰지 않는다. 구조 변경을 합치는 일이 교육생별 개인 데이터까지 합친다는 뜻은 아니다. 운영 데이터 이관이 필요하면 계정·프로젝트 대응과 중복 처리 범위를 따로 정한다.

교육생은 자기 결과와 받아온 통합본을 직접 확인한다. 동료가 사용해 주거나 평가해 주는 일을 실습 완료 조건으로 두지 않는다. 공개·게시 동작은 서로 다른 교육용 작성·검토 계정으로 확인하며, 실제 회사 운영의 검토 책임과는 구분한다.

## 4시간 수업을 운영하는 기준

강사 운영 기준은 도입·마무리 합계 10분, 네 교시 각 50분, 휴식 세 번 각 10분으로 총 240분이다. 개발 교시는 설명·판단 기준 안내를 짧게 마치고 약 40분을 계획 판단·개발·직접 확인·보완에 사용한다. 학생 슬라이드와 워크북에는 고정 분 단위 시간을 표시하지 않는다.

각 개발 교시의 표에 나열한 동작은 모두 필수다. 첫 요청 하나를 실행한 것을 교시 완료로 보지 않는다. 기능별로 계획을 읽고 바꿀 점을 정한 다음 실행하고, 다음 동작을 더한다. 이름 변경·반복 타이핑·AI 대기·샘플 설치 문제로 실습 시간을 채우지 않는다.

빠른 교육생에게는 공통 과제와 겹치지 않는 추가 개발을 준비한다. 검색의 전체 자료 단위 페이지 처리, 수정 의견의 담당별 보기, RFP 확인 내역의 일괄 처리 등이다. 질문 목록 검색·비교 목록 보관·위치 변경 안내는 이미 공통 과제이므로 선택으로 돌리지 않는다. 추가 도전은 다음 회차의 필수 조건에 넣지 않는다. 본 과제가 어려우면 다음 교시에 필요한 최소 연결부터 코칭하고 남은 기능을 기록한다.

실제 소요 시간은 아직 측정하지 않았다. 회차별 상세화 뒤 대표 실습을 진행해 요구 판단·개발·직접 확인·AI 대기·강사 개입을 나누어 측정한다. 슬라이드 수나 요청문 수로 4시간 분량을 검증했다고 하지 않는다. 통합·운영 교시는 실제 수행 시간을 따로 측정한다.

## 슬라이드와 워크북에 반영할 공통 형식

- **도입 1장:** 현재 실제 화면과 오늘 만들 결과를 구분하고, 하단 핵심어를 네 교시의 결과와 연결한다.
- **도입 2장:** 시작할 화면 → 개발할 동작 → 완성 결과 → 다음 교시에서 쓸 것을 보여 준다.
- **도입 3장:** 실제 메뉴·계정·샘플·기존 기능을 확인한다. 개발용 AI 요청도 대상 메뉴와 기능부터 말한다.
- **교시별:** 현재 화면과 불편 → 계획 요청 → 교육생 판단 → 실행 요청 → 후속 기능 → 직접 확인. 계획·실행 요청은 따로 보내고 각 상자는 한 번에 복사한다.
- **마지막 장:** 직접 확인한 결과·미확인·남은 일과 다음 회차의 출발 상태를 정리한다.

교육생이 워크북을 열지 않아도 슬라이드만으로 입력할 곳·예시·순서·예상 결과를 알 수 있어야 한다. 강사 노트에는 꼭 전할 말·예시·판단할 질문·막혔을 때 코칭·앞뒤 장의 연결을 둔다. 워크북에는 같은 요청과 확인 순서를 짧게 제공하며 강사용 운영 메모를 넣지 않는다.

상단 헤더 위치와 글자 규칙은 3회차의 공통 스타일을 사용한다. 긴 요청문은 기능 단계로 나누고 복사 버튼과 다음 영역이 겹치지 않는지 확인한다. 장수는 기능의 순서와 읽을 분량에 따라 정하며 3회차의 61장에 억지로 맞추지 않는다.

## 현재 확인 근거와 세부 작업 전 준비
