# 13단계 — 관계를 이용한 검색

2026-09-09 구현·계약 시험·실제 모델 개발 표본 검증 완료. 실제 고객 업무 판정은 미검증이다.

## 위키 관계와 검색

위키 유형·별칭은 공식 편집 폼에서 수정해 새 버전으로 저장한다. 기존 버전의 메타데이터와 원문 연결은 그대로 보존한다. 본문의 마크다운 링크를 AST로 읽어 현재 게시 위키의 UUID 관계를 재구성하므로, 예전 위키 본문을 덮어쓰거나 별도 복제 테이블을 만들지 않는다. 코드 블록·이미지는 위키 연결로 세지 않는다. 제목이 바뀌어도 ID 연결을 유지하고 같은 제목·별칭의 서로 다른 페이지를 임의로 합치지 않는다. 병합·철회로 게시 대상이 사라지면 해당 노드와 연결을 제거한다. 이전 링크를 다른 페이지로 자동 치환하지 않으며 필요한 수정은 검토 변경안으로 처리한다.

원본 `graph-relevance.ts`의 계산을 다음과 같이 적용했다. 경로마다 네 신호의 내역을 남기며 유형 점수만 있는 페이지는 관계로 만들지 않는다. 기존에 없던 절차·사례 유형에는 원본의 미지정 유형 값 0.5를 적용한다.

| 신호 | 계산 |
| --- | --- |
| 직접 링크 | 양방향 링크 유무의 합 × 3 |
| 공통 출처 | 현재 공개된 같은 원문 버전 수 × 4 |
| 공통 이웃 | 공통 이웃별 `1 / ln(max(허용된 입·출력 차수 합, 2))` 합 × 1.5 |
| 유형 친화도 | 원본 유형 행렬, 미지정 조합 0.5 |

키워드·벡터 결합의 기존 상위 8개를 유지하고, 최대 8개 시작 위키에서 직접 링크·공통 출처·공통 이웃의 1~2단계 관계를 탐색한다. 관련 페이지의 현재 원문 문단을 최대 4개 추가한다. 연결 점수는 원문을 찾은 이유이며 사실 인용의 대체물이 아니다. 기존 ‘관련 지식’ 보기에서도 같은 관계 계산을 우선 사용한다.

## 범위와 캐시

작업공간·도메인·프로젝트·선택 원문·선택 위키 조건을 먼저 적용한다. 제한된 노드는 중간 경로·공통 출처·차수 계산에도 넣지 않는다. 캐시를 읽을 때도 현재 공개 자료를 DB에서 다시 확인하고, 검색 범위·공개 버전·원문 근거·설정을 포함한 지문을 비교한다. 캐시는 최근 8개 범위만 보관한다.

최대 1,000개 위키, 본문 합계 800만 자, 직접 연결 20,000개, 시작점별 후보 256개로 제한하고 관계 조회에 2초 DB 실행 한도를 둔다. 초과·오류가 나면 추가하던 관계 결과를 버리고 기존 검색으로 되돌아가며 안내를 표시한다. 답변의 현재 원문뿐 아니라 중간 위키·공통 출처·본문 링크의 버전도 재확인한다. 철회되거나 범위를 벗어난 경로가 있으면 진행 중 답변을 중단하고 이전 답변을 숨긴다.

검색된 위키 본문에도 범위 밖 링크가 남을 수 있어, 채팅 문맥에서는 해당 링크의 표시 문구·주소를 생략하고 이를 표시한다. 저장된 위키 본문은 유지한다. 기존 E1~E8의 순서와 추가 E9~E12의 순서를 새로고침 후에도 숫자 순서로 유지한다.

## 문맥과 화면

질문·기본 지시·해당 도메인의 목적·용어를 먼저 확보한다. 남은 예산에서 이전 대화와 관계 설명에 각각 12%를 배정하고, 원문·위키에 나머지를 배분한다. 짧은 근거의 남는 공간은 다른 근거에 배분하며 JSON 안에 포함되는 문자열 이스케이프까지 계산한다. 목적이 너무 크면 중간에서 잘라 의미를 바꾸지 않고 범위를 줄이도록 안내한다. 이전 답변은 그때 사용한 구간이 이번 근거에도 그대로 포함될 때만 다시 전달한다.

기존 위키의 첫 10,000자 제한을 없애고 전체 본문에서 검색한다. 긴 원문은 질문과 관련된 연속 구간을 정확히 발췌하며 시작·끝 문자 위치와 원문 행·쪽 정보를 유지한다. 범위 밖 링크를 생략한 위키는 문자 위치가 생략 이후 기준임을 표시한다. 발췌 과정에서 뒤의 금지 조건이 잘린 문제를 고쳐 ‘37분 대기’와 ‘추가 연결 금지’를 함께 보존하는 회귀 시험을 추가했다.

질문 범위의 공식 Checkbox로 ‘원문만 사용’을 선택·저장·복원할 수 있다. 이 경우 위키와 관계 확장을 제외하고 공개 원문만 검색한다. 여러 도메인에서는 `domainId`별 목적과 용어를 분리하며 목적·잠정 가정을 사실의 근거 ID로 사용하지 않는다.

금액 단가와 고객 업무 검토는 확인하지 않았다. 관계 점수는 진위나 인용 적합성의 확률이 아니며, 위키 전체의 구조·의미 품질 점검은 다음 14단계에서 구현한다.

## 긴 임베딩 입력 보완

12단계 실제 검증에서 긴 원문 문단이 제공자의 입력 한도를 넘으면 색인 요청 묶음 전체가 실패하는 문제를 발견했다. 원문과 긴 질문을 UTF-8 6,000바이트 이하의 구간으로 나누고 요청당 최대 32구간을 처리한다. 모든 구간의 길이를 가중치로 벡터를 합쳐 정규화하며 한 구간인 경우 기존 벡터를 유지한다. 본문 문자를 생략하지 않는다. 검색에 보여 줄 발췌는 별도로 처리한다.

이 바이트 상한은 현재 연결한 바이트 토큰 기반 모델에 여유를 둔 내부 기준이다. 모델의 토큰 수 자체를 측정했다는 의미가 아니다. [공식 API 문서](https://developers.openai.com/api/reference/resources/embeddings/methods/create)의 입력당 8,192토큰과 요청 전체 300,000토큰 한도를 확인했다. 원문별 문단 ID는 그대로이며 임베딩 식별자에 분할·결합 버전을 포함해 이전 색인과 구분한다. 각 실제 요청의 사용량 기록을 유지하고 중간 실패·취소·응답 차원 변경은 완료 결과로 반환하지 않는다.

TypeScript 검사와 긴 한글·이모지·표·문서 끝 조건, 여러 배치의 실패·취소 계약 시험 2개를 통과했다. 실제 색인 작업 한 차례는 1.162초에 성공했으며 API 요청 2개, 입력 10,746토큰, 실패 0개를 확인했다. 작업자는 이후 남은 현재 공개 자료를 같은 방식으로 색인한다. 전체 검색 회귀와 실제 답변 품질 검증은 관계 탐색 구현 후 진행한다.
