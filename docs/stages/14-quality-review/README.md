# 14단계 — 위키 품질 점검과 수정 검토

작성: 2026-09-10. 구현·전체 회귀·실제 모델 대조를 완료했다.

## 입력과 권한

`/w/{workspaceId}/quality`에서 도메인과 프로젝트를 선택한다. 검토 직원과 관리자에게만 점검 실행·결과·예약·담당 처리를 허용한다. 프로젝트를 선택하면 해당 프로젝트와 공통 페이지를 검사한다. 게시 이력이 있는 현재 게시 버전을 대상으로 하므로 근거가 개정된 게시본도 검토 직원이 확인할 수 있다. 초안을 자동 게시하지 않는다.

본문·현재 게시 및 최신 변경안 버전·원문 구간의 현행성·Purpose·용어·모델 설정·검사 버전을 지문에 포함한다. 조회 시에도 현재 지문을 비교한다. 실행 중에는 2초마다 자료와 요청자 권한을 재확인하며 변경·취소 시 후보 공개를 중단한다. 마지막 결과 저장 전에 같은 범위의 점검과 문서 변경을 잠금으로 조정하고 재검사한다.

## 구조 점검

원본 `lint-structural-core.ts`의 고립, 나가는 연결 없음, 끊긴 링크 규칙을 DB 입력으로 적용했다. 마크다운 AST로 실제 UUID 연결만 읽으며 코드 예시의 링크는 제외한다. 다른 범위에 실제로 게시된 대상은 끊긴 링크로 오판하지 않는다. 제목이 비슷한 페이지를 연결 대상으로 추측하지 않는다.

| 검사 | 표시 | 의미 |
| --- | --- | --- |
| 원문 근거 없음 | 수정 필요 | 해당 게시 버전의 연결 원문 구간이 없음 |
| 근거 재확인 | 확인 필요 | 연결 원문이 개정·철회되어 현재 근거가 아님 |
| 끊긴 연결 | 확인 필요 | 연결한 페이지에 현재 게시 대상이 없음 |
| 들어오는 연결 없음 | 참고 안내 | 선택 범위에 이 페이지로 들어오는 링크가 없음 |
| 나가는 연결 없음 | 참고 안내 | 선택 범위의 다른 페이지로 연결하지 않음 |

관계가 적은 독립 안내문을 오류로 단정하지 않는다. 최대 1,000페이지·본문 800만 자까지 검사하며 초과하면 범위를 좁히도록 안내한다.

## AI 의미 점검

원본 `lint.ts`의 의미 점검 개념을 별도 `quality_run`과 `quality_step`으로 적용했다. 전체 본문을 문자 손실 없이 구간으로 나누어 각각 읽는다. 연결·공통 원문·제목으로 페이지마다 최대 3개 관련 페이지를 고르고, 선택한 쌍의 관련 구간을 비교한다. 서로 다른 프로젝트끼리의 쌍은 비교하지 않는다. JSON 문자열 예산을 미리 확인하고 목적을 중간에서 자르지 않는다.

100페이지·본문 60만 자·200구간이 실행 상한이다. 모든 본문 구간을 읽지만, 모든 문서 쌍의 상충이나 설명 공백을 완전하게 검사한다는 뜻은 아니다. 비교 범위와 전체/완료 구간 수를 화면에 표시한다.

중복·상충·설명 보완·핵심 질문 보완을 후보로만 저장한다. 모든 후보에 입력에 실제로 있는 연속 구절과 정확한 페이지·버전·문자 위치를 요구한다. 중복과 상충은 서로 다른 두 페이지의 구절이 필수다. Purpose 보완은 실제 핵심 질문의 문장과 연결한다. 목적 밖 자료를 자동 오류로 판단하지 않고 목적 변경은 검토 제안과 관리자 저장으로 남긴다.

모델 호출은 기존 지식 정리 설정과 공간별 동시 요청 한도를 사용한다. 한도에 도달하면 대기하며 이미 완료한 구간을 중복 호출하지 않는다. `generation.kind='wiki-quality'`로 실제 요청·모델·입출력 토큰을 기록한다. 응답 구절 검증에 실패해도 받은 사용량은 남긴다. 모델이 보고하지 않은 토큰은 미확인으로 유지한다.

## 수정·해결·재발

후보에서 비교한 위키 버전, 원문 구간, 기존 위키의 새 변경안 작성으로 이동한다. 변경안은 기존 검토·게시 절차를 따른다. 검토함에서 담당 검토 직원을 지정하고 확인 중·보류·해결·다시 접수를 처리한다. 보류와 상태 변경에는 이유가 필요하다. 현재 자료로 재점검하기 전에는 이전 판정을 해결 처리할 수 없다.

범위·검사 종류·대상 페이지/연결을 기준으로 같은 문제를 하나의 항목에 모은다. 동일 묶음의 여러 AI 구절과 설명도 합쳐 보존한다. 구조 재점검에서 사라진 문제는 해결 이력을 남긴다. AI 재점검에서 재발견하지 못한 후보는 이전 구절과 함께 보존하고, 해결 여부는 직원이 현재 원문과 대조해 결정한다. 해결 후 다시 발견되면 같은 항목을 열고 발견 횟수와 재발 이력을 남긴다.

정기 점검과 개정 후 점검은 기본값이 꺼져 있다. 설정한 도메인 전체에 적용되며 처리한 입력과 다음 점검일을 저장하여 같은 개정 때문에 반복 실행하지 않는다. 실패·중단은 자동 무한 재시도를 하지 않는다. 실행 중 작업자의 연결이 30초 이상 끊기면 중단 이력을 남기고 새 점검을 실행할 수 있다. 예약한 직원의 검토 권한이 철회되면 자동 점검도 실행하지 않는다.

## 검증 상태

- 전용 통합시험 15개 통과(22.7초): 구조 오탐·장문 끝 부정문·정확한 구절·역할/공간/프로젝트 경계·동시 등록/작업자·Purpose·사용량·공식 변경안/게시/재검사·보류/재발·실행 중 개정/취소/중단·예약 중복 방지·AI 미발견 후 직원 해결·동시 요청 대기·실행 중 권한 철회·390px 이동.
- 발견 후 수정: 동시 등록 시 오래된 트랜잭션 읽기로 중복 충돌하던 문제, 검토 메뉴가 390px 바깥으로 밀리던 문제, AI 재검사에서 사라진 후보를 새 자료로 검토할 수 없던 흐름.
- 전체 회귀 192개 통과(10.8분), 관련 운영·품질 27개 통과, 생산 빌드·정적 검사 통과. 품질 작업의 갱신 시간을 기존 작업 만료 기준에 섞어 발생한 회귀도 수정했다.
- [실제 모델 대조](../../evaluation/core/quality-14/README.md): 개정 전후 의미 점검 12회 호출, 입력 8,961·출력 3,869토큰, 사용량 미확인 0건. 30일·45일 상충을 찾고 45일 개정 후 이전 구절 보존·현재 원문 대조·해결까지 확인했다. 데스크톱/390px 품질·검토 화면 8개와 원문/위키 링크를 확인했다.
- 고객 업무 문서의 전문가 검토: 미검증.
