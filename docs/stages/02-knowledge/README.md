# 2단계 — 원본과 게시 위키

작성일: 2026-09-09. 대상: P2-01~P2-05. [전체 작업 목록](../../IMPLEMENTATION_BACKLOG.md).

후속 UI 반영: 기존 폼을 공식 shadcn/ui 컴포넌트로 통일했다. [적용 범위·검증·화면](./UI_COMPONENTS.md)을 참고한다.

자료 등록 → 문서 추출 → 다른 검토 직원의 공개 승인 → 근거를 연결한 위키 작성 → 제출·게시 → 일반 직원의 검색·원문 확인을 구현했다. 이번 단계에서는 실제 모델을 호출하지 않는다. 채팅과 실무 기록은 준비 화면이며, 3단계는 사용자의 2단계 확인 후 시작한다.

## 실행

프로젝트 루트에서 실행한다. 기존 1단계 DB와 계정은 유지한다.

```bash
npm ci
npm run setup:local
npm run db:up
npm run db:migrate
npm run db:bootstrap
npm run db:content-team
npm run dev
```

별도 터미널에서 문서 작업자를 실행한다.

```bash
npm run worker
```

접속 주소는 [http://localhost:3010](http://localhost:3010)이다. 현재 `dev` 스크립트의 포트에 맞춰 환경 예시와 신규 환경 생성 기본값을 3010으로 맞췄다. 기존 `.env.local`은 덮어쓰지 않으므로 `BETTER_AUTH_URL=http://localhost:3010`인지 확인한다. 1단계 문서는 당시 3000번 포트의 검증 기록을 유지한다.

Node.js 22.23.1과 PostgreSQL 17에서 검증했다. `pg-boss`는 Node.js 22.12 이상이 필요하다. 작업자가 실행되지 않아도 업로드는 DB 대기열에 남는다. 웹과 작업자는 같은 DB와 `ORIGINALS_DIR`에 접근해야 한다.

## 확인 계정

| 계정 | 역할 | 비밀번호 파일 |
| --- | --- | --- |
| `admin@wiki.local` | 공간·직원 관리, 이용 직원 | `.local/initial-accounts.json` |
| `reader@wiki.local` | 이용 직원 | `.local/initial-accounts.json` |
| `writer@wiki.local` | 작성 직원 | `.local/content-accounts.json` |
| `reviewer@wiki.local` | 검토 직원 | `.local/content-accounts.json` |

비밀번호는 무작위로 생성하며 위 파일과 `.env.local`은 Git에서 제외한다. 계정 준비 명령을 다시 실행하면 기존 계정을 유지한다. 관리자 권한만으로 자료를 작성하거나 승인할 수는 없다. 업무 역할은 별도로 지정한다.

## 화면 확인 순서

1. 작성 직원으로 로그인한다. 자료실의 **새 자료 등록**에서 제목·도메인·프로젝트·분류와 TXT·MD·텍스트 PDF를 선택한다. 한 파일은 10MiB 이하이다.
2. 등록된 문서의 처리 완료를 기다린다. MD·TXT는 제목과 행 범위, PDF는 페이지 번호를 확인한다. **원본 내려받기**와 **PDF N쪽 열기**에서 실제 파일을 확인할 수 있다.
3. 검토 직원으로 로그인한다. 검토함 또는 자료 상세에서 원문과 추출 결과를 비교한 뒤 **자료 공개 승인**을 누른다. 반려에는 의견이 필요하다. 작성자는 최신 반려 버전에서 **다시 검토 요청**을 할 수 있다.
4. 작성 직원으로 위키에서 **새 위키 작성**을 연다. 마크다운 본문을 작성하고 공개 원문 문단을 선택한 뒤 **초안 저장**, **검토 요청**을 누른다.
5. 검토 직원이 본문·근거·기준 게시본과의 차이를 확인하고 **위키 게시 승인**을 누른다. 본인이 작성하거나 올린 버전은 다른 검토 직원이 승인해야 한다.
6. 이용 직원은 게시 위키를 검색하고 근거 링크를 누른다. 원본 버전의 해당 문단으로 이동하며 선택 문단이 강조된다. 검토 전 자료와 위키 초안은 보이지 않는다.
7. 수정은 **새 원본 버전 등록** 또는 **새 변경안 작성**으로 저장한다. 이전 본문은 유지된다. 다른 변경안이 먼저 게시되면 오래된 기준의 변경안은 승인되지 않는다.

개발 표본은 [평가 자료](../../evaluation/README.md)와 [PDF·Office 표본](../../evaluation/stage-02/fixtures)에 있다. 실제 고객 지침으로 사용하지 않는다.

## 저장과 상태

원본은 `public` 밖의 `.local/originals/<작업공간 UUID>/<버전 UUID>`에 저장한다. 파일명으로 경로를 만들지 않으며, 내려받을 때 세션·역할·공개 상태와 SHA-256을 확인한다. 원본 저장소는 `put/read/remove` 인터페이스로 분리했다. 로컬 파일은 0600, 생성 디렉터리는 0700으로 제한한다.

| 구분 | 동작 |
| --- | --- |
| 원본 처리 | 대기 → 처리 중 → 완료/실패. 대기·처리 중 취소, 실패·취소 상태에서 재시도 |
| 원본 공개 | 검토 대기 → 공개/반려. 최신 완료 반려본 재제출. 공개본 철회, 새 공개본 승인 시 이전 버전으로 전환 |
| 위키 | 초안 → 검토 대기 → 게시/반려. 반려 뒤 새 버전 작성, 게시 철회 |
| 버전 | UUID와 증가하는 버전 번호. 저장된 원본·위키 본문·근거를 덮어쓰지 않음 |
| 중복 파일 | 같은 작업공간·도메인·프로젝트에서 조회 가능한 동일 해시 자료는 기존 버전 반환. 동시 등록도 DB 잠금으로 중복 방지 |
| 근거 | 원본 버전·문단 UUID와 행/페이지 위치. 위키 저장·제출·승인 시 현재 공개 근거와 범위 재검사 |

`pg-boss` 큐 등록과 원본 버전 저장은 같은 DB 트랜잭션으로 묶었다. 작업자가 강제 종료되면 임대 만료 후 재시도하며, 기본 임대는 120초이다. 기본 설정에서는 만료 감지가 최대 약 15초의 점검 간격을 추가로 기다릴 수 있다. 자동 재시도는 최대 2회이며, 실패·취소 뒤 사용자가 새 작업을 요청할 수 있다. 완료된 버전은 다시 추출하지 않아 근거 문단 ID가 유지된다.

문서 파서는 자식 프로세스에서 실행한다. 처리 제한 시간은 45초, V8 힙 한도는 256MiB이다. PDF는 최대 300쪽, 추출 결과는 200만 자·5,000문단 이하이다. 이는 전체 프로세스의 메모리를 제한하는 운영 격리 환경은 아니며, 외부 운영 환경의 격리는 후속 단계에서 다룬다.

## 검색과 권한

자료실과 위키는 같은 검색 서비스를 사용한다. 명칭·본문의 대소문자를 구분하지 않는 키워드 검색이며, 여러 단어는 모두 포함해야 한다. 도메인·프로젝트·자료 유형을 선택할 수 있고 최대 50건을 반환한다. 프로젝트 필터에는 해당 프로젝트 자료와 같은 도메인의 공통 자료를 포함한다. 의미 검색·동의어·임베딩은 3단계 이후의 작업이다.

현재 작업공간의 승인 자료는 같은 공간의 이용 직원이 공유한다. 도메인·프로젝트는 검색·근거 범위이며 별도 직원별 접근 제어 목록은 아니다. 비공개 원본은 작성자와 검토 직원, 위키 초안은 해당 버전 작성자와 검토 직원만 열 수 있다. 조회와 직접 API에 같은 규칙을 적용한다.

원본 공개 버전이 바뀌거나 철회되면 그 구버전을 참조하는 위키는 일반 조회·검색에서 즉시 제외한다. 작성자·검토 직원은 허용된 수정 화면에서 영향 안내를 보고 새 근거를 연결할 수 있다. 새 버전 게시 전까지 기존 본문을 자동 수정하지 않는다. 대화·캐시·벡터 색인까지의 영향 추적은 아직 구현 대상이 아니다.

## 변경 파일과 검증

- DB: `src/server/db/schema.ts`, `drizzle/0001_knowledge.sql`. 원본·버전·문단, 위키·버전·근거, 검토 이력 테이블 7개를 추가했다.
- 서버: `src/server/{storage,parsers,jobs,services}`, `src/worker`, `scripts/parse-child.ts`. 세션·권한·범위·상태 전이를 서비스에서 검사한다.
- 화면: `src/app/w/[workspaceId]/{sources,wiki,reviews}`, 관련 콘텐츠 컴포넌트. 마크다운의 원시 HTML과 외부 이미지는 표시하지 않는다.
- API: `/api/workspaces/[workspaceId]` 하위 `sources`, `wiki`, `search`, `reviews`, 버전별 `action`과 원본 `file` 경로.
- 검사: [검증 결과](./VERIFICATION.md), [파서 비교와 결정](./PARSER_EVALUATION.md).

DOCX·PPTX는 초기 비교 평가만 완료했다. 실제 업로드는 TXT·MD·텍스트 PDF만 지원한다. 스캔 PDF·OCR, 이미지 설명, 복잡한 표의 의미, 회사 모델 연결, 운영 배포·백업은 지원 완료로 간주하지 않는다.
