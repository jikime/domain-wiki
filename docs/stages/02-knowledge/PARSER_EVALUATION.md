# 2단계 파서 초기 비교

이 문서는 2단계 당시의 비교 기록이다. 현재 DOCX·PPTX 업로드와 PDF 표 보완은 [5단계](../05-discovery/README.md)에 구현했으며, 당시 표본과 결과는 비교를 위해 보존한다.

평가일: 2026-09-09. 직접 작성한 개발 표본 6개를 사용했다. 실제 고객 문서는 확보되지 않았으며, 아래 결과는 고객 문서 전반의 정확도를 뜻하지 않는다. [기계 판독 결과](../../evaluation/stage-02/results.json)에 파일별 SHA-256·추출 문자열·구조·위치와 필수 검사 결과를 저장했다.

## 재현

```bash
npm ci
npm run evaluation:parsers
```

평가에는 Node.js 22.23.1과 Python 3 표준 라이브러리를 사용한다. 표본을 다시 만들 때는 Chromium이 필요하다.

```bash
npx playwright install chromium
node scripts/generate-parser-fixtures.mjs
python3 scripts/generate-office-fixtures.py
npm run evaluation:parsers
```

PDF 생성 시각에 따라 파일 해시는 달라질 수 있으므로 다시 생성한 표본과 결과를 함께 보관한다. 자동 검사는 조건·부정문·단위·페이지, 스캔·손상 실패, DOCX 표의 값, PPTX 발표자 주석의 총 8항목을 확인한다. 읽기 순서와 표의 의미는 아래 관찰 내용을 함께 읽어야 한다.

## 비교 결과

| 표본 | 서비스 파서 `pdf-parse 2.4.5` | 비교 파서 `officeparser 7.8.0` | 판단 |
| --- | --- | --- | --- |
| 텍스트 PDF 2쪽 | 1쪽 30초·부정문, 2쪽 60초와 페이지 번호 보존 | 두 페이지 구조와 내용 보존. `30 초`처럼 공백이 추가됨 | 현재 표본의 페이지 인용·키워드 일치에는 서비스 파서 채택 |
| 다단·표 PDF 1쪽 | 조건 A 다음 예외 B 순서. 표의 문자는 남지만 셀 구조는 평문으로 변환 | 같은 높이의 좌우 열이 한 줄에 섞임. 표의 문자 보존 | 두 후보 모두 복잡한 배치의 의미 보존을 보장하지 못함. 원문 대조 안내 필수 |

| 손상 PDF | 읽기 실패를 사용자용 문장으로 반환 | `Invalid PDF structure` 오류 | 두 후보 모두 추출 불가 |
| DOCX 표·부정문 | 서비스 업로드 미지원 | 문단·3행 3열 표 구조와 행·열 번호 보존. 30초/10초, 두 부정문 보존 | Office 후보로 유지. 병합 셀·각주·도형·변경 추적 등 추가 평가 필요 |
| PPTX 화면 문구·주석 | 서비스 업로드 미지원 | 슬라이드 1의 문구와 별도 발표자 주석 보존. 원본 도형 ID는 평가 출력에 없음 | 슬라이드만으로 화면 요소의 위치를 설명하기 부족함. 도형 매핑 보완 필요 |

PDF 후보를 같은 Node 프로세스에서 차례로 실행하면 PDF.js의 전역 작업자 버전 충돌(`6.3.289` API와 `5.4.296` 작업자)이 발생했다. 비교 스크립트는 Office 후보를 별도 프로세스로 실행해 각 후보의 독립적인 결과를 얻는다. 서비스 작업자에도 두 PDF 엔진을 한 프로세스에 섞지 않는다.

Office 후보의 의존성 `pdfjs-dist 6.1.200`에서 발견된 높은 심각도의 취약점 때문에 같은 주 버전의 `6.3.289`로 override했다. 이 구성에서 위 6개 파일을 실제 실행했다. `officeparser`는 평가용 개발 의존성으로만 설치하며 서비스 업로드에 연결하지 않는다.

## 원문 위치 검증

서비스 TXT·MD는 1부터 시작하는 행 범위와 가장 가까운 마크다운 제목을 저장한다. PDF는 페이지별 문단으로 나누고, 원본 파일 주소에 `#page=N`을 붙여 연다. 현재 PDF 영역 좌표나 표 셀 좌표를 제공하지 않는다.

Office 비교에서는 Python 표준 ZIP/XML로 **직접 만든 표본의 구조만** 읽어 위치를 대조했다. DOCX의 30초는 본문 요소 3의 표, 2행 2열이며 발표 자료의 조건 문장은 슬라이드 1 도형 ID 4이다. 주석은 별도 notesSlide의 도형 ID 5이다. 결과의 `rawLocations`에 이 위치를 기록했다. DOCX는 화면·폰트·용지 설정에 따라 쪽이 달라질 수 있으므로 임의 페이지 번호를 붙이지 않았다.

## 기존 Rust 파서 재사용 검토

참조 프로젝트 `llm_wiki/src-tauri/src/commands/fs.rs`와 `extract_images.rs`를 읽기 전용으로 검토했다. PDF 경로는 `pdfium-render`와 전역 잠금·네이티브 라이브러리 위치·Tauri 앱 핸들에 의존한다. DOCX는 `docx-rs`와 XML 보완, PPTX는 ZIP/XML 기반 마크다운 추출 로직을 사용한다.

이 코드를 이번 단계에서 서버로 이식하거나 실제 Rust 추출기를 실행하지 않았다. 재사용하려면 Tauri 경로·UI 이벤트에서 문서 변환을 분리하고 원본 버전·문단 UUID·도형/표 위치 계약에 맞춰야 한다. 따라서 이번 결정은 TXT·MD 자체 처리와 텍스트 PDF의 Node 파서 사용이다. 복잡한 PDF·Office는 고객 표본을 확보한 뒤 Rust 분리·Node 보완 중 실제 결과가 나은 쪽을 선택한다.

## 후속 평가 조건

5단계 P5-03에서는 실제 고객의 PDF·PPTX·DOCX로 부정문, 조건과 적용 대상, 숫자·단위, 표의 행·열·병합 관계, 슬라이드 도형·주석, 이미지 설명과 누락을 검증한다. 스캔·혼합 PDF에는 OCR 품질 및 페이지 영역 매핑을 별도로 평가한다. XLSX·HWP/HWPX는 필수 여부부터 확인한다.

참고한 공식 소스: [pdf-parse 저장소](https://github.com/mehmet-kozan/pdf-parse), [OfficeParser 저장소](https://github.com/harshankur/officeParser). 버전·실행 동작은 이 프로젝트의 잠금 파일과 실제 설치 코드를 기준으로 확인했다.
