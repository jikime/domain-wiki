# 8단계 — 공식 자료와 RFP 분석

기관 자료의 원문 확보·검토와 RFP 보고서 작성·게시를 기존 자료실·검토함에 연결했다. 모델 없이 직접 작성할 수 있으며 AI 초안도 직원의 검토를 거쳐야 공유된다. 실제 기관 주소와 대표 RFP는 아직 제공되지 않아 개발 표본으로 기능을 검증했다.

## 화면과 사용 순서

| 화면 | 경로 | 이용 역할·동작 |
| --- | --- | --- |
| 업무 도구 | `/w/[workspaceId]/tools` | 모든 직원. RFP 보고서와 역할에 맞는 도구로 이동 |
| 수집 허용 사이트 | `/w/[workspaceId]/admin/sites` | 관리자. 공식 기관의 HTTPS 주소·허용 경로 등록, 수집 중지·재개 |
| 공식 자료 수집 | `/w/[workspaceId]/tools/official` | 작성·검토 직원. 허용 주소에서 원문을 확보하고 후보 상태 확인 |
| 자료 후보 | `/w/[workspaceId]/tools/official/[candidateId]` | 작성자·검토자 및 확인된 후보를 보는 작성 직원. 원문·해시·첨부·날짜 확인 |
| RFP 보고서 | `/w/[workspaceId]/tools/rfp` | 모든 직원. 일반 직원은 현재 유효한 게시본만 조회 |
| RFP 작성·수정 | `/w/[workspaceId]/tools/rfp/new`, `/[reportId]/edit` | 작성·검토 직원. 원문 선택, 관련 근거 검색, 직접 작성 또는 AI 초안 |
| 보고서 상세 | `/w/[workspaceId]/tools/rfp/[reportId]` | 작성·검토·게시 권한에 따라 버전, 근거, 질문, 검토 이력, Markdown 내려받기 |

1. 관리자가 확인한 기관 주소와 수집할 경로를 등록한다. 사이트 목록은 처음에 비어 있다.
2. 작성 직원이 자료의 제목·URL·도메인·프로젝트를 지정해 원문을 수집한다. 첨부는 각각 선택해 별도로 수집한다.
3. 다른 검토 직원이 추출 원문을 확인해 자료실에 공개하고, 기관·발행일·시행일·첨부를 대조한 기록을 남긴다. 자동 추출한 날짜는 후보일 뿐이며 미확인 날짜는 비워 두고 사유를 기록할 수 있다.
4. RFP 원문을 자료실에 등록·공개한 뒤 ‘이 자료로 RFP 분석 작성’ 또는 업무 도구에서 분석한다.
5. 원문 구절을 인용하고 요구의 의미, 적용 범위, 확인 질문을 작성한다. 관련 기준·사례는 같은 도메인 및 허용된 프로젝트 범위에서 검색한다.
6. 초안을 제출하면 검토함에서 담당자를 지정할 수 있다. 다른 검토 직원의 승인 이후 일반 직원이 보고서와 근거를 열거나 내려받을 수 있다.

## 원문 수집

- HTTPS 기본 포트, 허용한 도메인·경로만 사용한다. 내부·예약 IP, 인증 정보가 포함된 주소, 별도 포트, 허용 범위를 벗어난 이동을 거부한다. DNS 결과를 검사한 IP로 연결하며 이동할 때마다 다시 검사한다.
- HTML 본문 2MiB, PDF·DOCX·PPTX 첨부 10MiB, 수집 시간 30초 제한이다. 서버가 반환한 HTML을 읽고 브라우저 스크립트나 외부 리소스를 실행하지 않는다. 로그인·동적 렌더링·압축 전송·UTF-8 외 HTML은 지원 범위 밖이다.
- HTML 제목·문단·표 행 위치를 추출하고 받은 원본 파일과 SHA-256, 수집 시각, 최종 주소, 날짜 후보, 첨부 주소를 보관한다. HTML 원본은 내려받기로 제공한다. HWP·HWPX·XLSX·ZIP 링크는 지원 여부와 함께 표시하며 자동 변환하지 않는다.
- 같은 요청 번호는 중복 실행하지 않는다. 수집 중 사이트가 중지되면 원본 저장 전에 다시 차단한다. 끊긴 수집은 작업자가 실패 상태로 정리한다.
- 자료실의 공개 승인과 기관 메타정보의 확인은 별도 기록이다. 후보 반려는 이미 공개한 자료의 철회를 대신하지 않는다. 개정·철회된 원문을 가진 후보에는 재확인 표시가 나온다.

## RFP 보고서의 근거와 검토

| 구분 | 저장 조건 |
| --- | --- |
| RFP 명시 요구 | 선택한 RFP 원문의 실제 구절·문단 필수 |
| 관련 기준·의무 | RFP 이외의 공개된 기준 자료 구절·문단 필수. 실제 적용 여부는 검토 |
| 과거 사례 | 별도 프로젝트 자료 또는 검토된 실무 기록의 구절·문단 필수 |
| 분석·추론 | 추론임을 구분하고 확인 질문 필수 |
| 불명확한 범위 | 불명확한 조건과 확인 질문. 보고서 전체에 RFP 근거를 가진 요구 또는 불명확 항목이 하나 이상 필요 |

인용 구절이 실제 근거에 있는지, 근거 ID가 제공된 범위와 현재 공개 상태에 맞는지 서버에서 검사한다. 이 검사는 해석의 정확성이나 기준의 법적 적용을 자동 판정하지 않는다. 적용 예외·부정문·수치·의무와 사례의 차이는 직원이 원문과 대조한다.

보고서 최대 30항목, 근거 문단 총 30개다. AI에 전달할 문단은 RFP 20개·참고 10개, 총 28,000자까지 선택한다. 회사 모델 설정이 없으면 생성 버튼과 안내가 이를 표시하고 직접 작성은 계속 사용할 수 있다.

새 초안은 기존 게시본을 덮어쓰지 않는다. 기준 버전 충돌과 자기 승인을 거부하고 제출·반려·승인·철회 기록을 남긴다. 근거가 개정·철회되면 일반 직원의 목록·상세·내려받기에서 제외하고, 작성자에게 재검토 필요 상태를 보여 준다. 진행 중인 AI 결과도 저장 직전에 같은 검사를 거친다.

원본 영향 화면에 연결된 RFP 보고서가 나타난다. 보고서 근거 또는 수집 확인 이력이 참조하는 원본은 영구 삭제할 수 없다. 원본·검토 근거를 보존하기 위한 기존 정책을 확장한 것이다.

## 실행과 확인

```sh
npm run db:migrate
npm run dev
# 별도 터미널
npm run worker
# 검사
npm run test:official
npm run test:integration
```

[검증 기록](./VERIFICATION.md)과 [실제 팀 시험표](../07-deployment/TEAM_ACCEPTANCE.md)를 함께 참고한다. 실제 기관의 TLS·콘텐츠 형식·개정 구조와 대표 RFP의 AI 분석 품질은 해당 주소·자료·모델을 제공받은 뒤 확인할 항목이다.
