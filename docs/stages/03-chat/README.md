# 3단계 — 근거를 확인하는 직원 채팅

구현 범위: 본인 대화 생성·목록·재열기, 질문 범위, 검색과 스트리밍, 인용 확인, 중지·재시도·피드백, 모델 연결 점검.

**실제 회사 모델 연결과 업무 답변 품질은 아직 검증하지 않았다.** 현재 개발 환경에는 모델 접속 설정이 없다. 별도 시험 DB와 명시적인 시험 응답 서버로 API·저장·권한·오류 처리를 검증한다. 실제 모델 연결 검증이 필요한 P3-02·P3-03은 구현과 검증 상태를 분리해 기록한다.

## 사용하기

1. `npm run db:up`으로 pgvector 확장까지 준비하고 `npm run db:migrate`를 실행한다.
2. `npm run dev`와 별도 터미널의 `npm run worker`를 실행한다. 개발 화면은 <http://localhost:3010>이다.
3. 채팅에서 도메인·프로젝트를 선택한다. 기존 대화의 범위를 바꿀 때는 **범위 적용**을 누른다. 범위 변경 전 질문에는 당시 범위가 보존된다.
4. 질문을 보내고 답변 아래 **근거 확인하기**를 열면 자료 버전과 행·페이지 또는 게시 위키로 이동한다. 자료·위키 상세 화면의 **질문하기**는 해당 자료와 연결 근거로 범위를 좁힌다.
5. 진행 중에는 **답변 중지**, 실패·중단 후에는 **다시 질문**을 사용한다. 다시 질문은 별도의 실행 이력을 남긴다.
6. 답변의 **의견 남기기**로 수정할 조건을 적으면 검토함에 평가와 의견이 전달된다. 개인 대화 본문은 자동 공개하지 않는다.

대화 목록과 본문은 소유자만 볼 수 있다. 관리자도 직원의 대화를 대신 열 수 없다. 원본이 철회·개정되면 관련 과거 답변을 숨기며 후속 질문의 모델 문맥에서 제외한다. 이미 전송된 화면 내용이나 내려받은 파일의 회수를 보장하는 기능은 아니다.

## 회사 모델 설정

관리 화면에서 설정된 모델명과 연결 상태를 확인할 수 있다. **모델 연결 확인**은 업무 자료가 없는 점검 요청을 보내 채팅 스트림과 임베딩 벡터 수신 여부를 확인한다.

`.env.local` 또는 운영 환경 변수에 아래 값을 넣는다. 키는 저장소에 커밋하거나 브라우저용 환경 변수로 만들지 않는다.

```dotenv
AI_BASE_URL=https://company-model.example/v1
AI_MODEL=company-chat-model
AI_API_KEY=SET_ON_SERVER_ONLY
AI_EMBEDDING_MODEL=company-embedding-model
# 임베딩 서버가 별도일 때만 지정
AI_EMBEDDING_BASE_URL=
AI_EMBEDDING_API_KEY=
AI_TIMEOUT_SECONDS=90
AI_MAX_CONCURRENT=3
```

변경 후 웹 서버와 작업자를 재시작한다. `chat/completions`, `embeddings` 방식의 회사 호환 서버를 대상으로 한다. URL 끝에 붙인 요청 경로는 중복되지 않게 정리한다. vLLM의 [공식 서버 문서](https://docs.vllm.ai/en/latest/serving/online_serving/)를 참고해 서버가 제공하는 모델과 기능을 확인한다. Azure 배포 주소·Anthropic 전용 메시지 프로토콜·CLI 실행은 이 연결 방식의 지원 대상에 포함되지 않는다.

임베딩이 없거나 실패하면 이유를 표시하고 키워드 검색을 사용한다. 작업자는 10초 간격으로 아직 색인이 없는 공개 자료를 확인한다. 현재 저장 단위는 원본 문단과 게시 위키 버전이며, 한 주기·작업공간당 최대 16개를 처리한다. 다시 실행해도 같은 모델·대상의 벡터가 중복 저장되지 않는다.

벡터는 모델·서버 식별값과 차원을 함께 저장하고, 현재 공개 상태와 선택 범위를 다시 결합해 검색한다. 현재는 pgvector의 정확한 코사인 거리 검색을 사용한다. 모델 차원·자료 규모가 확정되기 전에는 HNSW 근사 색인을 임의로 만들지 않는다. 서로 다른 차원의 벡터 저장과 색인 조건은 [pgvector 공식 설명](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column)을 따른다.

## 참조 코드와 웹 적용

- `llm_wiki/src/lib/llm-client.ts`: 스트림 버퍼·UTF-8 분할·최종 레코드·완료 전 단절 처리를 참고했다. Tauri 전송 대신 서버 `fetch`를 사용한다.
- `llm_wiki/src/lib/endpoint-normalizer.ts`: 입력한 URL의 중복 요청 경로를 정리하는 방식에 맞췄다.
- `llm_wiki/src/lib/search.ts`, `search-rrf.test.ts`: 검색 결과의 순위를 결합하는 방식을 웹 DB에 적용했다. 한국어 기본 토큰과 현재 공개 조건은 웹 서비스에서 관리한다.
- 개인 파일 경로와 클라이언트 모델 키 저장은 복사하지 않았다. 본인 대화, 조직 소속, 공개 버전 조건을 서버에서 추가했다.

## 동작과 한계

인용 검증은 제공된 근거 ID의 존재를 검사한다. 모델의 각 주장과 원문이 의미상 일치한다는 증명은 아니므로 실제 회사 질문·문서로 평가해야 한다. 스트리밍 중 내용은 작성 중임을 표시하며 최종 인용 검증에 실패하면 성공 답변으로 보관하지 않는다.

현재 한 실행은 최대 8개 검색 근거를 사용하며, 위키 문맥은 버전 본문의 앞 10,000자까지다. 후속 질문에는 현재 유효한 최근 대화를 사용하고, 이전 답변은 이번에도 모든 연결 근거를 확인할 수 있을 때만 모델에 전달한다. 이전 답변의 인용 번호를 현재 근거 번호로 오인하지 않도록 제거한다.

한 대화에서 하나의 답변만 작성한다. 작업공간 동시 실행 수를 DB 잠금으로 제한하며 요청 ID가 같은 재전송은 기존 실행을 반환한다. 살아 있는 스트림은 주기적으로 실행 상태를 갱신하고, 30초 이상 갱신이 없는 실행은 다음 조회 때 연결 중단으로 정리한다. 서버 시간 제한은 기본 90초다.
