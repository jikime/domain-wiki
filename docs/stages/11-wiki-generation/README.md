# 11단계 — 기존 지식 대조와 여러 위키 변경안

2026-09-09 구현·검증 완료. 전체 분석 결과를 현재 공개된 관련 지식과 비교하고, 여러 위키의 변경안을 작은 검토 묶음으로 연결한다.

## Purpose 보완

추가 요청인 `purpose.md`의 역할을 도메인 설정에 적용했다. 기존 목적은 유지하며 핵심 질문·포함할 범위·제외할 범위·잠정 판단·성공 기준을 선택 입력한다. `purpose_guide` JSON에 저장하고 기존 도메인 수정 API의 관리자 권한·작업공간 경계를 유지한다. 기존 요청이 이 필드를 생략하면 저장된 선택 항목을 지우지 않는다.

요약·문서 전체 분석·기존 단일 위키 생성은 같은 도메인 목적·용어·양식·선택 항목을 읽는다. 가정을 사실로 다루거나 제외 범위라는 이유로 원문 조건을 누락하지 않도록 지시한다. 전체 분석 입력 예산과 규칙 해시에 포함하고, 선택 항목이 모두 비어 있으면 이전 분석 해시를 유지한다. 실행 기준이 바뀐 대기 작업은 호출 전에 실패하며 단일 변경안도 저장 트랜잭션에서 도메인을 잠그고 같은 기준인지 다시 검사한다. 채팅·품질 점검 연결은 각각 13·14단계의 작업이다.

- DB 마이그레이션 `0011_domain_purpose` 적용, 빌드·TypeScript 및 Biome 검사 통과.
- Purpose 전용 통합시험 4개 통과(27.9초). 저장·복원·비우기·기존 API 호환·권한·범위·길이 검사, 세 종류 모델 입력, 대기 및 실행 중 기준 변경, 입력 예산 초과 시 호출 차단을 확인했다. 고정 응답 모델을 사용한 계약 검사이며 실제 모델의 업무 품질 판정은 아니다.
- 전체 회귀 중 저장 직후의 관리 폼 재편집이 늦게 도착한 서버 화면으로 초기화되는 문제를 확인했다. `SettingsForm`이 저장 후 화면 갱신까지 기다리도록 수정했다. 의도적으로 화면 응답을 지연한 권한 검사 및 Purpose를 포함한 관련 8개 시험이 47.9초에 통과했다. 최종 전체 회귀 143개가 6.9분에 통과했다.
- 실제 개발 화면 1440px·390px에서 HTTP 200, 가로 넘침 0, 브라우저 오류 0. [화면 검사](purpose-browser-check.json), [데스크톱](purpose-1440.png), [모바일](purpose-390.png). 화면 예시는 새 도메인 폼에 입력만 했으며 업무 설정에 저장하지 않았다. 긴 폼 캡처에서 고정 헤더가 본문을 가리지 않도록 캡처에만 헤더 고정을 해제했다.

## 분석 기반 위키 생성

완료된 전체 분석에서 `분석으로 위키 생성`을 실행한다. 현재 원문 버전·도메인 기준·모델·분석 프롬프트가 같은 분석만 사용한다. 작업은 서버에서 지속되며 계획과 페이지별 완료 단계를 저장한다. 실패·취소 후에는 완료한 계획과 본문을 재사용한다.

- 같은 작업공간·도메인의 현재 공개 지식 중 해당 프로젝트와 도메인 공통 자료만 대조한다. 공통 자료는 참고할 수 있지만 다른 프로젝트 범위에서 수정·병합하지 않는다. 현재 위키 최대 20개와 관련 원문 최대 10문단을 후보로 넣고, 각 위키 본문과 근거를 온전히 전달한다. 입력에 넣지 못한 후보는 이유를 기록한다. 후보 검색은 단어·분석 대상·공통 원문을 이용하며 4신호 관계 검색은 13단계에서 추가한다.
- 모든 분석 주장을 문서 요약 페이지에 배정하며, 독립적으로 활용할 대상·개념·절차·사례 등의 페이지를 함께 계획한다. 제목이 같다는 이유만으로 같은 대상으로 확정하지 않도록 적용 범위와 변경 이유를 요구한다. 모델의 ID·중복 대상·근거 누락·잘못된 페이지 참조를 검사한다.
- 페이지별 본문은 배정한 원문 주장으로 생성한다. 수치·단위 조합·부정·명시적 적용 조건·대상을 원문 인용과 대조한다. 기존 본문과 병합 대상의 본문·원문 근거는 보존하고 추가 단락을 붙인다. 삭제·교체·모순 확인이 필요한 변경은 직원 수정과 확인 표시를 거쳐 다시 검토한다. 문장 의미의 완전한 일치를 보증하는 검사는 아니다.
- 새 페이지 주소는 작업 ID와 계획 키로 고정한다. 서로 참조하는 페이지는 같은 묶음에서 원자적으로 승인한다. 한 묶음 최대 5개, 전체 최대 40개이며 6개 이상 순환 참조는 명시적으로 차단한다. 다른 묶음을 참조하면 그 묶음을 먼저 승인해야 한다. 검토 화면의 미게시 링크는 해당 검토 페이지로 연결하고 일반 직원에게 초안을 공개하지 않는다.
- 수정은 같은 페이지 식별자와 그룹 번호를 유지한 새 변경 묶음으로 저장한다. 목록·검토함·미처리 활동에는 최신 수정만 표시하고 이전 내용과 결정 이력은 보존한다. 오래된 묶음의 승인과 승인 후 재제출을 차단한다. 승인 시 대상 버전·공개 근거·연결·선행 묶음을 다시 검사하고 하나라도 충돌하면 전체 게시를 되돌린다.
- 공개 원문·대조 자료·작성 권한이 바뀌면 진행 중 결과 저장을 차단하며, 완료 작업과 검토 화면의 이전 본문도 숨긴다. 수정 과정에서 추가한 원문 역시 검사한다. 계획에 사용한 위키를 이 작업 자체가 승인·병합한 경우에는 완료 결과를 계속 확인할 수 있다.
- `wiki_version.metadata`에 유형·별칭·본문 링크와 연결 이유를 저장한다. 직원이 게시 위키를 직접 수정하거나 수동 변경 묶음으로 수정해도 유형·별칭을 보존하며 링크는 실제 마크다운 AST에서 다시 읽는다. 수동 위키 본문에는 생성 계획의 40개 링크 제한을 적용하지 않고 최대 500개 관계를 저장한다. 코드 예시·이미지 주소는 위키 관계로 계산하지 않는다. 공개 위키 목록·활동 기록·도메인 홈이 원본의 index·log·overview 역할을 맡는다.

DB 마이그레이션 `0012_wiki_generation`은 분석 작업 연결, 생성 묶음의 작업·그룹·수정·의존 관계, 예정 페이지 ID와 버전별 메타데이터를 지원한다. 수동 변경 묶음의 기존 API는 유지하며 자동 생성 전용 필드를 임의의 수동 요청에 추가하는 것은 차단한다.

## 입력과 지원 한도

생성 계획은 전체 분석을 한 번에 읽는다. 직렬화한 입력이 모델 입력 설정의 85%를 넘으면 일부 분석을 잘라 성공으로 처리하지 않고 입력 공간 부족으로 실패한다. 필요한 경우 모델 입력 설정을 늘려 새 분석·생성 작업을 시작해야 한다. 계획 자체를 여러 호출로 나누는 기능은 아직 없다. 한 페이지 변경안은 기존 본문을 포함해 20,000자·원문 근거 30문단까지이며 초과 시 분리가 필요하다는 오류를 표시한다.

기존 본문은 자동으로 재작성하거나 지우지 않으므로 중복 단락이 생길 수 있다. 검토자가 대조 화면에서 내용을 정리한다. 자동 승인, 고객 문서의 정답 판정, 모델의 의미 정확성 보장은 포함하지 않는다.

## 검증 결과

최종 전용 시험 20개를 포함한 전체 통합시험 143개가 6.9분에 통과했다. 빌드·TypeScript와 Biome 260개 파일 검사도 통과했다. 여섯 페이지·두 묶음, 순환 참조의 동시 게시, 의존 순서, 수정 후 주소 유지, 오래된 묶음 차단, 부분 실패 재시도, 잘못된 ID·수치·링크, 기존 위키 보완·병합, 권한·공개 상태 변경을 확인했다. 수정 시 추가한 원문 철회, 입력 한도 초과 시 호출 0회, 미완료 분석 차단까지 확인했다. 전체 회귀에서 기존 검색·채팅·문서 처리·권한·복구·편집 동작도 통과했다. 일곱 가지 오류 응답을 한 시험에 묶은 검사에서 제한 시간이 초과되어 항목별 독립 시험으로 분리했다. 모의 모델의 지연·오류 조건도 대조 원문 속 일반 단어가 아니라 해당 시험 원문의 제목으로 선택하도록 한정했다. 검사 제한 시간을 늘리거나 재시도·건너뛰기를 추가하지 않았다. 수동 위키의 60개 링크와 변경 묶음 수정 후 유형·별칭 보존 검사도 추가해 총 20개 전용 항목을 최종 회귀에 포함했다.

실제 모델의 첫 계획 두 번은 `kind`에 지식 분류를 넣고 `type`을 생략하여 차단됐다. 유효하지 않은 응답으로 변경 묶음을 저장하지 않았다. `wiki-generation-v2`에는 두 필드의 차이와 생성 스키마를 명시했다. 새 작업에서 위키 2개를 생성했고 분석 주장 14/14개와 중요 조건 6/6개를 확인했다. 작성·검토·일반 직원 계정으로 브라우저 검토 요청·승인·게시 위키와 상호 링크 열기까지 통과했다.
