# 4단계 — 실무 경험과 위키 변경 묶음

2026-09-09. 실무 기록·변경 묶음·AI 생성 API와 화면을 구현했다. 실제 회사 모델이 설정되지 않아 AI 생성 품질 평가는 별도로 남긴다.

## 사용할 수 있는 흐름

1. **실무 기록**에서 상황, 판단 이유, 결과, 추가 확인 사항을 작성한다. 작성 당시 메모와 공개 원문 연결은 선택 사항이다.
2. 저장하면 작성자 진술인 Markdown 원본과 구조화된 항목을 같은 버전에 보관한다. 문서 처리·검토·공개는 자료실과 같은 절차를 따른다. 개정은 이전 진술을 바꾸지 않고 새 버전으로 저장한다.
3. 공개된 자료에서 **AI 위키 변경안 만들기**를 연다. 사용할 원문 문단과 새 위키 또는 수정할 기존 위키를 고를 수 있다.
4. **위키 변경 묶음**에서 최대 5개의 신규·수정·병합·모순 확인 제안을 함께 작성한다. 본문, 이유, 근거와 기준 버전을 저장하고 묶음 검토를 요청한다.
5. 검토자는 변경 전후 차이와 원문을 확인한 뒤 전체 승인하거나 수정 요청한다. 본인 작성 묶음은 다른 검토자가 승인해야 한다.
6. AI 메모 정리는 먼저 제안을 보여주며, 직원이 확인하고 반영해야 작성 항목이 바뀐다. 작성 당시 메모는 유지한다.
7. 작성 직원은 본인의 완료된 채팅 답변을 지식 제안으로 남길 수 있다. 답변과 원문 근거를 검토자에게 전달한다는 안내를 먼저 표시한다. 다른 질문·대화는 공유하지 않으며 답변을 새 원본으로 만들지 않는다.

## 정확한 버전과 묶음 승인

- 저장한 변경 묶음의 본문·근거·대상 버전은 고정된다. 수정할 때 새 묶음을 저장하고 이전 묶음을 연결한다.
- 제출·승인 시 도메인·프로젝트, 원문의 현재 공개 상태, 위키의 최신·게시 버전을 다시 검사한다.
- 승인은 한 DB 트랜잭션에서 묶음 전체를 처리한다. 하나라도 충돌하면 아무 위키도 게시하지 않는다.
- 병합은 기존 위키의 근거를 모두 연결해야 한다. 승인하면 대상 위키의 새 버전을 게시하고 병합한 기존 위키의 게시를 철회한다. 이전 버전과 원문은 보존한다.
- 모순 확인 제안은 바로 승인할 수 없다. 원문을 대조하고 새 변경 묶음으로 수정해야 한다.

## AI 입력·출력 경계

- 원문 생성은 현재 공개된 문단 중 최대 20개·18,000자를 전달한다. 초과하면 직원이 나누어 선택한다. 기존 위키는 문맥으로만 제공한다.
- 모델이 반환한 근거 ID는 실제 전달한 ID의 부분집합이어야 한다. 없는 ID·중복 ID·잘못된 응답·중단된 답변을 거부한다.
- 참조 프로젝트의 `ingest.ts` FILE 블록 해석과 `ingest-sanitize.ts` 정제 함수를 순수 TypeScript 파일로 분리했다. CRLF, 코드 울타리, 미완성 블록, 위험한 경로를 검사한다. 모델의 파일 경로로 서버 파일을 쓰지 않는다.
- 작업의 요청 ID·입력 해시·상태·모델·토큰 사용량을 저장한다. 같은 요청을 재전송해도 같은 결과를 돌려준다. 한 공간의 동시 생성은 3개이며 오래 끊긴 작업은 다음 생성 요청에서 실패로 정리한다.
- 생성 완료와 변경 묶음 저장은 같은 트랜잭션으로 연결한다. 답변에서 만드는 제안은 원문으로 관계를 거슬러 올라가며, 기존 AI 답변이 독립적인 근거가 되지 않는다.

## 품질 확인의 범위

같은 범위의 같은 제목과 의무·부정·수치·예외 표현을 검토 단서로 표시한다. 이는 의미상 중복·모순의 자동 판정을 보증하지 않는다. 실제 회사 모델과 고객 자료로 사실·수치·부정문 보존을 평가해야 한다.

모델 설정이 없으면 실제 오류 안내를 표시한다. 시험용 응답 서버는 별도 시험 DB·환경에서만 사용했으며 개발 화면의 모델로 연결하지 않았다.
