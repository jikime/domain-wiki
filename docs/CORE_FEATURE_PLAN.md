## 목표와 완료 범위

직원이 자료를 등록하고 원본의 공개를 승인하면, 시스템이 추출된 문서 전체를 분석해 기존 지식과 비교하고 여러 위키의 변경안을 만든다. 검토자가 승인한 내용은 위키·관계·검색에 반영된다. 원본 개정 시 필요한 부분을 다시 정리하고, 위키 전체의 문제를 찾아 검토 작업으로 연결한다.

원본의 세 핵심 동작인 **수집·위키 구축(Ingest), 검색·질의(Query), 품질 점검(Lint)**을 회사용 서비스에서 완성하는 것이 이번 범위다. 데스크톱 저장 방식·모든 파일 형식·외부 연동까지 원본 전체와 같아진다는 의미는 아니다. 파일 생성 대신 DB의 페이지·버전·근거·검토 묶음으로 결과를 저장한다.

자동화의 기본 흐름:

```text
자료 등록 → 원문 추출·확인 → 원본 공개 승인
  → 문서 전체 분석 → 기존 지식 대조 → 여러 위키 변경안 생성
  → 직원 검토·승인 → 게시 위키·관계·검색 갱신 → 근거 기반 채팅

원본 개정·철회 → 영향 확인 → 필요한 분석·변경안 재생성 → 재검토
정기 품질 점검 → 문제 후보·근거 확인 → 수정 변경안 → 재검토
```

AI 결과의 생성과 팀에 게시하는 승인은 구분한다. 기존 작성자·검토자 분리, 작업공간·도메인·프로젝트 범위, 현재 공개 근거 검사, 개인 대화 보호를 모든 단계에 적용한다.

추가 사용자 요청인 **Purpose와 Knowledge Graph with Relevance Model**은 [원본 코드 검토](audits/2026-09-09/PURPOSE_GRAPH_REVIEW.md)를 기준으로 아래 단계에 적용한다. 현재 전체 분석에 사용 중인 도메인 목적을 보완하고 생성·질의·품질 점검에 일관되게 전달한다. 원본의 그래프 화면용 점수와 Rust 채팅 검색은 별도 구현이므로, 점수 계산을 옮기는 것만으로 검색 적용을 완료했다고 보지 않는다.

착수 당시 `generation.ts`의 단일 AI 생성은 HTTP 요청 수명에 연결돼 있었다. 파일 추출 큐와 별도로 장시간 AI 분석의 재개 구조가 필요했다. 참조의 `graph-search.ts`는 그래프 화면 필터이므로, 질의의 관계 확장에는 `graph-relevance.ts`와 관련 문맥 구성 코드를 따로 적용했다.

## 단계와 실행 작업

### 9단계 — 모델·평가 기준과 AI 작업 기반

목표: 실제 모델과 비교할 기준을 만들고, 오래 걸리는 AI 작업을 서버가 관리한다.

- [x] **P9-01** 참조 버전·기능별 입력/출력·재사용할 함수와 웹에서 대체할 부분을 기록한다. 기존 75개 통합시험을 회귀 기준으로 등록한다.
- [x] **P9-02** 서버 모델 설정을 채팅·지식 생성·임베딩 용도로 구분한다. 기존 공통 설정을 기본값으로 유지하고 관리 화면에서 설정 여부·연결·문맥 제한을 확인한다. 비밀키는 서버에서만 다룬다.
- [x] **P9-03** 문서 버전별 AI 실행·단계별 결과·원문 처리 범위·사용량을 저장한다. 영속 큐, 실행 중 갱신, 취소·재시도·작업자 재시작, 같은 작업의 중복 결과 방지를 구현한다. 기존 생성 작업의 고정 3분 실패 정리를 장기 실행과 충돌하지 않도록 수정한다.
- [x] **P9-04** 개발 평가 문서와 실제 자료 평가표를 준비하고 현재 검색·답변·단일 변경안의 기준 결과를 기록한다. 같은 역할·원문·질문·모델 설정으로 후속 결과를 비교한다.

통과 기준: 웹을 닫거나 작업자를 중지해도 실행 상태를 복구하며 완료 결과를 중복 저장하지 않는다. 비활성 계정·철회된 원문·범위 밖 자료의 후속 처리를 차단한다. 모델이 없는 상태는 명시적으로 대기 처리한다. 실제 모델 연결 검증은 실제 설정을 받은 뒤 별도 통과시킨다.

9단계 결과: [구현·검증 기록](stages/09-ai-foundation/README.md), [실제 모델 기준 평가](evaluation/core/baseline-09/README.md). 전체 104개 및 최종 보완 관련 24개 통합시험 통과. 고객 문서·업무 담당자 평가는 미검증이다.

### 10단계 — 긴 문서 전체의 구조화 분석

목표: 문단을 사람이 나누어 고르지 않아도 문서 전체의 사실·조건·개념을 분석한다.

- [x] **P10-01** 제목·절·표의 구조를 유지하며 모델 입력 예산에 맞게 분석 단위를 나눈다. 각 단위를 원문 버전·문단·위치와 연결한다.
- [x] **P10-02** 원본 `buildAnalysisPrompt`, `splitSourceIntoSemanticChunks`, 문맥 예산 계산을 분리·적용한다. 도메인 목적·용어·지식 유형을 문맥으로 제공한다.
- [x] **P10-03** 단위별 핵심 개념·대상·사실·의무·예외·수치·불명확 사항을 구조화된 결과로 저장하고 문서 단위로 통합한다. 각 주장에는 원문 구절·문단 근거를 붙인다.
- [x] **P10-04** 자료 상세의 분석 상태에 처리 범위, 실패한 구간, 재시도와 요약을 제공한다. 일부 단위가 실패한 실행을 전체 분석 완료로 표시하지 않는다.

통과 기준: 추출된 모든 문단은 처리 결과 또는 명시적 제외 사유를 갖는다. 문서 끝·표·각주의 중요 조건도 고정 평가에서 확인한다. 부정문·단위·대상의 혼합을 검사하고 중간 실패 후 이미 완료한 단위를 불필요하게 다시 호출하지 않는다. OCR로 읽지 못한 페이지까지 분석했다고 표시하지 않는다.

10단계 결과: [구현·검증 기록](stages/10-document-analysis/README.md), [실제 모델 평가](evaluation/core/analysis-10/README.md). 최종 전체 115개 통합시험 통과. 실제 모델로 14문단 전체와 중요 조건 6개를 확인했으며 고객 업무 품질 판정은 미검증이다.

### 11단계 — 기존 지식 대조와 여러 위키의 자동 변경안

목표: 분석 결과를 문서 요약·개념·절차·사례 등의 위키로 연결한다.

- [x] **P11-01** 현재 공개된 같은 범위의 위키·원문에서 관련 후보를 검색한다. 제목이 같다는 이유만으로 같은 개념으로 확정하지 않는다.
- [x] **P11-02** 저장한 분석을 입력으로 두 번째 생성 단계를 실행한다. 도메인의 유형·양식에 맞춰 신규·보완·병합·모순 확인을 구분하고 근거 있는 페이지에 한해 제안한다.
- [x] **P11-03** 문서 요약, 대상 페이지 목록, 변경 이유, 근거, 해결되지 않은 질문을 묶어 기존 검토함에 연결한다. 현재 최대 5개 제안 제한은 전체 작업을 작은 묶음으로 나누되 상태와 의존 관계를 추적하는 방식으로 확장한다.
- [x] **P11-04** 같은 묶음의 새 페이지끼리 참조할 수 있는 안정적인 식별자를 부여한다. 검토 화면에서 분석 범위·변경 전후·원문을 대조하고 승인된 묶음만 반영한다. 공개된 페이지 목록·활동 이력·도메인 개요로 원본의 index·log·overview 역할을 구현한다.
- [x] **P11-05** 기존 도메인 목적을 보존하면서 핵심 질문·포함/제외 범위·잠정 판단·성공 기준을 관리 화면에서 편집한다. 분석·생성에 같은 기준을 전달하고 규칙 해시·입력 예산에 포함한다. 목적을 사실 근거로 사용하거나 목적에 덜 맞는다는 이유로 원문 처리 범위를 누락하지 않는다.

페이지 목록·활동 이력은 DB 기록에서 구성한다. AI가 작성한 도메인 개요에는 다른 위키와 같은 원문 근거·검토·개정 규칙을 적용한다.

통과 기준: 하나의 평가 문서에서 필요한 여러 위키의 변경안을 만들고 각 근거로 이동할 수 있다. 허위 원문 ID·미완성 응답·존재하지 않는 페이지 참조를 검사한다. 한 묶음은 원자적으로 반영하며 묶음 간에는 반영·대기 상태를 명확히 표시한다. 새 위키 간 링크가 미승인 내용을 노출하지 않고, 검토 중 기존 페이지가 바뀌면 재검토한다. 생성 실패를 내용 없는 성공 페이지로 대체하지 않는다.

11단계 결과: [구현·검증 기록](stages/11-wiki-generation/README.md), [실제 모델 평가](evaluation/core/generation-11/README.md). 전용 20개를 포함한 전체 143개 통합시험 통과. 실제 모델로 2개 위키 생성·검토·게시, 분석 주장 14/14개와 중요 조건 6/6개를 확인했다. 고객 업무 품질 평가는 미검증이다.

### 12단계 — 자동 실행·증분 갱신·캐시

목표: 자료의 등록·개정에 따라 필요한 정리만 자동으로 수행한다.

- [x] **P12-01** 도메인별 자동 정리 설정과 수동 실행을 제공한다. 기본 실행 조건은 원문 추출 완료와 공개 승인이다. 승인 이벤트와 작업 등록 사이의 누락·중복을 복구할 수 있게 연결한다.
- [x] **P12-02** 원본 내용·분석 단위·파서·모델·프롬프트·도메인 규칙을 식별해 결과를 재사용한다. 같은 요청 ID 처리와 분석 캐시는 구분한다.
- [x] **P12-03** 변경된 단위와 그 영향을 받는 통합 분석·위키만 다시 처리한다. 원문 분석은 같아도 관련 위키가 개정되면 기존 지식 대조·생성은 갱신한다. 원본의 내용이 같더라도 새 버전의 실제 문단 ID로 근거를 다시 연결하고 검증한다.
- [x] **P12-04** 원본 개정·철회·삭제 요청, 모델 변경, 미처리 검토안, 진행 중 동시 실행을 조정한다. 자료 목록에 자동 정리 상태·결과·재시도·재사용 여부를 표시한다.

통과 기준: 같은 파일·같은 설정·유효한 결과의 재처리에서는 새 AI 호출과 중복 변경안이 생기지 않는다. 일부 개정은 필요한 범위만 다시 처리하고 변경된 절이 문서 전체의 의미에 영향을 주면 통합·생성도 재실행한다. 사용자가 수정한 게시 위키를 과거 캐시로 덮어쓰지 않는다. 철회된 근거를 캐시·기존 초안·실행 중 결과에서 재사용하지 않는다.

12단계 결과: [구현·검증 기록](stages/12-ingest-automation/README.md), [실제 모델 평가](evaluation/core/ingest-12/README.md). 전체 165개 및 최종 생성 프롬프트 보완 관련 42개 통합시험 통과. 실제 원문 자동 정리·개정·검토·게시, 기존 2개 위키 주소 유지, 분석 구간 재사용 및 같은 실행의 추가 호출 0을 확인했다. 고객 업무 품질은 미검증이며 긴 입력의 임베딩 색인 한도 문제는 다음 검색 단계에서 보완한다.

### 13단계 — 위키 관계와 그래프를 이용한 검색

목표: 문구가 직접 겹치지 않는 관련 지식까지 근거로 찾는다.

- [x] **P13-01** 위키 유형·별칭·위키 간 링크·공통 원문 관계를 버전에 연결해 저장한다. 기존 위키는 내용을 덮어쓰지 않고 관계를 재구성한다. 이름 변경·중복 이름·병합·철회를 처리한다.
- [x] **P13-02** 원본 `graph-relevance.ts`의 직접 링크·공통 출처·공통 이웃·유형 관계를 적용한다. 기존 키워드·벡터 검색의 상위 후보에서 제한된 1~2단계 관계 탐색을 수행한다.
- [x] **P13-03** 각 탐색 단계에서 현재 공개·도메인·프로젝트 조건을 적용한다. 제한된 중간 노드를 통해 다른 자료의 존재가 드러나는 것도 차단한다. 그래프 장애 시 기존 검색으로 되돌아간다.
- [x] **P13-04** 모델 문맥에 질문·후속 대화·원문·위키·관계 근거를 예산에 맞춰 배분한다. 답변 근거에 실제 원문 위치를 유지하고 ‘원문만 사용’ 범위를 명시적으로 제공한다.
- [x] **P13-05** 선택한 범위의 Purpose·용어를 채팅 문맥에 포함하고 여러 도메인의 기준을 구분한다. 근거가 없는 목적·가정은 사실 인용에 사용하지 않는다. 관계 점수는 4개 신호의 내역을 보존하고 유형 점수만으로 관계를 생성하지 않는다. 캐시에는 작업공간·검색 범위·공개 버전·설정을 포함한다.

통과 기준: 직접 키워드가 부족한 관계 질문에서 필요한 원문을 찾고, 관련성만 있는 페이지를 사실의 근거로 단정하지 않는다. 기존 중요한 질문의 근거 검색이 나빠지지 않는지 상위 근거 재현율을 비교한다. 잘린 위키 본문·긴 원문·후속 질문도 예산 범위 안에서 처리한다. 비공개 노드·간선·집계는 일반 직원에게 노출되지 않는다.

13단계 결과: [관계 검색·문맥·원문만 사용](stages/13-graph-search/README.md). 전체 177개 E2E와 최종 채팅 25개 재검사, 기존 기대 근거 7/7 회귀, 실제 모델의 간접 원문 비교를 확인했다. 고객 업무 검토는 미검증이다.

### 14단계 — 위키 전체 품질 점검과 수정 흐름

목표: 지식이 쌓일수록 늘어나는 오류를 발견하고 수정까지 추적한다.

- [x] **P14-01** `lint-structural-core.ts`를 DB 페이지·관계 입력으로 적용한다. 끊긴 링크, 근거가 없는 페이지, 오래된 근거, 연결이 부족한 페이지를 검사한다.
- [x] **P14-02** `lint.ts`의 의미 점검을 별도 AI 작업으로 실행한다. 중복·상충하는 조건·빠진 설명을 근거 구절과 함께 문제 후보로 기록한다. 관계가 적다는 이유만으로 잘못된 문서로 단정하지 않는다.
- [x] **P14-03** 새 품질 점검 화면과 기존 검토함을 연결한다. 범위·심각도·담당자·원문을 확인하고 수정 변경안 작성→검토→재점검으로 이어지게 한다.
- [x] **P14-04** 수동·정기·개정 후 점검, 같은 문제의 중복 등록 방지, 보류 사유, 해결·재발 이력을 구현한다. 페이지·근거 버전이 바뀌면 이전 판정을 다시 확인한다.
- [x] **P14-05** Purpose의 핵심 질문·범위에 따른 설명 부족을 문제 후보에 연결한다. 목적 밖 자료를 자동 오류 판정하지 않고, 목적 변경은 검토 제안과 관리자 저장으로 처리한다.

통과 기준: 고정 표본의 구조 오류를 발견하고 정상 페이지의 오탐을 확인한다. 의미 점검의 결과에는 비교 근거가 있어야 하며 자동으로 사실이나 수정 승인으로 취급하지 않는다. 수정 후 다시 점검해 문제 해결을 확인하고, AI 분석과 점검이 서로 무한히 새 작업을 만들지 않는다.

14단계 결과: [구현·검증](stages/14-quality-review/README.md), [실제 모델 개정 전후 대조](evaluation/core/quality-14/README.md). 전체 E2E 192개 통과.

### 15단계 — 지식 그래프 화면·군집·공백 탐색

목표: 직원이 지식의 관계와 부족한 부분을 탐색할 수 있게 한다.

- [x] **P15-01** 그래프 화면에 유형·도메인·프로젝트·검색 필터, 확대·축소·선택한 노드의 근거·본문 이동을 제공한다. 기존 작은 관련 보기와 같은 관계 데이터를 사용한다.
- [x] **P15-02** 원본 `wiki-graph-analysis.ts`의 군집 분석과 `graph-insights.ts`의 고립·희박한 연결·연결 지점 탐색을 분리해 적용한다. 사실 관계와 계산된 관련성은 표시를 구분한다.
- [x] **P15-03** 지식 공백에서 자료 등록·검토 요청·질문으로 이동한다. 외부 웹 조사는 후속 확장으로 분리한다.
- [x] **P15-04** 규모가 커져도 화면을 막지 않도록 노드 수·탐색 범위 제한, 비동기 계산·취소·캐시를 적용한다. 모바일에서는 목록으로도 같은 정보를 탐색할 수 있게 한다.

통과 기준: 선택한 관계의 이유와 원문을 확인할 수 있다. 같은 버전·설정에서 군집 결과를 재현하고 개정 후 갱신한다. 제한된 데이터의 수·이름·관계가 시각화나 군집 설명에 섞이지 않는다. 대표 규모에서 화면 반응·메모리·조회 시간을 기록하고 모바일·키보드 대체 경로를 확인한다.

15단계 결과: [그래프·군집·연결 보완](stages/15-knowledge-graph/README.md), [개발 자료 브라우저 확인](evaluation/core/graph-15/README.md). 전체 E2E 198개, 데스크톱·모바일 4개 화면 통과.

### 16단계 — 실제 모델로 핵심 흐름 검증·운영 반영

목표: 기능이 있다는 것과 실제 업무에 쓸 수 있다는 것을 함께 확인한다.

- [x] **P16-01** 동일한 자료·모델·평가 질문으로 변경 전 결과와 새 결과를 비교한다. 가능하면 원본 앱도 별도 시험 복사본에서 실행해 입력·출력·누락 기능을 비교한다. 현재 참조 저장소 자체의 업무 데이터는 변경하지 않는다.
- [x] **P16-02** 직접 질문, 후속 질문, 다른 프로젝트 조건, 개정 전후, 간접 관계, 근거 부족을 포함한 고정 평가와 별도 새 질문을 실행한다. 검색 근거, 인용·사실·수치·부정문, 생성 페이지의 유용성, 시간·토큰 비용을 기록한다.
- [x] **P16-03** 원본 등록→공개→전체 분석→자동 변경안→검토→게시→채팅→개정→재검토→품질 점검을 실제 계정과 브라우저로 확인한다. 기존 기능과 신규 통합시험, 작업자 중단·중복·동시 개정 시험을 통과시킨다.
- [x] **P16-04** 새 분석·캐시·관계·품질 결과까지 포함해 빈 DB 마이그레이션, 운영 이미지, DB+원본 백업·새 환경 복원·실패 복귀를 검증한다. 기능별로 구현·계약 시험·실제 모델 시험·업무 검토 결과를 분리해 완료표를 작성한다.

통과 기준: 평가 표본에서 중요한 부정문·수치·적용 범위의 잘못된 변경이 없고 근거를 실제로 열 수 있다. 별도 새 질문에서도 결과를 확인한다. 치명적 권한·버전·복구 회귀가 없으며 미해결 품질 문제와 지원 제한을 기록한다. 실제 모델이나 담당자의 업무 검토가 없으면 해당 완료 칸은 비워 둔다.

16단계 결과: [실제 모델·운영 검증](stages/16-core-validation/README.md), [동일 입력 전후 비교](evaluation/core/final-16-fixed/README.md), [원본 별도 실행](evaluation/core/reference-16/README.md), [백업·새 환경 복원](evaluation/core/deployment-16/README.md). 전체 198개와 마지막 분석 보완 관련 50개 통과. 고객 업무 검토·외부 배포는 미실시다.

## 순서와 중간 확인점

| 구간 | 사용자에게 보이는 결과 | 선행 조건 |
| --- | --- | --- |
| 9~10 | 문서 전체를 나누어 분석하고 진행 상태·근거를 확인 | 기존 문서 처리·권한·원본 버전 |
| 11~12 | 공개 승인 후 여러 위키 변경안이 자동 생성되고 개정 시 재정리 | 전체 분석·기존 변경 묶음 검토 |
| 13~14 | 간접 관계까지 검색하고 위키 전체의 문제를 검토함에서 처리 | 게시 위키·버전별 관계·AI 작업 |
| 15~16 | 그래프 탐색·군집·실제 모델 평가와 운영 복원 확인 | 관계 데이터·검색·품질 점검 |

**첫 실사용 목표는 12단계까지다.** 실제 모델이 연결되면 문서 등록부터 자동 변경안·검토·게시·채팅까지 한 흐름으로 시연한다. 원본의 그래프·Lint를 포함한 이번 핵심 범위 완료는 16단계의 평가까지 확인한 뒤 판정한다.

각 단계는 DB·서버·화면·검사·검증 기록까지 마친 뒤 다음 단계로 진행한다. 순수 규칙에는 필요한 단위 검사를, 권한·상태 전이·중복·복구에는 통합시험을 사용한다. 화면은 실제 폼·키보드·모바일로 확인한다. 모의시험은 장애·계약 검사용이며 실제 품질 시험을 대신하지 않는다.

모델·자료 입력이 없으면 의존하지 않는 스키마·큐·규칙·화면·계약 시험을 진행할 수 있다. 실제 모델 검증을 통과했다고 표시하거나 단계 전체가 완전히 검증됐다고 선언하지 않는다.

## 재사용·변경할 코드 경계

참조 경로는 `llm_wiki` 저장소 기준이다. 원본의 Tauri·파일 쓰기·전역 화면 저장소 의존성은 서버 업무 서비스와 분리한다. 함수를 옮길 때 해당 테스트도 입력/출력 계약에 맞게 가져오고, 외부 패키지는 실제 도입 시 설치 문서·버전을 확인한다.

| 원본 코드 | 적용 대상 |
| --- | --- |
| `src/lib/ingest.ts`: 분석·생성 프롬프트, 긴 문서 분할·예산·요약 보완 | 새로운 서버 분석·생성 모듈. 현재 [생성 서비스](../src/server/services/generation.ts)와 연결 |
| `src/lib/ingest-cache.ts`, `ingest-queue.ts` | 결과 재사용 조건·수명 관리. 현재 [영속 큐](../src/server/jobs/queue.ts)와 DB 실행 이력으로 구현 |
| `src/lib/sources-merge.ts`, `ingest-sanitize.ts` | 근거 합치기·정제 규칙. 실제 문단 ID와 [변경 묶음](../src/server/services/proposals.ts) 검증 유지 |
| `src/lib/graph-relevance.ts`, `context-budget.ts` | 관계 점수·문맥 배분. 현재 [검색 서비스](../src/server/services/retrieval.ts) 확장 |
| `src/lib/wiki-graph.ts`, `wiki-graph-analysis.ts`, `graph-insights.ts` | 버전별 그래프·군집·공백, [기존 관련 보기](../src/server/services/discovery.ts) 확장 |
| `src/lib/lint-structural-core.ts`, `lint.ts` | 구조·의미 점검, [기존 검토 대기함](../src/server/services/review-desk.ts)과 연결 |

공식 shadcn/ui 컴포넌트를 직접 조합하는 현재 UI 기준을 따른다. 로컬 경로를 모델에 맡겨 서버 파일을 쓰거나, 게시본을 AI가 직접 바꾸는 경로를 추가하지 않는다.

## 필요한 입력과 이번 범위 밖의 후속 목록

실제 검증에는 회사 모델의 접속 주소·채팅/생성/임베딩 모델·사용 가능한 문맥 크기, 대표 문서와 중요 조건·기대 질문, 작성·검토 담당자가 필요하다. 키는 서버 환경에 설정한다. 모델별 실제 처리 시간·자료 규모가 확인되기 전에는 완료 날짜나 비용을 확정하지 않는다.

아래는 당시 세 핵심 동작 이후의 후보 목록이다. 브라우저 웹 클리퍼와 MCP 외부 연결은 2026-09-10 후속 사용자 요청으로 제외했다. 나머지 항목의 최신 상태는 [복원표](ORIGINAL_FEATURE_PARITY.md)를 따른다. 이 목록을 남겨 원본 전체 기능을 모두 이식했다고 오해하지 않도록 한다.

- [ ] OCR·문서 내 이미지 분석·MinerU 연계, 전자책·음성·영상 등 추가 형식.
- [ ] 여러 파일·폴더 일괄 등록, 승인된 서버 저장소의 자동 감시, 이관·교환용 프로젝트 내보내기/가져오기.
- [ ] 웹 심층 조사·예약 수집. 현재 공식 기관 수집과 원문 검토 체계에 연결.
- [ ] Skill·도구 실행형 에이전트, 생성 파일 미리보기·Mermaid 등 출력 확장.
- [ ] 원본과 같은 다양한 공급자·프로젝트별 모델 설정, Obsidian 호환·데스크톱 전용 연동.
