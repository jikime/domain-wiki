# 엠큐닉 도메인 위키 교육 운영계획서 검토 의견

검토 대상 · 운영계획서_엠큐닉V1.pdf, 총 21쪽
검토일 · 2026년 9월 30일

**검토 결론은 ‘교육 방향은 적절하며, 실시 전 운영·평가 기준을 보완할 필요가 있음’이다.** 회사 자료를 위키에 축적하고 RFP·설계 업무에 적용한 뒤 AI로 기능을 개선하는 흐름은 엠큐닉이 제시한 문제와 잘 맞는다. 7개 단원의 순서와 총 30시간은 유지하되, 각 단원에서 무엇을 남기고 어느 수준까지 수행해야 하는지를 구체화하는 편이 좋다.

이번 검토는 사용자가 최종안으로 지정한 PDF를 기준으로 한다. 교육생은 12명, 훈련기간은 2026. 10. 1. ∼ 2026. 11. 27. 예정이며 수업은 4시간 단원 6개와 6시간 단원 1개로 구성된다(3·11·13쪽). 이전 제안서의 인원·일정을 이번 문서의 오류로 보지 않았다. 아래 의견은 교육 설계와 운영 준비에 관한 검토이며 실제 수업 성과나 행정 승인 여부를 판정한 결과는 아니다.

**유지할 부분**

요구분석에서 반복 조사, 현장 규칙의 늦은 발견, 요구 변경에 따른 재작업, 담당자마다 다른 검토 기준을 구체적으로 짚었다(5·7·10쪽). 이를 회사 자료 적용, 검색·답변 평가, 기능 개선과 검증으로 연결한 방향이 타당하다.

실습도 사용법 체험에 그치지 않는다. 입력·저장·재조회 확인, 정상·실패 입력과 역할별 동작 비교, 자료 개정 영향 확인, 개인별 수행과 인계까지 포함했다(13쪽). 이 항목들은 상세 수업안에서도 유지할 가치가 있다.

포트폴리오 평가와 사전·사후 자기평가, 종료 후 3개월 내 현업적용도 조사가 이미 마련되어 있다(14~21쪽). 새 평가 체계를 만드는 것보다 기존 양식에 수행 증거와 채점 기준을 덧붙이는 편이 효율적이다.

**우선 보완할 세 가지**

합격 기준의 수치와 평가 용어를 정리하고 도메인 지식이 설계 판단으로 이어지는 대표 결과물을 정하며 12명 실습의 팀 구성·환경·개인 확인 방식을 확정한다. 이 세 가지가 갖춰지면 교육의 기대 수준과 실제 운영 사이의 차이를 줄일 수 있다.

**도메인 위키와 UX/UI 업무를 연결할 결과물**

계획서는 도메인 목적·목차·기록 양식, 원문·버전·근거 비교를 포함한다(13쪽). 다만 자료를 등록하고 요약을 확인하는 것만으로는 여러 사업에서 재사용할 지식이 쌓였는지 알기 어렵다. 같은 주제에 자료를 추가하고 기존 조건과 예외가 함께 남는지를 확인하는 실습을 명시하면 좋다.

예를 들어 RFP에는 기본 조건, 회의록에는 현장 예외, 개정 자료에는 변경 조건이 있다고 가정한다. 교육생은 세 자료를 같은 주제 위키에 연결하고 각 조건의 적용 대상·프로젝트·시점·출처를 구분한다. 문서 요약은 원문별로 유지하되 주제 위키에는 관련 지식을 모은다. 값이 충돌하면 최신 자료라는 이유만으로 덮어쓰지 않고 적용 범위를 확인한다. 이 실습은 추가 단원을 만들지 않고 회사 도메인 구성과 자료 개정 실습에 넣을 수 있다.

문서에 없는 현장 규칙도 별도 확인이 필요하다. 담당자의 경험을 기록할 때 확인자·확인일·적용 범위와 미확정 여부를 남기고 고객 회신을 받은 뒤 확정한다. 프로젝트에서 사용한 조건을 회사 전체의 공통 규칙으로 넓힐 때에는 별도 검토가 필요하다. 이 과정은 신규 시스템 개발 대신 기록 양식과 동료 검토로 시작해도 된다.

요구분석은 요구사항–기능–화면–테스트의 연결과 상태·예외 설계를 강조한다(8~10쪽). 반면 단원별 세부 내용에는 그 연결을 확인할 공통 산출물이 명시되어 있지 않다(13쪽). 아래 연결표를 대표 요구 1건에 작성하고 개정 전후로 비교할 것을 권장한다. 전사 추적성 관리 시스템을 30시간 안에 구축한다는 의미는 아니다.

| 연결 항목 | 실습에서 남길 내용 |
| --- | --- |
| 요구와 근거 | 요구 ID, 원문 위치·버전, 관련 위키, 적용 범위 |
| 업무 판단 | 확정 조건, 미확정 조건, 고객 확인 질문과 회신 상태 |
| 기능과 화면 | 관련 기능·화면 ID, 정상·오류·빈 상태 중 해당 상태 |
| 변경과 확인 | 변경 이유, 영향받는 항목, 확인 입력·기대 결과·실제 결과 |

회사 디자인 기준과 컴포넌트를 적용한다는 9쪽의 설명도 선택한 화면 개선에 연결하면 된다. 필수 과제는 화면·기능 개선 1건으로 제한하고 Figma 신규 설계나 상태 전이 다이어그램 전체 작성까지 필수로 요구할지는 별도로 정한다. 필수 범위를 넓히면 위키 검토와 실제 동작 확인 시간이 줄어든다.

다음은 기존 13쪽의 순서와 시간을 유지한 제안이다. 일곱 단원을 일곱 주로 확정한 일정표는 아니며 실제 회차 배치는 훈련기간 안에서 별도로 정한다. 각 단원은 같은 대표 업무 사례와 앞 단원의 결과물을 이어서 사용한다.

비개발자의 역할을 명시하면 수업 난이도에 대한 오해를 줄일 수 있다. 교육생은 요구와 완료 기준을 정하고 AI의 계획을 판단하며 실제 결과를 확인한다. AI는 코드 조사·구현·기술 검사를 수행한다. 코드 문법을 직접 작성하는 능력보다 적절히 요청하고 검증하는 능력을 평가한다.

마지막 6시간의 배분 예시는 새 RFP 적용 100분, 개인 확인 90분, 팀 시연·피드백 90분, 인계 50분, 휴게 30분이다. 개인 확인 90분에는 1인당 6분씩 12명, 총 72분을 배정하고 나머지 18분은 전환·보완에 사용한다. 이는 경과시간 360분의 예시이므로, 문서의 6시간이 순수 훈련시간을 뜻한다면 휴게는 별도로 편성해야 한다.

**평가를 실제 수행과 연결하는 방법**

강사용 평가표는 일곱 단원에 맞춰 구성되어 있어 그대로 활용할 수 있다(16쪽). 보완할 부분은 점수마다 무엇을 관찰할지와 어떤 증거를 남길지다. 17쪽의 일반적인 수행 수준 설명만으로는 같은 결과를 두고 강사나 교육생이 다르게 해석할 수 있다.

| 수준 | 이번 과정에 적용할 관찰 기준 제안 |
| --- | --- |
| 1 | 과제의 요구와 근거를 설명하지 못하고 지원 후에도 결과를 확인하지 못한다. |
| 2 | 강사의 단계별 안내가 있어야 요청·수행·확인을 이어 간다. |
| 3 | 예시와 피드백을 참고해 수행하나 적용 범위나 예외 확인에 일부 누락이 있다. |
| 4 | 허용된 AI·자료를 활용해 스스로 요청하고 근거·완료 기준·실제 결과를 대조하며 제한을 설명한다. |
| 5 | 다른 조건에도 적용하고 동료가 재현할 수 있는 검토 기준을 제시한다. |

여기서 독립 수행은 AI를 사용하지 않는다는 뜻이 아니다. 교육생이 요구·판단·확인을 맡았는지를 본다. 팀 포트폴리오에는 개인별 요청, 실제 결과, 보완 의견과 강사의 도움 수준을 연결한다. 강사가 핵심 판단을 대신했다면 다른 입력으로 다시 수행하도록 한다.

합격 기준은 우선 7개 중 5개 이상이라는 개수 기준으로 정리하되, 도메인 구성과 결과 검증이 모두 미흡해도 나머지 항목만으로 합격할 수 있다는 점을 검토해야 한다. 핵심 과제에서 원문 근거·적용 범위를 확인하고 변경 후 실제 동작을 재검증하는 수행을 필수로 둘 것을 제안한다. 이는 원문에 없는 추가 제안이므로 과정 담당자가 채택 여부와 재수행 기회를 정해야 한다.

사전·사후 자기평가의 네 문항은 같아 비교가 가능하다(15·19쪽). 다만 성취도는 긍정 응답이 1점, 만족도와 일부 현업적용도는 긍정 응답이 5점이다(18~21쪽). 기존 양식을 유지한다면 원점수의 방향을 명시하고 비교·집계 때 역코딩 여부를 정한다. 자기평가의 상승만으로 실제 수행 능력이 입증됐다고 해석하지 않는다.

교육 효과는 같은 자료·질문·조건에서 근거를 찾은 건수, 요구의 모호함을 확인 질문으로 남긴 건수, 검토 누락 건수 등을 비교한다. 시간 단축을 측정한다면 기록 방법도 같아야 한다. 종료 후 3개월 내 조사에는 실제 활용 사례와 검토 기록을 함께 받으면 도움이 된다. 현재 문서만으로 재작업 감소율이나 생산성 향상 수치를 확정할 수는 없다.
