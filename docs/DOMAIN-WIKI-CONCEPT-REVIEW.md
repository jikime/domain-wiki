# 도메인 위키 개념·구현 점검

점검일: 2026-09-24

후속 진행: 아래는 수정 전 점검 기록이다. 대상–수치 대응과 병합 후 검증을 보강한 1단계의 변경·검사·제한은 [개선 진행 기록](DOMAIN-WIKI-IMPROVEMENT-PROGRESS.md)에 구분했다.

대상은 `my-domain-wiki`의 설계 문서, 데이터 구조, 지식 생성·병합·검토·검색 코드와 기존 평가 기록이다. 참고 원본인 `llm_wiki/llm-wiki.md`의 설계 취지와 비교했다. 이번에는 저장된 고객 데이터나 실행 중 화면을 확인하지 않았다. 실제 모델·전체 통합시험도 새로 실행하지 않았다. 아래 검증 함수 재현만 현재 코드에서 별도로 실행했다.

## 판단

도메인 위키의 기본 개념과 구현 방향은 맞다. 원문을 보관하고, 목적과 작성 규칙에 따라 위키를 생성·갱신하며, 사람이 검토하고 업무에서 다시 활용하는 구조가 실제 코드에 있다. 회사 공동 활용에 필요한 승인·권한·버전 관리도 갖추었다.

다만 현재 증거로 확인할 수 있는 수준은 **근거와 검토 절차를 갖춘 도메인 지식 서비스의 기반**이다. 여러 회사 자료에서 재사용할 지식이 계속 축적되는지, 실제 업무 판단이 정확해지는지까지 완성됐다고 보기는 어렵다. 다음 단계의 중심은 기능 수 확대보다 주제별 통합, 프로젝트 경험의 공통 지식화, 주장과 근거의 대응 검증, 실제 업무 평가에 두는 것이 좋다.

## 이 프로젝트에서 사용할 정의

> 도메인 위키는 특정 업무 분야의 용어·대상·규칙·절차·사례를 주제별로 연결하고, 각 내용의 근거·적용 범위·예외·검토 상태를 관리하여, 새 자료와 실무 경험이 들어올 때 기존 지식을 갱신하는 공동 지식 공간이다.

이 정의는 이번 제품을 점검하기 위한 기준이다. 특정 저장 방식이나 그래프 데이터베이스의 사용을 필수 조건으로 삼지 않는다. PostgreSQL에 마크다운 본문과 관계를 저장하는 현재 구조로도 구현할 수 있다. 채팅은 지식을 활용하는 경로이고, RFP 분석은 지식을 적용하는 업무 사례다. 위키 자체에는 대화가 끝난 뒤에도 읽고 검토할 수 있는 지식이 남아야 한다.

회사에서 다루는 업무 영역을 도메인으로, 개별 발주·수행 건을 프로젝트로 구분하는 것이 적절하다. 예를 들어 교통관제 업무가 도메인이라면 특정 도시의 구축 사업은 프로젝트다. 이때 한 사업의 갱신 주기나 검수 조건을 전체 도메인의 공통 규칙으로 바꾸어서는 안 된다.

## 우선 보완할 부분

### 1. 문서 정리를 넘어 주제별 지식이 축적되는지 확인

생성 프롬프트는 주제별 페이지와 기존 지식의 보완을 지원한다. 그러나 확인한 2026-09-10 실제 모델 평가 표본의 최초 결과는 문서 요약 3개와 절차 1개였다. 이 결과는 단일 원문의 정리·개정 능력을 보여주지만, 서로 다른 여러 문서를 하나의 개념·업무 판단 기준으로 통합하는 품질까지 입증하지 않는다. 이 한 표본으로 전체 서비스가 요약에만 머문다고 단정해서도 안 된다.

예를 들어 RFP, 검수 기준, 회의록이 모두 화면 갱신을 다룬다면 각 자료의 요약과 함께 ‘화면 갱신 요구를 확인하는 방법’이라는 주제 페이지가 있어야 한다. 새 자료가 들어왔을 때 그 페이지의 조건·예외·확인 질문이 보완되는지 평가해야 한다.

기존 위키 비교는 문자 일치 점수로 후보를 고르고 입력 예산에 맞추는 구조다. 일반 후보 조회는 최대 21개, 관련 원문 문단은 최대 10개이며 개정 대상은 별도 경로로 우선 다룬다. 명칭이 다른 동일 개념이나 자료가 많아진 상황에서의 누락·중복은 따로 검증할 필요가 있다. 이러한 제한이 곧 오류를 의미하지는 않는다.

근거: `src/server/ai/generation-knowledge.ts`, `docs/evaluation/core/ingest-12-original-parity-20260910/initial.json`.

### 2. 프로젝트 경험을 회사 공통 지식으로 올리는 절차

현재는 특정 프로젝트와 공통 자료를 함께 참고할 수 있지만, 다른 프로젝트의 근거를 섞거나 프로젝트 자료를 공통 위키의 근거로 바로 연결하는 것을 제한한다. `checkEvidence`는 근거의 프로젝트가 대상 위키의 프로젝트와 다르면 차단한다. 채팅 답변 저장도 여러 프로젝트가 섞이면 범위를 좁히도록 요청한다.

이 장치는 사업별 조건을 잘못 일반화하는 일을 막는다. 다만 A·B 프로젝트의 경험을 비교해 회사 공통 업무 지침으로 정리하려면 별도의 검토 경로가 필요하다. 현재 확인한 코드에는 프로젝트별 근거를 유지하며 공통 지식으로 승격하는 전용 흐름이 보이지 않는다.

보완 시에는 기존 범위 검사를 일괄 해제하지 않는다. 검토자가 공유 가능한 사례를 선택하고, 공통으로 재사용할 판단·적용 조건·예외를 명시하며, 원래 프로젝트와 근거 이력을 보존하는 방식이 적절하다. 구체적인 수치나 계약 조건은 해당 사업의 조건으로 남겨야 한다.

근거: `src/server/services/wiki.ts:48`, `src/server/services/chat-wiki.ts:151`, `src/lib/wiki-generation.ts:138`.

### 3. 근거의 연결과 문장의 정확성을 구분

문서 분석과 생성 단계에는 주장 ID, 원문 인용, 대상, 수치·단위, 조건, 부정·불확실성 검사가 있다. 이는 유용한 방어 장치다. 다만 숫자와 대상 이름이 단락에 존재하는지를 확인하는 것만으로 각 주장의 뜻이 보존됐다고 판단할 수는 없다.

이번 점검에서 `validateGeneratedSections`를 직접 호출해 다음을 재현했다. DB 저장이나 모델 호출 없이 메모리 안에서 실행했다.

| 입력 | 결과 |
| --- | --- |
| 원문 주장 1: 주 화면은 30초마다 갱신한다. 주장 2: 보조 화면은 90초마다 갱신한다. | 두 주장을 같은 생성 단락에 배정 |
| 생성문: 주 화면은 30초마다 갱신한다. 보조 화면은 90초마다 갱신한다. | 검증 통과 |
| 생성문: 주 화면은 90초마다 갱신한다. 보조 화면은 30초마다 갱신한다. | **잘못된 대응인데도 검증 통과** |

이 결과는 해당 검증 함수의 한계를 확인한 것이다. 실제 모델이 이 오류를 냈거나 검토자가 잘못된 글을 게시했다고 확인한 것은 아니다.

또한 여러 원문을 병합할 때는 먼저 검증한 단락을 다시 모델로 통합한다. 병합 함수가 반환하는 최종 본문에는 동일한 주장별 검증이 다시 적용되지 않는다. 게시 위키의 근거 연결도 기본적으로 위키 버전과 원문 문단의 관계이며, 생성 중 존재하는 단락·주장 대응이 게시본의 필수 구조로 유지되는 것은 아니다.

우선 보완할 것은 주장별 대상–속성–값–조건의 대응 확인, 병합 후 최종 본문의 재검증, 검토 화면에서 각 문장과 근거를 나란히 비교하는 흐름이다. 자동 검사 통과와 직원의 내용 검토 완료는 계속 구분해야 한다.

근거: `src/lib/wiki-generation.ts:361`, `src/server/ai/wiki-generation.ts:355`, `src/server/ai/wiki-merge.ts:19`, `src/server/db/schema.ts:567`.

### 4. 현재 게시본과 업무상 적용 시점을 구분

현재 원문 여부는 게시된 버전·처리 상태·연결된 근거의 상태를 중심으로 판단한다. 공식 자료 수집에는 발행일·시행일 입력이 있지만, 이번에 확인한 검색·생성 경로에서 그 날짜를 이용해 특정 시점의 적용 여부를 자동 판정하지는 않는다.

향후 시행 자료, 과거 계약에 적용되는 이전 기준, 발주처별 예외를 다룬다면 ‘가장 최근에 게시한 자료’와 ‘이 업무에 적용할 자료’를 구분해야 한다. 처음부터 복잡한 규칙 엔진을 만들 필요는 없으며, 위키의 적용 기간·대상·예외를 명시하고 관련 질문을 평가에 포함하는 것으로 시작할 수 있다.

근거: `drizzle/0005_operations.sql:65`, `src/server/db/schema.ts`의 `officialCandidate`, `src/server/ai/knowledge-index.ts`.

### 5. 실제 업무에서 지식 축적의 효과 평가

기존 실제 모델 평가에는 수치·부정·예외 보존, 개정, 프로젝트 구분, 경험의 일반화 방지, 근거 부족 응답을 확인한 기록이 있다. 다만 개발용 가상 자료를 사용했고 고객 업무 담당자의 판정은 포함하지 않았다. 이번 점검에서도 그 제한을 해소한 새 평가를 실행하지 않았다.

다음 평가는 실제 RFP·검토 기준·실무 경험을 함께 사용하고, 기존 위키가 어떻게 보완됐는지와 새 업무에서 무엇을 재사용했는지를 확인해야 한다. 페이지 수·업로드 수·그래프 연결 수만으로 성과를 판단하지 않는다.

근거: `docs/evaluation/core/final-16-fixed/README.md`, `docs/evaluation/core/ingest-12-original-parity-20260910/README.md`.

## 그래프와 업무 자동화의 위치

현재 그래프는 위키 링크, 공통 출처, 이웃, 유형 등을 이용해 관련 페이지를 탐색한다. 이는 유용한 관계 탐색 기능이다. 연결선이 있다는 이유만으로 인과관계나 ‘요구사항이 이 화면과 테스트에 완전히 구현됐다’는 사실이 성립하지는 않는다.

도메인 위키에는 이러한 탐색 그래프로도 충분히 가치가 있다. 요구사항–기능–화면–테스트의 추적까지 제품 목표에 넣으려면 관계의 종류, 근거, 버전과 검증 상태를 별도로 정의해야 한다. RFP·UX/UI 교육에서도 위키 구축·활용과 전체 설계 자동화의 완료를 구분해서 설명하는 것이 맞다.

근거: `src/lib/knowledge-graph.ts`, `src/lib/wiki-metadata.ts`.

## 다음 단계의 완료 기준 제안

다음 여섯 항목으로 작은 실제 업무 표본을 평가한다. 아래는 제안하는 평가이며 이번에 통과한 결과가 아니다.

1. 같은 주제를 다루는 자료 3개를 순서대로 넣고, 기존 주제 위키가 주소를 유지하며 보완되는지 확인한다.
2. 서로 다른 사업의 수치와 예외가 섞이지 않는지 확인한다.
3. 새로운 실무 경험이 ‘사례’로 남고, 공통 규칙으로 옮길 때 별도 판단과 근거가 남는지 확인한다.
4. 서로 모순되는 자료를 넣고, 임의로 하나를 확정하지 않으며 확인할 질문과 검토 과제가 남는지 확인한다.
5. 원문을 개정하고, 기존 위키의 영향·새 근거·이전 버전과 현재 답변을 확인한다.
6. 새 RFP에 기존 개념·절차·사례를 적용하고, 업무 담당자가 결과와 근거를 평가한다.

현재 구조를 전면 교체할 필요는 없다. 먼저 재현된 대상–수치 대응 검증을 보강하고, 작은 도메인의 대표 주제 위키를 만든 뒤, 공통 지식화 절차와 실제 업무 평가를 이어가는 순서가 적절하다.
