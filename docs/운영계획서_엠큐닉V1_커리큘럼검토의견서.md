# 엠큐닉 도메인 위키 교육 커리큘럼 검토 의견

검토 대상 · 운영계획서_엠큐닉V1.pdf의 학습 목표와 교육내용
검토일 · 2026년 9월 30일

**현재 커리큘럼은 체험부터 이해·적용·개선·검증으로 이어지는 순서가 적절하다. 다만 도메인 지식을 RFP 분석과 화면 설계에 사용하는 실습을 더 분명하게 연결할 필요가 있다.** 7개 단원과 총 30시간은 유지하고 같은 업무 사례를 각 단원에서 발전시키는 방식으로 보완할 것을 권한다.

검토 기준은 9쪽의 대상 업무, 12쪽의 학습 목표, 13쪽의 단원별 교육내용이다. 학습 내용·순서·난이도·실습의 연결만 검토했다. 아래에 제시한 시간 내 활동과 결과물은 보완 제안이며 원문에 확정된 내용과 구분한다.

**유지할 학습 흐름**

스타터킷을 먼저 사용한 뒤 구조를 이해하는 순서는 비개발자가 기술의 쓰임을 익히기에 적절하다. 회사 자료로 위키를 구성하고 검색·답변의 문제를 찾은 다음 기능을 개선하도록 한 순서도 자연스럽다. 구현 이후 입력·저장·재조회와 실패 사례를 확인하게 한 점은 AI가 만든 결과를 그대로 받아들이지 않는 학습으로 이어진다(13쪽).

AI 활용 경험이 있는 비개발자를 대상으로 한다는 설명을 고려하면(10쪽), 기술 용어를 처음부터 자세히 가르치기보다 이미 사용해 본 기능의 내부 흐름을 설명하는 방식이 적합하다. 코드 개선 실습도 유지하되 교육생의 역할은 업무 요구 작성, AI에 요청, 계획 판단, 실제 결과 확인으로 명확히 하는 편이 좋다.

**보완할 핵심 내용**

첫째, 도메인 위키를 만드는 기준을 더 구체적으로 배워야 한다. 3단원에는 목적·목차·기록 양식과 원문 비교가 포함되어 있지만 여러 자료를 같은 주제에 모으는 방법과 프로젝트별 조건·예외·충돌을 구분하는 실습은 명시되어 있지 않다. 이 내용을 기존 자료 등록·동료 검토 안에 넣어야 문서 요약을 넘어 재사용 가능한 지식을 만드는 경험이 된다.

둘째, 위키 지식을 설계 판단에 연결하는 과제가 필요하다. 9쪽은 요구사항–기능–화면–확인 항목의 연결과 정상·오류·빈 상태를 다루지만 13쪽에는 그 결과물이 구체적으로 드러나지 않는다. 대표 요구 1건의 근거를 찾고 확인 질문을 만든 뒤 관련 화면의 조건을 정하는 과제를 공통 실습으로 삼으면 좋다.

셋째, 업무 적용을 마지막 단원까지 미루지 않는 편이 좋다. 1단원에 RFP·설계 문제 정의가 이미 있으므로, 3단원부터 같은 요구를 위키에 적용하고 4단원에서 판단의 품질을 확인한다. 마지막 단원에서는 앞서 배운 적용 방법을 새 RFP로 다시 수행한다.

**단원별 검토와 보완 제안**

시간과 단원 순서는 원문 13쪽을 유지했다. 결과물은 별도 과제를 늘리기 위한 것이 아니라 다음 단원에서 이어 쓸 학습 증거다.

| 단원과 시간 | 커리큘럼 검토 의견 | 같은 시간 안에서 보완할 실습 |
| --- | --- | --- |
| 1. 스타터킷 체험과 업무 문제 정의 · 4시간 | 전체 흐름을 먼저 체험하는 출발점은 적절하다. 환경 준비가 길어지면 업무 문제를 정의하는 시간이 줄어들 수 있다. | 작은 예제 자료로 등록→위키→질문→근거 확인을 끝까지 경험한다. 이후 대표 RFP 요구 1건과 해결할 업무 문제를 고른다. |
| 2. 아키텍처와 AI 개발 방법 · 4시간 | 실행 도구, 화면·서버·작업자·DB·원본 저장소, 코드 수정까지 다루므로 설명이 깊어지면 부담이 크다. | 앞 단원의 자료가 처리되는 경로로 각 요소의 역할을 설명한다. DB 설계·청킹 구현은 심화로 두고 첫 수정은 도움말이나 표시 문구처럼 작게 제한한다. |
| 3. 회사 도메인과 지식 구성 · 4시간 | 목적·목차·양식은 포함되어 있다. 지식을 어떻게 나누고 합칠지에 관한 판단을 보강할 필요가 있다. | 관련 자료 2~3개를 한 주제에 연결하고 출처·적용 범위·예외를 구분한다. 대표 RFP 요구에 답할 수 있는 내용과 추가 확인할 내용을 나눈다. |
| 4. 검색·답변 품질 및 중간 점검 · 4시간 | 개선 전에 현재 결과를 측정하는 순서는 적절하다. 검색 문제만 보면 업무 판단의 오류를 놓칠 수 있다. | 근거가 있는 요구, 모호한 요구, 예외가 있는 요구를 비교한다. 원문 부족·검색 누락·답변 해석 오류를 구분하고 자료·작성 규칙·코드 중 무엇을 고칠지 정한다. |
| 5. AI를 활용한 기능 개선 · 4시간 | 공식 자료 조사와 구현·검증을 모두 수행하려면 과제 범위가 작아야 한다. | 4단원에서 확인한 문제에 연결된 화면·기능 1건을 개선한다. 공식 자료는 해당 변경에 필요한 부분을 AI와 확인하고 입력·저장·재조회까지 마친다. |
| 6. 오류 해결과 개선 검증 · 4시간 | 코드 오류 수정과 자료 개정 영향 확인은 서로 다른 학습 내용이다. 함께 바꾸면 원인을 구분하기 어렵다. | 같은 자료에서 코드 수정 전후를 확인한 다음 같은 코드에서 자료 개정 전후를 비교한다. 대표 오류 1건과 대표 개정 1건으로 범위를 제한한다. |
| 7. 업무 적용과 성과 공유 · 6시간 | 새 RFP에 적용하는 마무리는 적절하다. 앞 단원에서 적용 절차를 익혔다는 전제가 필요하다. | 새 요구의 근거·모호함·관련 화면·확인 항목을 스스로 정리한다. 기존 개선 기능을 사용해 보고 이전 사례와 달라진 판단을 설명한다. |

4단원의 모든 문제를 코드로 해결할 필요는 없다. 자료 보완이나 위키 작성 규칙 변경이 필요한 문제는 그 방법으로 다루고 5단원에서는 코드 변경의 목적이 분명한 작은 과제를 선택한다.

**한 사례를 끝까지 연결하는 실습 예시**

다음은 커리큘럼을 구체화하기 위한 가상 사례다. RFP에는 상태 화면의 갱신 조건이 있고 회의록에는 통신 단절 시 예외가 있으며 이후 개정 자료에서 일부 조건이 바뀐다고 가정한다.

1단원에서는 해당 요구를 읽고 어떤 근거가 필요한지 질문한다. 2단원에서는 그 자료가 위키와 답변으로 이어지는 경로를 살펴본다. 3단원에서는 기본 조건과 예외를 같은 주제에 모으고 출처·대상·미확정 항목을 나눈다. 4단원에서는 정상 상태와 통신 단절 상태에 관한 질문으로 답변을 비교하고 설계 전에 확인할 질문을 남긴다.

5단원에서는 그 과정에서 발견한 불편과 연결된 작은 기능을 개선한다. 예를 들어 미확정 요구를 검토 화면에서 쉽게 구분하는 표시 기능을 후보로 삼을 수 있다. 실제 과제는 스타터킷에 이미 구현된 기능과 수정 난이도를 확인한 뒤 정한다. 6단원에서는 기능 오류와 자료 개정을 각각 검증하고 7단원에서는 다른 조건의 새 요구에 같은 판단 절차를 적용한다.

이 실습에서 연결할 내용은 ‘원문 요구 → 관련 위키와 근거 → 확정 조건·확인 질문 → 기능·화면 조건 → 실제 확인 결과’다. 연결 정보를 표로 남겨도 충분하다. 교육시간 안에 별도의 추적성 관리 시스템을 새로 구축할 필요는 없다.

**30시간 안에서의 학습 범위**

필수 학습은 원문과 근거를 확인하는 능력, 주제별 지식과 적용 범위를 정리하는 능력, RFP 요구를 화면 조건으로 구체화하는 능력, AI에 작은 변경을 요청하고 결과를 확인하는 능력으로 좁히는 것이 좋다. 단원마다 새로운 도구와 별도 프로젝트를 추가하기보다 같은 자료·질문·코드를 계속 사용한다.

DB 설계와 청킹 알고리즘의 직접 구현, 대규모 지식베이스 구축, 다수 화면의 신규 설계, Figma의 상세 제작 기법은 이번 30시간 과정의 필수 범위에 포함하지 않을 것을 권한다. 기술 요소의 역할과 회사 디자인 기준은 실제 실습에 필요한 만큼 다룬다. 학습자는 무엇을 왜 바꿨고 결과가 맞는지를 설명할 수 있어야 한다.

과정명에 UX/UI가 포함되어 있으므로 최종 산출물에는 화면 설계 판단이 드러나야 한다. 예쁜 화면을 새로 만드는 것보다 요구의 근거를 확인하고 정상·오류·빈 상태 중 필요한 상태, 표시 조건, 확인 항목을 정리하는 실습이 이번 과정의 도메인 위키 학습과 직접 연결된다.

**최종 의견**

현재 단원 구성을 전면 개편할 필요는 없다. 3단원에 주제별 지식 축적과 범위 판단을 구체화하고 3~7단원에 RFP 요구와 화면 조건을 연결하는 공통 과제를 이어 넣는 보완을 권한다. 2단원의 기술 설명과 5~6단원의 개발 과제는 이 업무 적용을 뒷받침하는 수준으로 제한한다. 그렇게 구성하면 위키 사용, AI 개발, UX/UI 설계가 하나의 업무 문제를 해결하는 학습으로 이어진다.
